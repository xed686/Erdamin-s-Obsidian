## 1. 什么是文件上传漏洞

> **文件上传漏洞**是指网页服务器**允许用户上传文件**,但**没有充分验证**文件的名称、类型、内容或大小等信息。

如果这些限制没有被妥善执行,**即使是最基本的图片上传功能**(比如上传头像),也可能被滥用来上传**任意且可能有危险的文件**——其中最危险的一种,就是**支持远程代码执行的服务器端脚本文件**(比如一个 `.php` 文件)。

**两种危害路径:**

| 危害方式 | 说明 |
|---|---|
| **上传本身就造成损害** | 比如上传一个超大文件耗尽磁盘空间,或上传包含恶意内容的文档(钓鱼) |
| **上传后触发执行** | 攻击者**再发一个 HTTP 请求去访问**这个已上传的文件,触发服务器**执行**里面的脚本代码 |

> 本章重点讲的是**第二种**——上传恶意脚本,再通过访问它来执行代码,这是渗透测试里最常见、危害最大的利用方式。

## 2. 文件上传漏洞是如何产生的

### 现实情况:完全不设防的网站很少见

鉴于危险性很明显,**现实中几乎不会有网站对上传文件毫无限制**。更常见的情况是:**开发者确实做了验证,但这些验证本身存在缺陷,或者容易被绕过**。

### 常见的三种"验证缺陷"模式

**① 黑名单扩展名检查存在疏漏**

开发者可能把**危险的文件扩展名列入黑名单**(比如禁止 `.php`、`.asp`),但是:

- **解析文件名时忽略了细节差异**——比如 `.pHp`、`.php5`、`.phtml`、文件名末尾带空格或 null 字节等变体,都可能被黑名单漏掉
- 黑名单本身**很容易遗漏冷门的危险扩展名**(比如服务器其实也会把 `.phtml`、`.php3` 当 PHP 执行,但黑名单里没写)

**② 只检查"用户能轻易篡改"的属性**

有些网站检查文件类型时,看的是**请求里由客户端提供、且用户可以随意修改**的信息——比如 HTTP 请求里的 `Content-Type` 头。这类检查可以很轻松地用 **Burp Proxy 或 Burp Repeater** 这样的工具**拦截请求并手动改掉**对应字段,从而绕过检查。

**③ 多台服务器/目录配置不一致**

即使验证机制本身很"稳健",**构成网站的多台主机、多个目录之间的配置也可能不一致**——比如上传目录 A 禁止执行脚本,但另一个用于展示头像的目录 B 却配置成了"任何文件都当脚本执行",这种**配置差异**本身就能被利用。

## 3. 网页壳(Web Shell)原理与代码讲解

### 什么是网页壳(Web Shell)?

> **网页壳**是一种**恶意脚本**,一旦被放到服务器上,攻击者就能通过向**正确的网址(端点)发送 HTTP 请求**,在**远程服务器上执行任意命令**。

**打个比方:** 正常情况下,你只能通过服务器"允许"的功能(登录、查看商品)和服务器打交道。但如果你成功把一个网页壳放到了服务器上,相当于你在服务器里**装了一个后门遥控器**——只要能访问到这个文件的 URL,你就能让服务器**执行你想要的任意指令**。

**危害有多大?** 一旦网页壳上传成功,你就**完全控制了服务器**,这意味着你可以:

- **读写任意文件**
- **窃取敏感数据**(数据库配置、用户密码等)
- **利用服务器做跳板**,攻击内部网络或外部其他服务器

### 代码逐行讲解

#### 第一段代码:只会"读文件"的简单网页壳

```php
<?php echo file_get_contents('/path/to/target/file'); ?>
```

逐部分拆解:

| 代码片段 | 含义 |
|---|---|
| `<?php ... ?>` | PHP 代码的**起止标记**。服务器看到这对标记,就知道里面是要**当作 PHP 脚本执行**的代码,而不是普通文本 |
| `file_get_contents('路径')` | PHP 的**内置函数**,作用是:**读取指定路径的文件内容**,并把内容作为一个字符串返回 |
| `echo` | PHP 的**输出语句**,作用是:把后面的内容**打印到页面上**,也就是会出现在 HTTP 响应的内容里 |

**整体含义:** "读取 `/path/to/target/file` 这个文件的全部内容,然后把它打印到页面上返回给请求者。"

**怎么用?** 这段代码被当成一个文件(比如 `exploit.php`)上传到服务器后,攻击者只需要用浏览器或 Burp **访问这个文件的 URL**(比如 `https://xxx.com/files/exploit.php`),服务器执行这段 PHP 代码,**就会把目标文件的内容打印在响应页面里返回给你**——相当于你"偷看"了服务器上本来看不到的文件。

#### 第二段代码:能执行"任意系统命令"的网页壳(威力更大)

```php
<?php echo system($_GET['command']); ?>
```

逐部分拆解:

| 代码片段 | 含义 |
|---|---|
| `$_GET['command']` | PHP 里**获取 URL 查询参数**的写法。`$_GET` 是 PHP 内置的一个"数组",专门用来存放 URL 里 `?key=value` 这种查询参数。`$_GET['command']` 就是取出 URL 里**名叫 `command` 这个参数对应的值** |
| `system(...)` | PHP 的**内置函数**,作用是:把括号里的字符串,当成**操作系统命令**在服务器上**真正执行**,并把命令的输出结果返回 |
| `echo` | 同上,把 `system()` 执行命令后的**输出结果打印到页面上** |

**整体含义:** "从 URL 的 `command` 参数里拿到一段文字,把这段文字当作**系统命令**在服务器上执行,然后把执行结果打印到页面返回。"

**怎么用?** 攻击者访问:

```
GET /example/exploit.php?command=id HTTP/1.1
```

这里 `?command=id` 的意思是:把字符串 `id` 作为 `command` 参数传进去。服务器执行这段 PHP 代码时,相当于在**服务器的终端里敲了一条命令:`id`**(Linux 下用来查看当前用户身份的命令),然后把执行结果打印出来返回给你。

> **为什么说这个"更灵活"?** 第一段代码**只能读一个写死的文件**,想读别的文件就得重新上传一次脚本。第二段代码相当于给了你一个**万能的命令行窗口**——只要改 URL 里 `command=` 后面的内容,就能让服务器执行任意命令(列目录、建文件、开反弹 shell 等等),**完全不需要再重新上传**。

> **实战提醒:** 这正是为什么网页壳如此危险——它把"文件上传"这个本来看起来人畜无害的功能,变成了一个**远程命令执行(RCE)入口**。

## 4. multipart/form-data 请求格式详解

### 为什么文件上传不用普通的表单格式?

浏览器提交普通 HTML 表单时(比如填写姓名、地址),通常用 `POST` 请求,内容类型是:

```
Content-Type: application/x-www-form-urlencoded
```

这种格式**只适合传输简单的文本**。但如果要传**整张图片、整个 PDF 这种大量二进制数据**,这种格式就不合适了——这时候浏览器会改用:

```
Content-Type: multipart/form-data
```

### 逐段拆解请求示例

假设有一个表单,包含:**上传图片**、**图片描述**、**用户名**三个字段,提交后请求大致是:

```http
POST /images HTTP/1.1
Host: normal-website.com
Content-Length: 12345
Content-Type: multipart/form-data; boundary=---------------------------012345678901234567890123456

---------------------------012345678901234567890123456
Content-Disposition: form-data; name="image"; filename="example.jpg"
Content-Type: image/jpeg

[...example.jpg 的二进制内容...]

---------------------------012345678901234567890123456
Content-Disposition: form-data; name="description"

这是我图片的一段有趣描述。

---------------------------012345678901234567890123456
Content-Disposition: form-data; name="username"

wiener
---------------------------012345678901234567890123456--
```

**关键术语解释:**

| 术语                                                                     | 含义                                                                                                                              |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `boundary=---...`                                                      | **分隔符**。整个请求体会被这个字符串**切割成多个部分(part)**,每个表单字段对应一个部分。这个分隔符的值可以是任意字符串,只要在请求体里不会和正文内容混淆                                             |
| `Content-Disposition: form-data; name="image"; filename="example.jpg"` | 说明这一部分对应的是表单里 **`name="image"`** 这个输入框提交的内容,并且这是一个**文件**,原始文件名叫 `example.jpg`                                                   |
| 每部分自己的 `Content-Type`                                                  | 比如图片这部分有自己的 `Content-Type: image/jpeg`,用来告诉服务器:**这部分提交的数据的 MIME 类型是 JPEG 图片**。这个值是**客户端(浏览器)自己写的**,**理论上可以被用户随意篡改**——这正是后面漏洞的关键 |

**消息体结构总结:** 整个请求体被分成一段一段,每段开头是分隔符,然后是这一段对应哪个表单字段(`Content-Disposition`)、这段数据的类型(可选的 `Content-Type`),再然后是真正的数据内容(文本或二进制)。

## 5. 有缺陷的文件类型验证机制

### 一种常见但脆弱的验证方式

有些网站验证上传文件类型的方法是:**检查上面讲的那个"针对单个字段的 `Content-Type` 请求头"**,看它是否匹配预期的 MIME 类型。比如,如果服务器只期望图片文件,可能只允许 `image/jpeg`、`image/png` 这类值通过。

### 问题出在哪?

> **如果服务器"隐式信任"这个 `Content-Type` 请求头的值,而不去进一步检查"文件的实际内容是否真的匹配这个所声称的 MIME 类型",这种防御就形同虚设。**

因为这个 `Content-Type` 值,**完全是由发请求的客户端自己填写的**——它只是浏览器(或攻击者手动构造的请求)"自称"的文件类型,服务器如果不做额外检查,等于是在**相信攻击者自己报的身份**。

**这个缺陷可以很容易地用 Burp Repeater 这样的工具绕过:** 攻击者只需要拦截上传请求,把 `Content-Type: application/octet-stream`(或其他被禁止的值)**手动改成** `Content-Type: image/jpeg`,服务器一看"类型对了",就会放行——**但文件的真实内容其实是一段 PHP 代码**。

## 6. 实验案例一:无限制文件上传 → 远程代码执行

### 实验室场景设定

> 该实验室包含一个**易受攻击的图像上传功能**。它**不会在用户上传的文件存储到服务器文件系统前进行任何验证**——也就是对应前面讲的"完全不设防"的情况。

**目标:** 上传一个基础的 PHP 网页壳,并用它**导出** `/home/carlos/secret` 文件的内容。

**凭证:** `wiener:peter`(登录自己的账号用)

### 真实操作过程还原

**第 1 步:登录账号,上传一张图片做头像**

用 `wiener:peter` 登录后,找到"上传头像"的功能,随便上传一张正常图片。回到账号页面,确认**头像预览能正常显示**——这说明图片上传、存储、再被展示这一整条流程是通的。

**第 2 步:用 Burp 观察"头像是怎么被访问到的"**

打开 Burp 的 **HTTP 历史(HTTP history)**,用"按 MIME 类型筛选"里的**图片复选框**过滤出图片相关的请求,会看到浏览器加载头像时,实际发出的是这样一个请求:

```
GET /files/avatars/<YOUR-IMAGE>
```

> **这一步的意义:** 你搞清楚了服务器把上传的文件存到了 `/files/avatars/` 这个目录下,并且**可以通过直接访问这个路径拿到文件内容**。既然图片能这样被访问,那如果上传的不是图片、而是一个脚本呢?

把这个 `GET` 请求发送到 **Burp Repeater**,留着备用。

**第 3 步:在本地写一个网页壳**

在自己电脑上新建一个文件 `exploit.php`,内容就是前面讲过的那段"读文件"网页壳:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

**这段代码的作用:** 一旦服务器执行它,就会把 `/home/carlos/secret`(受害者 carlos 的私密文件)的内容读出来并打印在响应里。

**第 4 步:用头像上传功能,把这个 PHP 文件传上去**

因为这个实验室**对上传的文件完全没有验证**(对应前面"完全不设防"的场景),所以这里**不需要绕过任何黑名单或类型检查**,直接把 `exploit.php` 当成头像文件提交上去就行。**服务器返回的消息确认了上传成功**——这说明服务器老老实实地把这个 `.php` 文件存到了磁盘上,和存图片时的处理方式一模一样。

**第 5 步:在 Burp Repeater 里,把路径指向你刚上传的 PHP 文件**

还记得第 2 步留着的那个请求吗?

```
GET /files/avatars/<YOUR-IMAGE>
```

现在把 `<YOUR-IMAGE>` 这部分,改成你刚上传的文件名:

```
GET /files/avatars/exploit.php
```

**第 6 步:发送请求,见证代码执行**

发送这个请求后,服务器收到"请求访问 `/files/avatars/exploit.php`"这个指令。因为这个路径下的文件**会被服务器当作 PHP 脚本来执行**(而不是当作普通文件原样返回),所以:

1. 服务器**执行**了 `exploit.php` 里的代码
2. 这段代码里的 `file_get_contents('/home/carlos/secret')` 被运行,读取了 carlos 的秘密文件
3. `echo` 把这个内容打印了出来
4. 这段打印出来的内容,**就作为这次 HTTP 请求的响应内容**,返回到了 Burp Repeater 的响应窗口里

于是,攻击者在响应里**直接看到了 carlos 的私密文件内容**。

**第 7 步:提交秘密,解锁实验室**

### 这个实验的核心逻辑

> **漏洞点:** "上传文件"这个环节**完全没有做任何检查**——不管你上传的是图片还是脚本,服务器都会**原样接受并存到磁盘上**。而更致命的是,存放这些上传文件的目录(`/files/avatars/`)被配置成了**"遇到 `.php` 文件就执行",而不是"原样把文件内容返回"**。这两个条件叠加在一起,就让"上传头像"这个看似无害的功能,变成了一个完整的**远程代码执行(RCE)**入口。

## 7. 实验案例二:绕过有缺陷的文件类型验证

### 实验室场景设定

> 这个实验室包含一个**存在漏洞的图片上传功能**。它试图阻止用户上传意料之外的文件类型,但**依赖于检查用户可控的输入**来做这个验证——这正对应前面讲的"隐式信任 `Content-Type` 请求头"的缺陷。

**目标:** 同样是上传一个基础 PHP 网页壳,导出 `/home/carlos/secret`。

**凭证:** `wiener:peter`

### 真实操作过程还原

**第 1 步、第 2 步:和实验一完全一样**

登录、上传一张正常图片做头像、在 Burp HTTP 历史里找到 `GET /files/avatars/<YOUR-IMAGE>` 这个请求,发送到 Repeater 留着备用。

**第 3 步:同样准备一个网页壳文件**

本地创建 `exploit.php`:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

**第 4 步:直接尝试上传——这次会被拦下来**

这一次,尝试把 `exploit.php` 作为头像直接上传。**这次服务器的响应会提示:你只被允许上传 MIME 类型为 `image/jpeg` 或 `image/png` 的文件。**

> **这一步证明了:** 这个实验室和实验一不一样——它**确实做了检查**,不是完全不设防。接下来的问题是:**这个检查到底是怎么做的?是看文件的真实内容,还是只看请求里"自称"的类型?**

**第 5 步:回到 Burp 代理历史,找到真正发起上传的那个请求**

在 Proxy > HTTP history 里,找到刚才那次上传动作对应的请求:

```
POST /my-account/avatar
```

把这个请求也发送到 **Burp Repeater**(这次是修改请求用,和前面那个"下载头像"的 `GET` 请求是两个不同的 Repeater 标签页)。

**第 6 步:关键一步——手动篡改请求里的 `Content-Type`**

在 Burp Repeater 里打开这个 `POST /my-account/avatar` 请求,找到**和文件这部分相关的消息体片段**,会看到类似:

```http
Content-Disposition: form-data; name="avatar"; filename="exploit.php"
Content-Type: application/octet-stream

<?php echo file_get_contents('/home/carlos/secret'); ?>
```

把这里的 `Content-Type` **手动改成**:

```http
Content-Type: image/jpeg
```

**为什么这样改就能骗过服务器?** 回忆第 5 章讲的原理:服务器的验证逻辑,只是在**检查这个请求头里写的字符串是不是 `image/jpeg` 或 `image/png`**,它**并没有去看文件里真正的二进制内容、也没有去验证这个 PHP 代码到底算不算"图片"**。既然 `Content-Type` 这个值是请求里的普通文本、客户端(也就是攻击者,借助 Burp)完全可以随便填,那只要把它**伪装成**服务器期望看到的值,这道检查就直接**形同虚设**。

**第 7 步:发送篡改后的请求,确认上传成功**

发送这个被修改过的请求。响应会表明:**文件上传成功了**——注意此时**文件本身(内容)还是那段 PHP 代码,只是请求里"自称"的类型从 `application/octet-stream` 变成了 `image/jpeg`**,而服务器只检查了这个自称的标签,没有检查真实内容,于是放行了。

**第 8 步:访问刚上传的"伪装成图片的 PHP 文件"**

切换到另一个 Repeater 标签页(第 2 步留着的那个下载头像用的请求),把路径里的图片文件名改成 `exploit.php`:

```
GET /files/avatars/exploit.php
```

发送请求——因为文件在服务器磁盘上的**真实内容依然是 PHP 代码**,而且这个目录依旧是"遇到 `.php` 就执行"的配置,所以服务器**照常执行了这段脚本**,响应里返回了 carlos 的秘密。

**第 9 步:提交秘密,解锁实验室**

### 这个实验的核心逻辑

> **漏洞点:** 服务器**确实做了类型检查**,但检查的对象选错了——它只看了**请求里的 `Content-Type` 请求头**(一个由客户端自己填写、可以随意伪造的"自我声明"),而**没有去验证文件的真实二进制内容是否真的是一张图片**。这就好比机场安检只检查你**自己填的申报单上写的是什么**,却不打开行李箱看一眼——你当然可以在申报单上写"衣物",箱子里实际装什么都行。

---

## 8. 两个实验的本质区别

| 对比项 | 实验案例一 | 实验案例二 |
|---|---|---|
| **服务器做了验证吗** | **完全没有**任何验证 | **做了验证**,但验证方式有缺陷 |
| **验证检查的是什么** | 无 | 请求里的 `Content-Type` 请求头(用户可控、可伪造) |
| **攻击者需要做什么** | 直接上传 `.php` 文件即可 | 先尝试直接上传(会被拦) → 用 Burp 拦截请求 → 手动把 `Content-Type` 改成 `image/jpeg` → 再发送 |
| **绕过的关键动作** | 无需绕过 | 利用 Burp Repeater **篡改**这个本该由服务器"不信任"的字段 |
| **相同点** | 两者上传目录都被配置成"遇到 `.php` 文件就执行",且最终都通过"重新请求上传后的文件路径"来触发代码执行并窃取 `/home/carlos/secret` | 同左 |

> **一句话区分:** 实验一是"门根本没锁",实验二是"门锁了,但钥匙孔(`Content-Type`)形同虚设,随便拿张纸条写上'我是钥匙'就能糊弄过去"。

---

## 9. 速记对比表

| 概念 | 核心问题 | 关键点 |
|---|---|---|
| **文件上传漏洞** | 服务器是否充分验证了上传文件 | 名称、类型、内容、大小,只要有一项没验证好就可能出问题 |
| **网页壳(Web Shell)** | 上传后能不能被执行 | `file_get_contents()` 读文件 / `system($_GET[...])` 执行任意命令,本质是把上传功能变成远程命令执行入口 |
| **multipart/form-data** | 二进制文件怎么通过 HTTP 传输 | 用 boundary 分隔多个字段,每个文件字段自带 `Content-Disposition` 和可选的 `Content-Type` |
| **有缺陷的类型验证** | 服务器信任的是"自称"还是"事实" | 只检查客户端自报的 `Content-Type`,而不检查文件真实内容 = 可被 Burp 直接篡改绕过 |
| **目录配置不一致** | 上传目录是否会"执行"文件 | 即使类型检查做得再好,如果存放目录把文件当脚本执行,危险依然存在 |

## 10. 渗透测试检查清单

以下方法仅用于**授权的测试环境或靶场**。

- [ ] 找到所有文件上传入口(头像、简历、附件、图片等)
- [ ] 尝试直接上传 `.php`/`.jsp`/`.asp` 等脚本文件,观察是否被拦截
- [ ] 若被拦截,用 Burp 拦截上传请求,检查判断依据是**文件扩展名**、**`Content-Type` 请求头**,还是**文件真实内容(魔术字节/文件头)**
- [ ] 若只检查 `Content-Type`:用 Burp Repeater 把它改成 `image/jpeg`、`image/png` 等允许值,重新发送
- [ ] 若只检查扩展名(黑名单):尝试冷门扩展名(`.phtml`、`.php5`、`.pht`)、大小写变体(`.PhP`)、双扩展名(`.jpg.php`)、null 字节截断等
- [ ] 上传成功后,**找到文件被存储/访问的真实路径**(通过观察下载请求,如 `GET /files/avatars/xxx`)
- [ ] 尝试直接访问上传的脚本文件路径,确认该目录是否会**执行**而非仅**返回**文件内容
- [ ] 若能执行,优先验证影响范围小的 PoC(如读取一个已知无害文件),再按授权范围决定是否进一步利用

---

## 11. 防御思路

| 问题 | 正确做法 |
|---|---|
| 完全不验证上传文件 | 至少限制**文件扩展名白名单**、**文件大小**、**存储位置** |
| 只信任 `Content-Type` 请求头 | 服务器应**检查文件的真实内容**(如读取文件头的"魔术字节"来判断真实类型),而不是信任客户端自报的值 |
| 黑名单扩展名易遗漏 | 优先使用**白名单**(只允许明确安全的扩展名),而非黑名单(禁止已知危险的) |
| 上传目录配置为可执行 | 上传文件应存放在**不会被当作脚本执行的目录**(比如关闭该目录的脚本执行权限),或存到**完全独立于 Web 根目录之外**的位置 |
| 文件名可控导致覆盖/路径穿越 | 服务器应**自己生成随机文件名**,不要直接使用用户提交的原始文件名 |

---

## 12. 一句话总结

> **文件上传漏洞的本质,是"服务器相信了不该相信的东西"**——要么完全不检查(实验一),要么只检查了一个**客户端自己填写、可以随意伪造**的标签(实验二的 `Content-Type`),而没有真正验证文件的**实际内容**。只要上传目录又恰好被配置成"遇到脚本就执行",攻击者就能把一次普通的"上传头像"操作,变成一次完整的**远程代码执行**。
