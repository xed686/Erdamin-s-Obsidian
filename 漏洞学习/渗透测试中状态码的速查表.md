# 渗透测试中看到状态码的"第一反应"速查表

核心心法一句话：**状态码不是用来判断"对不对"的，是用来判断"服务器那边发生了什么"的信号。** 渗透测试里几乎不存在"这个状态码是坏消息"这种说法，只有"这个状态码告诉了我什么信息"。

---

## 一、正常业务测试场景（打的是你能直接访问到的站点）

| 状态码                 | 第一反应                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------ |
| **200**             | 请求被正常处理了。接下来看返回内容里有没有敏感信息、业务逻辑是否符合预期，而不是看到 200 就结束。                                              |
| **301 / 302**       | 发生了跳转。第一反应：**看 `Location` 头跳去了哪**——跳转目标里可能藏着真实接口地址、未授权的内网地址，或者可以拿来做开放重定向/SSRF 跳转绕过。              |
| **400**             | 我的请求格式本身有问题（参数缺失、格式不对）。说明服务器"理解到了我在瞎传"，但还没走到业务逻辑层，先检查自己请求包写对了没有。                                 |
| **401**             | 需要身份验证。说明这个资源**存在**，但要带凭证才能看——可以去找认证方式（Cookie/Token/Basic 认证），不代表路径错了。                           |
| **403**             | 资源存在，但明确拒绝访问。第一反应：**是权限不够，还是被 WAF/黑名单拦了？** 可以试试换路径大小写、加 `/../`、换 `X-Forwarded-For` 等常见 403 绕过手法。 |
| **404**             | 路径本身不存在。第一反应：**我是不是把路径/参数写错了**，而不是代表"这里没漏洞"——很多时候是字典跑太快漏看了拼写。                                    |
| **500**             | 服务器内部出错了。第一反应：**我的输入是不是触发了后端异常**，尝试构造更多畸形输入观察报错信息（报错回显本身也可能泄露技术栈、路径等信息）。                         |
| **502 / 503 / 504** | 网关/后端服务本身的问题（后端挂了、过载、超时），一般不是你直接打出来的业务逻辑问题，但如果是**集中批量出现**，要留意是不是把目标打崩了（压测效果），注意控制速率。             |

## 二、盲打内网 / SSRF 探测场景（你刚做的那个实验属于这一类）

这个场景下，思路完全不一样：**你根本不知道目标在哪，状态码是用来"定位谁是真实存在的"，而不是用来判断权限。**

| 看到的现象                                  | 第一反应                                                                                                                        |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **一大片结果长得一模一样**（状态码相同、长度也相同）           | 这是"噪音基线"——大概率是服务器尝试连接失败/超时后统一返回的错误页，**先确定这个"大多数"长什么样，把它当作背景色**。                                                             |
| **某一条和"大多数"不一样**（状态码不同，或状态码一样但长度/内容不同） | **这才是真正的信号！** 不管它是 200、404 还是 403，只要"跟别人不一样"，说明这个地址背后**真的有一个活的 HTTP 服务在响应**，优先深挖它。                                          |
| **这条异常结果恰好是 404**                      | 不要被"404=没有资源"的惯性带偏。在这个场景下，404 能返回，本身就证明：请求**真的送达了**一台正常运行 HTTP 服务的机器，只是你当前请求的这个具体路径它没有而已。换个路径（比如直接访问根目录 `/` 或 `/admin`）继续探。 |
| **这条异常结果是 200**                        | 最理想的情况，直接有内容可看，不需要再换路径。                                                                                                     |
| **这条异常结果是 403/401**                    | 同样是好信号——说明目标存在且有访问控制，可以考虑能不能借助 SSRF 发起的请求本身绕过这层控制（就像你这次 `/admin` 直接被当作"内部可信请求"放行一样）。                                        |

---

## 三、一句话记忆法

- **正常测试场景**：404 = 我大概率走错路了，500 = 我的输入可能戳到后端了，403 = 东西在但进不去，401 = 东西在但没登录。
- **盲打/遍历场景**：别看"是不是 200"，看"**是不是和别人不一样"——跟大多数长得不一样的那一个，才是你要的活靶子。
