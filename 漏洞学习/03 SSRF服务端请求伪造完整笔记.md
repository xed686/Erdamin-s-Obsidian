# SSRF（服务端请求伪造）完整笔记

## 一、什么是 SSRF

**SSRF（Server-Side Request Forgery，服务端请求伪造）** 指的是：应用程序提供了一个"由服务器代替用户去请求某个 URL"的功能，但由于服务器没有对这个 URL 做严格校验，攻击者得以**操控服务器去访问攻击者指定的地址**——而不是开发者原本预期的地址。

核心本质可以用一句话概括：**本该由用户自己发起的请求，变成了由服务器"代发"，而服务器本身往往拥有比用户更高的网络权限（能访问内网、本地服务、管理后台等）**，这就是 SSRF 危害的根源。

---

## 二、针对服务器自身的 SSRF 攻击

### 1. 正常业务场景

设想一个购物网站，提供"查看某商品是否在特定门店有库存"的功能。要实现这个功能，应用服务器需要去查询后端各个门店独立维护的库存 REST API。为了实现灵活调度（比如前端可以指定查哪个门店、走哪个库存接口），开发者图省事，**直接把要请求的 API 地址作为参数，由前端传给后端**，后端拿到这个地址后代替用户去发起请求。

用户在前端查询库存时，浏览器实际发出的请求是这样的：

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://stock.weliketoshop.net:8080/product/stock/check%3FproductId%3D6%26storeId%3D1
```

（URL 解码后即 `http://stock.weliketoshop.net:8080/product/stock/check?productId=6&storeId=1`）

服务器收到这个请求后，会**向 `stockApi` 参数指定的地址发起请求**，拿到库存结果后再返回给用户。

### 2. 漏洞利用：篡改目标地址

问题就出在这里：服务器**没有校验 `stockApi` 到底指向哪里**，只要是一个合法的 URL 格式，服务器就会老老实实地替你发请求。攻击者完全可以把这个参数改成服务器自己的地址：

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://localhost/admin
```

此时服务器会"请求自己"——去访问本机的 `/admin` 路径，并把拿到的响应内容（也就是后台管理页面的内容）当作"库存查询结果"原样返回给攻击者。

> `127.0.0.1` 和 `localhost` 都指向**回环接口（loopback）**，即服务器请求"自己"。无论用哪种写法，效果都是让服务器向自己发起请求。

### 3. 为什么这样就能绕过权限控制？

正常情况下，`/admin` 管理后台通常要求用户必须登录（经过身份验证）才能访问，攻击者直接用浏览器访问是看不到任何内容的。但当这个请求**来自服务器本机**时，情况就不同了：

> **攻击者可以访问 `/admin` 这个 URL，但管理功能通常仅对经过身份验证的用户开放，所以攻击者本来是看不到任何内容的。可一旦这个请求是从服务器本机发出的，常规的访问控制就被绕过了——应用会认为"来自本机的请求=可信的内部操作"，于是直接给予完整的管理权限。**

也就是说，SSRF 之所以能生效，根源在于**应用对"请求来源"的信任判断出了问题**：它把"请求是从哪台机器发出的（网络层面的来源）"当成了"这个请求是否已经过身份验证（业务层面的权限）"的替代依据，而这两者本不该划等号。

### 4. 为什么应用会做出这种"信任本地请求"的设计？（三类常见原因）

1. **访问控制检查被绕在了前面的组件**
   权限校验逻辑可能实现在部署于应用服务器**前方**的另一个组件上（比如反向代理、WAF、网关）。当一个连接是"从内部绕回服务器自身"时，这一层校验直接被跳过了——因为这类校验通常只拦截"从外部进来"的流量，没考虑到"服务器请求自己"这种内部回环场景。

2. **灾难恢复目的的后门设计**
   应用可能故意设计成：只要是来自本机的请求，任何用户无需登录即可进行管理访问。这是为了在管理员意外丢失登录凭据时，仍能通过本机直接恢复系统访问权限。这个设计的前提假设是"只有完全可信的人才能直接登录到服务器本机操作"——但 SSRF 恰恰打破了这个假设，让**远程攻击者"伪装成"本机发起请求**，而不需要真的拿到服务器的登录权限。

3. **管理界面监听了不同端口**
   管理后台可能监听在主应用程序之外的另一个端口上，这个端口原本的设计意图是"用户从外部网络无法直接访问到"，开发者因此放松了这个端口上的权限校验强度。但服务器自己发起请求时并不受这层"外部不可达"的网络隔离限制，SSRF 可以让攻击者间接访问到这个本应被网络层面隔离保护的端口。

**小结**：这三种情况有一个共性——**系统把"请求的网络来源"当作了一种隐性的信任凭证**，而 SSRF 的本质就是伪造这个来源，让原本应该受限的请求"看起来"像是从可信位置发出的。这种信任关系的存在，是 SSRF 能成为**高危（甚至严重）漏洞**的关键原因。

## 三、针对其他后端系统的 SSRF 攻击（打内网）

### 1. 攻击目标从"服务器自身"扩展到"内网其他机器"

SSRF 不仅能让服务器"请求自己"，更常见、危害更广的场景是：**让服务器替攻击者去访问它所在内网中的其他机器**。

在很多企业网络架构中，应用服务器往往能与一些**攻击者本来完全无法从公网直接访问**的后端系统进行交互——这些系统通常使用**不可路由的私有 IP 地址**（如 `192.168.x.x`、`10.x.x.x`、`172.16.x.x`-`172.31.x.x`），只在内网范围内可达。

### 2. 为什么内网系统更容易被打穿

- 这些内部系统的设计前提是"反正外部网络到不了这里"，因此**安全防护强度普遍偏低**（受到网络拓扑隔离的"保护"，本身代码/接口的安全加固往往被忽视）。
- 很多内部后端系统直接承载着一些**敏感管理功能**，而且常常是"任何能连上它的人，无需身份验证即可访问"——因为设计者默认"能连上就说明你已经在内网里，已经是可信的"。

这正是 SSRF 最危险的地方：攻击者原本站在公网，**根本碰不到这些内网机器**；但只要能让应用服务器（它本身处于内网，具备访问这些机器的网络能力）替自己发起请求，就相当于**借用服务器的网络位置，把攻击面从"公网"直接延伸进了内网**。

### 3. 实战示例

延续前面购物网站的例子，假设在内网中，`192.168.0.68` 这台机器上存在一个管理接口 `http://192.168.0.68/admin`。攻击者可以构造如下请求来利用 SSRF，让服务器代为访问这个原本攻击者自己完全连不到的内网管理界面：

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://192.168.0.68/admin
```

应用服务器收到请求后，会像处理正常的库存查询一样，向 `192.168.0.68/admin` 发起请求，并把响应内容（内网管理后台的页面内容）返回给攻击者——此时攻击者实际上已经实现了**从外网跳板进入内网**，完成了一次内网资产探测/访问。

## 四、SSRF 的常见利用场景（知识点补充）

| 场景 | 说明 |
|---|---|
| 内网端口/服务探测 | 通过修改目标 URL 遍历内网 IP + 端口，根据响应时间/内容差异判断内网哪些主机、端口是开放的（内网端口扫描） |
| 访问云环境元数据接口 | 云服务器通常有一个固定的本地元数据地址（如 `http://169.254.169.254/`），可能泄露云主机的临时密钥、角色权限等高度敏感信息，是云上 SSRF 最经典的利用方向之一 |
| 攻击内网未授权服务 | 如 Redis、Memcached、Elasticsearch 等常见"内网默认无需认证"的服务，配合特定协议（如 `gopher://`）可能进一步实现命令执行 |
| 读取本地文件 | 部分场景下可通过 `file://` 协议读取服务器本地文件 |
| 绕过防火墙/黑名单做跳板 | 利用服务器的网络位置访问原本被边界防火墙拦截的目标 |

## 五、常见过滤绕过思路

实际测试中，开发者往往会对传入的 URL 做一些简单过滤（如禁止 `127.0.0.1`、`localhost`、内网网段），但这类黑名单过滤很容易被绕过，常见手法包括：

- **进制变形**：`127.0.0.1` 可写成十进制整数 `2130706433`、八进制 `0177.0.0.1`、十六进制 `0x7f.0.0.1` 等等效形式。
- **IPv6 回环地址**：`[::1]` 等效于 `127.0.0.1`。
- **特殊域名**：注册一个解析到内网/本机 IP 的域名，绕过对字面量 IP 的黑名单检测。
- **DNS 重绑定（DNS Rebinding）**：首次解析返回正常公网 IP 通过校验，后续请求实际发出时该域名已被重新解析指向内网地址。
- **302 跳转绕过**：先请求一个受信任/校验通过的外部地址，由该地址返回 302 跳转到真正想访问的内网地址，部分实现只校验了最初的 URL，未对重定向后的最终地址做二次校验。
- **URL 解析差异**：利用 `@`、多个 `/`、不同解析库对畸形 URL 的解析差异（如 `http://trusted.com@127.0.0.1/`），让校验逻辑和实际发起请求的逻辑"看到"不同的目标地址。

## 六、防御思路

1. **白名单优先**：能限定可访问的目标域名/IP 范围，就不要用黑名单去"排除"危险地址——黑名单天然存在被绕过的可能性。
2. **禁止跟随重定向**，或对重定向后的最终目标地址做二次校验，防止 302 跳转绕过。
3. **统一使用安全的 URL 解析库**做校验和发起请求，避免因为解析逻辑不一致产生的"校验与实际请求不一致"问题。
4. **网络层面隔离**：应用服务器本身的出网权限应最小化，不该能访问的内网段/端口在网络策略层面直接禁止，而不仅仅依赖应用代码层面的过滤。
5. **去除对"请求来源"的隐性信任**：管理接口等敏感功能应统一走身份验证，而不能仅凭"请求是否来自本机/内网"就判定为可信。
6. **云环境单独加固**：禁止或限制访问云平台的元数据服务地址，或要求该类请求必须携带额外的身份令牌（如 IMDSv2 机制）。

---

## 七、总结

1. SSRF 的本质是：应用把"该由用户自己做的网络请求"交给服务器代劳，却没有限制服务器能代劳访问的目标范围。
2. 危害程度取决于**服务器自身的网络位置**——服务器能访问到的范围越广（本机管理接口、内网后端系统、云元数据接口等），SSRF 能造成的危害就越大，有时足以从"信息泄露"升级为"打穿整个内网"。
3. SSRF 之所以屡见不鲜且危害严重，核心原因是很多系统**把"请求来源的网络位置"误当成了"请求是否可信"的判断依据**，这是审计和设计防御方案时都应该重点关注的逻辑漏洞点。
