# 资产收集到漏洞验证 —— subfinder / ffuf / nuclei 工作流

这三款工具分别负责渗透测试/Bug Bounty 流程中的三个不同阶段，各自只做好自己擅长的一件事，串联起来就是一条从"找资产"到"确认漏洞"的完整流水线：

```
subfinder（子域名发现）
      ↓
httpx（可选，存活探测，此处不展开 看关联文档笔记）
      ↓
ffuf（路径 / 参数 / 目录爆破）
      ↓
nuclei（漏洞特征确认）
```

## 各工具在链路中的角色

| 阶段         | 工具        | 负责什么               | 回答的问题                  |
| ---------- | --------- | ------------------ | ---------------------- |
| 1. 资产发现    | subfinder | 被动收集目标域名下的子域名      | "这个公司都有哪些子域名？"         |
| 2. 路径/资产探测 | ffuf      | 对存活资产做目录、参数、虚拟主机爆破 | "这个站点上还有哪些没被公开链接到的路径？" |
| 3. 漏洞确认    | nuclei    | 用已知漏洞特征模板批量验证      | "这些路径/资产里，有没有已知类型的漏洞？" |

三者的关系可以理解为：subfinder 负责把"目标范围"从一个域名扩展成一整片资产；ffuf 负责在这片资产上"挖"出更多没有被直接暴露的路径和入口；nuclei 负责对这些入口做"是否真的有洞"的最终判断。前两者是**发现型工具**，只负责扩大信息面，不判断风险；nuclei 是**验证型工具**，负责把"存在"翻译成"有没有已知漏洞特征"。

## 完整命令链路示例

```bash
# 第一步：被动收集子域名
subfinder -d target.com -silent > subs.txt

# 第二步：存活探测（推荐加一步 httpx，过滤掉不可访问的子域名，减少后续无效扫描）
httpx -l subs.txt -silent > alive.txt

# 第三步：对存活资产做路径爆破
ffuf -w /path/to/wordlist.txt -u FUZZ/FUZZ2 \
     -w alive.txt:FUZZ -w paths.txt:FUZZ2 \
     -mc 200 -s > found.txt

# 第四步：把爆破出的路径喂给 nuclei 做漏洞特征确认
nuclei -l found.txt -o final_result.txt
```

也可以跳过 ffuf，直接把存活资产整体喂给 nuclei（因为 nuclei 自己也内置了大量路径类检测模板，如敏感文件泄露、后台面板识别等）：

```bash
nuclei -l alive.txt -o final_result.txt
```

两种用法的区别：直接扫存活资产，覆盖的是 nuclei 模板库里"已经写好路径"的检测项；先用 ffuf 爆破再喂给 nuclei，能额外覆盖模板库里没有收录、但字典里有的自定义路径。实战中通常两条路都会走一遍。

## 为什么要分开用三个工具，而不是一个工具全干

- **各自数据源/检测逻辑不同**：subfinder 靠被动数据源查询（证书透明度日志等），ffuf 靠主动字典爆破，nuclei 靠模板匹配，三者的技术路线完全不同，硬塞进一个工具里会互相拖累效率
- **速度与准确率的取舍不同**：subfinder 追求快速摸清资产范围，ffuf 追求字典覆盖度，nuclei 追求匹配准确率（减少误报），分开维护更容易针对各自目标做优化
- **可组合性**：分开的工具都遵循"接收标准输入 / 输出到标准输出"的 Unix 哲学，任意两个都能通过管道直接拼接，换成别的替代工具（如把 subfinder 换成 amass）也不影响整条链路

## 后续可以补充的环节

当前链路是最基础的三段式，实战中通常还会补充：按照使用顺序排序（从上到下）

- **httpx**：在 subfinder 之后加一步存活探测和技术指纹识别，减少无效目标（已补充）
- **naabu**：端口扫描，覆盖非 HTTP 服务（配合 nuclei 的 `network`/`tcp` 协议模板）
- **katana** 或类似爬虫工具：在 ffuf 字典爆破之外，补充"从页面里实际抓取到的链接"，覆盖字典猜不到的路径
