# 鉴权与身份验证技术全景笔记

## 一、核心三要素

登录鉴权技术的基础是三个核心要素：

| 要素 | 说明 |
|---|---|
| 用户身份 | 用户在系统中的唯一标识，如用户名、邮箱 |
| 用户凭证 | 证明身份的信息，如密码、动态验证码 |
| 鉴权机制 | 验证身份和权限的过程，包含"身份验证"与"权限验证"两个环节 |

---

## 二、HTTP 协议基础（鉴权相关部分）

### 1. 数据包结构
- **Request**：请求方法、请求路径、请求头
- **Response**：状态码、响应头

### 2. 常用请求方法

| 方法 | 说明 |
|---|---|
| GET | 请求指定资源，仅获取数据 |
| POST | 提交数据进行处理（登录、表单、文件上传），非幂等 |
| HEAD | 与 GET 相同但不返回响应体，仅获取报头信息 |
| PUT | 上传/替换指定资源内容，幂等 |
| DELETE | 请求删除指定资源 |
| OPTIONS | 查询服务器支持的方法/探测服务器能力 |
| TRACE | 回显服务器收到的请求，用于测试诊断，是最安全的方法 |
| CONNECT | 将连接改为隧道方式的代理方法 |

### 3. 状态码与安全含义

| 类别 | 含义 |
|---|---|
| 1xx | 请求已接收，继续处理 |
| 2xx | 请求成功（如 200 OK） |
| 3xx | 重定向，需进一步操作 |
| 4xx | 客户端错误 |
| 5xx | 服务端错误 |

**常见状态码**：200（成功）、301（永久重定向）、302（临时重定向，**存在被劫持风险**）、400（请求语法错误）、401（未授权）、403（拒绝服务）、404（资源不存在）、500（服务端异常）、503（服务不可用）。

**渗透测试中的容错/误报陷阱**：
- 网站做容错处理时，错误页面可能统一跳转到固定地址（3xx，中间件配置或代码跳转两种实现，需区分请求路径/文件是否真实存在）。
- 部分网站访问错误页面仍返回 **200 状态码**（而非 404），会造成扫描器/人工判断的误报，需结合返回内容而非仅看状态码判断。

### 4. HTTP vs HTTPS

| 维度 | HTTP | HTTPS |
|---|---|---|
| 加密 | 明文传输，可被截获查看 | SSL/TLS 加密，防截获篡改 |
| 身份验证 | 无 | 数字证书验证服务器身份，防中间人攻击 |
| 默认端口 | 80 | 443 |

## 三、Authorization 请求头体系

`Authorization` 是 HTTP 提供的通用权限控制与认证框架，解决的是**跨系统、跨域**身份验证问题（单系统内 Cookie 即可满足需求）。其运行依赖两个标头：

- **`WWW-Authenticate`**（响应头）：服务器以 `401 Unauthorized` 响应时，通过该头告知客户端应使用的认证方案（`<auth-scheme>`，如 Basic / Digest / Bearer）及必要参数。
- **`Authorization`**（请求头）：客户端按对应方案处理凭证后，在该头中携带凭证重新发起请求。

标准通用流程：
1. 客户端请求授权（账户密码/密钥等）。
2. 服务端验证后返回授权码/令牌。
3. 客户端在 `Authorization` 头中携带令牌请求资源。
4. 服务端验证令牌有效性和权限，放行或拒绝。

### 常见认证方案速览

| 方案 | 现状 | 一句话说明 |
|---|---|---|
| Basic 认证 | 已过时，仅内网/简单场景使用 | 用户名:密码 经 Base64 编码后放入头部，**编码非加密**，明文风险高 |
| Digest 认证 | 已较少使用 | 用 nonce + 用户名密码做哈希摘要，比 Basic 安全，但已被 Bearer/JWT 取代 |
| Bearer 认证 | 主流 | 基于 OAuth2.0，持有令牌即可访问，广泛用于跨系统/跨域 |
| JWT 认证 | 主流，推荐 | 一种特殊的 Bearer 令牌，令牌自身包含可验证的用户信息，无状态 |
| API 密钥认证 | 主流（开放平台/第三方接口） | 每次请求携带唯一 Key，服务端比对后放行，可配合速率限制做访问控制 |
| 双因素认证（2FA） | 主流，安全加固手段 | 密码之外叠加短信/动态码/硬件密钥/生物识别等第二因素 |
| 其他（一句话带过） | 特定场景/遗留系统 | OpenID Connect（基于 OAuth2 的单点登录协议）、SAML（企业级跨域单点登录 XML 标准）、Kerberos（内网强认证协议）、LDAP（对接 AD 等目录服务）、生物识别、智能卡（高安全环境） |

> Basic / Digest 的详细字段（如 `nonce`、`opaque`、`qop`、`cnonce`、`nc` 等重放防护参数）目前在现代 Web 应用中已很少见，了解其"防重放"设计思路即可，不再逐字段展开。

## 四、四大主流鉴权方案详解

### 1. Cookie + Session

**注册与登录流程**：
1. 注册时服务端用**足够长的随机 salt** 对密码加盐加密后存储，防止数据泄露后被直接撞库。
2. 登录时服务端用 salt 对输入密码做同样的哈希（如 SHA）与库中密文比对。
3. 验证通过后创建 Session 对象，`sessionId` 通过 Cookie 下发给浏览器；此后每次请求携带该 Cookie，服务端据此识别身份。
4. **Session 续期**：Session 有效期较短，为避免用户频繁重新登录，通常在中间件层面对每次合法请求刷新过期时间（`当前时间 + 过期时长`）。

**优点**：实现简单（仅需 `Set-Cookie`）；数据可分离存放（不敏感信息放 Cookie，Session 在服务端相对安全）。

**缺点**：
- Cookie 被截获即可能被冒用，即使加密也可被原样转发重放。
- 分布式系统下 Session 需额外做多机共享（如 Redis 集中存储），增加架构复杂度。
- 服务端需持续存储、清理过期 Session，带来内存/CPU 开销。
- Cookie 有数量（每域名通常 ≤20 条）和大小（单条 ≤4KB）限制，用户禁用 Cookie 则机制失效。

### 2. Token

服务端生成的一串加密字符串，登录成功后下发，客户端后续请求通过 GET/POST/Header 携带。

**典型组成**：`uid`（用户标识）+ `time`（时间戳）+ `sign`（签名，哈希压缩生成）。

**完整流程**：登录 → 服务端校验并生成 Token → 返回给客户端存储 → 客户端后续请求携带 Token → 服务端校验合法性并维持状态 → Token 到期自动失效，需重新登录。

**优点**：无状态、服务端压力小；随机性高、过期时间短，不易伪造；天然支持跨域。

**缺点**：有效期短带来体验问题（需配合 `refresh_token` 机制）；若存储在前端（如 `localStorage`）存在被 XSS 窃取的风险；刷新机制增加系统复杂度。

### 3. JWT（JSON Web Token）

结构：`Header.Payload.Signature`，三段分别 Base64 编码后用 `.` 拼接。

| 部分 | 内容 |
|---|---|
| Header | 令牌类型与签名算法（如 HS256） |
| Payload | 声明（Claims）：Registered claims（`iss`签发者、`exp`过期时间、`sub`主题、`aud`接收者、`iat`签发时间、`nbf`生效时间、`jti`唯一ID 等标准字段）、Public claims（自定义公共信息）、Private claims（业务私有信息） |
| Signature | 对 Header+Payload 用指定算法配合密钥签名，防篡改 |

**优点**：体积小、无状态、可跨域、支持前后端分离、自带防篡改签名、减少数据库查询。

**缺点**：**一旦签发无法主动撤销**（需靠短过期时间+刷新机制弥补）；载荷若含敏感信息且被窃取则直接泄露；密钥泄露则可伪造任意令牌；不支持多会话级别的精细控制。

### 4. OAuth 2.0

授权框架，让第三方应用在**不获取用户密码**的前提下，得到有限范围的资源访问权限。

**通用流程**：
1. 用户在第三方应用发起授权请求。
2. 重定向到授权服务器完成身份认证。
3. 用户确认授权范围（scope）。
4. 授权服务器颁发 Access Token。
5. 第三方应用凭 Token 访问受保护资源。

**四种授权模式**：`authorization_code`（授权码模式，最常用最安全）、`implicit`（简化模式，已不推荐）、`password`（密码模式，需高度信任第三方）、`client_credentials`（客户端模式，用于服务间调用）。

**典型应用场景**：社交账号登录第三方应用、开放 API 访问、企业 SSO。

## 五、四类方案技术选型对比

| 方案 | 适用场景 | 核心特点 |
|---|---|---|
| Cookie + Session | 内网、单体应用 | 简单、成熟，但分布式扩展和安全性有短板 |
| Token | 跨域、外网 API | 无状态、跨域友好，需自行设计刷新与吊销机制 |
| JWT | 单点登录（SSO）、前后端分离 | 自包含、免查库，但天然不可撤销 |
| OAuth 2.0 | 第三方系统登录、开放平台授权 | 灵活，不暴露密码，但流程复杂、攻击面较大 |

## 六、红蓝对抗视角要点

### 红队关注点
1. **UA 头（系统/设备识别）**：若站点将 UA 写入数据库做统计，接收+入库环节可能存在 SQL 注入；部分站点限制"仅允许一种设备类型访问"，可通过伪造 UA 绕过。
2. **Cookie（身份标识）**：核对是否存在权限字段可被客户端篡改（Cookie 脆弱）。
3. **POST 数据**：登录接口是否可被暴力破解（无验证码/Token/频率限制）。
4. **返回状态码**：用于目录/文件探测（结合"200 误报"陷阱综合判断真实存在性）。

### OAuth 2.0 常见漏洞
- `redirect_url` 校验不严，导致授权码 `code` 被劫持到恶意站点（需测试各类绕过写法）。
- `client_id` 与 `redirect_url` 不匹配，被滥用劫持。
- 一个应用签发的 `code` 可在另一应用复用。
- `state` 参数缺失，导致 CSRF 风险。
- `scope` 提权：低权限 `code` 被用于高权限场景。
- 传输层被劫持（HTTP 明文、中间人攻击）。
- 点击劫持：透明 iframe 覆盖授权按钮，诱导用户在不知情下完成授权点击。

### JWT / Token 攻防要点
- 签名算法混淆攻击（如 `alg: none` 绕过验签）。
- 密钥爆破/泄露导致任意令牌伪造。
- Token 未做吊销机制，注销后仍可用至自然过期。
- Payload 明文可读，避免在其中存放敏感信息。

---

## 七、总结

1. 身份鉴权技术从早期的 **Basic/Digest**（已基本淘汰）演进到 **Cookie+Session**（内网够用），再到 **Token/JWT**（跨域、前后端分离首选），最终发展出 **OAuth2**（第三方授权场景）——各方案并非替代关系，而是按场景组合使用。
2. 测试/审计时需同时具备 HTTP 协议基础（方法、状态码、头部）与鉴权机制原理，才能准确判断具体系统中该实现是否存在逻辑缺陷。
