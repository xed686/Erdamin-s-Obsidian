## 一、Java 面向对象基础概念（看懂后面一切的地基）

这几个词是 Java 世界的"语法骨架"，后面讲到的反射、反序列化、框架原理，全部建立在这几个概念上。

| 概念 | 一句话理解 | 类比 |
|---|---|---|
| **类（Class）** | 一张"设计图纸"，描述某一类事物应该有哪些属性、哪些行为 | 盖房子用的图纸 |
| **对象（Object）** | 根据图纸造出来的"实体"，一个类可以造出无数个对象 | 根据图纸盖出来的一栋栋具体的房子 |
| **接口（Interface）** | 只规定"必须能做什么"，不规定"具体怎么做"——是一份"能力约定" | 招聘启事上写"必须会开车"，不规定用什么车 |
| **继承（Extends）** | 一个类直接复用另一个类已有的属性和行为，再加上自己的新东西 | 儿子继承了父亲的姓氏和部分财产，自己再挣新的 |
| **实现（Implements）** | 一个类按接口的约定，具体把每个能力"实现"出来 | 按招聘启事的要求，证明自己真的会开车 |
| **抽象类（Abstract Class）** | 介于"类"和"接口"之间，部分方法写好了，部分留空等子类补充 | 半成品图纸，关键结构留白 |
| **封装** | 把数据和操作数据的方法打包在一起，外部只能通过规定的"接口"访问，不能直接动内部细节 | 遥控器——你只管按按钮，不用管内部电路 |
| **多态** | 同一个方法调用，根据对象的实际类型不同，表现出不同行为 | 同样是"叫一声"，猫和狗叫的声音不一样 |

> **这节在后面哪里会用到**：反射机制的核心操作对象就是"类"和"方法"；反序列化漏洞的核心就是"利用对象的方法调用链"；框架（Spring 等）的底层设计思想（IoC/AOP）也完全建立在接口和多态之上。

## 二、反射机制（Reflection）—— Java 安全里最核心的一个概念

### 1. 是什么
正常情况下，你写代码时必须**提前知道**要调用哪个类、哪个方法，代码里写死调用关系，编译时就确定好了。

**反射**打破了这个限制：程序在**运行时**（而不是写代码时）才去"查询"某个类有哪些方法、哪些属性，并且可以动态地创建对象、调用方法——哪怕你写代码的时候根本不知道这个类叫什么名字，只要运行时能拿到这个类的"名字字符串"，就能通过反射把它创建出来并调用。

### 2. 为什么需要它（正常开发用途）
这不是什么"黑客专用技巧"，而是 Java 框架的**底层基石**：
- Spring 框架能做到"你只需要在配置里写个类名，它就自动帮你创建对象并把需要的东西注入进去"，底层全靠反射实现。
- 各种 ORM 框架（Hibernate/MyBatis）能把数据库查出来的一行数据自动"转换"成一个 Java 对象，也是靠反射动态读写对象的属性。

### 3. 为什么安全圈特别关注它
**如果攻击者能控制"要反射调用哪个类、哪个方法"这个输入，就相当于让程序在运行时执行攻击者指定的任意代码逻辑**——这正是后面"反序列化漏洞"和"Gadget 链"的根本原理：攻击者构造一段特殊数据，让程序在"反序列化还原对象"的过程中，被反射机制"顺手"调用到了一些危险方法（比如执行系统命令的方法），从而实现远程代码执行。

> **一句话记住**：反射 = "运行时动态决定要调用谁"，这个"动态"本身是把双刃剑——用得好是框架的灵活性，被攻击者控制就是代码执行漏洞。

## 三、动态代理（Dynamic Proxy）

### 1. 是什么
代理（Proxy）就是"找个中间人代替你做事"。**动态代理**指的是：不需要事先写好一个具体的"代理类"，而是在程序运行时，**根据某个接口动态生成一个代理对象**，这个代理对象可以在真正执行目标方法之前/之后，插入一些额外的处理逻辑（比如记录日志、权限检查、性能统计）。

### 2. 和反射的关系
动态代理**依赖反射机制**实现——生成代理对象、转发方法调用，底层都是靠反射在运行时动态完成的。

### 3. 在哪里会遇到
- Spring 框架的 **AOP（面向切面编程）**（比如"所有方法执行前自动打印日志"这种横切逻辑）就是用动态代理实现的。
- Java 反序列化攻击链中，`InvocationHandler`（动态代理的核心接口之一）经常是构造 Gadget 链时的关键一环——攻击者利用动态代理"方法调用会被自动转发并执行额外逻辑"这个特性，把恶意代码"挂"在正常的方法调用过程中。

> **先知道这个词和反射是"近亲"关系即可**，具体怎么构造利用链，留到小迪课程讲到具体案例时再深入。

## 四、序列化与反序列化（Serialization / Deserialization）

### 1. 是什么
- **序列化**：把一个 Java 对象（内存里的数据结构）转换成一串可以存储或传输的字节/文本（比如存文件、通过网络发送）。
- **反序列化**：反过来，把这串字节/文本还原成一个 Java 对象。

### 2. 为什么需要它
对象只存在于程序运行的内存里，程序一关就没了。如果要把一个对象存到文件里、或者通过网络发给另一台服务器，就必须先"序列化"成能传输的格式，接收方再"反序列化"还原回对象。这是分布式系统、缓存、网络通信中非常基础的需求。

### 3. 为什么是高危漏洞
反序列化这个"还原对象"的过程，**本质上是程序在自动执行一系列创建对象、调用方法的操作**（回想第二节反射的内容）。如果这份"要还原的数据"来自不可信的用户输入，攻击者就可以精心构造一份恶意数据，让反序列化过程"顺手"触发一连串原本不该被调用的方法——这一连串被利用的方法调用关系，就叫 **Gadget 链（利用链）**。

**JDK 原生反序列化**、**FastJson**、**XStream**、**SnakeYaml** 等，都是 Java 生态中常见的"序列化/反序列化实现方式"，它们各自都有被发现过的、臭名昭著的反序列化漏洞和对应的 Gadget 链。

> **这节现在不需要懂怎么手写 Gadget 链**，只需要记住这个因果关系：**反序列化 = 程序自动按数据内容创建对象、调方法 → 数据可控就等于让攻击者控制了"调什么方法"→ 构造出一条能最终执行命令的方法调用链，就是一次反序列化攻击**。

## 五、JNDI / RMI / LDAP / DNS —— 几个"服务发现"相关名词

这几个词放在一起理解会更轻松，它们都和"程序在运行时去远程查找/调用某个资源"有关：

| 名词 | 全称 | 一句话理解 |
|---|---|---|
| **JNDI** | Java Naming and Directory Interface | Java 提供的一套统一接口，用来"按名字查找"各种资源（数据库连接、远程对象等），不用关心这个资源具体存在哪 |
| **RMI** | Remote Method Invocation | Java 自带的"远程方法调用"机制，可以像调用本地方法一样调用另一台服务器上的 Java 对象的方法 |
| **LDAP** | Lightweight Directory Access Protocol | 一种用于访问"目录服务"（类似电话簿，按条件查找用户/资源信息）的协议 |
| **DNS** | Domain Name System | 大家熟悉的域名解析系统，这里被提及是因为 JNDI 查找资源时也可以走 DNS 这类"命名服务" |

**为什么连在一起讲**：JNDI 可以通过 RMI、LDAP、DNS 等多种"协议"去查找远程资源。而 JNDI 注入漏洞（最著名的就是 Log4j 的 Log4Shell）的核心原理是：**如果攻击者能控制 JNDI 要去"查找"的地址，就可以让服务器主动连接攻击者控制的恶意 RMI/LDAP 服务器，并把恶意返回内容加载执行**——这也是为什么这几个名词总是一起出现。

> **现在只需要知道这几个词都和"远程查找/调用资源"有关，JNDI 是统一入口，RMI/LDAP/DNS 是它背后可能走的几种具体协议**，具体 Log4j 这类漏洞的完整利用链，留到小迪课程讲具体案例时再深入。

## 六、常见高危组件家族速览（现在只需要"认脸"，不需要会打）

这些都是 Java 生态里非常流行、但历史上都爆出过严重漏洞的第三方组件，先混个脸熟：

| 组件 | 用途 | 为什么出名/危险 |
|---|---|---|
| **Log4j** | 日志记录库，几乎所有 Java 项目都在用 | Log4Shell（JNDI 注入）漏洞，影响范围是整个 Java 生态历史上最大规模的一次 |
| **Shiro** | 身份验证与权限控制框架 | 历史上多次爆出"记住我"（RememberMe）功能相关的反序列化漏洞 |
| **FastJson** | 阿里巴巴出的 JSON 处理库（把 Java 对象和 JSON 字符串互相转换） | 处理 JSON 时的反序列化机制多次被发现可构造 Gadget 链 |
| **XStream** | 把 Java 对象和 XML 互相转换的库 | 同样因反序列化机制被发现多个远程代码执行漏洞 |
| **SnakeYaml** | 处理 YAML 格式配置文件的库 | YAML 反序列化同样可以构造恶意对象实例化链 |

> **记忆方法**：看到"某个库 + 反序列化/注入"的新闻，先反应出"它是干嘛用的"（日志/权限/JSON/XML/YAML 处理），再去理解具体漏洞原理会轻松很多。

## 七、打包与构建：JAR / WAR / Maven

| 概念 | 一句话理解 |
|---|---|
| **JAR**（Java Archive） | 把一堆编译好的 Java 类文件打包成一个压缩文件，方便整体分发、运行——类似"把一堆文件打成一个 zip" |
| **WAR**（Web Application Archive） | 专门给 **Web 应用**用的打包格式，里面除了 Java 代码，还包含了网页、配置文件等，可以直接丢进 Tomcat 这类 Web 服务器里跑起来 |
| **Maven** | Java 最主流的"项目管理 + 依赖管理"工具，核心是一个 `pom.xml` 配置文件——你只需要在里面写"我要用哪个库、哪个版本"，Maven 自动帮你下载好并处理好各个库之间的依赖关系 |

> **审计角度的意义**：`pom.xml` 里列出了项目用到的所有第三方库和版本号，审计时第一步往往就是打开这个文件，看看有没有用到上面第六节那些"历史上爆过漏洞"的组件，以及版本号是不是停留在有已知 CVE 的旧版本。

## 八、Spring / SpringBoot 全景地图

这是目前 Java Web 开发**事实上的行业标准框架**，概念较多，这里只建立"全貌"，不展开细节。

### 1. Spring 核心思想（两个词）

| 概念 | 一句话理解 |
|---|---|
| **IoC**（控制反转，Inversion of Control） | 传统写法是"你的代码主动去 new 一个对象"；IoC 是反过来，"你只需要声明需要什么，框架自动把对象创建好并交给你"——控制权从你手里"反转"交给了框架 |
| **DI**（依赖注入，Dependency Injection） | IoC 的具体实现方式——框架在创建一个对象时，自动把它需要用到的其他对象"注入"进去，不需要你手动拼装 |
| **AOP**（面向切面编程） | 把"日志记录""权限检查"这类很多方法都需要的通用逻辑抽出来，统一"切入"到需要的地方，不用在每个方法里重复写——底层就是第三节讲的动态代理 |

### 2. SpringBoot 是什么
SpringBoot 是在 Spring 基础上做的"开箱即用"封装——大幅简化了原本 Spring 繁琐的配置过程，内置了常用的默认配置，开发者可以用很少的代码快速搭起一个可运行的 Web 服务。目前绝大多数新的 Java Web 项目都是基于 SpringBoot 搭建的。

### 3. SpringBoot 生态里你在课程表里看到的那几个名词

| 名词 | 一句话理解 | 安全意义 |
|---|---|---|
| **Actuator** | SpringBoot 自带的"应用监控与管理"模块，可以查看应用运行状态、配置信息等 | 如果没有做好权限控制，相当于直接把应用的内部运行信息、甚至敏感配置暴露给了外部访问者 |
| **Swagger** | 自动生成 API 接口文档的工具 | 如果未授权就能访问，等于把整个后端的接口列表、参数结构"文档化"地直接交给了攻击者，大幅降低信息收集成本 |
| **HeapDump** | 把 Java 程序当前内存"快照"导出成文件（用于排查内存问题） | 内存快照里可能直接包含用户密码、Session、Token 等运行时敏感数据，是非常严重的信息泄露点 |
| **模板注入（SSTI）** | 和此前 PHP 的 Smarty 原理完全一致，只是换成了 Java 生态的模板引擎 | **Thymeleaf**、**Freemarker**、**Velocity** 是 Java 最常见的三个模板引擎，都存在各自的 SSTI 利用方式，原理与 Smarty SSTI 笔记完全通用 |
| **JWT 令牌** | 此前《鉴权与身份验证技术全景笔记》里已经详细讲过的 JSON Web Token | SpringBoot 项目里常配合 **Spring Security** 框架实现鉴权，审计重点是 JWT 签名校验是否严谨、是否存在鉴权绕过逻辑 |
| **Security** | Spring 官方的安全框架，负责登录鉴权、权限控制 | 配置不当（如拦截规则写漏、放行了不该放行的路径）是常见的权限绕过来源 |

> **这一节的好消息是**：模板注入、JWT 鉴权，这两块的底层原理你其实已经通过之前的 PHP/JS 笔记学过一遍了——Java 这边只是"换了个马甲"，概念是完全相通的，到时候复现起来会比反序列化那块轻松很多。

## 九、JavaEE Web 开发核心三件套（你已经学过，这里只做地图定位）

此前《JavaEE Servlet/Filter/Listener 安全笔记》已经详细讲过，这里只放回地图中帮你串联：

```
请求进来 → Listener（监听事件）→ Filter（层层过滤/鉴权）→ Servlet（真正处理业务逻辑）
```

这是最底层、最原始的 JavaEE Web 开发方式；而 Spring/SpringBoot 本质上是在这套底层机制之上，做了大量封装和自动化（比如你不再需要手写 `web.xml` 配置路由，而是用注解 `@RequestMapping` 等方式替代）。

## 十一、全景地图：这些概念分别出现在一个 Java Web 项目的哪个位置

```
【项目构建层】
  Maven（pom.xml 管理依赖）→ 打包成 JAR/WAR

【请求处理层】（底层机制 or Spring 封装后的高层写法）
  Listener → Filter → Servlet
        ↑（SpringBoot 中这一层被大量注解和自动配置封装了）

【业务逻辑层】
  Controller（接收请求）→ Service（业务逻辑）→ 可能用到 AOP（如权限检查、日志，基于动态代理）

【数据持久层】
  JDBC / Hibernate / MyBatis → 连接数据库

【底层机制支撑】（贯穿以上各层，是框架能"自动化"的根本原因）
  反射（Reflection）→ 动态代理（Dynamic Proxy）→ IoC/DI（Spring 容器自动创建、注入对象）

【容易出问题的"边缘功能"】（往往不是业务主逻辑，而是辅助功能）
  模板引擎渲染（SSTI）、序列化/反序列化（Gadget 链）、JNDI 查找资源（JNDI 注入）、
  Actuator/Swagger/HeapDump（信息泄露）、JWT/Security（鉴权绕过）
```

## 十二、给你的学习建议

1. **先把这份"地图"大致记在脑子里，不追求记住每个细节**——下次再听到"反射""动态代理""JNDI"这些词，至少知道它们大概归在"底层机制支撑"这一类，不会再是完全陌生的孤立概念。
2. **继续往后听课时，带着"这个概念属于地图上的哪一块"去听**，而不是试图每一行代码都看懂——理解"攻击链条的因果关系"比"手写出每一步代码"重要得多，手写能力可以等你后面系统学 Java 语法后再补。
3. **SSTI 和 JWT 鉴权这两块你会相对轻松**，因为底层原理你已经通过 PHP/JS 笔记学过一遍，到时候重点关注"Java 生态下的具体 API 和工具"就够了。
4. **反射、动态代理、反序列化这三个是真正的硬骨头**，心理预期放低一些完全正常，等后面课程到具体案例时，建议结合实际的 Gadget 链代码一步步跟着复现，比单纯看视频理解快得多。
