## 零、一条主线:身份验证的本质,是在解决"你凭什么是你"这个难题

在讲具体机制之前,先建立一个总纲——**Cookie、Session、Token 不是三个孤立的知识点,而是一场持续演进的攻防博弈,每一代都是为了补上一代的漏洞而生的。** 理解了这条演进线,后面所有细节都会自动归位。

### 核心矛盾:HTTP 是"无状态"的,但业务需要"记住你"

一切的根源在于——**HTTP 协议本身是"无状态"的**:服务器处理完你这个请求,就把你忘了;你下一个请求过来,它完全不认识你,不知道你是不是刚才那个登录过的人。

但业务偏偏需要"记住你"——你登录一次,后面浏览购物车、下单、改资料,总不能每点一下都重新输一次账号密码吧?

**所以身份验证机制要解决的核心难题就是:在一个"天生健忘"的协议上,想办法让服务器'记住'你是谁、并且'确信'你就是你本人,而不是别人冒充的。** 下面三代机制,就是对这个难题的三次升级回答。

### 三代演进:凭证从"明文塞给你"到"只给你一把钥匙"到"给你一张防伪证件"

| 代际 | 方案 | 解决了什么 | 又暴露了什么新问题 |
|---|---|---|---|
| 第一代 | **纯 Cookie** | 服务器把"你是谁"的信息(如 `user=admin`)直接写进 Cookie 交给你保管,下次你带回来它就认得你了 | **致命**:凭证存在客户端、用户完全可控 → 你把 `user=admin` 改成别人甚至管理员,服务器就信了(**伪造/篡改**) |
| 第二代 | **Session** | 不再把"你是谁"交给你保管,只给你一个**无意义的随机门牌号(Session ID)**,真正的身份信息锁在服务器自己手里。你改门牌号也没用,因为服务器查不到对应的人 | 门牌号(Session ID)本身如果被偷/被固定,还是能冒充(**会话劫持 / 会话固定**);且服务器要为每个用户存会话,有**存储压力**,跨域也麻烦 |
| 第三代 | **Token(如 JWT)** | 给你一张**自带防伪签名的"证件"**:证件上写着你是谁,但有服务器的数字签名,你改一个字签名就对不上 → 服务器不用存会话,靠验签就知道真假。天然适合跨域、前后端分离 | 证件一旦签发**难以主动吊销**(没到期就一直有效);证件被偷了照样能用(需配合短有效期);签名密钥泄露则全盘崩溃 |

> 💡 **看懂这张表,你就看懂了整个身份验证的历史**:每一代都是在补上一代的洞——
> - Cookie 把凭证交给用户保管 → **用户能篡改** → Session 改成"只给无意义门牌号,身份锁服务器"
> - Session 的门牌号能被偷/固定 → **会话劫持** → 需要登录后重新生成门牌号(`session_regenerate_id`)
> - Session 要服务器存、跨域难 → Token 改成"自带签名的证件,服务器不用存"
>
> **而每一代新暴露的问题,恰恰就是你做渗透时要盯的攻击面**:Cookie 看"能不能篡改"、Session 看"门牌号能不能偷/固定"、Token 看"签名能不能绕、能不能重放"。审计时带着"这一代是为了补什么洞而生的,它自己又留了什么洞"这个视角,比死记函数名有用一百倍。

### 这条主线怎么指导你审计

记住一个贯穿全篇的审计总问题:**"这个系统凭什么确信'发来这个请求的人'就是'当初登录的那个人'?这个'确信'的依据,能不能被攻击者伪造出来?"**

- 如果依据是"Cookie 里写着 `admin`" → 能伪造(直接改)→ 高危
- 如果依据是"有一个服务器认识的 Session ID" → 看这个 ID 能不能被偷/被预先固定
- 如果依据是"一个签名合法的 Token" → 看签名能不能绕过、Token 能不能重放/是不是别人的

**把这个总问题带进下面每一节,你读到的就不再是孤立的机制,而是'攻击者会从哪撬开这道门'的地图。**

## 一、五种身份验证实现方式（代码审计练习脉络）

| 序号 | 验证方式 | 涉及文件流转 |
|---|---|---|
| 1 | 数据库操作验证用户 | `login.php` → `index.php` |
| 2 | Cookie 验证后台登录 | `loginc.php` → `indexc.php` → `loginc_out.php` |
| 3 | Session 验证后台登录 | `logins.php` → `indexs.php` → `logins_out.php` |
| 4 | Session + Token 防爆破登录 | `loginst.php` → `logincheck.php` → `indexst.php` → `loginst_out.php` |
| 5 | 代码审计实战案例 | XHCMS（Cookie 脆弱）、YXCMS（Session 固定） |

> 这五个层级本质上是身份验证方案的演进路径：从最原始的"数据库比对"，到"客户端凭证"（Cookie），到"服务端会话"（Session），再到"Session + Token 双因子"用于防御暴力破解。审计时应重点关注每一级新增的验证逻辑是否被正确实现，而不是简单存在。

## 二、Cookie 身份验证

> 🎯 **这一代的定位(对照零章主线)**:Cookie 是第一代方案——服务器把"记住你的信息"**交给你(客户端)保管**。它的致命缺陷从诞生起就注定了:**凡是交给用户保管的东西,用户就能篡改。** 所以纯 Cookie 存身份信息,本质上是"把保险箱钥匙和保险箱一起交给了小偷"。下面的工作原理要带着这个视角看——注意它在哪一步把"可被篡改的信息"交到了客户端手里。

### 1. 工作原理

```
Client                              Server
  |--- 1. HTTP request -------------->|
  |<-- 2. Set-Cookie ------------------|
  |    3. Save cookie                 |
  |--- 4. HTTP request (带Cookie) --->|
  |    5. Read cookie                 |
  |    6. Process request             |
  |<-- 7. HTTP response ---------------|
```

**流程说明：**
1. 客户端向服务器发送 HTTP 请求。
2. 服务器检查请求头中是否包含 Cookie 信息。
3. 若包含则用其识别客户端；若不包含则生成一个新的 Cookie。
4. 服务器在响应头（`Set-Cookie`）中下发 Cookie。
5. 客户端接收并将 Cookie 保存在本地。
6. 客户端后续请求会自动携带该 Cookie。
7. 服务器每次收到请求都会校验 Cookie 的有效性，无效则要求重新登录。

### 2. 相关函数

| 函数/变量         | 作用                             |     |
| ------------- | ------------------------------ | --- |
| `$_COOKIE`    | 关联数组，包含客户端传递给当前脚本的所有 Cookie    |     |
| `setcookie()` | 设置一个 Cookie 并发送到客户端浏览器         |     |
| `unset()`     | 删除指定的 Cookie（需配合设置过期时间清除客户端副本） |     |

### 3. 安全审计要点（从渗透测试角度）
- **明文/弱加密存储敏感信息**：若 Cookie 中直接存放用户名、管理员标识、权限等级（如 `is_admin=1`），可被客户端篡改，属于典型的"Cookie 脆弱"漏洞（对应下文 XHCMS 案例）。
- **缺少 `HttpOnly` 标志**：未设置会导致 Cookie 可被 JavaScript 读取，增加 XSS 窃取会话的风险。
- **缺少 `Secure` 标志**：Cookie 可能在 HTTP 明文信道中被中间人截获。
- **缺少 `SameSite` 属性**：增加 CSRF 攻击面。
- **可预测/可爆破的 Cookie 值**：若身份凭证是简单规律的字符串（如用户 ID 拼接），可被枚举伪造。

## 三、Session 身份验证

> 🎯 **这一代的定位(对照零章主线)**:Session 是对 Cookie 缺陷的直接回应——**既然"把身份信息交给客户端"会被篡改,那就不交了。** 服务器只给客户端一个**无意义的随机门牌号(Session ID)**,真正的身份数据(你是谁、是不是管理员)全部锁在**服务器自己手里**。
> 关键升级:**你改门牌号没用**——因为服务器是拿这个号去自己的"登记簿"里查对应的人,你把 `session_id=abc` 改成 `session_id=xyz`,服务器查不到 `xyz` 对应谁,直接当你没登录。这就从根上堵死了 Cookie"直接改 `user=admin`"的篡改路子。
> 但它引入了新攻击面:**门牌号本身**。如果攻击者能偷到你的门牌号(Session 劫持),或者预先给你塞一个他已知的门牌号再诱导你登录(Session 固定),照样能冒充你。所以下面的审计要点,核心都围绕"**这个门牌号安不安全**"。

### 1. 工作原理

```
Client                                          Server
  |--- 1. Sends HTTP Request --------------------->|
  |<-- 2. 生成唯一 session ID 并存储于服务端 --------|
  |<-- 3. HTTP Response，session ID 作为 Cookie 下发-|
  |    4. Client 将 session ID 作为 Cookie 保存 ---- |
```

**存储对比：**
- Session ID 存储：**客户端**（以 Cookie 形式）
- Session 数据：**服务端**（文件、数据库、Redis 等）

### 2. 流程说明
1. 客户端发送 HTTP 请求。
2. 服务器为客户端生成唯一的 Session ID，并将会话数据存储在服务端存储器中。
3. 服务器将 Session ID 作为 Cookie 发送给客户端。
4. 客户端保存该 Cookie，后续请求自动携带。
5. 服务器通过 Session ID 检索对应的会话数据，实现状态保持。

### 3. 相关函数

| 函数/变量               | 作用                                    |
| ------------------- | ------------------------------------- |
| `session_start()`   | 启动或恢复一个已存在的会话                         |
| `$_SESSION`         | 关联数组，包含当前脚本的所有 Session 内容             |
| `session_destroy()` | 销毁当前会话中的所有数据                          |
| `session_unset()`   | 释放当前会话中的所有变量                          |
| Session 存储路径        | 由 `php.ini` 中的 `session.save_path` 设置 |

### 4. 安全审计要点
- **Session 固定（Session Fixation）**：若登录成功后未调用 `session_regenerate_id()` 重新生成 Session ID，攻击者可预先诱导受害者使用已知的 Session ID 登录，从而劫持会话（对应下文 YXCMS 案例）。
- **Session 劫持**：Session ID 一旦泄露（如通过 Referer、URL 参数传递），等同于账号被接管。
- **服务端存储路径可被读取/写入**：若 `session.save_path` 可被文件包含（如 LFI），配合 Session 文件写入可能导致代码执行。
- **未校验 Session 归属**：仅校验 Session 是否存在而不校验对应用户角色，可能导致越权。

## 四、Token 身份验证（防爆破 / 唯一性判断）

> 🎯 **这一代的定位(对照零章主线)**:Token 要解决的是 Session 的两个痛点——① 服务器得为每个在线用户**存一份会话**(存储压力);② Session 靠 Cookie 传递,**跨域/前后端分离时很麻烦**。
> 它的思路很巧妙:**给你一张"自带防伪签名的证件"**。证件上明文写着你是谁(载荷),但末尾有一段用服务器密钥算出的**签名**。你改证件上任何一个字,签名就对不上了。这样服务器**不用存会话**——收到证件,当场验一下签名真假就知道能不能信,验签通过就认。
> ⚠️ 注意:本节课程语境里的 "Token" 讲的是**登录防爆破的一次性 Token**(类似 CSRF Token/验证码的作用),和上面说的"身份凭证 Token(JWT)"是两个不同层面的东西——前者是"防止登录接口被脚本批量提交"的一次性随机值,后者是"代替 Session 的身份证件"。本节的使用要点讲的是前者,但二者的**安全三要素(随机、一次性、有效期)是相通的**,所以放一起理解。

### 使用要点
1. 生成 Token 并将其存储在 Session 中（服务端持有比对基准）。
2. 生成 Token 并绑定到 Cookie 中触发下发。
3. 登录表单提交时携带 Token，服务端校验一致性后才放行登录逻辑。
4. **安全特性思考**：
   - Token 应具备**一次性**（提交后立即失效，防止重放）。
   - Token 应具备**随机性**（避免可预测，防止伪造）。
   - Token 应设置**有效期**（防止长期有效被截获后重放）。
   - 主要用途是**防止登录接口被暴力破解/自动化脚本批量提交**，本质类似验证码/CSRF Token 的思路，而非替代完整身份认证。

## 五、机制对比

### 1. Cookie vs Session

| 维度   | Cookie                          | Session                       |
| ---- | ------------------------------- | ----------------------------- |
| 存储位置 | 客户端（浏览器）                        | 服务端                           |
| 安全性  | 较低，易被窃取/篡改                      | 较高，敏感数据留在服务端                  |
| 存储容量 | 有限，约 4KB                        | 理论无限制，取决于服务端配置                |
| 生命周期 | 可设置长期有效，浏览器关闭后仍可能存在             | 默认浏览器关闭即失效（依赖 Session Cookie） |
| 访问方式 | 可被 JavaScript 访问（除非设置 HttpOnly） | 仅服务端可访问                       |
| 典型场景 | 存储少量非敏感信息（如用户名、偏好设置）            | 存储购物车、登录状态等重要数据               |

**选型建议**：涉及敏感信息或数据量较大时优先使用 Session；仅需少量数据且需要客户端读取时可用 Cookie。

### 2. Token 机制 vs Session 机制

| 维度     | Token 机制                              | Session 机制                        |
| ------ | ------------------------------------- | --------------------------------- |
| 身份验证方式 | 登录后下发 Token，每次请求携带校验                  | 登录后创建 Session，请求携带 Session ID 校验  |
| 服务端存储  | 通常无需存储完整登录状态（如 JWT 自包含），仅需存储/校验 Token | 需在服务端持久化保存会话状态                    |
| 安全性    | Token 泄露一般不直接暴露密码等敏感信息                | 服务端一旦被攻破，可能连带泄露大量用户会话/敏感数据        |
| 跨域支持   | 通过 HTTP 头 `Authorization` 传递，天然适合跨域   | 依赖 Cookie 传递，跨域需额外处理（CORS + 凭证配置） |
| 实现复杂度  | 需自行实现签发、校验、刷新、吊销逻辑，相对复杂               | 框架原生支持，相对简单                       |

**结论**：Token 机制安全性与跨域适配更优，但实现成本更高；Session 机制简单但集中式存储风险更高。具体选型需结合业务架构（单体 vs 前后端分离/微服务）权衡。

## 六、代码审计实战案例

### 1. XHCMS — Cookie 脆弱
- **漏洞本质**：身份/权限信息直接存储在客户端 Cookie 中且缺乏签名校验，攻击者可直接修改 Cookie 值伪造管理员身份。
- **审计思路**：定位登录成功后 `setcookie()` 写入的字段 → 检查后台鉴权逻辑是否仅依赖该 Cookie 字段的存在性/取值，而未做服务端二次校验或签名验证。

### 2. YXCMS — Session 固定
- **漏洞本质**：登录流程中未在身份确认后重新生成 Session ID，导致攻击者可预先设置目标的 Session ID 并诱导其登录，从而在登录后复用同一 Session ID 完成会话劫持。
- **审计思路**：定位登录成功后是否调用 `session_regenerate_id(true)`；若缺失，则登录前后 Session ID 保持不变即为漏洞点。

**参考资料**：https://xz.aliyun.com/t/2025

## 七、审计速查清单（渗透测试视角总结）

- [ ] Cookie 中是否存储了可被篡改利用的敏感/权限字段？
- [ ] Cookie 是否设置了 `HttpOnly` / `Secure` / `SameSite`？
- [ ] Session ID 是否在权限变更（登录成功）时重新生成？
- [ ] Session 数据的服务端校验是否与 Cookie/Token 校验存在逻辑割裂（只判断存在不判断归属）？
- [ ] Token 是否具备随机性、一次性、有效期三要素？
- [ ] 登录接口在 Session+Token 双因子下是否仍可被爆破（如 Token 校验可被绕过或未生效）？

## 八、串联：身份验证如何牵动 XSS、CSRF、越权(这节让知识活起来)

> 身份验证不是一个孤岛——它是 Web 安全里**好几类漏洞共同的"靶心"**。把它和你学过的其他漏洞串起来,你会发现它们攻击的其实是同一个东西:**那张"证明你是你"的凭证**。

### 1. 身份验证 ×（XSS）：XSS 为什么盯着 Cookie

XSS 的一大利用目标就是**偷 Cookie**（详见《03 XSS跨站-攻击利用手法》）。为什么?因为在 Cookie/Session 机制下,**那个 Cookie(Session ID)就是你的"身份"本身**——谁拿到它,谁就是你。所以:
- **HttpOnly** 这个 Cookie 标志,本质是身份验证机制给自己上的一道"防 XSS 偷窃"的锁——让 JS 读不到 Cookie,XSS 就偷不走你的身份。
- 这解释了为什么"身份验证"和"XSS"要放一起看:**XSS 偷的不是别的,正是身份验证所依赖的那张凭证。**

### 2. 身份验证 ×（CSRF）：CSRF 为什么能冒充你

CSRF（详见《CSRF跨站请求伪造》）的根基,正是 Cookie 机制的一个"天性"——**浏览器向某网站发请求时会自动带上该网站的 Cookie**。攻击者正是利用这一点:他不需要偷你的 Cookie,只要诱导你的浏览器发请求,浏览器就"自动替你出示了身份凭证"。
- **SameSite** 这个 Cookie 属性,就是身份验证机制给自己上的"防 CSRF"的锁——限制 Cookie 在跨站请求时不自动携带,CSRF 就冒充不了你。
- 所以:**CSRF 攻击的,是"浏览器会自动出示身份凭证"这个便利性带来的副作用。**

### 3. 身份验证 ×（越权）：验证了"你是谁",但验证了"你能不能做这件事"吗

这是最容易被忽略、却最高发的一类——**身份验证(authentication)解决"你是谁",但不等于解决了"你能做什么"(授权 authorization)**。
- 很多系统校验了"你有个合法的 Session"(确认了身份),却没校验"你这个身份有没有权限操作这条数据"(授权)。
- 于是出现 **IDOR / 水平越权**:你是合法登录的用户 A,但你把请求里的 `id=A` 改成 `id=B`,系统只验证了"你是合法登录的"(✅),没验证"这条 B 的数据是不是你的"(❌)→ 你看到了别人的数据。
- **审计总问题升级版**:不仅要问"它凭什么确信你是你",还要问"**它确信了你是你之后,有没有再确认你有权做这件事**"。身份对了 ≠ 权限对了。

---

## 九、一句话升华

> **身份验证的所有机制(Cookie/Session/Token)、所有防护(HttpOnly/Secure/SameSite/签名)、以及攻击它的所有漏洞(Cookie 篡改、会话劫持/固定、XSS 偷 Cookie、CSRF 冒充、越权),本质上都在围绕同一个问题打转——"那张证明你是你的凭证,能不能被伪造、被偷走、被冒用、或被用来做它不该做的事"。**
>
> 你把每一个知识点都挂到这个核心问题上,这篇笔记就不再是"Cookie/Session/Token 三个概念",而是一张"攻击者会从哪撬开身份这道门"的完整地图。审计时带着这张地图,你看的就不是代码,而是"这道门的每一个锁,牢不牢"。
