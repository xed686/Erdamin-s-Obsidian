# PHP 安全防御机制笔记（php.ini 配置 / 全局过滤 / 内置函数）

前几份笔记梳理的是**攻击面**（弱类型比较、文件操作、代码执行、SSTI 等），这一份对应的是**防御面**：从"服务器配置层" → "全局流量/文件检测层" → "代码内置函数层"，三层纵深防御体系。

---

## 一、通用防御：php.ini 安全设置

| 配置项                                     | 作用                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `safe_mode`                             | 安全模式，开启后命令执行类函数会被禁用（**PHP 5.4 起已移除该配置**，遗留系统/老版本中仍可能见到）                                          |
| `open_basedir`                          | 限制 PHP 脚本可访问的文件路径范围，防止目录遍历等文件操作类攻击越界                                                             |
| `disable_functions`                     | 禁用函数名单，可视为 `safe_mode` 的"升级版"，可自定义禁用任意危险函数（如 `exec`、`system`、`eval` 等）                           |
| `magic_quotes_gpc`                      | 魔术引号，自动对 GET/POST/COOKIE 数据中的特殊字符转义（作用与 `addslashes()` 相同，**PHP 5.4 起已移除**），本质上是早期版本的 SQL 注入过滤手段 |
| `max_connections`                       | 限制数据库连接/访问次数，可用于防止数据库账号被暴力破解                                                                     |
| `allow_url_include` / `allow_url_fopen` | 控制是否允许通过 URL 远程包含/打开文件，是防止**远程文件包含（RFI）**的关键开关，生产环境应关闭                                           |
| `session.cookie_httponly`               | 禁止 JavaScript 读取 Session Cookie，防止 XSS 窃取会话                                                      |
| `session.cookie_secure`                 | 强制 Cookie 仅通过 HTTPS 传输，防止中间人攻击（MITM）截获                                                           |

> 标 `*` 的几项（`open_basedir`、`disable_functions`、`magic_quotes_gpc`、`session.cookie_httponly`/`session.cookie_secure`）是当前仍然有效、现代 PHP 版本中依然常用的配置；`safe_mode` 与 `magic_quotes_gpc` 已在新版本中被移除，更多作为"历史背景知识"理解其设计思路即可。

## 二、全局文件引用层检测

这一层的思路是：在业务代码真正处理请求之前，先通过一道"全局引用文件"或"前置中间件"对请求内容做统一检测拦截。

### 1. 关键内容检测（黑白名单）
针对文件上传、SQL 注入、XSS 跨站等常见攻击类型，在全局入口处对请求参数做**黑名单**（匹配危险特征则拦截）或**白名单**（仅放行符合预期格式的内容）校验。

### 2. 流量行为检测（基于规则或 AI 算法）
比黑白名单更进一步的思路是对请求流量本身的行为模式进行建模检测，常见架构：

```
客户端请求数据 → 中间件搭建平台 → 服务器代码文件处理   （无检测，直接到业务层）

客户端请求数据 → WAF/流量监控（规则或 AI 模型） → 正常数据 → 中间件搭建平台 → 服务器代码文件处理
客户端请求数据 → WAF/流量监控（规则或 AI 模型） → 异常数据 → 拦截终止
```

**技术组合示例**：Python Flask + PHP Curl + 自训练检测模型，即用 Flask 搭建独立的流量分析服务，PHP 应用通过 Curl 将请求转发给该服务做前置判定，再决定是否放行进入真正的业务代码。

## 三、代码层：内置函数防御

### 1. 类型/内容检测函数

这类函数的核心用途是校验"数据的类型是否符合预期"，从而在源头上过滤掉非预期类型的恶意输入。

| 函数 | 作用 |
|---|---|
| `gettype()` | 获取变量的类型 |
| `is_int()` | 检测是否为整数 |
| `is_float()` | 检测是否为浮点型 |
| `is_bool()` | 检测是否为布尔型 |
| `is_null()` | 检测是否为 NULL |
| `is_numeric()` | 检测是否为数字或数字字符串 |
| `is_string()` | 检测是否为字符串 |
| `is_array()` | 检测是否为数组 |
| `is_object()` | 检测是否为对象 |
| `is_resource()` | 检测是否为资源类型 |
| `is_scalar()` | 检测是否为标量（int/float/string/bool） |

> 这组函数也呼应此前《PHP弱类型比较漏洞笔记》中提到的审计原则：对反序列化/JSON 解析结果等不可信数据，应显式用 `is_array()` 等函数校验类型后再使用，而非依赖隐式真假值判断。

### 2. `filter_var()` 与常用过滤器

`filter_var()` 使用指定过滤器对变量进行过滤/校验，是比逐个手写正则更规范的方式。

| 过滤器 | 作用 |
|---|---|
| `FILTER_SANITIZE_STRING` | 过滤 HTML 标签和特殊字符 |
| `FILTER_SANITIZE_NUMBER_INT` | 过滤非整数字符 |
| `FILTER_SANITIZE_URL` | 过滤 URL 中的非法字符 |
| `FILTER_VALIDATE_EMAIL` | 验证邮箱地址格式有效性 |

## 四、针对具体漏洞类型的过滤函数

### 1. SQL 注入过滤

| 函数 | 作用 |
|---|---|
| `addslashes()` | 在单引号 `'`、双引号 `"`、反斜线 `\`、NULL 字符前加反斜线转义 |
| `stripslashes()` | 反转义，去除 `addslashes()` 添加的转义符（注意与 `magic_quotes_sybase` 配置的联动行为） |
| `addcslashes()` | 对指定字符列表（`charlist` 参数）中的字符统一加反斜线转义 |
| `stripcslashes()` | 反转义，支持识别类 C 语言的 `\n`、`\r` 等转义序列及八/十六进制描述 |
| `mysql_escape_string()` | 早期 MySQL 扩展函数，**不转义 `%` 和 `_`**，已随 `mysql_*` 系列一同废弃 |
| `mysql_real_escape_string()` | 调用 MySQL 库函数，对 `\x00`、`\n`、`\r`、`\`、`'`、`"`、`\x1a` 等字符添加反斜线转义，同样已随旧版 `mysql_*` 扩展一起废弃（现代开发中应使用 `mysqli`/`PDO` 对应方法） |
| 魔术引号（`magic_quotes_gpc`） | 效果等同于全局自动调用 `addslashes()`，已移除，不应依赖 |
| **预编译机制（参数化查询）** | 现代 PHP 中防 SQL 注入的**根本解法**：使用 `PDO`/`mysqli` 的预处理语句（`prepare()` + `bindParam()`/占位符），让 SQL 语句结构与数据内容彻底分离，而非依赖转义函数"打补丁" |

> 审计/开发建议：上述转义类函数更多是了解其历史演进与原理，**现代代码应优先使用预编译/参数化查询**，从根本上避免 SQL 注入，而不是依赖转义函数做"事后补救"。

### 2. XSS 跨站过滤

| 函数 | 作用 |
|---|---|
| `htmlspecialchars()` | 把预定义字符（`<`、`>`、`&`、`"` 等）转换为 HTML 实体，输出到页面时避免被解析为标签 |
| `strip_tags()` | 直接剥除字符串中的 HTML、XML 以及 PHP 标签 |

### 3. 命令执行过滤

| 函数 | 作用 |
|---|---|
| `escapeshellcmd()` | 确保用户只能执行一个命令（可带任意数量参数），防止通过 `;`、`&&`、`\|` 等拼接执行额外命令 |
| `escapeshellarg()` | 确保传给命令的是**一个参数整体**（自动加引号转义），防止用户在参数中插入额外的命令片段 |

> 结合此前《PHP代码执行与命令执行安全笔记》：审计时若看到 `exec`/`system`/`shell_exec` 等函数调用了这两个转义函数，应进一步确认转义顺序和使用场景是否正确（例如常见误区是只转义了 `escapeshellcmd()` 而未对每个独立参数单独使用 `escapeshellarg()`）。

### 4. 其他漏洞过滤
对于 SSRF、XXE、反序列化等其他类型漏洞的过滤方案，通用思路仍是"类型校验 + 白名单 + 禁用危险特性"，可结合具体漏洞类型针对性设计参数过滤规则。

## 五、三层防御体系总结

| 层级 | 防御手段 | 特点 |
|---|---|---|
| 配置层 | php.ini（`open_basedir`、`disable_functions`、`allow_url_include` 等） | 服务器级别的"兜底防线"，一次配置全局生效 |
| 流量/全局检测层 | 黑白名单检测、WAF/流量行为建模 | 在业务代码之前拦截，可统一应对多种攻击类型 |
| 代码层 | 类型校验函数、`filter_var()`、专项过滤函数、预编译查询 | 最贴近业务逻辑，防御精度最高，但依赖开发者正确使用 |

**核心结论**：任何单一层级都不是银弹——`disable_functions` 可能被已知绕过手法突破，WAF 规则可能被编码/变形绕过，转义函数也可能因使用位置不当失效。真正可靠的防御需要**三层叠加 + 从源头使用预编译/参数化等根本性方案**，而不是依赖某一个"过滤函数"一招解决问题。
