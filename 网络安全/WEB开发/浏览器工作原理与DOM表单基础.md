## 0. 为什么要专门学这个

你在打 xss-labs 时一定遇到过这些困惑:
- 为什么我输入 `<script>` 被转义成 `&lt;script&gt;` 就打不了,而 `<img onerror>` 换个位置就能打?
- 为什么防御方把 `<` 实体化能防住 XSS,我攻击方用实体编码却能绕过?——同一个技术,怎么方向相反?
- 为什么 F12 Elements 面板里看到的 `&quot;`,和"查看网页源代码"里看到的不一样?
- 为什么 hidden 隐藏参数"看不见",却照样能 XSS、还会被表单提交?

**这些问题的答案,全在"浏览器到底怎么工作"这一套底层机制里。** 不懂它,你只能靠背 payload、碰运气;懂了它,你能看着任何一个过滤结果,推出该怎么绕。这就是老手和新手的分水岭。

## 1. 浏览器工作的整体流程(先建框架)

把浏览器想象成一个"**把一堆代码文本,变成你能看、能点的网页**"的翻译机。它大致走这几步:

```
① 下载:从服务器拿到 HTML 文本(本质就是一堆字符串)
      ↓
② 解析 HTML:把 HTML 文本 ──→ 解析成 DOM 树   ← DOM 在这一步诞生(最关键)
      ↓
③ 解析 CSS:算出样式规则,决定每个元素长什么样
      ↓
④ 渲染:根据 DOM + CSS,把页面画到屏幕上(你看到的样子)
      ↓
⑤ 执行 JS:运行页面里的 JavaScript(JS 会去操作 DOM)
      ↓
⑥ 交互:你点击、输入、提交表单,触发事件,JS 响应 / 发请求
```

**各类漏洞分别出在哪一步(帮你定位):**
- **反射型/存储型 XSS**:出在第②步——服务器把你的 payload 拼进了 HTML,浏览器解析时把它当成了真标签。
- **DOM 型 XSS**:出在第⑤步——JS 运行时把用户输入写进了 DOM(原始 HTML 里没有,所以"查看源代码"看不到)。
- **CSRF**:出在第⑥步——你的浏览器发请求时自动带上了 Cookie。

本篇重点讲第②步(DOM 的诞生)和第⑥步会用到的表单。

## 2. DOM 是什么、什么地位、什么作用(🔴 核心)

### 2.1 DOM 是什么:HTML 文本被解析后,在内存里形成的"树状结构"

**一句话:HTML 是"文本"(字符串),DOM 是"把这段文本解析后,在浏览器内存里建成的一棵结构树"。**

看例子。这段 HTML 文本:
```html
<body>
  <form>
    <input name="keyword">
    <button>搜索</button>
  </form>
</body>
```

浏览器解析后,在内存里建成这样一棵**树**(这就是 DOM):
```
body
 └── form
      ├── input (name=keyword)
      └── button ("搜索")
```

- **每一个标签 → 变成树上的一个"节点(node)"**
- **标签的嵌套关系 → 变成树的"父子关系"**(body 是 form 的父节点,input 和 button 是 form 的子节点)

**所以 DOM 的本质:HTML 文本 → 解析 → 一棵由"节点"组成的树,存在浏览器内存里。** HTML 是"写在纸上的字",DOM 是"照着字在内存里搭出来的立体模型"。

### 2.2 DOM 的地位:它是"网页的真身",一切操作的对象

**你在屏幕上看到的网页、JS 要操作的东西、浏览器提交表单时读的东西,全都是 DOM,不是原始 HTML 文本。**

- **屏幕上的页面** = 浏览器根据 **DOM** 画出来的
- **JS 改页面**(`innerHTML = ...`) = JS 在**改 DOM**,改完浏览器重画
- **提交表单** = 浏览器从 **DOM** 里读 input 的值

**原始 HTML 文本,在解析完、生成 DOM 之后就"功成身退"了——后面一切都围绕 DOM 转。**

这解释了你之前的两个困惑:
- **F12 的 Elements 面板看的是 DOM**(网页真身),不是服务器返回的原始文本。
- **DOM 型 XSS 为什么"查看网页源代码"看不到**——因为它是 JS 运行时**直接改 DOM** 注入的,原始 HTML 文本里压根没有它,只有解析后的 DOM 里才有。

### 2.3 DOM 的作用:代码和"你看到/操作的网页"之间的桥梁

```
HTML 文本 ──解析──→ DOM ──→ 画成页面(你看)
                     ↑↓
                    JS 操作(增删改元素)
                     ↓
              提交表单时从这读值
```

**一句话:DOM 是网页的"活的、可操作的结构表示"。代码变成它,你看到的是它,JS 操作的是它,表单提交读的也是它。它是整个网页的核心枢纽。**

## 3. 【最核心】浏览器解析 HTML 的顺序:先认结构,后解码(🔴 核心)

> 这一节是整篇的灵魂——**XSS 所有编码绕过、闭合逃逸的原理,全在这个"解析顺序"里**。吃透它,你就理解了"为什么防御方实体化能防住、攻击方实体编码却能绕过"这个看似矛盾的现象。

### 3.1 解析分两个有先后顺序的阶段

浏览器把 HTML 文本变成 DOM,**不是一口气看完,而是分成两个阶段,且有严格先后顺序:**

**阶段一:分词/建树(认结构)** —— 解析器从左往右扫,靠**没解码的原始** `<` `>` `"` `=` 这些符号,判断"哪里是标签、哪里是属性名、属性值范围到哪"。

**阶段二:解码实体(还原字符)** —— 结构定死之后,才把属性值/文本里的 HTML 实体(`&lt;`、`&#x6a;`)解码成真实字符。

### 3.2 用一个例子看清这个顺序

```html
<input value="&lt;script&gt;alert(1)&lt;/script&gt;">
```

**阶段一(认结构)**:解析器从左扫:
- 看到 `<input` → 一个标签开始
- 看到 `value="` → value 属性的值开始(记住这个开引号)
- 扫到 `&lt;script&gt;...` → **此刻 `&lt;` 在解析器眼里就是四个普通字符 `& l t ;`,还没解码!** 所以它认定"value 属性里就是一串普通文字"
- 看到第二个 `"` → value 属性值结束
- 看到 `>` → input 标签结束
- **结构在此刻定死:只有一个 input 标签,value 是一串文字,没有别的标签。**

**阶段二(解码)**:现在才把 `&lt;` 解码成 `<`,页面上显示出 `<script>alert(1)</script>` 这行文字。**但此刻结构早定死了**,这个解码出来的 `<` 只是"value 里的一个文字字符",解析器不会回头把它当成新标签。

### 3.3 比喻:机场安检

- **阶段一(认结构) = 安检清点行李**:安检员按行李"当下的样子"登记——此刻 `&lt;` 是四个字符,登记成"普通文字"。
- **阶段二(解码) = 过安检后还行李**:还给你时 `&lt;` 变回了 `<`。但**清点(认结构)已经做完了**,就算现在 `<` 现形,安检员也不会回头重新清点——流程已经过了那一步。

**一句话:浏览器"先认结构,后解码实体"。结构在实体解码之前就定死了,所以解码后冒出来的 `<` 当不成新标签。**

## 4. 用"解析顺序"解开 XSS 的核心谜题(🔴 核心)

### 4.1 为什么防御方把 `<` 实体化能防住 XSS

假设攻击者想用 `&lt;script&gt;` 解码出 `<script>` 来伪造一个新标签:
```
阶段一(认结构):解析器看到 &lt; 是普通字符 → 认定是文字 → 结构定死,没有新标签。
阶段二(解码):  才把 &lt; 解码成 < → 页面显示出 <script> 文字。
               → 但"认标签"的窗口已永久关闭 → 它只是纯文字,不是标签 → 不执行。
```

**核心:你想伪造的是"标签结构",而标签结构在阶段一(解码之前)就定死了;你的 `<` 要等阶段二才现身,来晚了。** 这就是防御方把 `<` `>` 实体化(`htmlspecialchars`)能挡住"打新标签"的根本原理。

### 4.2 为什么攻击方(xss-labs 第8关)用实体编码却能绕过

第 8 关的场景:关键字被过滤、`htmlspecialchars` 挡住了打标签,但你的输入落在 `<a href="你的输入">` 的 href 属性里。攻击者的做法**不是伪造标签**(知道那是死路),而是:
1. **利用一个已合法存在的标签**(`<a href>` 本来就在,结构完整,不用伪造)
2. **把 `javascript:alert()` 的关键字用 HTML 实体编码**(`&#x6a;&#x61;...`)藏进 href 的值里
3. href 的值**在解码之后才被解释用途**(当成 URL/协议处理),所以解码出的 `javascript:` 正好赶上"被当协议执行"的时机 → 伪协议生效

**伪造标签(死路) vs 第8关(活路)对比:**

| | 伪造标签(失败) | 第8关(成功) |
|---|---|---|
| 想干什么 | 用 `&lt;` 变出 `<` 来**造新标签** | 在**已有标签**的属性值里藏功能 |
| 依赖的时机 | 需要"解码后还能被当标签识别" | 需要"解码后还能被当协议处理" |
| 成/败原因 | ❌ 标签识别在解码**之前**,来不及 | ✅ href 协议解释在解码**之后**,正好赶上 |

### 4.3 关键澄清:同一个"HTML 实体编码",防御和攻击方向相反

`&#x6a;` 的**正式名字是 HTML 实体编码(数字字符引用)**,不是"Unicode 编码"——只是它内部的数字恰好是字符的 Unicode 码点,所以常被俗称 Unicode,这个叫法不精确。

| | 防御方的实体化(`htmlspecialchars`) | 攻击方(第8关)的实体编码 |
|---|---|---|
| 谁做 | 网站后端/开发者 | 攻击者手动构造 payload |
| 对什么做 | 对**危险结构符号** `<` `>` `"` 做 | 对**自己 payload 的关键字字母** `javascript` 做 |
| 目的 | 破坏标签结构,让 payload **失效** | 藏住关键字骗过过滤,让 payload **生效** |
| 结果 | XSS 打不了 | XSS 能打 |

**判断它是"防御"还是"攻击",不看用没用实体化,而看:它编码的是"破坏结构的符号"还是"躲避检测的关键字"。** 前者让 payload 死(结构被毁、解码太晚),后者让 payload 活(结构没动、只藏关键字、解码后生效)。

### 4.4 为什么必须用 HTML 实体(`&#x6a;`)而不是 JS 转义(`\u006a`)

有几种东西都和"编码"沾边,但**谁来解码、在哪解码**完全不同,选错就失败:

| 写法 | 正式名字 | 谁解码 | 在 HTML 属性里会还原吗 |
|---|---|---|---|
| `&#x6a;` / `&#106;` | **HTML 实体编码** | **HTML 解析器** | ✅ 会(第8关用的就是这个) |
| `\u006a` | JavaScript Unicode 转义 | JS 引擎 | ❌ 不会(这是 JS 语法,HTML 解析器不认) |
| `%6a` | URL 编码 | URL 解析器/服务器 | ❌ 不会(这是 URL 的规矩) |

**判断任何编码绕过能不能成功,核心永远是问:我的 payload 落在哪个解析环境(HTML / JS / URL)?那个环境会不会自动解码我用的这种编码?** 选对和当前解析环境匹配的编码才能成功。

### 4.5 "解码后仍会执行值"的 Sink 清单(可迁移规律)

第8关能成功,本质是 `href` 是一个**"值在解码之后,还会被当成功能性指令执行"的位置**。这样的位置不止 href:

| Sink | 用法/作用 |
|---|---|
| `<a href="javascript:alert(1)">` | 点击链接时执行伪协议里的 JS |
| `<iframe src="javascript:alert(1)">` | 加载 iframe 时执行(比 a 更自动) |
| `<img src=x onerror="alert(1)">` | 图片加载失败自动触发 onerror(最常用,无需用户操作) |
| `<svg onload="alert(1)">` | SVG 加载完自动触发 |
| `<input onfocus="alert(1)" autofocus>` | autofocus 让元素自动获焦,触发 onfocus |

> **共性:这些位置的值都在"解码之后"才被解释用途(当协议、当事件 JS)。** 而普通的"标签之间的文本"(`<div>这里</div>`)没有这个特性——文本解码后只会**显示**,不会被**执行**。**落点决定打法:落在这类 Sink 就能用编码藏关键字绕过;落在纯文本区就得想办法打新标签(而打新标签又会被实体化挡住)。**

## 5. 正向解析 vs 逆向序列化:为什么 F12 里还看到 `&quot;`(🟡 重要)

你打 xss-labs 时发现:同一个元素,**普通显示** 和 **右键"编辑为HTML"** 看到的样子不一样,后者还带 `&quot;`。这不是"没解码",而是涉及一个反方向的动作。

### 5.1 两个相反的方向

```
正向(解析):  HTML 文本  ──解析:认结构+解码──→  DOM(内部是解码后的真字符)
逆向(序列化):DOM  ──序列化:把有歧义的字符再转义──→  HTML 文本(含 &quot;)
```

- **正向解析**:文本 → DOM,解码发生在这,DOM 里存的是**真字符**(真的双引号 `"`)。
- **逆向序列化**:DOM → 文本(F12 的"编辑为HTML"、或 DOM 序列化时),为了让"生成的文本重新解析还能得到同样 DOM",把 DOM 里有歧义的字符(如属性值里的 `"`)**重新转义成 `&quot;`**。

### 5.2 所以那个 `&quot;` 是怎么来的

比如某属性的值,DOM 内部真实存的是 `javascript:alert()"`(末尾有个真双引号)。F12 要把它显示成 `属性="..."` 时,如果把内部双引号原样显示会变成 `属性="...""` 产生歧义,所以显示时转义成 `属性="...&quot;"`。

**`&quot;` 不是"还没解码"留下的,而是"从解码好的成品 DOM,反向生成文本时主动加上的"。方向反了——不是"没解码",而是"解码完之后又反向编码回文本"。**

### 5.3 怎么看 DOM 里的真实值(一锤定音)

在 F12 Console 里用 JS 读属性真值:
```javascript
document.querySelector('input[name=keyword]').getAttribute('focus')
```
返回的是 `javascript:alert()"`(**里面是个真双引号,没有 `&quot;`**)——证明 DOM 里存的是解码后的真字符,`&quot;` 只是文本视图的转义展示。

### 5.4 三种"形态"别搞混

| 形态 | 是什么 | 在哪看 |
|---|---|---|
| 原始 HTML 文本 | 服务器返回的、还没解析的文本 | "查看网页源代码" |
| DOM(内存结构) | 解析后、已解码的真身 | F12 Elements(普通显示)、JS 读 |
| 逆向序列化的文本 | 从 DOM 倒着生成的文本(有 `&quot;`) | F12 "编辑为HTML" |

## 6. 表单(form)是什么(🔴 核心)

### 6.1 本质:一个"收集用户输入、打包发给服务器"的容器

你在网上**填信息、点提交**的场景(登录、搜索、注册、评论),背后几乎都是表单:
```html
<form action="/search" method="GET">
  <input name="keyword">                              ← 可见的输入框
  <input name="t_sort" type="hidden" value="date">    ← 隐藏字段,看不见但也会被提交
  <button type="submit">搜索</button>                  ← 点它就"提交"
</form>
```

### 6.2 三个核心要素

| 要素 | 作用 |
|---|---|
| `<form>` | 容器,把要一起提交的输入框圈在一起 |
| `action` | 提交到**哪个地址**(服务器哪个接口) |
| `method` | 用**什么方式**提交(GET=参数拼 URL;POST=参数放请求体) |
| `<input>` | 一个个字段,收集具体数据 |

### 6.3 表单提交时发生了什么

点"提交"时:
1. 浏览器**遍历这个 form 下的所有 input**(从 DOM 里读),收集每个 input 的 `name` 和 `value`。
2. 按 `method` 打包:GET → 拼成 `/search?keyword=xxx&t_sort=date`;POST → 放请求体。
3. 发给 `action` 指定的地址。

**关键:它收集的是"form 下所有 input",包括 `type="hidden"` 的。**

### 6.4 这解开了两个重要困惑

**① 为什么 hidden 隐藏参数"看不见"却能 XSS、还会被提交?**
- `type="hidden"` 是"**渲染了,但不可见**"——它被解析进了 DOM(是个真实的 input 节点,value 也被解析了),只是浏览器不把它画出来。
- **"不可见" ≠ "没渲染"**:它完全经过了解析、进了 DOM,所以有 XSS 土壤(你可以闭合它的 value、改成 type=text 显形、加事件);它也在 form 里,所以提交时照样被读出来发走。
- **为什么它要被解析**:因为浏览器提交表单时要从 DOM 里读 input 的值,而要进 DOM 就必须先解析。解析是"能被读取和提交"的前提。开发者让 hidden 参数被解析的本意是"随表单携带数据",副作用就是给了攻击者一个可控的注入位置。

**② 为什么 hidden 参数能在 URL 里加(`&t_sort=`)?**
- 因为这个 GET 表单的每个字段(含 hidden)都对应一个 URL 参数。你直接在 URL 里写 `&t_sort=xxx`,就等于"替这个 hidden 字段填了值"。这就是 xss-labs 第10关"隐藏参数注入"的原理。

### 6.5 CSRF 为什么能利用表单(串联)

CSRF 的核心(详见《CSRF跨站请求伪造》)正是利用了第 6.3 步——攻击者在恶意页面放一个"自动提交、指向目标站接口"的表单,受害者一访问,浏览器就自动提交它,且**自动带上目标站的 Cookie**(第⑥步交互阶段的行为)。表单 + 浏览器自动带 Cookie = CSRF 的技术基础。

## 7. 把它全串起来:一个请求的完整生命周期

```
① 服务器返回 HTML 文本(里面有 form、input,可能含你的 payload)
        ↓ 解析(先认结构,后解码)
② 浏览器建成 DOM 树(form/input 成为节点,hidden 的也在,只是不可见)
   ← XSS 在这步成立:你的 payload 被解析成了 DOM 里一个真实的恶意节点
        ↓ 渲染
③ 可见元素画到屏幕(hidden 不画);CSS 决定长相
        ↓ 执行 JS
④ JS 运行,可能操作 DOM ← DOM 型 XSS 在这步注入
        ↓ 你交互(点击/提交)
⑤ 提交表单:遍历 DOM 读所有 input 值,带上 Cookie 发给服务器
   ← CSRF 利用这步:自动带 Cookie 替你发请求
```

**所有前端漏洞,都能在这条生命周期里找到自己的位置。** 这就是为什么说这篇是"地基"——它不是某一个漏洞,而是所有前端漏洞共享的那套底层机制。

## 8. 自测(先自己想,再看答案)

1. 用自己的话说清楚:HTML、DOM、"查看网页源代码看到的" 三者是什么关系?DOM 型 XSS 为什么在"查看网页源代码"里看不到?
2. 为什么防御方把 `<` 实体化成 `&lt;` 能防住 XSS?(用"先认结构后解码"的顺序解释)
3. 一个 `type="hidden"` 的隐藏 input,页面上看不见。它经过浏览器渲染了吗?它有没有 XSS 的可能?为什么?

<details>
<summary>参考答案</summary>

1. HTML 是服务器返回的原始文本;浏览器解析它(先认结构、后解码)后,在内存里建成 DOM 树(网页真身);"查看网页源代码"看到的是服务器返回的**原始 HTML 文本**,而 F12 Elements 看到的是**解析后的 DOM**。DOM 型 XSS 是 JS 运行时直接改 DOM 注入的,原始 HTML 文本里压根没有它,所以"查看网页源代码"看不到,只能在 F12 Elements(DOM)里看到。
2. 因为浏览器"先认结构、后解码"。防御方把 `<` 变成 `&lt;` 后:阶段一认结构时,解析器看到的是普通字符 `&lt;`(还没解码),认定它是文字、不是标签起始符,结构就定死了(没有新标签);阶段二才把 `&lt;` 解码成 `<`,但此时"认标签"的窗口已永久关闭,这个 `<` 只能当文字显示,无法再变成一个标签 → 打不出 XSS。
3. 渲染了(更准确说:被解析进了 DOM)。"不可见"只是 `type="hidden"` 让浏览器不把它画出来,但它是 DOM 里一个真实的 input 节点,value 也被解析了。所以它有 XSS 可能——你可以闭合它的 value、把 type 改成 text 让它显形、给它加事件属性;就算不显形,只要能注入出自动触发的结构(如 `<img onerror>`),一样能 XSS。"不可见 ≠ 没渲染 ≠ 没 XSS"。

</details>
