## 1. Workflow Agent 是什么 🟡 重要 —— 懂原理,用到会查

### 1.1 定义

**Workflow Agent（工作流智能体）是 Agentic AI 的一类：它不靠自己临场想"下一步干什么"，而是按一条预先编排好的流程走——把大目标拆成有序子步骤，维护执行状态，处理分支和失败重试，自动调工具，走完整条业务/操作链路。**

用户原话里的几个关键词，逐个翻译成工程语言：

| 原文措辞 | 工程含义 | 对应机制 |
|---|---|---|
| 目标驱动 | 输入是一个目标，不是一条命令 | 入口接收 goal，向下拆解 |
| 按流程编排 | 步骤和顺序是**事先设计好的**，不是每次现场生成 | 编排图 / 有向图 / SOP 定义 |
| 多步骤串行/分支 | 支持 if-else、循环、并行 | 条件边、循环节点 |
| 自动调用工具 | 每个节点绑定具体工具 | MCP / 工具注册表 |
| 根据中间结果做决策 | 上一步的输出决定走哪条边 | 状态 + 条件路由 |
| 维护执行状态 | 断点在哪、跑到第几步、哪些成功了 | 状态机 / 持久化执行记录 |
| 分支/失败重试 | 失败了重试或换路，而不是整条崩掉 | retry 策略、回滚 |
| 走完整条业务链路 | 交付的是一个完整结果，不是单个动作 | 终态节点输出报告/证据 |

> 类比：**工作流型 Agent 像工厂流水线，自主型 Agent 像带着任务出门的侦探。**
> 流水线每个工位干什么是设计好的，良品率高、可审计、出问题能定位到工位；侦探没有固定路线，能发现设计者没想到的线索，但你无法提前知道他今天会去哪、花多少钱、几点回来。
> **类比和真实情况的差别**：现实里的产品大多是**混合体**——主干是流水线，某些工位允许"侦探模式"自由发挥（下方案例里两个项目正好各偏一头）。

### 1.2 为什么会存在（root cause）

要理解工作流为什么存在，得先看**"什么都不编排、纯靠 LLM 现想"会出什么问题**。最朴素的自主 Agent 就是一个循环：

```
想一步 → 调工具 → 看结果 → 再想一步 → ……直到自己觉得完成了
```

这个循环（ReAct 那一套）在**探索类**任务上很强，但一旦拿去做**要交付、要审计、要交给客户**的生产任务，暴露四个工程缺陷：

| 缺陷 | 具体表现 | 工作流怎么解 |
|---|---|---|
| **不可预测** | 同一个任务跑两次，路径不一样、结果不一样，测试报告没法复现 | 步骤固定，路径可枚举 |
| **不可审计** | "它为什么扫了这个 IP?"——只有一段自然语言思考，说不清 | 每一步有节点 ID、有输入输出、有执行记录 |
| **成本不可控** | 可能在一个死循环里反复调工具，token 烧穿 | 步数/预算上限挂在图的边上 |
| **合规检查点无处安放** | 授权边界要求"扫公网前必须人工确认"，纯自主循环里没有"必须停下等人"的位置 | 图里插**审批门（approval gate）**节点 |

**一句话 root cause：LLM 的自由度是探索能力的来源，也是交付能力的敌人。工作流就是把"必须可预测、必须可审计、必须能卡住"的那部分流程，从模型的脑子外面搬到一张显式的图上。**

> 🔎 **补充（非原笔记内容）**：这其实是 [[00_MCP与Skill整理笔记]] 里"Skill = 流程层"的**工程化升级**。Skill 阶段的流程是"写给模型看的文字 SOP"，执行时仍靠模型自觉遵守；工作流阶段把同一份 SOP 变成**可执行、可断点、可审批的图**——从"说明书"变成"产线设备"。看到"Skill 升级成 workflow"，本质是同一件事的两种成熟度。

### 1.3 工作流型 vs 自主探索型：本篇最该记住的区别 🟡 重要

这是选型时唯一真正要判断的一件事。

| 维度 | 工作流型（Workflow Agent） | 自主探索型（Autonomous Agent） |
|---|---|---|
| **谁决定下一步** | 人预先画好的图 / 条件规则 | LLM 现场规划（planner） |
| **路径** | 可枚举，重复运行结果稳定 | 每次不同，靠状态图记录"走到哪了" |
| **擅长** | 已知套路的批量执行：资产收集→指纹→扫漏洞→出报告 | 未知面的探索：挖新方向、串攻击链、找设计者没想到的路 |
| **短板** | 只能测"你想得到的"，遇到新情况不转弯 | 贵、慢、不可复现、难审计、容易跑偏 |
| **人工介入点** | 图里显式插审批节点，天然合规 | 只能旁路观察（人在环路对话），很难"卡住必须先批" |
| **典型成本** | 低且可预算 | 高且难预算 |
| **落到安全场景** | 例行漏洞扫描、复测、合规检查、报告生成 | 授权范围内的攻击路径探索、0day 挖掘辅助、内网横向 |

**判断口诀（可迁移）**：
> **"这条链路我能不能提前写出步骤？"** 能写出来且要重复跑 → 工作流。
> 写不出来、每次都不同、需要现场判断 → 自主型，但要接受"贵 + 不可复现"，并且必须配**预算上限 + 审批门 + 双图式的过程记录**才敢上真实目标。

**混合才是常态**：真实产品基本都是"工作流做骨架（保证可控），自主 Agent 做节点里的血肉（保证灵活）"。下面两个案例正好各偏一头。

### 1.4 一张工作流长什么样（示意）

下面是一张**示意**编排图（不是任何产品的真实配置文件，只是帮你看懂结构）：

```yaml
# 示意：一次授权范围内的 Web 资产例行检查工作流
nodes:
  - id: scope_check          # ① 范围校验：节点，不是工具
    type: guard              # 校验失败直接终止，这是"卡住"的位置
    rule: target in authorized_scope

  - id: subdomain            # ② 子域枚举
    type: tool
    tool: subfinder
    input: ${target}
    output: subs.txt

  - id: alive                # ③ 存活探测（串行，依赖 ②）
    type: tool
    tool: httpx
    input: subs.txt

  - id: fingerprint          # ④ 指纹识别
    type: tool
    tool: whatweb

  - id: decide_scan          # ⑤ 分支节点：按指纹走不同路
    type: condition
    if: ${fingerprint.tech} contains "wordpress"
    then: wpscan             # 分支 A
    else: nuclei             # 分支 B

  - id: wpscan
    type: tool
    tool: wpscan
    retry: {max: 2, on: timeout}   # 失败重试策略

  - id: nuclei
    type: tool
    tool: nuclei

  - id: human_review         # ⑥ 审批门：高危结论必须人确认
    type: approval
    reviewer: human

  - id: report               # ⑦ 终态：输出结构化报告
    type: output
    template: finding_report
```

**读这张图只需要抓三个东西**：
1. **节点（node）= 谁干活**：工具节点、判断节点、审批节点、输出节点。
2. **边（edge）= 顺序和条件**：串行就是硬依赖，`if/else` 就是分支，`retry` 是失败后回头重跑。
3. **状态（state）= 中间产物怎么传下去**：每个节点的 `output` 是下一个节点的 `input`（`subs.txt` 被 ③ 消费），这就是"维护执行状态"最朴素的样子；产品级实现会把它持久化到数据库，断电重跑不丢。

> 这也是为什么 §1.1 那张表里"状态"被单独列一行：**没有状态传递，工作流就退化成了一串互不相干的命令，失败也没法从中间续跑。**

## 2. 两个真实案例 🟢 了解 —— 知道有这回事,会去翻文档即可

两个项目都用 **Go** 写后端，都在 2026-11 仍活跃提交（联网核实的实测数据，非官方宣传）：

| 项目 | 定位一句话 | Star（2026-11-23） | 许可证 | 形态 |
|---|---|---|---|---|
| [RuoJi6/ARTEX](https://github.com/RuoJi6/ARTEX) | AI 自主渗透测试系统（Go + Next.js + PostgreSQL） | ~2.4k | AGPL-3.0 | **偏自主探索型**（planner 现场派意图） |
| [AIPentest/CyberStrikeAI](https://github.com/AIPentest/CyberStrikeAI) | AI 原生安全操作平台，把意图变成**受治理的执行** | ~9.0k | Apache-2.0 | **偏工作流/编排型**（图工作流 + 四种编排模式） |

### 2.1 ARTEX 🟢 了解 —— 读一遍知道它长什么样即可

**它是什么**：一个"给目标、Agent 自己探索"的自主渗透系统。后端单体 Go（前端 Next.js 内嵌），数据库 PostgreSQL，Docker 一条命令起，默认 `http://localhost:8787`，需要配 LLM key（Anthropic 或 OpenAI，或在 UI 里配）。

**用户笔记里列的那几个"核心"，对应到项目里是什么**（已核对 README）：

| 你笔记里的说法 | 项目里是什么 |
|---|---|
| LLM 配置 | UI 里的 LLM 配置页 + `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`，可按 Agent 绑定不同模型 |
| 任务对话 | 任务会话 + **人在环路对话（mainagent）**，可随时插话纠偏 |
| 资产记忆 | 资产图（跨任务共享的资产真值库）+ memory 子系统 |
| 架构拓扑（自带体系） | **双图架构**：探索图（goal/intent/fact/finding/hint 构成的血缘链）+ 资产图（域名/子域/IP/服务/端点），两图靠"锚点"相连，配力导向的**资产覆盖图** |
| ~~消息推送~~ | ⚠️ 未在 README 中核实到独立的"消息推送"模块，见 §6 待核实 |

**它的内部结构（对理解"自主型"极有帮助，值得看两眼）**：

```
goals（目标分解 + 提取范围）
   ↓
planner（唯一的意图生成者：只派"还没测过的新方向"）
   ↓ 派意图进 frontier 队列
worker ×N（领一条意图 → 跑真实工具 → 把新资产/事实/漏洞写回双图 → 停）
   ↓ 写回触发下一轮
（图一变就唤醒 planner …… 直到 prove_goal）
```

配套的四个支撑件，正好是上一篇讲过的四种攻击面意识的反面教材：
- **guard / intercept**：工具审批门（= 权限分层，防过度授权）
- **记录型 MITM 代理**：Bash/HTTP 全程留痕（= 可审计）
- **MCP（http / sse）+ skills 目录 + memory**：连接层与流程层都在
- **发现归并与统一报告、漏洞复测**：交付环节（Reporter 判断"是否同一根因"才归并）

**看它该看什么**：不要看它的功能清单（会变），看**planner/worker 分工**和**双图 + 锚点**这个设计——那是"自主型 Agent 怎么做到不完全失控"的现成答案。

### 2.2 CyberStrikeAI 🟢 了解 —— 读一遍知道它长什么样即可

**它是什么**：比 ARTEX 更像"平台"——把规划、执行、人工监督、证据、回放放在一个可审计的工作台里。

**和你已学的概念对得上的地方（这才是值得看的）**：

| 它的模块 | 对应你学过的哪个概念 |
|---|---|
| **Pi 编排**：单 Agent / Deep / Plan-Execute / Supervisor 多 Agent 四种模式 | [[01_AI赋能网络安全-Agent工具横评]] §0 的"编排层"，它把 Pi 当编排内核 |
| **Graph workflows**：把 Agents、工具、条件、审批、输出组合成可复用流程 | 本篇 §1 的**工作流型 Agent**，教科书级实现 |
| **Agent Skills**：标准 Skill 目录 + 按需渐进加载 | [[00_MCP与Skill整理笔记]] 的 Skill 流程层 |
| **MCP**：HTTP / stdio / SSE / 联邦 / 动态发现 | MCP 连接层 |
| **知识库**：查询改写 + 向量检索 + 重排 | RAG（不是本篇重点，知道有即可） |
| **HITL 审批**：审批模式、工具白名单、审计 Agent 复核 | 审批门 + 最小权限 |
| **调用拦截**：MCP 执行前可配正则检查，政府域名保护默认开启 | 把"授权边界"做进了产品 |
| **资产 / 漏洞管理、攻击链、回放、RBAC** | 业务侧交付物 |

**看它该看什么**：**四种编排模式的差别**（单 Agent 一路干 / Deep 深挖一条线 / Plan-Execute 先规划再执行 / Supervisor 多个子 Agent 分工），这是"自主程度可调"的具体实现——同一个平台，既能当工作流跑，也能放开当自主 Agent 跑。

> 🔎 **补充（非原笔记内容）**：两个项目摆在一起看，正好构成一个"自主度光谱"——
> **工作流（图固定，最可控）←→ 编排模式可调（CyberStrikeAI）←→ 事件驱动的 planner/worker 探索（ARTEX，最自由）**。
> 选型时不要问"哪个更强"，要问"我的场景需要多可控"。

### 2.3 用这类平台前必须有的安全意识 🟡 重要

上一篇 §4 讲过"你用的工具本身是攻击面"，这里更严重一层，因为这两个平台**自带高危能力**：

- CyberStrikeAI 明确包含 **WebShell 管理、内置 C2**（监听器、加密 beacon、任务队列），并附带 **Burp 插件和浏览器插件**；ARTEX 带记录型 MITM 代理和 100+ 工具链。
- 这意味着：**装在自己机器上 = 装了一个攻击平台**。它一旦被 prompt injection 劫持（[[00_MCP与Skill整理笔记]] §3），攻击者拿到的是你机器上现成的 C2 和 100 个工具。
- 所以：只在自己可控的靶场/授权环境跑；**别把它的 Web UI 暴露到公网**（它要连数据库、存 API key、跑 MITM 代理）；装之前先改默认密码和默认配置；跨版本升级前备份（ARTEX 有内置备份/恢复，恢复会**覆盖全量数据**）。

## 3. Claude 模型分档 🟡 重要 —— 懂取舍逻辑,版本号用到再查

### 3.1 分档逻辑：一条"能力 × 速度 × 价格"的帕累托前沿 🟡 重要

你笔记里的顺序 **Fable > Opus > Sonnet > Haiku** 是**能力从强到弱**的排列，同时价格从贵到便宜、速度从慢到快。这不是四个并列的模型，而是**一条取舍曲线**：越往左越聪明越慢越贵，越往右越笨越快越便宜。

**关键认知：没有"最好的模型"，只有"对这个任务最划算的模型"。** 分档的价值在于让你**按任务难度花钱**——把 80% 的简单活扔给便宜模型，只在真正难的那 20% 上升级。

> 类比：**像请团队干活**。Fable 是"院士级顾问"（一天咨询费顶别人一个月工资，但硬骨头只有他能啃）；Opus 是"资深主力"（日常最值，Anthropic 自己都建议大多数人从它开始）；Sonnet 是"全能中层"（大多数活干得又快又够好）；Haiku 是"流水线工人"（单件便宜到可以随便用，适合大批量重复）。

### 3.2 四档对照表 🟢 了解 —— 数字会变,用到去官方定价页查

下面是 2026-11 核实到的档位（价格单位：美元 / 百万 token，标准 API 价）：

| 档位 | 2026-11 版本 | 输入 / 输出 | 速度 | 官方定位 | 典型用途 |
|---|---|---|---|---|---|
| **Fable** | Fable 5.2（2026-11-09 发布） | $8 / $40 | 中等 | 公开能买到的最强旗舰 | 超长周期 Agent、硬核科研、复杂数学、最难的开源项目级改造 |
| **Opus** | Opus 5.5（2026-09-22） | $4 / $20 | 中等 | **官方推荐的主力**（daily driver） | 深度研究、复杂方案、长途编码 Agent、computer use |
| **Sonnet** | Sonnet 5.5（2026-09-28） | $2 / $10 | 快 | 平衡万金油 | 日常编码、文档、分析、普通 Agent |
| **Haiku** | Haiku 5.5（2026-10-07） | $0.10 / $0.50（单次提示 ≤100k token）<br>$0.50 / $2.50（超 100k） | 最快 | 轻量高速 | 批量抽取、分类、路由、简单问答 |

四档共同点：**上下文 1M token、单次最大输出 128K**，思考（reasoning）自适应常开。

> 🔎 **补充（非原笔记内容）对你原话的两处修正/细化**：
> 1. **"Fable 是最强旗舰"成立，但"最强 = 默认用它"不成立。** Anthropic 官方口径是：日常编码和知识工作**从 Opus 5.5 开始**（比 Fable 5.2 便宜一半），只有当你在 Opus 上把思考档位调高、跑自己的评测仍达不到要求时，才升到 Fable。**"贵 2 倍、换 1~2 分提升"这笔账，只有最难的开阔任务才划算。**
> 2. **"Opus 价格中等偏高"需要更新**：Opus 5.5 是 $4/$20，只有 Fable 5.2 的一半；在很多编码类基准上 Opus 5.5 甚至略胜（官方系统卡里 GDPval、AA-Briefcase 两项是 Opus 领先）。**它的性价比比"中等偏高"的印象更好。**

### 3.3 安全方向的坑：Fable 会拒绝渗透请求 🟡 重要 —— 用 Claude 跑安全 Agent 前必读

> [!warning] 🔎 补充（非原笔记内容，2026-11 核实，对你的方向影响很大）
> **Fable 5.2 带网络安全 / 生物安全分类器，会主动拒绝渗透测试、漏洞利用代码生成这类请求。** 被拦下时不会死掉，而是**回落到 Opus 4.8 来回答网络安全类问题**（生物类回落到 Opus 5）。
> Anthropic 对同一底座模型做了两个配置：
> - **Claude Fable 5.2**：护栏严格，所有用户可用（价格 $8/$40）。
> - **Claude Mythos 5.2**：同一个底座、护栏更宽松，**只给通过审核的组织**（Cyber Verification Program 网络安全验证、或 Life Sciences 验证；企业客户还有 Claude Security 这条路），价格相同。
>
> **这对你意味着什么**：如果你做的是**授权范围内的渗透测试/安全研究**，用 Fable 跑"帮我写这个漏洞的 PoC"会被拦；要么走验证通道拿 Mythos，要么就别在这类任务上用 Fable（用 Opus/Sonnet 反而可能直接给）。官方同时说明这类分类器**会误拦一部分合法请求**（相比上一代，误拦量减少了约 55%）——遇到"正经需求被拒"，先想到是分类器，不是模型不行。
>
> **顺手学到的思路**：这是"AI 供应商把安全边界做进模型"的活案例，也是 [[00_MCP与Skill整理笔记]] §3 里"过度授权"的反向操作——**不是限制用户权限，而是在模型层限制能力**。做 AI 应用安全的人会越来越多地碰到「模型的拒答策略」这一层。

### 3.4 贵模型当大脑、便宜模型干杂活 🟡 重要 —— 可迁移的降本套路

这是把 §3.1 的分档逻辑真正用起来的方法，而且**正好对上本篇 §1 的工作流结构**：

| 打法 | 做法 | 谁在用 |
|---|---|---|
| **Orchestrator（编排者）** | 强模型定计划、把简单子任务派给便宜模型 | Anthropic 官方给 Fable 5.2 列的角色之一；ARTEX 的 planner 派意图给 worker 是同一思路 |
| **Advisor（顾问）** | 便宜模型干活，遇到难题时回头问一次强模型 | 官方给 Fable 的另一角色；也对应"卡住了才升级" |
| **分级路由** | 按任务难度/长度直接选档：简单分类→Haiku，日常→Sonnet，复杂→Opus，极限→Fable | 几乎所有聚合平台和 Agent 产品的默认做法 |

**为什么这样省钱**：token 成本由"次数 × 单次长度 × 单价"决定。工作流里绝大多数节点是机械动作（跑个扫描、抽个字段、分个类），这些用 Haiku/Sonnet 就够；真正需要"想"的只有 planner 和报告撰写那几个节点——**把它们放在贵模型上，其余全降级，总成本能差一个数量级。**

> 迁移提示：给 Agent 配模型时，**先问"这个节点需要多聪明"，再问"这个模型多少钱"**。反过来（先选贵的，再把活都塞给它）是新手最典型的烧钱方式。

## 4. 把它串起来：选型决策流程

```
┌─ 第一步：这条链路我能不能提前写出步骤？
│
├─ 能写出来、且要重复跑 ────────────► Workflow Agent（图编排）
│     · 例：例行资产测绘、漏洞复测、报告生成、合规检查
│     · 必须配：范围校验节点、审批门、预算/步数上限、执行记录
│
├─ 写不出来、每次都不同、要现场判断 ──► 自主探索型 Agent（planner + worker）
│     · 例：授权范围内的攻击路径探索、内网横向、未知面挖掘
│     · 必须配：双图式过程记录（走到哪/测过什么）、人在环路、MITM 留痕、预算硬上限
│
└─ 两者之间 ──────────────────────► 选"编排模式可调"的平台（如 CyberStrikeAI 的
                                     单Agent/Deep/Plan-Execute/Supervisor）

┌─ 第二步：这个节点需要多聪明？
│
├─ 机械动作（抽取/分类/路由/格式转换） ─► Haiku
├─ 日常执行（写脚本、读输出、常规分析）─► Sonnet
├─ 复杂判断（定计划、串攻击链、写报告）─► Opus（官方默认主力）
└─ 极限开放任务（长周期自主、硬骨头）  ─► Fable（预算够、且不是安全敏感请求）

┌─ 第三步：这个任务是安全敏感的吗？
└─ 是（渗透/漏洞利用） ─► 确认不会被供应商护栏拦：要么换模型，要么走验证通道
```

**一句话总结这套选择**：**用最可控的形态跑最需要交付的活，用最便宜的模型干最不需要脑子的活，并且在每个"可能越界"的位置插一扇门。**

## 5. 自测（先自己想，再看答案）

1. 用一句话说清"工作流型 Agent"和"自主探索型 Agent"的区别，并举一个各自该用的安全场景。
2. 为什么说"只有纯自主循环、没有工作流"在生产环境是危险的？说出至少两个工程缺陷。
3. ARTEX 里 planner 派意图、worker 执行的这套结构，对应 Claude 分档里的哪种省钱打法？
4. 你想让 Claude 帮你写一段授权靶场用的 PoC，结果被拒了——最可能的原因是什么，怎么办？

<details>
<summary>参考答案</summary>

1. 区别在**谁决定下一步**：工作流型是人事先把步骤画成图（或规则），按图跑，路径可枚举、可审计、可重试；自主探索型是 LLM 现场规划，每次路径不同，灵活但贵且难复现。安全场景上：例行资产测绘/漏洞复测/合规检查 → 工作流；授权范围内的攻击路径探索、未知面挖掘、内网横向 → 自主型（且必须配预算上限、审批门和过程记录）。
2. ①不可预测/不可复现：同一任务两次结果不同，报告无法复现；②不可审计：说不清"为什么扫了这个目标"；③成本不可控：可能在循环里反复调工具烧穿 token；④合规检查点无处安放：授权边界要求"扫公网前必须人工确认"，纯自主循环里没有"必须停下等人"的位置。（答出两条即可，工作流的解法是：显式图 + 状态持久化 + 审批门 + 预算上限。）
3. 对应 **Orchestrator（贵模型当大脑、便宜模型干活）**：planner 用强模型定方向/派意图，worker 只领一条明确意图去执行——把"需要思考的节点"和"机械执行的节点"分开，分别配不同档位的模型，成本能差一个数量级。
4. 最可能是 **Fable 的网络安全分类器拦截**（渗透测试/漏洞利用代码属于被拦的高风险类别），被拦后官方会用 Opus 4.8 代答。办法：换用 Opus/Sonnet 这类型号再做这类请求、或走 Anthropic 的验证通道（Cyber Verification Program）拿 Mythos、或换别家模型。注意分类器会误杀合法请求，先怀疑分类器，不要以为模型能力不行。

</details>
