## 1. 大前提:黑名单 vs 白名单,是两种相反的防御 🔴 核心 —— 必须吃透

所有绕过的起点,是先认清你面对的是哪种防御,因为它俩是**反着来的**:

| | 黑名单(blacklist) | 白名单(whitelist) |
|---|---|---|
| 规则 | "**这几个坏东西不许进**"(拦 `127.0.0.1`、拦 `admin`) | "**只有这几个好东西能进**"(只允许 `weliketoshop.net`) |
| 弱点 | 只拦它想到的那几个确切写法 | 判断"是不是许可值"这个动作本身可能有漏洞 |
| 绕法思路 | **换个马甲躲开它**(同一个东西的另一种写法) | **要么伪装成它认的好人,要么借它认的人带路** |

> 为什么这个区分是总开关:黑名单你靠"换写法躲"(§2),白名单你躲不了(你根本不在许可名单里),只能"伪装成好人"(§3)或"借好人带路"(§4)。判断错了方向,招式全使不上。

## 2. 绕黑名单:换个写法躲开 🔴 核心 —— 必须吃透

### 2.1 IP 黑名单 → 换 IP 写法

黑名单拦 `127.0.0.1`/`localhost`/内网段时,换"**看着不是内网、解析出来却是内网**"的写法。完整招式(进制、省略、十进制整数、`0`、loopback 整段、域名解析)详见 [[00_SSRF服务端请求伪造-整理笔记_2 (2)]] §5,这里只记靶场最常用的两个:

- `127.0.0.1` → **`127.1`**(省略写法,`127.1` 会被补全成 `127.0.0.1`)。
- 整个 **`127.0.0.0/8`** 段都是回环,`127.anything` 都是本机。

> 原理一句话:**黑名单比对的是字符串,解析器算的是最终 IP,两者对不上就是缝。**

### 2.2 关键词黑名单 → double URL encoding(重点)

当它拦路径关键词(如 `admin`)时,用**双重 URL 编码**绕。以 `admin` 为例:

- `a` 的 URL 编码 = `%61`;再把 `%` 编码一次(`%`→`%25`)= **`%2561`**。
- payload:`http://127.1/%2561dmin`(只需打断一个字母)。

**为什么要编码两次而不是一次(核心机制):请求在后端被解码两次,黑名单检查卡在两次之间:**

```
你发的:  %2561dmin
   │ 后端第 1 次解码(%25 → %)
   ▼
      %61dmin   ← 黑名单在这层查 "admin"?没有(还藏在 %61 里)→ 放行
   │ 传到真正发请求那层,第 2 次解码(%61 → a)
   ▼
      admin     ← 最终真正访问 /admin
```

- 只编一次(`%61dmin`):第 1 次解码就变 `admin`,当场被拦。
- 编两次(`%2561dmin`):检查那一刻 `admin` 还"伪装"着,躲过;之后又被解回 `admin` 正常用上。

> 这就是 Lab: SSRF with blacklist-based input filter 的解法:`stockApi=http://127.1/` 过 IP 黑名单 → `http://127.1/%2561dmin` 过关键词黑名单 → 删 carlos。

### 2.3 怎么知道该编码几层?——试出来的,不是看出来的 🔴

> [!note] 🔎 这是"方法论"级的,比 payload 重要
> 你**事先看不到后端解码几次**,没人能从外面看到后端代码。层数是**试 + 看反馈**推出来的。

靠两个反馈信号定位:**信号 A「拦没拦」**(反映检查层)、**信号 B「生效没生效」**(反映使用层)。从原文开始逐层加编码:

| 试的 | 反馈 | 推断 |
|---|---|---|
| `admin`(0 层) | 被拦 | 基线:确实在黑名单里 |
| `%61dmin`(1 层) | 还被拦 | 黑名单在"解码至少 1 次后"才查 → 检查层会解 1 次 |
| `%2561dmin`(2 层) | 过且生效 | 检查层解 1 次没看到,使用层再解 1 次用上 → 成 |

> **编码层数 = 你试到"既绕过检查、又能被正确使用"的那个层数。** 多一层使用层解不干净、URL 失效;少一层骗不过检查。这套"逐层加、盯两个信号"的打法,对任何关键词黑名单都通用。

## 3. 绕白名单:利用 URL 解析不一致,伪装成"它认的好人" 🔴 核心 —— 必须吃透

白名单只放行特定域名,你换写法躲不掉。但它要判断"你这 URL 的 host 是不是我允许的那个"——而**"从 URL 里准确抠出 host"是个技术活,开发者手写的判断常很烂**,和真正发请求时的解析对不上。你在这个分歧里做文章:

| 写法 | 真正的 host 是谁 | 为什么白名单看错 |
|---|---|---|
| `https://expected-host@evil-host` | **`evil-host`** | `@` 前是用户名,后才是 host。白名单看到开头有 expected-host 就放行 |
| `https://evil-host#expected-host` | **`evil-host`** | `#` 后是 fragment,不参与定 host;白名单若"包含即可"就被骗 |
| `https://expected-host.evil-host` | **`evil-host`** | 这是一个整域名,`evil-host` 是主域名(你的),expected-host 只是子域名前缀 |
| URL 编码 / 双重编码 | 看后端解码而定 | 过滤层和发请求层解码处理不一样;见 §2.2 |

> 共同点:白名单想确认 host,但它的判断方式有漏洞,你让它把"你的地址"看成"它允许的地址"。**还是那句:校验看到的 ≠ 实际连的。**
> 类比:`@`=快递单写"收件人:张三@实际送李四家",只核对了名字;`#`=信封地址后的备注,邮差不看;子域名=公司名"财务部.骗子公司.com",前面写着财务部,整个公司是骗子的。

## 4. Open Redirection 绕过:借白名单内的"自己人"带路 🔴 核心 —— 必须吃透

### 4.1 它解决什么问题

当白名单做得**很严**,真的准确解析出 host 且死认某个域名,§3 那些"伪装 host"的招全失效——你的域名一个字都塞不进去。换思路:**不自己硬闯,找一个白名单信任的、本身有跳转漏洞的合法站点,替你把路带进内网。**

### 4.2 什么是 open redirection

一个站点上的功能,会按你给的参数**把访问者跳转到另一个地址**,例如 `/product/nextProduct?currentProductId=1&path=http://目标`。本来是正常跳转功能,但如果它**不限制 `path` 能填什么**,你填内网地址它就乖乖跳过去——这种"谁都能指定跳哪"的毛病就是 open redirect。

### 4.3 怎么利用(Lab: SSRF with filter bypass via open redirection)

正确 payload(用**相对路径**):

```
stockApi=/product/nextProduct?currentProductId=1&path=http://192.168.0.12:8080/admin
```

| 片段 | 为什么这么写 |
|---|---|
| `/product/nextProduct` | 打在**真正有 open redirect 的那个端点**上(不是域名根,根上 `?path=` 无意义) |
| 用**相对路径**(`/` 开头,不写域名) | 相对路径天然"相对本应用 host" → 等于指向应用自己 → **过白名单**;还省得手敲又长又易错的 lab 域名 |
| `currentProductId=1` | 该端点要求的参数,填个存在的商品 ID |
| `path=http://192.168.0.12:8080/admin` | 让端点 302 跳转到内网 admin |

链路:白名单看 → 是本应用的 `/product/nextProduct` ✅ → 服务器请求它 → 返回 302 跳内网 admin → 服务器跟随 → 够到内网。

### 4.4 怎么找 open redirect 端点 🔴(方法论,别背端点名)

端点名是目标特有的、背不得;**找法是通用的**:

1. **先把站点正常点一遍**(Burp 开着代理):留意哪些功能会让地址栏跳转——"下一个/返回"导航、登录后 `returnUrl=`、外链中转、分享。(这个 lab 的入口就在页面底部那个 "Next product" 链接 → `/product/nextProduct`。)
2. **盯参数名**:`path` `url` `redirect` `next` `return` `dest` `continue`——值长得像地址的,强信号。(和找 SSRF 参数是同一个雷达。)
3. **测**:把该参数改成外部地址(或 Collaborator),看响应是不是 `302 + Location: 你的地址`,跳了就是 open redirect。
4. 嫌慢用 Burp 被动扫描 / sitemap 过滤带 URL 参数的请求。

### 4.5 实操踩坑(我真踩过的)🟡

- **重复 `stockApi=`**:把 `stockApi=/product/...` 整段粘进了**值**的位置,变成 `stockApi=stockApi=/product/...`,后端拿 `stockApi=/product/...` 当 URL 解析 → `Invalid URL`。只保留一个 `stockApi=`。
- **`&` 被当参数分隔符**:body 是 `x-www-form-urlencoded`,`&` 是参数分隔符,`&path=...` 可能被当成**独立参数**,导致 path 没进 stockApi 的值(现象:不报 Invalid 了但没跳 admin)。解法:把那个 `&` 编码成 **`%26`**。

## 5. 一个必须钉死的本质:你够不到内网,一切操作都得经服务器 🔴 核心

打到后面容易犯的错:**看到回显的 admin 页面,就想自己在浏览器点里面的删除按钮。** 点了却 `Not Found`。为什么?

- 你回显看到的 admin 页面,是**服务器替你访问内网、再把 HTML 转述给你**的——相当于"**服务器站在内网拍了张照片给你看**"。
- **你本人的浏览器根本够不到内网 `192.168.0.12`**(那是 lab 服务器的内网)。你点页面里的 Delete(指向内网地址),浏览器到不了,就把它拼成畸形路径(`https://lab域名/http://192.168...`)→ lab 上没这路径 → Not Found。

**正解:删除动作也必须走 SSRF**,在你成功的那条 payload 基础上把 path 末尾改成删除 URL:

```
stockApi=/product/nextProduct?currentProductId=1&path=http://192.168.0.12:8080/admin/delete?username=carlos
```

让**服务器**替你去点删除。

> **本质**:SSRF 全程你都是"遥控服务器替你访问内网",你自己从没碰到内网一下。所以对内网的**任何**操作(看页面、删用户)都得经过 SSRF 这根管子。能动内网的永远只有服务器;你能做的,只是构造喂给它的那个 URL。

### 5.1 怎么从回显的 HTML 读出"剩下的参数和值怎么填" 🟡

你不用猜,操作的接口全写在**回显页面的 HTML 源码**里:

- 在 Burp 响应面板切 **Raw**,搜 `delete`/`carlos`,找到那个链接:
  ```html
  <a href="/admin/delete?username=carlos">Delete</a>
  ```
  路径(`/admin/delete`)、参数名(`username`)、值(`carlos`)一目了然,照抄进 path。
- **一定看清 GET 还是 POST**:
  - `<a href="...">` → **GET**,参数在 URL 里,open redirect 的 GET 跳转够用。
  - `<form method="POST" action="..."><input name="...">` → **POST**,参数在 body,open redirect 的 GET 发不出 POST body,得换手段(能控请求体的 SSRF / gopher 构造 POST)。

> 通用技能:**SSRF 回显的页面就是你的"地图",任何操作的"请求长什么样"(路径/参数/值/方法)都写在 `<a href>` 和 `<form>` 里。读 HTML 扒出来,不是猜。** 跟你按 F12 看按钮发什么请求是一回事。

## 6. Blind SSRF:没回显时的另一套打法 🔴 核心 —— 必须吃透

### 6.1 什么是 blind、影响为什么更低

**Blind SSRF = 你能让服务器替你向某 URL 发后端请求,但响应不回显给你。** 对比 §5 那种有回显的——服务器照样发了、照样够到内网,但死活不告诉你结果,你两眼一抹黑。

它是**单向(one-way)** 的:能让服务器"发出去",但拿不回任何数据。所以 §5 那套"读回显→扒接口→操作"全废,危害天然更低。**但**某些情况仍能到 RCE(见 6.4)。

### 6.2 怎么确认它存在:OAST / Burp Collaborator 🔴

核心思路转弯:**既然它不把结果告诉你,就让它去访问"你自己的服务器",你蹲在那头看有没有人来敲门。**

- **OAST(out-of-band,带外)**:信息不走原通道(前端响应)回来了,就让它从另一条通道(你的外部服务器收到的连接)回来。
- **Burp Collaborator** = Burp 给你的"陷阱服务器 + 唯一域名",谁访问了都记录。

**操作流程(Lab: Blind SSRF with out-of-band detection,SSRF 点在 `Referer` header):**

1. Burp → **协作器(Collaborator)** 标签 → **复制到剪贴板(Copy to clipboard)**,拿到唯一域名(如 `xxx.oastify.com`)。
2. 抓一个**商品详情页**请求(`/product?productId=X`)发到 Repeater,把 **`Referer`** 头的值改成 `http://你的域名`。
3. 发送。
4. 回协作器面板,**立即轮询(Poll now)**。
5. 列表出现来自目标的交互(**DNS 或 HTTP**)→ 证明服务器真拿 Referer 去访问了你的域名 → blind SSRF 坐实,通关。

### 6.3 只看到 DNS、没有 HTTP?——也算成功 🟡

很常见:Collaborator 只收到目标对你域名的 **DNS 查询**,没有后续 HTTP。原因:服务器发 HTTP 前要先 DNS 解析你的域名(触发了 DNS),但真正的 HTTP 连接被**网络层防火墙拦了**。基础设施通常放行出站 DNS(太多东西依赖它),却拦截到意外目标的 HTTP。

> 所以:**哪怕只看到 DNS,也已证明 blind SSRF 存在**——它确实尝试解析/连接你的域名了。别因为没 HTTP 就以为没戏。

### 6.4 怎么升级危害 🟢 了解

光能发带外请求不值钱(看不到响应)。两条升级路:

- **路 A:盲扫内网打已知漏洞**。盲扫内网 IP 段,对每台发"专打某已知漏洞"的 payload,**若该漏洞利用本身也带外回连**,就能隔着盲 SSRF 命中某台没打补丁的内网机。(像看不见靶子,但朝每个方向扔会爆的雷,哪传回爆炸声哪就中。)
- **路 B:让它来连你的恶意服务器**。诱导应用连你控制的服务器,你返回**恶意响应**,若应用的 **HTTP client**(处理响应的库)有严重客户端漏洞,可能被触发,在应用基础设施里 RCE。

## 7. 找隐藏攻击面:SSRF 不只在"明显的完整 URL 参数" 🟡 重要 —— 懂原理,会查

> 对 Bug Bounty 尤其关键:明显的 SSRF 早被捡光,**隐藏的才是机会**。

**攻击面可见度光谱**(越右越隐蔽、越少人测):

```
最明显 ───────────────────────────────► 最隐蔽
url=完整URL   部分URL(拼接)   数据格式内嵌(XXE)   header(Referer)
```

| 类型 | 它藏在哪 | 为什么会 SSRF |
|---|---|---|
| **完整 URL 参数** | `stockApi=http://...` | 谁都会测,最明显 |
| **Partial URL(部分 URL)** | 参数只给 hostname 或 path 一段 | 服务端把它**拼进完整 URL** 去请求。利用受限(你只控一段,不控整个 URL),但换 hostname 成内网 IP 仍可基本 SSRF |
| **数据格式内嵌 URL** | 你提交 XML 等,格式**内部**允许嵌 URL(外部实体) | 解析器解析时去请求那个 URL → **SSRF via XXE**。最隐蔽:你没在任何参数写 URL,得想到"应用在解析 XML"。详见 [[XXE注入]] |
| **Referer header** | 请求头里 | 服务端**分析软件**常记录 Referer 并**主动访问**里面的 URL(分析来源站内容/锚文本)→ 见 §6 那关 |

> **关于 Referer 的那个困惑(为什么服务器会访问它)**:Referer 本身**没有魔力**,HTTP 里它只是个信息头,正常只被读取/记录。是这网站**额外装的分析软件**写了"去访问来源 URL"的逻辑才有 SSRF。换个没装的站,改 Referer 屁事没有。**SSRF 成立只看一件事:有没有代码拿某个"用户可控的值"去发请求。** 值在 body、query 还是 header(Referer),都一样。

**怎么知道哪个点会被服务端访问?——撒 Collaborator 盲测**:你看不到后端代码,就把 Collaborator 域名**撒进每一个输入点**(所有 header:`Referer`/`X-Forwarded-For`/`Host`...;所有参数),发出去看**谁回连**,谁回连谁就是 SSRF 点。工具 **Collaborator Everywhere**(Burp 扩展)能自动把 payload 注入所有 header,一次性帮你发现。

## 8. 贯穿一切的两套方法论(本篇最该带走的)🔴 核心 —— 必须吃透

前面所有招式,底层都是这两套思维。**招式会忘、会过时,这两套能迁移到任何目标。**

### 8.1 "检查时 ≠ 使用时"(TOCTOU 家族)

你会发现这一路的绕过,根子全是同一个:**让"校验环节看到的"和"实际使用的"不是同一个东西。**

| 招式 | 校验看到的 | 实际用到的 |
|---|---|---|
| `127.1` 绕 IP 黑名单 | 字符串 `127.1` | 解析后的 `127.0.0.1` |
| double encoding 绕关键词 | `%61dmin`(没 admin) | 解回的 `admin` |
| `@`/`#`/子域名 绕白名单 | 以为的 host | 真正连的 host |
| open redirection | 你给的合法站点 URL | 它 302 跳到的内网 |
| DNS Rebinding(见原理笔记) | 校验那次解析的外网 IP | 访问那次解析的内网 IP |
| Tomcat `/1.jsp/` 尾斜杠(见原理笔记) | 校验看到不以 .jsp 结尾 | 落地存成 `1.jsp` |

> **直觉口诀**:见到任何过滤/校验,第一反应——"**它检查的那一刻,和真正用的那一刻,是同一个形态吗?中间会不会被解码一次、解析一次、跳转一次?**" 有缝就在那里。

### 8.2 "看不到内部,就用探针试,靠反馈反推"(黑盒方法论)

你永远看不到后端代码,所有判断都是**改一点 → 看反馈 → 推断内部**:

| 你想知道 | 探针 / 反馈 |
|---|---|
| 该编码几层 | 逐层加编码,看「拦没拦」+「生效没生效」(§2.3) |
| open redirect 端点在哪 | 改跳转参数,看「跟不跟随 302」(§4.4) |
| 哪个输入点会发请求 | 撒 Collaborator,看「谁回连」(§7) |
| 盲 SSRF 存不存在 | Collaborator,看「有没有交互」(§6) |

> 这和你学 SQL 注入时"加单引号看报错"是**同一套**。黑盒测试的核心永远是:**用一个可观测的外部信号,逼近看不见的内部逻辑。** 会不会设计探针、盯对反馈,才是真功夫。

## 9. 自测(先自己想,再看答案)

1. 同样是过滤,为什么黑名单你"换写法躲",白名单却得"伪装成好人或借人带路"?
2. `%2561dmin` 为什么要编码两次?如果目标后端只解码一次,你该用几层?怎么试出来?
3. open redirection 绕的是黑名单还是白名单?它和"VPS 返回 302"那种 3xx 绕过的本质区别是什么?
4. Blind SSRF 里,你改了 Referer 却只在 Collaborator 看到 DNS、没有 HTTP,算不算成功?为什么?
5. 用一句话说清:为什么服务器会去访问 Referer 头里的地址?你怎么在一个陌生站点判断哪个输入点会被服务端拿去发请求?

<details>
<summary>参考答案</summary>

1. 黑名单是"名单外都能进",所以换个不在名单上的写法就躲开了;白名单是"只有名单内能进",你换写法也还是不在名单里,只能让它**看错**(把你当成名单上的 host)或**借名单内有跳转漏洞的站点**替你带路。
2. 因为后端解码两次、而黑名单检查卡在两次之间:编两次时,检查那层解一次仍是 `%61dmin`(没 admin)放行,使用层再解一次成 `admin`。若后端只解一次,就用一次编码(检查前不解 → 一次就够);层数靠"逐层加编码,盯拦没拦 + 生效没生效"试出来。
3. 绕**白名单**。区别:VPS 返回 302 那种是你**自己当带路人**(绕黑名单,黑名单不拦你 VPS);open redirection 是你当不了带路人(白名单不认你),只能**借白名单内一个本身有跳转漏洞的合法站点**带路。
4. **算成功**。服务器发 HTTP 前要先 DNS 解析你的域名(触发了 DNS),HTTP 被防火墙拦了而已——DNS 交互已证明它尝试访问你的域名,盲 SSRF 成立。
5. 不是 Referer 有魔力,是服务端分析软件有"访问来源 URL"的逻辑;只看"有没有代码拿这个用户可控的值去发请求"。判断陌生站点哪个点会发请求:把 Collaborator 域名撒进所有 header 和参数,看谁回连(可用 Collaborator Everywhere 自动化)。

</details>
