## 1. 什么是 OS Command Injection

### 翻译

> OS command injection 也叫 shell injection(shell 注入)。它允许攻击者在**运行该应用的服务器**上执行操作系统命令,通常会**完全攻陷该应用及其数据**。攻击者往往还能利用这个漏洞**进一步攻陷托管基础设施的其他部分**,并利用**信任关系**,把攻击**横向渗透**到组织内的其他系统。

### 为什么要学这个 / 它的作用是什么

这是渗透测试里**危害等级最高**的一类漏洞之一。前面学的文件上传漏洞,最终目的其实也是为了**拿到命令执行能力**(比如 `system($_GET['command'])` 这种 Web Shell)。而 OS command injection 是**另一条更直接的路径**——不需要上传文件,只要应用**本身的某个功能会调用系统命令**,而且把用户输入直接拼了进去,就能让服务器执行任意命令。

理解这个漏洞的核心价值在于:它教你识别一种**特定的代码模式**——"应用为了实现某个功能,偷懒调用了系统 shell 命令,并且把用户输入未经处理地拼进命令字符串里"。这种模式在真实世界的遗留系统(legacy system)里**极其常见**,因为很多老功能是"调用外部程序"实现的,而不是用编程语言自己写逻辑。

## 2. Useful Commands(常用命令)

### 翻译

> 一旦你发现了 OS command injection 漏洞,执行一些**初始命令**来获取系统信息会很有用。下面总结了一些在 Linux 和 Windows 平台上有用的命令:

| 命令用途 | Linux | Windows |
|---|---|---|
| 当前用户名 | `whoami` | `whoami` |
| 操作系统信息 | `uname -a` | `ver` |
| 网络配置 | `ifconfig` | `ipconfig /all` |
| 网络连接 | `netstat -an` | `netstat -an` |
| 正在运行的进程 | `ps -ef` | `tasklist` |

### 为什么要先跑这些命令 / 这么做能带来什么作用

这是**渗透测试的标准动作**,背后遵循"由浅入深、风险递增"的信息收集逻辑:

1. **`whoami`——先确认"我现在是谁"。** 这是**最安全、最低风险、信息量却足够大**的第一步命令。它能立刻告诉你:当前执行命令的身份是普通用户还是 `root`/`SYSTEM`(高权限),这直接决定了你接下来能做什么、这个漏洞的严重程度有多高。在真实渗透测试里,`whoami` 几乎永远是验证命令注入是否真的能执行的第一条命令,因为它**输出简单、无副作用、容易判断是否成功**。

2. **`uname -a` / `ver`——摸清操作系统版本。** 知道了系统版本,才能判断**后续还有哪些已知漏洞(CVE)可以配合利用**,也能知道该用什么语法写后续命令(Linux 和 Windows 的命令语法不一样)。

3. **`ifconfig` / `ipconfig`、`netstat`——摸清网络环境。** 这一步是在为"横向移动"做准备——了解这台服务器连接着哪些内网 IP 段、开放了哪些端口,**决定了能不能从这台机器跳到组织内的其他系统**(对应原文说的"pivot the attack to other systems")。

4. **`ps -ef` / `tasklist`——看正在运行的进程。** 这能帮你判断服务器上**还运行着什么其他服务**(比如数据库、杀毒软件、监控程序),从而评估**进一步利用的空间和风险**。

> **思路总结:** 这几条命令的顺序不是随便排的,而是遵循"**先确认权限 → 再摸清系统 → 再摸清网络 → 再摸清环境**"这个逻辑——这正是渗透测试方法论里"**侦察(Reconnaissance)**"阶段的典型做法。

## 3. Injecting OS Commands(注入场景示例)

### 翻译

> 在这个例子里,一个购物应用允许用户查看某件商品在某个门店是否有库存。这个信息是通过以下 URL 访问的:
> ```
> https://insecure-website.com/stockStatus?productID=381&storeID=29
> ```
> 为了提供库存信息,这个应用必须查询多个遗留系统(legacy system)。出于历史原因,这个功能是通过**调用一条 shell 命令**、并把商品 ID 和门店 ID 作为参数传进去来实现的:
> ```
> stockreport.pl 381 29
> ```
> 这条命令会输出指定商品的库存状态,并返回给用户。

### 为什么要先讲这个场景 / 它想说明什么

这段话在交代一个**关键的背景逻辑**:**这个漏洞为什么会存在,根本原因是"图省事"。**

应用本来应该用 Python/Java/PHP 这些语言,自己写代码去查询数据库拿库存数据。但因为历史遗留原因(可能是早年有个用 Perl 写的旧脚本 `stockreport.pl` 能查库存,图方便就**直接调用这个脚本**,而不是重写逻辑),开发者选择了"**让网页程序去调用一条 shell 命令,把 URL 参数原样拼进命令行参数里**"这种偷懒的实现方式。

> **核心思路:** 以后遇到类似"这个功能背后肯定是在调用某个外部程序/脚本"的迹象时(比如功能名字很"系统工具化",如"生成 PDF 报表"、"查询库存"、"转换文件格式"这种往往底层调用命令行工具的功能),就应该**优先怀疑这里可能存在 OS command injection**。

## 4. Injecting OS Commands - Continued(如何验证漏洞)

### 翻译

> 这个应用**没有对 OS command injection 做任何防御**,所以攻击者可以提交以下输入来执行任意命令:
> ```
> & echo aiwefwlguh &
> ```
> 如果这个输入被提交在 `productID` 参数里,应用实际执行的命令就变成了:
> ```
> stockreport.pl & echo aiwefwlguh & 29
> ```
> 这条命令会导致提交的字符串被**回显(echo)**在输出里——这是**测试某些类型的 OS command injection 的有效方法**。`&` 这个字符是一个 **shell 命令分隔符**。在这个例子里,它导致**三条独立的命令被依次执行**。返回给用户的输出是:
> ```
> Error - productID was not provided
> aiwefwlguh
> 29: command not found
> ```
> 这三行输出证明了:
>
> - **原本的命令** `stockreport.pl` **在缺少预期参数的情况下被执行了**,所以返回了一条报错信息
> - **注入的命令** `echo` **被执行了**,提交的字符串被原样回显在输出里
> - **原本的参数** `29` **被当作一条命令执行了**,导致报错
>
> 在注入的命令**后面**再加一个命令分隔符是有用的做法,因为这样可以把**注入的命令**和**注入点之后原本还会跟着的内容**分隔开。这能降低"后面的内容导致注入的命令无法正常执行"的风险。

### 为什么要这样构造 payload / 这么做能带来什么作用

#### 第一层:为什么选 `&` 这个符号?

`&` 在 shell(命令行解释器)里是一个**命令分隔符**,意思是:**"把这一行里的多条命令,一条接一条地分别独立执行"**。举个例子,在终端里直接敲:

```bash
ls & pwd & whoami
```

会依次执行 `ls`、`pwd`、`whoami` 这三条**互不相关**的命令。

**关键洞察:** 只要应用**把用户输入原封不动拼进一条 shell 命令里**,而用户输入里**包含了 `&` 这类分隔符**,攻击者就能**在原本那条命令的基础上,"夹带"一条自己的命令**进去一起执行——这正是"注入(injection)"这个词的含义:**不是替换掉原来的命令,而是在它旁边"塞进"自己的命令**。

#### 第二层:为什么具体输入是 `& echo aiwefwlguh &`,前后都有 `&`?

这是最值得记住的设计思路,拆成两半讲:

**① 前面的 `&`——负责"切开"原本的命令,把自己的命令接上去**

原始命令模板是:

```
stockreport.pl <productID> <storeID>
```

一旦 `productID` 参数被替换成 `& echo aiwefwlguh &`,拼接后就变成:

```
stockreport.pl & echo aiwefwlguh & 29
```

前面这个 `&` 的作用是:**把原本应该紧跟在 `stockreport.pl` 后面的 `productID` 参数位置"截断"**,让 shell 认为"`stockreport.pl` 这条命令(不带参数)已经结束了,接下来是一条全新的命令"。

**② `echo aiwefwlguh`——为什么选"回显一串随机字符"作为测试手段?**

这是**命令注入漏洞最经典、最安全的"探测(probe)"方法**。思路是:

- `echo` 命令的作用就是**把给它的字符串原样打印出来**
- `aiwefwlguh` 是一串**完全随机、绝不会出现在正常程序输出里的字符串**

**为什么要用随机字符串?** 因为需要一个**极其明确的信号**:如果这串**毫无意义、不可能是程序本身会产生的内容**,**出现在了返回的响应里**,那就**百分之百证明**——注入的命令**真的被服务器执行了**,而不是凭空猜测或者碰巧看到了别的内容。这是一种**低风险、高置信度**的验证手段:没有执行任何真正有破坏性或者有实际作用的命令(比如删文件、读敏感数据),只是单纯"打个招呼",却能**精确无误地确认漏洞是否存在**。

> **这背后的思路,本质上和 SQL 注入、XSS 的"探测手法"是同一个底层逻辑:先用一个无害但特征明显的 payload 去"试探",确认漏洞存在后,再考虑下一步真正有价值的利用。**

**③ 后面的 `&`——为什么还要再加一个?**

拼接后的完整命令是:

```
stockreport.pl & echo aiwefwlguh & 29
```

如果**没有**后面这个 `&`,命令会变成:

```
stockreport.pl & echo aiwefwlguh 29
```

这样一来,`29`(原本的 `storeID` 参数)就会被当成 **`echo` 命令自己的参数**,执行结果就变成 `echo` 把 `aiwefwlguh` 和 `29` 一起打印出来——**虽然这种情况下依然能看到 `aiwefwlguh`,这次测试本身可能还是会"侥幸成功"**。

但原文想强调的是一个更普遍、更稳妥的工程原则:

> **在注入的命令后面,主动补一个命令分隔符,目的是把"注入的命令"和"注入点后面本来就存在的、无法控制的内容"彻底隔离开。**

想象一个更复杂的场景——如果注入点后面跟着的不是简简单单一个数字 `29`,而是**一段会导致语法错误、或者会把命令"吃掉"的内容**,那么**没有后面这个分隔符**,注入的命令就可能**因为后面接了一堆不兼容的内容而执行失败**,哪怕注入点本身没问题。

**所以这是一个"防御性的 payload 设计习惯":每次构造注入 payload 时,前后都加上分隔符,把自己的命令像个独立的三明治一样"包起来"**,这样不管注入点前后原本是什么内容,命令都能**独立、干净地执行**,不受干扰。

#### 第三层:怎么解读返回的三行报错?

```
Error - productID was not provided
aiwefwlguh
29: command not found
```

这三行其实是**三条独立命令各自的执行结果**,需要学会像读"案发现场"一样逐行解读:

| 行 | 对应哪条命令 | 为什么会这样 |
|---|---|---|
| `Error - productID was not provided` | `stockreport.pl`(被前面的 `&` 截断,没拿到参数) | 这条命令发现自己**没有收到预期的 productID 参数**(因为参数位置被 payload 占了),于是报错——**这反过来证明了,`&` 确实成功把原命令"截断"了** |
| `aiwefwlguh` | `echo aiwefwlguh` | 这就是**命令注入成功的铁证**——这串无意义字符被真正执行并打印出来了 |
| `29: command not found` | `29`(被当成了一条独立命令尝试执行) | 因为后面那个 `&` 把 `29` 从 `echo` 的参数里"解放"了出来,变成了**独立的第三条命令**,而 shell 系统里根本没有一个叫 `29` 的程序,所以报"找不到命令" |

> **核心思路:** 看到报错信息**不要慌、更不要忽略它**——报错信息本身往往是**最有价值的诊断信息**。这三行报错,与其说是"失败的证据",不如说是**"注入成功、而且命令被正确切成了三段"的完美证明**。

## 5. Lab: OS Command Injection, Simple Case(实验室)

### 翻译

> 这个实验室的商品库存查询功能里存在一个 OS command injection 漏洞。
> 应用会执行一条包含**用户提交的商品 ID 和门店 ID** 的 shell 命令,并把命令的**原始输出**直接返回在响应里。
> 解题目标:执行 `whoami` 命令,确定当前用户的名字。
>
> **解决方案:**
> 1. 使用 Burp Suite **拦截并修改**一个用来查询库存等级的请求。
> 2. 修改 **`storeID`** 参数,把它的值改成 `1|whoami`。
> 3. 观察响应里是否包含了当前用户的名字。

### 为什么这样做 / 每一步的作用是什么

#### 第 1 步:为什么要用 Burp 拦截请求,而不是直接改浏览器地址栏?

因为**这个实验室要注入的是参数值**,理论上也可以直接在浏览器地址栏把 URL 改成 `...&storeID=1|whoami` 后回车访问。用 Burp 的好处是:**能完整看到请求和响应的所有细节**(包括响应头、可能被截断的内容等),并且**方便反复修改、重放同一个请求**做多次尝试——这是渗透测试里的标准工作流,不只是为了这一个简单实验。

#### 第 2 步:为什么用的符号是 `|`,而不是前面例子里的 `&`?

这是需要特别注意的一个点——**OS command injection 有好几种不同的"命令分隔符"写法,效果和适用场景略有差异**(详见下方对照表)。

这里用的是 `1|whoami`,意思是:**先尝试把 `storeID` 设为 `1`(让原命令大概率能正常跑完,减少报错对观察结果的干扰),然后用 `|` 紧接着执行 `whoami`。**

**为什么要这样选,而不是像前面例子那样前后都加分隔符?** 因为这里的目标**不是"测试漏洞是否存在"(不需要 echo 随机字符去探测),而是直接拿到有价值的信息(当前用户名)**。前面的学习已经确认了这类功能普遍存在注入风险,这个实验室本身也明确告诉你"没有任何防御措施",所以可以**直接上"实战 payload"**,不需要再用无害字符串做前置探测这一步了。

#### 第 3 步:为什么解题目标偏偏是 `whoami`,而不是别的命令?

回到最开始"Useful commands"那张表格的逻辑——**`whoami` 是验证命令注入"从理论变成实锤"的标准试金石**。这个实验室选择用它来作为"过关条件",本质上是在训练一个**渗透测试的肌肉记忆**:**每次怀疑或确认一个命令注入点时,第一反应应该是跑一下 `whoami`**,因为:

1. 它的输出**极其简单、一眼就能判断对不对**(不像读文件内容那样容易被误判)
2. 它能立刻告诉你**接下来能做什么**——如果返回的是 `root` 或 `www-data`(Linux)、`SYSTEM`(Windows),就知道这台服务器的"命令执行权限"有多高,从而决定**这个漏洞到底值多少分、能不能进一步利用**

## 6. 实战深挖:HTTP 解析与 Shell 解析——两道关卡的较量

> 本节是在亲手做完第 5 节的实验室、用 Burp Repeater 反复试验不同 payload 后,整理出来的一份"踩坑记录"。它回答的问题是:**为什么同一个 `&` 符号,有时候能成功注入,有时候又完全没反应,甚至直接导致参数"消失"?**

### 6.1 先建立一个核心概念:你的输入要经过"两道关卡",不是一道

第 4 节讲 `&`、`|`、`#` 这些符号时,默认的前提是"这些符号已经原封不动地到达了 shell"。但**在真正到达 shell 之前,你的输入其实要先经过 HTTP 层面的解析**。这一点在第 4 节里没有展开,这里补上。

你发送的请求,本质上是 `productId=xxx&storeId=xxx` 这样的**表单数据**(格式是 `application/x-www-form-urlencoded`——这个格式和《文件上传漏洞笔记》里讲过的 `multipart/form-data` 是"表亲"关系,都是浏览器/服务器约定好的数据打包规则,只是这种更简单,专门用来传纯文本参数)。

你的输入要**依次经过两道完全不同的"关卡"**,才能最终变成服务器执行的 shell 命令:

```
你写的原始文本
   ↓
【第一道关卡】HTTP 表单解析器(Web 服务器/框架层面)
   ↓  —— 负责把请求体"切"成 productId 和 storeId 两个字段
得到 productId 的值、storeId 的值
   ↓
【第二道关卡】Shell 解释器(操作系统命令行层面)
   ↓  —— 负责把拼好的命令字符串"切"成一条条独立命令执行(这就是第4节讲的内容)
真正被执行的命令
```

**这是本节的总钥匙:这两道关卡,都会把 `&` 这个符号当成"切割用的分隔符"——但它们切割的"对象"完全不同,而且发生的"时间"也不同。**

| 关卡 | 把 `&` 当成什么 | 它负责切开的是什么 |
|---|---|---|
| **第一道:HTTP 表单解析** | **字段分隔符** | 把一整段请求体,切成 `productId=xxx` 和 `storeId=xxx` **两个独立的参数** |
| **第二道:Shell 解释**(第 4 节讲过) | **命令分隔符** | 把一条命令字符串,切成**多条独立命令**依次执行 |

下面用四组实测对比,拆解这两道关卡是怎么互相"打架"的。

### 6.2 案例对比一:直接写 `&`,为什么注入失败了?

**payload:**
```
productId=1 & whoami #& storeId=1
```

**结果:** 服务器返回了正常的库存数字,没有发生注入。

**原因拆解:** 这段文字里一共有**两个**没编码的 `&`,HTTP 表单解析器**压根不懂你的"注入逻辑"**,只认死规则——**遇到没编码的 `&`,就切一刀**:

```
productId=1 (&) whoami #(&) storeId=1
             ↑              ↑
          第1个&          第2个&
```

于是被切成了三段:`productId=1 `、` whoami #`(没有 `=` 号,解析器不认识这个字段,大概率直接丢弃)、` storeId=1`。

**结果:** 应用真正拿到手的,只有 `productId="1"`、`storeId="1"`——中间那段注入内容,**根本没能活到"拼进 shell 命令"那一步,就已经在第一道关卡被切碎丢掉了**。

> **一句话:** 你以为自己在"注入 shell 命令",但 `&` 从头到尾都没机会见到 shell 的面——它在 HTTP 这一层就被当成"两个参数之间的分界线"消耗掉了。

### 6.3 案例对比二:把 `&` 换成 `|`,为什么就成功了?

**payload:**
```
productId=1 | whoami #& storeId=1
```

**结果:** 响应里返回了 `whoami` 的执行结果(当前用户名)。

**原因拆解:** 关键区别只有一个——**`|` 这个符号,对 HTTP 表单解析器来说"毫无意义"**。HTTP 表单解析器只认识 `&`(字段分隔符)、`=`(键值分隔符)、`+`(代表空格)、`%XX`(编码字符)这几个特殊符号,`|` 在它眼里就是一个**普通字符**,不会被拿来做任何切割。

这次,HTTP 解析器扫描全文,**只找到了一个**没编码的 `&`(就是 `#` 后面那个),所以只切出两段:

- `productId = "1 | whoami #"`(**完整保留**,`|` 没有被当成分隔符)
- `storeId = "1"`

`productId` 的值里完整携带着 `| whoami #`,活着进入了**第二道关卡**。后端把它拼进 shell 命令模板:

```
stockreport.pl 1 | whoami # 1
```

这才轮到 Shell 登场:`|`(管道符,第 7 节对照表里有)让 `whoami` 被执行;`#` 是 **shell 的注释符**——告诉 shell"这一行,从 `#` 往后的内容全部无视",于是 `storeId` 的值(`1`)被一笔抹掉,不会干扰注入的命令。

> **一个值得记住的洞察:** 这里用 `#` 来"清理"注入点后面的内容,和第 4 节例子里"在后面再加一个分隔符(比如 `&`)把后面内容变成独立一条命令"是**两种不同思路**,但目的相同——都是不让后面的内容干扰注入。`#` 更彻底、更简单粗暴:它直接让 shell "眼瞎",连"报错"的机会都不给。

### 6.4 案例对比三:去掉 `#` 后面的 `&`,为什么又报错"缺少 store ID 参数"?

**payload:**
```
productId=1 | whoami #storeId=1
```

对比 6.3,只是少了 `#` 和 `storeId` 之间那个 `& `(一个 `&` 加一个空格)。

**容易产生的误解:** "反正 `#` 已经把后面内容注释掉了,系统应该不会再管 `storeId` 是什么了吧?"——这个直觉**本身没错,但搞错了"系统不会管它"发生在哪一道关卡**。

`#` 能让**第二道关卡(Shell)**不去管后面的内容,但它**完全管不到第一道关卡(HTTP 表单解析)**。而这次的报错,根本还没轮到 Shell 出场,就已经在第一道关卡出了问题。

因为这次整段文字里**一个没编码的 `&` 都没有了**,HTTP 解析器扫描一圈找不到任何分隔符,于是认定:**这整段话,从头到尾,全都是 `productId` 一个字段的值**:

```
productId = "1 | whoami #storeId=1"
```

**`storeId` 这个参数,直接从请求里"消失"了——它根本没有被当成一个独立字段发送出去。**

而这个应用(回忆第 5 节的实验室场景)在真正拼接、执行 shell 命令**之前**,通常会先做一个最基础的入参校验:检查 `productId` 和 `storeId` 这两个必填参数是不是都收到了。这一步发生在代码逻辑的最前面,和后面会不会拼 shell 命令、`#` 能不能注释掉东西,**完全没有关系**。既然 `storeId` 根本没被发送,这道"收件检查"自然不通过,应用直接报错,连"去拼 shell 命令"这一步都还没走到。

> **一句话总结:** `#` 是"shell 级别的隐身衣",只能让 **shell** 对后面内容视而不见;但它没办法让 **Web 应用的参数校验逻辑** 也对"这个参数到底存不存在"视而不见。这是两个完全不同层面的"不管",不能用对付 Shell 的办法去解决 HTTP 层面的问题。

### 6.5 案例对比四:把 `&` 换成 URL 编码 `%26`,为什么又成功了?

**payload:**
```
productId=1+%26+whoami+%23&storeId=1
```

**结果:** 同样成功拿到了 `whoami` 的输出。

**原因拆解:** 这里的关键是**编码**——这是用"正确姿势"解决了 6.2 失败的根本问题。

`%26` 和 `%23` 是什么?在 URL/表单编码规则里,**任何字符都可以用 `%` 加上它的十六进制 ASCII 码来表示**。`&` 的 ASCII 码十六进制是 `26`,所以 `%26` 代表"这里原本有一个 `&` 字符";同理 `%23` 代表 `#`,`+` 代表空格。

**为什么这样写能骗过第一道关卡?** 因为 HTTP 表单解析器在扫描请求体、寻找"哪里该切一刀"时,**只把"原始、没有编码过的" `&` 符号当成分隔符**。而 `%26` 这三个字符(百分号+2+6),在解析器眼里只是**三个普通文本字符**,不会被当成分隔符——它只是先按"没编码的 `&`"把字段切好,**切完之后**,才对每个字段的值做一次"解码"(把 `%26` 还原成 `&`、`+` 还原成空格)。

整个过程分两步:

**第一步(切分阶段):** 解析器扫描全文,只找到**一个**真正没编码的 `&`(`storeId=1` 前面那个),切出两段:
```
productId = "1+%26+whoami+%23"
storeId   = "1"
```

**第二步(解码阶段):** 把 `productId` 值里的编码字符翻译回原文(`+`→空格,`%26`→`&`,`%23`→`#`):
```
productId = "1 & whoami #"
```

**这次 `&` 和 `#` 都完整、原汁原味地活到了 `productId` 的最终值里**,接下来被拼进 shell 命令:
```
stockreport.pl 1 & whoami # 1
```

轮到 Shell 接手,看到的就是一个正常的、带 `&` 分隔符的命令,依次执行 `stockreport.pl 1`、`whoami`,`#` 后面照常被注释——结果和 6.3 一样成功。

> **这就是为什么渗透测试里"URL 编码特殊字符"是标准动作:** 想让某个特殊符号以"原始、完整"的样子活着通过 HTTP 这一层、交给后端代码去拼接命令,就必须先把它**编码**一下,防止它在半路就被 HTTP 解析器"误读"。这和 6.2 "直接写原始 `&`"形成鲜明对比——**同一个字符,编码与否,决定了它是在"HTTP 层被消耗掉",还是能"活着传递到 Shell 层发挥作用"。**

### 6.6 四个案例串成一条逻辑线

| 案例 | 你的输入(关键部分) | 第一道关卡(HTTP)怎么切的 | 第二道关卡(Shell)收到了什么 | 结果 |
|---|---|---|---|---|
| **6.2** | `1 & whoami #& storeId=1` | 两个未编码 `&` 都被当分隔符,中间内容被切碎丢弃 | 只收到干净的 `productId=1`,没有注入内容 | **没注入,返回正常库存** |
| **6.3** | `1 \| whoami #& storeId=1` | `\|` 不是分隔符被保留;只有最后那个 `&` 被当分隔符 | `1 \| whoami #` 完整到达,`#` 注释掉后面内容 | **注入成功,拿到 whoami** |
| **6.4** | `1 \| whoami #storeId=1` | 整段**没有**任何未编码 `&`,全部被当成 productId 一个字段的值 | storeId 参数**根本没被发送**,应用在校验阶段就报错 | **卡在 HTTP 参数校验,报错** |
| **6.5** | `1+%26+whoami+%23`(编码后) | 编码过的 `%26`/`%23` 不被当分隔符,只有最后真正的 `&` 被切分 | 解码后还原出 `1 & whoami #`,完整到达 shell | **注入成功,拿到 whoami** |

> **这四个案例连起来,教的是渗透测试里极其核心的一件事:注入攻击从来不是"我往输入框里塞个特殊符号就行",而是要搞清楚"你的输入要依次穿过哪几层解析,每一层分别把哪些符号当成'特殊字符'"。只有你想注入的符号,能够完整无损地"活着"穿过前面所有层,到达你真正想利用的那一层(这里是 Shell),攻击才会生效。** 这也是为什么 Burp Repeater 这类工具这么重要——它能让你精确控制"原始字节",反复试验不同编码方式,直到找到能让 payload 完整存活的写法。

## 7. 速记:命令分隔符对照表

| 分隔符                    | 名称        | 行为逻辑                                                       | 适用系统            |
| ---------------------- | --------- | ---------------------------------------------------------- | --------------- |
| `&`                    | 后台执行分隔符   | 让前后两条命令**都执行**,互不等待对方结果                                    | Linux / Windows |
| `&&`                   | 逻辑与       | **只有前一条命令执行成功**,才会执行后一条                                    | Linux / Windows |
| `\|`                   | 管道符(Pipe) | 把**前一条命令的输出**,作为**后一条命令的输入**;在命令注入场景里,通常简单理解为"让后一条命令也跟着执行" | Linux / Windows |
| `\|\|`                 | 逻辑或       | **只有前一条命令执行失败**,才会执行后一条                                    | Linux / Windows |
| `;`                    | 命令结束符     | 前一条命令结束后,**无论成功与否**,都接着执行下一条                               | 仅 Linux/Unix    |
| `` ` 命令 ` `` 或 `$(命令)` | 命令替换      | 把括号/反引号里命令的**输出结果**,替换到原命令中再执行                             | 仅 Linux/Unix    |

> **实战建议:** 遇到疑似命令注入点,没有把握对方用的哪种语法时,可以**逐个尝试这张表里的分隔符**,再结合 `echo 随机字符串` 这种无害探测手法,观察响应差异来判断漏洞类型和过滤规则。

## 8. 渗透测试检查清单

以下方法仅用于**授权的测试环境或靶场**。

- [ ] 寻找"功能名字很系统工具化"的接口(报表生成、格式转换、库存/状态查询、Ping/网络诊断类工具等),这类功能背后常常调用外部命令
- [ ] 用 `echo 随机字符串`(前后加分隔符包裹)做无害探测,观察响应里是否原样出现这个随机字符串
- [ ] 响应里出现报错信息时,**逐行分析**,判断是"原命令报错"还是"注入命令执行成功"
- [ ] 确认漏洞存在后,优先执行 `whoami` 判断当前权限等级
- [ ] 按需执行 `uname -a`/`ver`、`ifconfig`/`ipconfig`、`netstat -an`、`ps -ef`/`tasklist`,循序渐进收集系统、网络、进程信息
- [ ] 尝试表格中列出的多种分隔符(`&`、`&&`、`|`、`||`、`;`),确定目标系统实际支持/未过滤的是哪一种
- [ ] 用 Burp Repeater 反复修改参数值、观察响应差异,而不是每次都改浏览器地址栏

## 9. 核心思路总结

> OS command injection 之所以存在,根源在于**开发者为了省事,把"调用外部程序"和"拼接用户输入"这两件事直接绑在了一起**,而没有对用户输入做任何过滤或转义。攻击者利用 shell 自带的**命令分隔符**(`&`、`&&`、`|`、`;`),把自己的命令"夹带"进原本的命令里一起执行。**测试这类漏洞的标准思路是:先用无害的 `echo 随机字符串` 做探测,确认漏洞存在后,再用 `whoami` 这类低风险但信息量大的命令,快速判断当前权限有多高**——这是一套以后遇到任何疑似命令注入点,都可以直接套用的标准作业流程(SOP)。
