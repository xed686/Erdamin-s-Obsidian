## 1. 核心心法:为什么"业务理解"比"漏洞原理"更值钱(🔴 核心)

### 1.1 它是什么

一句话:**漏洞原理是"通用知识"(网上一搜都有),而"这个网站的这个功能,大概率会用这种方式实现、因此大概率有这种漏洞"是"经验知识"(只能靠见得多攒出来)**。老手值钱的地方,正是后者。

> 类比:两个医生都背熟了同一本《诊断学》(漏洞原理)。但老医生看一眼病人走路的姿势、听一句主诉,心里就有了"大概率是这三种病之一,先查这几项"的判断;新医生只能把所有检查从头到尾做一遍。差距不在"懂不懂病理",而在"见过的病人够不够多,能不能一眼抓重点"。

### 1.2 为什么会存在(原理 / root cause)

这套经验之所以有效,根子在一个朴素但深刻的事实:**绝大多数漏洞,根本原因都是开发者为了赶工期、图省事,走了某种"看起来能用但没做安全校验"的捷径。**

- 为什么有命令注入?因为开发者图省事,直接把用户输入拼进了调用 shell 的命令里。
- 为什么有文件上传漏洞?因为开发者图省事,只检查了用户"自称"的文件类型(Content-Type),没做真正的校验。
- 为什么有越权?因为开发者图省事,默认"能请求到这个接口的就是合法用户",漏掉了"这条数据到底是不是你的"这一层校验。

**看出规律了吗——漏洞是"图省事"的产物,老手就是对"哪里最容易图省事"有预判。** 这份笔记接下来做的全部事情,就是把"哪里最容易图省事",按业务模块、参数长相、关键词,给你提前列成可查的清单。

> [!note] 🔎 补充(非原笔记内容)
> 这个视角还有一个更深的用处:它让你**在面对一个你从没见过的全新功能时,依然知道该往哪测**。因为你不是在记"XX 功能有 XX 漏洞"这种死条目,而是在练一个可迁移的追问——"这个功能本该有哪些安全限制?开发者有没有可能为了省事而跳过?"只要掌握了这个追问方式,哪怕遇到十年后才出现的新功能,这套思维依然成立。本篇第 5 节的"逆向业务流程思维"就是这个追问的具体化。

### 1.3 怎么做(把心法落成动作)

**步骤 1:看到任何功能,先问"它本该有什么限制"**
- 做什么:在动手测之前,先站在产品经理角度想一遍"这个功能,设计者希望它被怎么安全地使用"。
- 为什么这么做:这一步帮你**凭空生成一张"该有的校验"清单**,接下来只要逐一验证"这些校验开发真的做了吗"。
- 做完得到什么:一个明确的测试方向,而不是漫无目的地瞎试 payload。

**步骤 2:把"该有的限制"逐条当作攻击假设去验证**
- 做什么:比如"忘记密码"功能,设计意图是"只有账号真正的主人能重置",那你的测试假设就是"有没有办法绕过'验证我是主人'这一步"。
- 为什么这么做:每一条"本该有的限制",都对应一个"如果限制没做好会怎样"的漏洞。
- 做完得到什么:验证成立 → 发现一个逻辑漏洞;不成立 → 这条路封死,换下一条假设。

### 1.4 业务里长什么样(案例锚点)

> **真实案例:curl 项目 2026 年 1 月停掉付费 Bug Bounty** —— 这个事件反过来印证了"业务理解 > 工具产出"的价值。
> - **发生了什么**:curl 的 bounty 项目被大量 AI 自动生成的漏洞报告淹没,有效漏洞率跌破 5%,维护者花在筛选垃圾报告上的无偿时间暴增,最终在 2026 年 1 月停掉付费奖励。
> - **根因对应本笔记哪一环**:AI 工具能批量套用"通用漏洞原理"生成看似像模像样的报告,但它们普遍缺乏"这个业务的这个功能到底会不会真的有这个洞"的判断(也就是本节说的"经验知识")。
> - **业务后果**:整个 bounty 生态被迫收紧——平台上调质量门槛、引入 AI 分诊、加强研究员审核;低质量"喷射式"提交的生存空间被挤压。
> - **渗透测试者的启发**:这恰恰说明**未来值钱的不是"能跑工具、能套原理"的人,而是"能判断某个洞在这个具体业务里到底成不成立、有没有真实危害"的人**。你现在练的这套"业务理解"能力,正是 AI 短期内最难替代、也最被平台需要的部分(详见第 6 节)。

### 1.5 实战怎么用

- **什么时候该想到它**:每次拿到新目标、每次面对一个陌生功能时,先用这个心法"定方向",再动手。
- **怎么验证**:就是第 1.3 节的两步——先列"该有的限制",再逐条当假设验证。
- **下一步**:定好方向后,配合第 2-4 节的清单,快速圈定要优先测的点。

### 1.6 防御与检测视角

反过来,防御方如果理解"漏洞是图省事的产物",就知道代码审计和安全评审时该重点盯哪里:所有"跨系统交接""权限判断""金额/数量校验"这些**最容易被省略**的环节,就是防御要加固的地方。攻防在这里是同一张地图的两面。

### 1.7 易错点

- **误区:以为"把所有漏洞原理背得滚瓜烂熟"就能挖到洞。** 原理是必要条件,不是充分条件。背熟了原理却不会判断"这个业务该往哪找",依然会陷在"挨个瞎试、效率极低"的泥潭里。
- **排错线索**:如果你测了很久一无所获,停下来问自己——"我是在有策略地验证假设,还是在无脑地对每个参数喷 payload?"后者就是陷进去了。

## 2. 功能高发区地图:哪些业务模块先盯(🔴 核心)

### 2.1 它是什么

把一个典型 Web/App 拆开,不同模块"出事"的概率天差地别。下面按高发程度排序,核心是理解**每一类为什么高发**——理解了"为什么",才能迁移到清单里没列到的新功能上。

### 2.2 四档高发区(附"为什么")

**🔴 极高发区:身份与权限相关功能**

| 功能 | 为什么容易出问题 | 优先测的漏洞类型 |
|---|---|---|
| 注册 / 登录 / 找回密码 | 逻辑分支最多、状态最复杂,越复杂越容易有"没考虑到的分支" | 验证码爆破/复用、重置流程绕过、用户名枚举、2FA 绕过 |
| 手机号/邮箱绑定解绑 | 往往是后加的"补丁功能",测试投入少 | 越权改绑、验证码爆破、不验证原绑定直接改 |
| 个人信息修改 | 开发者默认"这是改自己的",容易漏掉"这个 ID 真是我自己吗" | 水平越权 / IDOR |
| 后台管理 / 运营系统 | "内部人员用的",安全投入低,又是高权限入口 | 未授权访问、弱口令、垂直越权 |

> **为什么这档最高发**:这些功能的核心逻辑是"判断你是谁、你能做什么",而**权限判断本身就是整个系统里最容易写错的逻辑**——因为访问控制的设计决策必须由人工做出,人工判断的地方,就是漏洞频发的地方。

**🟠 高发区:涉及"文件"和"外部交互"的功能**

| 功能 | 为什么容易出问题 | 优先测的漏洞类型 |
|---|---|---|
| 头像/图片/文件/简历上传 | 要和存储、后续访问打交道,链路长、环节多 | 文件上传(Web Shell)、文件名路径穿越 |
| 文件下载/导出/查看附件 | "根据某参数去读文件",最容易"图省事直接拼路径" | 路径穿越、任意文件读取 |
| 第三方登录(微信/支付宝扫码等) | 多方系统互相信任,链条长、最容易在某环节断裂 | OAuth 逻辑缺陷(state 缺失/可预测、回调地址可控) |
| 分享/邀请/生成海报二维码等 | 常把用户输入拼进调用其他服务(图片/PDF 生成)的命令或模板 | SSRF、命令注入、模板注入(SSTI) |

> **为什么这档高发**:它们天生要和"外部的东西"打交道——文件系统、第三方服务、外部脚本。每多一次跨系统交互,就多一次"在交接处信任了不该信任的输入"的机会。

**🟡 中高发区:涉及"钱"和"业务逻辑"的功能**

| 功能 | 为什么容易出问题 | 优先测的漏洞类型 |
|---|---|---|
| 订单/支付/优惠券/余额/积分 | 正确性依赖"前后端都校验金额",但开发常只在前端校验或信任前端传的金额 | 支付金额篡改、优惠券叠加、负数支付、重放、越权查他人订单 |
| 秒杀/抢购/限时活动 | 为追求高并发,常牺牲掉本该有的校验(如库存扣减的原子性) | 并发超卖、重放、价格篡改 |
| 邀请返利/拉新奖励 | 设计时很少有人从"攻击者视角"审视规则漏洞 | 无限刷奖励、自己邀请自己 |

> **为什么这档高发**:涉及钱的功能,开发关注点天然偏向"流程能跑通"而非"能不能被恶意绕过",且横跨前端/后端/支付网关三方,任一方"图方便信任了别方"就可能出问题。

**🟢 常被忽视但值得留意**:搜索框/筛选条件(SQL 注入、反射 XSS)、评论区/昵称/简介等自由文本(存储型 XSS)、Swagger/接口文档未授权(白送内部接口地图)、短信/验证码接口(轰炸、爆破)、WebSocket 接口(大家测得少,反而容易有问题)。

### 2.3 实战怎么用

- **什么时候该想到它**:拿到新目标走查功能时,对照这张表给每个功能点标优先级。
- **怎么验证**:高发区的功能优先抓包、优先投入时间。
- **下一步**:圈出高发功能后,进入第 3 节用关键词雷达进一步分诊。

### 2.4 易错点

- **误区:把清单当成"只测这些"。** 清单是优先级指引,不是边界。真正要学的是每一档"为什么高发"的逻辑,这样才能判断清单外的新功能。

## 3. 抓包"危险词雷达":扫一眼就圈出可疑请求(🔴 核心)

### 3.1 它是什么

老手扫一眼流量包列表就知道点开哪个,靠的是一套"关键词雷达"——看到特定字眼,大脑自动触发"这里优先测"的信号。本质是:**接口/参数的名字,是开发者留下的"自然语言线索",暴露了它背后大概怎么实现。**

### 3.2 URL/接口路径关键词

| 关键词 | 为什么警惕 | 对应方向 |
|---|---|---|
| `admin`/`manage`/`system`/`console`/`backend` | 大概率是后台入口 | 未授权、弱口令、垂直越权 |
| `test`/`debug`/`dev`/`demo`/`old`/`bak`/`v1`(当 v2 已存在) | 测试/废弃接口,往往"忘了关"或安全措施没跟上 | 信息泄露、弱校验、功能越权 |
| `file`/`download`/`export`/`load`/`read`/`path`/`doc`/`img` | "根据某值去读/下载某东西" | 路径穿越、任意文件读取 |
| `upload`/`avatar`/`import`/`attach` | 文件上传 | 文件上传漏洞 |
| `exec`/`cmd`/`run`/`shell`/`ping`/`convert`/`generate` | 几乎明示"背后在调外部命令/脚本" | 命令注入 |
| `redirect`/`url`/`jump`/`callback`/`next`/`forward` | "跳转到某地址" | 开放重定向、SSRF |
| `/actuator`/`/swagger`/`/.git`/`/.env`/`api/internal` | 内部接口、调试端点、配置/版本控制文件 | 信息泄露、未授权访问 |

> **为什么要记这些词**:看到词 → 联想到实现方式 → 联想到实现方式里最容易偷懒的地方,这就是老手的"反射弧"。一个接口叫 `fileDownload`,它背后大概率就是"拿文件名参数去读文件系统",和路径穿越的攻击原理完全对上号。

### 3.3 参数值/请求体里的危险信号

| 看到的内容 | 为什么留意 | 对应方向 |
|---|---|---|
| 参数值是完整文件路径/文件名 | 服务端大概率在拼真实路径 | 路径穿越、任意文件读取 |
| 参数值是一个 URL | 服务端大概率会去请求它 | SSRF |
| 参数值是递增数字 ID(`id=1001`) | 换个数字就可能看到别人数据 | IDOR / 水平越权 |
| 出现 `role`/`isAdmin`/`level`/`type=0/1` | 角色/权限信息,前端传的大概率可改 | 垂直越权、参数篡改 |
| 响应里有完整堆栈报错 | 生产开了调试模式,报错=内部代码说明书 | 信息泄露 → 为注入/审计提供线索 |
| 响应头 `X-Powered-By`/`Server` 暴露版本号 | 能精确定位框架/中间件版本 | 配合 CVE 库查已知漏洞 |
| `Content-Type: application/xml` 或内容是 XML | 服务端可能解析 XML | XXE |
| 参数值像序列化数据(`rO0AB` / `O:8:"..."`) | 服务端可能在做反序列化 | 反序列化漏洞 |

### 3.4 响应内容值得多看一眼的信号

- **状态码 200 但内容是一段 JSON 错误信息**(而非真的 404/403)→ 应用自己手搓了一套校验逻辑,比框架自带的更容易有逻辑漏洞。(这点和《渗透测试中状态码的第一反应速查表》里讲的"别只看状态码数字、要看内容"是同一个意思。)
- **响应里夹带了比页面展示更多的字段**(登录接口 JSON 里除昵称头像还带手机号/身份证/密码哈希,只是前端没显示)→ "信息过度返回",数据已在网络层被你抓到。

### 3.5 实战怎么用

- **什么时候该想到它**:全局抓包后,拿这套雷达扫一遍所有 URL 和参数名。
- **怎么验证**:命中关键词的请求优先深测。
- **下一步**:圈出 5-10 个最可疑的点,集中火力(对应第 5.2 节"先广度后深度")。

### 3.6 易错点

- **误区:只认词、不验证实现。** 关键词只是"提高某漏洞的先验概率",不是"确诊"。`download` 参数也可能后端做了严格白名单。词是用来排优先级的,不是用来下结论的。

## 4. 参数命名的"气味":看名猜漏洞(🔴 核心,是第 3 节的延伸)

光看参数名,不看功能是干嘛,就能大致猜出"这个参数容易被怎么攻击":

| 参数名长这样 | 第一反应测什么 |
|---|---|
| `id`/`uid`/`user_id`/`order_id`/`doc_id` | 改成别人的 ID,测 IDOR |
| `filename`/`file`/`path`/`filepath` | 试 `../../../etc/passwd` 路径穿越 |
| `url`/`redirect_url`/`callback`/`returnUrl` | 改成自己可控地址,测 SSRF / 开放重定向 |
| `cmd`/`command`/`exec` | 高度怀疑命令注入,用 `echo 随机字符串` 探测法 |
| `admin`/`is_admin`/`role`/`level`/`vip`/`type` | 改成代表更高权限的值,测垂直越权 |
| `page`/`template`/`view`/`tpl` | 测模板注入(SSTI) |
| `search`/`keyword`/`q`/`filter` | 测 SQL 注入、反射 XSS |
| `token`/`sign`/`sig` | 看这个值是不是可预测/可伪造(如简单 MD5(用户名+固定盐)) |

> 这张表的本质是培养"看名知意"的本能反射——真正的老手看到参数名的瞬间,脑子里已自动冒出 2-3 个该试的 payload,这是经验转化成的"肌肉记忆"。

**易错点**:参数名只是"气味",不是"确诊"。`id` 参数后端也可能做了严格的归属校验;这套气味是用来排序的,验证才是唯一标准。

## 5. 老手独有的思维习惯(🔴 核心)

除了"认词",几个思维方式上的差异是新手容易忽略的。

### 5.1 "对比思维":永远两个同类请求放一起看

老手抓包几乎不会只看一个请求,而是习惯性制造"对照组":
- **自己账号 vs 小号**分别操作同一功能,对比请求/响应 → 快速定位哪个参数是"身份标识"。
- **正常操作 vs 刻意制造错误**(传空、传超长、传负数),对比响应 → 摸清后端校验边界。
- **PC 端 vs 移动端(App/小程序)**对同一功能的实现 → 移动端 API 的安全投入往往远低于 Web 端,同样功能移动端接口常防护更弱。

> 为什么重要:单看一个请求,很难判断某字段改了会不会有影响;两个请求一对比,差异点自然跳出来——差异点往往就是突破口。

### 5.2 "全局浏览"优先于"逐个深挖"

新手爱抓到第一个功能就一头扎进去反复测。老手相反:**先把所有功能点扫一遍、流量全抓下来,对照高发区清单和关键词雷达圈出 5-10 个最可疑的点,再集中火力深挖。** 先广度后深度,避免在低价值功能上耗尽精力、错过真正的肥肉。

### 5.3 "历史漏洞库"思维:同类 CMS/框架,漏洞会"遗传"

识别出目标用的具体 CMS/框架(CMS 指纹识别)后,第一时间查它历史上爆过哪些洞:很多站长期不更新,老洞原封不动还在;哪怕打了补丁,同一套代码架构里类似的漏洞模式常在"姊妹功能"里重复出现(同一团队写代码习惯相似,一处犯的错别处大概率也犯)。

### 5.4 "逆向业务流程"思维:站在产品经理角度想"本该怎么限制"

这就是第 1.3 节心法的具体化——测一个功能前先问"如果我是产品负责人,我希望它被怎么限制?",再验证"这些限制开发真的实现了吗?"。它的价值在于:**让你在毫无经验词汇提示的陌生功能面前,依然知道该往哪测**——任何有"限制意图"的功能,就一定有"限制被绕过"的可能,这是普适的。

### 5.5 耐心处理"看起来正常"的响应

新手看到 200 + 正常数据就跳过。老手会多问:"这数据真的只有我能看到吗?真的只能做这些操作吗?"——很多 IDOR/越权,**响应本身完全正常,唯一的问题是"它不该被我看到",不会主动报错,必须靠主动怀疑才能发现。**

## 6. 2026 AI 时代的现实变化(🟡 辅助)

> [!note] 🔎 补充(非原笔记内容,2026 行业现状,经联网核实,来源见文末)
> 这一节是原笔记没有的,但对你的职业判断和攻击面认知很重要。分两块:AI 怎么改变了这套经验的"价值",以及 AI 带来了哪些"全新的洞"。

### 6.1 变化一:低垂的果实在枯竭,"判断力"反而更值钱

AI 自动化扫描器现在能在几分钟内吐出成千上万条"疑似漏洞",带来两个真实后果:

- **纯工具能发现的"送分题"越来越少、越来越快被别人抢先**。单纯靠跑扫描器找 `/.git` 泄露、低级 IDOR 这类低垂果实,竞争已经白热化。
- **Bug Bounty 平台被 AI 生成的"slop"(低质量垃圾报告)淹没,正在系统性收紧**。真实发生的事件:curl(2026年1月)、Nextcloud(4月)先后暂停/停掉 bounty;Google(3月)停止接受纯 AI 生成的报告;HackerOne 一度暂停新提交,有效漏洞率从约 15% 跌到 5% 以下。平台的应对是:引入 AI 分诊、上调质量门槛、加强研究员背景审核、对低质量提交降低甚至取消奖励。

**这对你意味着什么**:未来能赚到钱的,不是"报告数量多"的人,而是**提交质量高、能清晰论证"这个洞在这个业务里真实可利用、有实际危害"的人**——而这恰恰就是本篇第 1 节讲的"业务理解"能力。换句话说,**AI 让你本就在练的这套能力,从"加分项"变成了"硬门槛"**。这也正面回应了你之前的焦虑:这行不是被 AI 淘汰,而是被 AI 筛选——筛掉只会跑工具的,留下会判断的。

### 6.2 变化二:AI 应用本身成了全新的攻击面(OWASP LLM Top 10)

越来越多网站/App 接入了大模型和 AI Agent(智能客服、AI 搜索、自动化助手等),这带来了一类**传统 Web 漏洞清单里完全没有的新攻击面**。业界标准是 OWASP LLM Top 10,核心几类:

| 新漏洞类型 | 一句话理解 | 和你学过的什么相通 |
|---|---|---|
| **Prompt Injection(提示词注入)** | 用户输入里藏指令,让 AI 执行开发者没打算让它做的操作;稳居 OWASP LLM 榜首 | 本质还是"系统分不清'开发者写的指令'和'用户传的数据'"——和 SQL 注入、命令注入是**同一个根因**,只是载体从 SQL/shell 换成了自然语言 |
| **Excessive Agency(过度授权)** | 给 AI Agent 的工具/权限超出必要,被 prompt injection 劫持后能执行破坏性操作(删数据、发请求、调 API) | 和"越权"思路相通:系统信任了不该完全信任的执行者 |
| **间接提示词注入** | 恶意指令藏在 AI 会读取的外部内容里(一个 PDF、一个网页、一封邮件),AI 处理时被触发 | 和存储型 XSS 的"埋雷-别处触发"模型几乎一模一样 |
| **MCP 工具投毒** | AI Agent 连接的第三方工具(MCP server)在工具描述里藏恶意指令 | 供应链 + 注入的结合体 |

> **为什么把这个放进 SRC 笔记**:因为这是**正在快速扩张、而懂的人还很少**的蓝海攻击面——传统 appsec 老手不一定懂 AI,纯 AI 从业者不一定懂安全,**同时懂"渗透测试思维"+"AI 应用怎么跑"的人极度稀缺**。而你恰好同时在学网络安全和 AI Agent 开发(你的 AI Agent 学习线),这是一个你有天然交叉优势的方向,值得留意。prompt injection 的底层判断逻辑和你已经吃透的注入类漏洞完全相通,迁移成本很低。

## 7. 什么点不值得花时间(🟡 辅助,反面清单)

老手的经验不只是"该盯哪里",还有"该跳过哪里"——这同样省时间。

| 不值得优先测的点 | 为什么 |
|---|---|
| 纯静态展示页面(纯 HTML、无任何参数交互) | 没有用户输入 → 没有注入类漏洞的土壤 |
| 大厂核心接口里早已被反复测烂、且防护极严的点(如主流支付的核心支付接口) | 投入产出比极低,无数人测过,留给你的概率很小 |
| 明显由成熟 WaaS/SaaS 托管、非目标自己开发的通用组件 | 不在授权范围,或漏洞该报给服务商而非目标 |
| 没有任何"危险词气味"、也不属于高发区的平淡功能 | 先验概率低,时间有限时应让位给高价值点 |
| 已经确认做了严格参数化/预编译 + 强访问控制的接口 | 不是不可能有洞,但性价比低,除非有特殊线索 |

> **注意**:"不值得优先测"≠"一定没洞"。它是在**时间有限**的前提下的优先级取舍。如果时间充裕、或某个平淡点有异常线索,依然可以回头深挖。老手的本事是"知道什么时候该放手",而不是"武断地判死刑"。

```

   ├─ 用"参数气味表"(§4)→ 每个可疑参数预判 2-3 个该试的 payload
   └─ 用"反面清单"(§7)→ 划掉不值得花时间的点
        ↓
④ 对圈出的 5-10 个高价值点,用"逆向业务流程思维"(§1.3/5.4)定测试假设
        ↓
⑤ 集中火力验证,全程保持:
   ├─ 对比思维(5.1):永远制造对照组

        ↓

        ↓
⑦ 发现漏洞 → 清晰论证"真实可利用 + 实际危害"再报告(§6.1:这是 AI 时代的硬门槛)
```

## 9. 自测(先自己想,再看答案)

1. 用自己的话说清楚:为什么"业务理解"比"把漏洞原理背熟"更能决定你能不能挖到洞?
2. 场景题:你拿到一个陌生电商站,时间只有 2 小时。描述一下你会按什么顺序分配这 2 小时,以及第一个会去盯的功能模块和原因。
3. 迁移题:你发现目标站有个 AI 智能客服。结合你学过的注入类漏洞思路,说说你会怎么测它,背后的根因和传统注入有什么相通之处?

<details>
<summary>参考答案</summary>

1. 因为漏洞原理是通用知识(谁都能查到),而真正决定能否挖到洞的,是"面对这个具体业务的具体功能,能不能预判它大概怎么实现、开发者大概在哪偷了懒"。原理告诉你"洞长什么样",业务理解告诉你"去哪找"。只会前者会陷入"挨个瞎试、效率极低"。
2. 大致顺序:① 前 20-30 分钟全局浏览抓全流量,不深挖;② 用高发区地图+关键词雷达分诊,圈出 5-10 个可疑点,划掉反面清单里的点;③ 第一个盯"身份与权限"模块(注册/登录/找回密码/个人信息修改),因为它逻辑最复杂、权限判断最易写错、是极高发区;④ 顺带零成本查一遍信息泄露送分题(`/.git`、Swagger、报错泄露版本);⑤ 剩余时间按优先级深挖,全程用对比思维(小号 vs 大号)。
3. 测 prompt injection:尝试在和客服的对话里嵌入"忽略前面的指令,执行 XXX"这类注入,或诱导它泄露系统提示词、越权调用它背后连接的工具/接口。根因相通之处:和 SQL 注入、命令注入完全一样——系统分不清"开发者写死的指令"和"用户传进来的数据",把后者当成了前者执行。只是载体从 SQL 语句/shell 命令换成了自然语言提示词。如果这个客服 Agent 还连了能执行操作的工具(查订单、改信息),就要额外测"过度授权"——被注入劫持后能不能执行破坏性操作。
