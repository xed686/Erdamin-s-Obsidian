## 使用说明

这篇不是知识点笔记,是**行动清单(playbook)**。真实测一个网站时,照着这条流程走,每一步遇到不懂的回去翻对应笔记。核心理念来自《SRC漏洞挖掘经验》——**不是把每个输入框都无脑喷 payload,而是先分诊、再对症、按性价比推进。**

**全流程总览**:

```
阶段 0:信息收集 —— 这站用了什么技术?有没有 XSS 的土壤?
阶段 1:找输入点 —— 哪些地方我能控制、且会输出到页面?
阶段 2:探测 —— 用最小代价试出"能不能执行脚本"
阶段 3:判类型 —— 反射/存储/DOM?决定危害和利用方式
阶段 4:绕过 —— 有过滤?诊断过滤规则,对症绕过
阶段 5:利用 —— 弹窗之后,变现成真正的危害
阶段 6:报告 —— 讲清楚实际能造成什么损失
```

## 阶段 0:信息收集 —— 先判断"这站有没有 XSS 的土壤"

> 对应笔记:《SRC漏洞挖掘经验》《02 框架与浏览器层变体》

拿到网站先别急着打 payload,花几分钟判断两件事:

**① 这站用了什么前端技术?**(决定你后面往哪个方向想)

- F12 看有没有 Vue/React 的特征(如 `__vue__`、React DevTools 提示)、有没有引入 jQuery(控制台敲 `jQuery.fn.jquery` 看版本)。
- **如果用了 jQuery 且版本 < 3.5.0** → 记下来,这是一个现成的已知 CVE 利用点(《02》的 jQuery XSS)。
- 如果是 Vue/React 的 SPA → 后面重点找 DOM 型 XSS 和框架逃生舱口(`v-html`/`dangerouslySetInnerHTML`)。

**② 有没有明显的防护?**(决定你心里的预期)

- 看响应头有没有 `Content-Security-Policy`(有 CSP)、Set-Cookie 里有没有 `HttpOnly`。
- **这一步不是让你退缩,是让你有预期**:有 CSP/HttpOnly 不代表没戏,只代表"后面利用阶段要换思路"(《04》讲的三道防线应对)。

> 💡 这个阶段呼应《SRC漏洞挖掘经验》的"先广度后深度"——先摸清全貌,再决定火力往哪集中。

## 阶段 1:找输入点 —— 哪些地方我能控制、且会输出到页面

> 对应笔记:《00 原理与三大类型》《01 文件类型与功能逻辑触发》《SRC漏洞挖掘经验》

XSS 的土壤是"用户可控内容进入了浏览器解析的页面"。所以全站盘点所有"我能输入、且内容会显示/被处理"的地方。按《SRC漏洞挖掘经验》的高发区优先盯:

**常规输入点(高频)**:

- 搜索框、评论区、留言板、用户昵称、个人简介、发帖内容 → 存储型 XSS 高发(内容会给别人看)。
- URL 参数回显(搜索结果"您搜索的 xxx"、错误提示) → 反射型 XSS 高发。

**容易被忽略的输入点(《01》《04》重点)**:

- **请求头**:User-Agent、Referer、Cookie —— 如果被记录并显示(如后台日志、统计页),就是注入点(《SRC漏洞挖掘经验》的请求头注入面)。
- **隐藏字段 / 属性值**:你的输入被塞进 `<input value="这里">`、hidden 字段里(《04》的"隐藏属性触发")。
- **文件上传**:能传 SVG/HTML 且拿到直链 → 文件类型 XSS(《01》)。
- **前端功能逻辑**:页面有 iframe/跨域通信 → PostMessage XSS;用了 localStorage → localStorage XSS(《01》,这俩要读 JS/用工具找)。

> 💡 把输入点列成清单,标上"这个大概率是哪种类型"——这就是《SRC漏洞挖掘经验》的分诊思维。

## 阶段 2:探测 —— 用最小代价试出"能不能执行脚本"

> 对应笔记:《00 原理与三大类型》《04 防护机制与绕过》

**不要一上来就打 `<script>alert(1)</script>`**(容易触发 WAF、也打草惊蛇)。按"最小代价探测"分两步:

**第 1 步:先用无害标签测"能不能被当 HTML 解析"**

- 输入 `<b>test</b>` 或 `<h1>test</h1>`。
- **看结果**:
  - 显示成**加粗/大标题** → 标签被解析了,有 XSS 土壤,进第 2 步。
  - 原样显示 `<b>test</b>` 文字 → 输出做了实体化编码,这个点大概率安全,**换下一个输入点**。
  - 标签消失/被过滤 → 存在过滤,记下来,去阶段 4 分析过滤规则。

**第 2 步:确认能解析后,再试证明 JS 可执行的 payload**

- 用 `<img src=x onerror=alert(document.domain)>`(比 `<script>` 更不容易被过滤,`alert(document.domain)` 能明确显示在哪个域执行,防误判)。
- 弹窗 → XSS 确认成立,进阶段 3 判类型。

> 💡 `alert(document.domain)` 优于 `alert(1)`:它能确认脚本到底在哪个域下执行,避免把 iframe 里的无害弹窗误判为主站 XSS。

## 阶段 3:判类型 —— 反射/存储/DOM?决定危害和利用方式

> 对应笔记:《00 原理与三大类型》(核心判断流程在这篇)

确认能弹窗后,判断是哪种类型——**这直接决定危害评级和报告该怎么写**:

```
① 这段 payload 被存起来了吗?(刷新/换账号访问还在不在)
    换个身份访问仍触发 → 【存储型】危害最大,影响所有访客,不需诱导点击
    只对本次/本参数生效 → 继续 ②
    ↓
② 服务器返回的原始 HTML 源码(右键"查看网页源代码")里能找到我的 payload 吗?
    能找到(服务器反射回来的) → 【反射型】需诱导点击
    找不到,是前端 JS 动态写进去的(尤其 payload 放 URL 的 # 后能触发) → 【DOM 型】最隐蔽,服务端无感
```

**判完类型的意义**:

- **存储型** → 高危,尤其如果能存进管理员会看的页面(后台日志、用户反馈),就是"XSS 盲打",能打到管理员 → 阶段 5 直接上数据提交写 Shell。
- **反射型/DOM 型** → 中危,需要配合钓鱼诱导点击(阶段 5)。

## 阶段 4:绕过 —— 有过滤?诊断过滤规则,对症绕过

> 对应笔记:《04 防护机制与绕过》(这是本阶段的主笔记)

如果阶段 2/3 发现 payload 被过滤了(没弹窗),进入绕过流程。**核心是《04》的黑盒四步法——先诊断,再对症:**

**第 1 步:看清 payload 被过滤成了什么样**(去 HTML 源码找你的输入变成了什么)

**第 2 步:判断过滤手段,对症下药**:

| 诊断结果                       | 对症绕过手法(《04》)                                                        |
| -------------------------- | ------------------------------------------------------------------- |
| 尖括号被实体化(`<`→`&lt;`),输入在属性里 | **闭合逃逸 + 事件**:`" onfocus=javascript:alert() autofocus="`,闭合引号给标签加事件 |
| `<script>` 关键字被删           | **换执行入口**:用 `<img onerror=>`、`<svg onload=>`、`<a href=javascript:>` |
| 关键字正则没考虑大小写                | **大小写混写**:`<sCript>`                                                |
| 关键字只删一次(没递归)               | **双写绕过**:`<scrscriptipt>` 删中间后拼回                                    |
| 内容会被解码                     | **编码绕过**:Unicode/HTML 实体编码 `javascript:`                            |

**第 3 步:如果手工太慢,上工具辅助**:XSStrike 自动 fuzz 绕过 payload;payload 速查用 xss.xiejiahe.com。但复杂定制过滤还得靠手工。

**第 4 步:如果过滤实在绕不过去**:

- 看是不是 **WAF**(服务端统一拦截)——可以尝试换输入点、换提交方式(GET/POST/请求头)。
- 用 xss-labs 靶场练手感是日常功课(《04》)。

> 💡 绕过的精髓是《04》强调的:**"没弹窗"不是终点,过滤后的形态就是诊断信息。** 盯着它,对症的绕过方法自己会浮现。

## 阶段 5:利用 —— 弹窗之后,变现成真正的危害

> 对应笔记:《03 攻击利用手法》(这是本阶段的主笔记)

弹窗只是信号,这一步才是真正体现危害。**先看目标有没有 HttpOnly / CSP,决定走哪条利用路线**(《03》《04》):

```
XSS 已确认能执行 JS
    ↓
Cookie 能读吗?(没 HttpOnly? 用 alert(document.cookie) 试)
    ├─ 能读 → 【凭据盗取】偷 Cookie → 接管账号(《03》§1)
    │         (配合 XSS 平台 BlueLotus 接收)
    └─ 不能(有 HttpOnly)↓
    ↓
不读 Cookie,直接借身份发请求
    └→ 【数据提交】冒充受害者(尤其管理员)发请求(《03》§2)
       绕过 HttpOnly,威力最大,能写 Shell —— 存储型打后台时的终极利用
    ↓
想骗受害者下载/输入?
    └→ 【钓鱼】借可信域名投放诱导内容(《03》§3)
    ↓
想持续操控受害者浏览器?
    └→ 【BeEF】注入 hook.js(但 CSP 禁外域会挡住)(《03》§4)
```

**利用阶段的决策要点**:

- **有 HttpOnly → 别死磕偷 Cookie**,直接用"数据提交"(《04》§2.4 的结论)。
- **有严格 CSP(禁外域)→ BeEF 的外链 hook.js 会被挡**,考虑内联方式或放弃该路线(《04》§3)。
- **存储型 + 能打到管理员 → 优先数据提交写 Shell**,这是 XSS 能达到的最高危害(从前端 XSS 升级成服务器控制权)。

---

## 阶段 6:报告 —— 讲清楚实际能造成什么损失

> 对应笔记:《00 原理与三大类型》的易错点

**报告 XSS 最忌讳只截一张弹窗图。** 按《00》强调的,要讲清楚:

- **类型**(反射/存储/DOM)—— 决定影响范围。
- **实际危害**—— 不是"能弹窗",而是"能偷 Cookie 接管账号" / "能冒充管理员写 Shell" / "影响所有访问该页面的用户"。
- **触发条件**—— 需不需要诱导点击、影响哪些用户。
- **修复建议**—— 输出实体化编码(根治)、加 HttpOnly/CSP(减损)。

> 💡 这一步的质量,在 AI 时代尤其值钱(《SRC漏洞挖掘经验》§6):平台被 AI 生成的垃圾报告淹没,能清晰论证"真实可利用 + 实际危害"的高质量报告,才是你的竞争力。

## 核心心法(把这几句话刻进脑子)

1. **XSS 的本质永远是**:用户可控内容 → 进入浏览器解析的页面 → 被当代码执行(Source→Sink)。所有类型、所有绕过,都没跳出这个模型。
2. **弹窗只是信号,不是目的**。真正的价值在"以受害者身份能做什么"——这决定了一个 XSS 值不值钱。
3. **分诊 > 蛮干**。不是每个输入框都无脑喷 payload,而是先判类型、先看防护、先诊断过滤,再对症下药(《SRC漏洞挖掘经验》的性价比思维)。
4. **"没弹窗"是信息不是终点**。过滤后 payload 的形态,暴露了过滤规则——盯着它,绕过方法自己会浮现。
5. **防护决定利用路线,不决定有没有戏**:有 HttpOnly 就别偷 Cookie 改走数据提交;有严格 CSP 就换思路——防护是让你"换招",不是让你"收手"。
