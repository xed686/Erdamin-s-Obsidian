## 1. 文件类型触发 XSS 的共同逻辑(先建立总纲)

### 1.1 它是什么

指攻击者不是直接在输入框里打 payload,而是把恶意 JS **藏进一个文件里**(SVG、PDF、SWF、HTML 等),通过网站的"文件上传"功能把它传上去,拿到这个文件的访问直链,再诱导受害者(或自己)去访问这个链接,文件被浏览器"解析"时触发其中的脚本。

> 类比:普通 XSS 像是你当面对服务员说一句暗语;文件类型 XSS 则像是你把暗语写进一张看似正常的"图片/文档"里交上去,等别人打开这份文件时暗语才被念出来。

### 1.2 为什么会存在(root cause)

两个条件叠加才成立:
1. **网站允许上传这类文件,且上传后能通过一个 URL 直接访问到原始文件**(而不是被转码/压缩/剥离成纯图片)。
2. **浏览器在访问这个文件时,会把它当成"可执行脚本的文档"来解析**,而不是当成纯静态资源。

关键在第 2 点——**SVG/HTML 本质上是"可以包含脚本的文档格式"**(SVG 是 XML,HTML 就是网页),浏览器直接访问它们时会执行里面的 `<script>`。这和 jpg/png 这种"纯图像数据"完全不同,后者浏览器只会画出图像,不会执行任何代码。

> [!note] 🔎 补充(非原笔记内容)
> 这里有个关键的实战前提,原笔记用一句"浏览器格式解析问题会导致失效"带过了,展开说清楚:**能不能触发,取决于服务器返回这个文件时的 `Content-Type` 响应头**。如果服务器给 SVG 文件返回的是 `Content-Type: image/svg+xml`,浏览器会把它当文档渲染、执行脚本 → 成立;但如果服务器强制返回 `Content-Type: image/png` 或者 `application/octet-stream`(当作下载),浏览器就不会执行脚本 → 失效。所以测这类 XSS 时,**必须用抓包工具看访问文件时服务器实际返回的 `Content-Type` 是什么**,这才是判断"能不能触发"的决定性因素,而不是文件后缀本身。

### 1.3 从文件上传到 XSS 的转换思路(红队玩法)

这是本篇最有实战价值的一句话——**把一个"文件上传"功能,转化成一个"XSS"利用点**:
1. 找到一个允许上传、且上传后能拿到原始文件直链的功能。
2. 上传一个内嵌恶意 JS 的 SVG/HTML 文件。
3. 拿到直链,配合钓鱼(把链接发给目标)诱导访问触发。

> 红队视角:这比传统 XSS 更隐蔽——因为"上传一张图片"是极其正常的操作,防御方很难对一个图片上传功能产生警觉,而一旦上传的 SVG 能执行脚本,就等于拿到了一个挂在"可信域名"下的 XSS 投递点。

## 2. SVG-XSS(🔴 核心)

### 2.1 它是什么

SVG(Scalable Vector Graphics,可缩放矢量图形)是一种**基于 XML 的二维矢量图格式**。和 jpg/png 不同:放大/缩放不失真、可以用任何文本编辑器打开编辑、主流浏览器都支持渲染。**关键是——因为它是 XML 文档,所以它内部可以合法地包含 `<script>` 标签。**

### 2.2 怎么做(payload 拆解)

```xml
<svg xmlns="http://www.w3.org/2000/svg" version="1.1">
   <circle cx="100" cy="50" r="40" stroke="black" stroke-width="2" fill="red" />
   <script>alert(1)</script>
</svg>
```

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `<svg xmlns="...">` | 声明这是一个 SVG 文档 | 让浏览器按 SVG(XML)格式解析它 |
| `<circle ... fill="red" />` | 画一个红色圆圈 | 让文件"看起来像一张正常的图",降低警觉(可选,纯伪装) |
| `<script>alert(1)</script>` | 真正的恶意脚本 | 浏览器渲染这个 SVG 文档时,会把它当脚本执行——这就是 XSS 触发点 |

### 2.3 实战怎么用

- **什么时候该想到它**:任何允许上传 SVG(或允许上传"图片"但没严格限制格式,能混进 SVG)的功能——头像上传、图片上传、富文本编辑器插图等。
- **怎么验证**:上传上面这个 SVG,拿到直链后在浏览器访问,看是否弹窗。**同时抓包确认服务器返回的 `Content-Type`**(见 1.2 补充)——这是成败关键。
- **怎么判断结果**:访问直链弹窗 = 成立。注意要"直接访问 SVG 文件的 URL",如果 SVG 是作为 `<img src=xxx.svg>` 被嵌进别的页面显示,很多情况下脚本不会执行(作为 img 加载的 SVG 受限),这是常见误判点。
- **下一步**:成立后配合钓鱼投递直链,或寻找该 SVG 会被"当文档渲染"给其他用户看的场景(升级成存储型,影响所有访问者)。

### 2.4 防御与检测视角

防御方应对上传的 SVG 做处理:要么服务端用过滤库(如 DOMPurify 的 SVG 模式)剥离其中的 `<script>` 和事件属性,要么强制以 `Content-Type: application/octet-stream`(下载)或转码成位图(png)后再存储,从根上让浏览器不去执行它。

### 2.5 易错点

- **误区:以为"文件后缀是 .svg、上传成功了"就等于能 XSS。** 真正决定成败的是访问时服务器返回的 `Content-Type`,以及是"直接访问"还是"作为 img 嵌入"。必须抓包验证,不能只看上传结果。

## 3. PDF-XSS(🟡 辅助)

### 3.1 它是什么

PDF 格式支持内嵌 JavaScript(本是为了做表单交互、动态内容)。如果网站允许上传 PDF 并能直接访问,一个内嵌了恶意 JS 的 PDF 被浏览器的 PDF 阅读器打开时,可能触发脚本。

### 3.2 怎么做(流程)

1. 用 PDF 编辑器(课程用的是"迅捷 PDF 编辑器试用版")创建一个 PDF,在里面加入动作 JS。
2. 通过文件上传功能上传,获取文件直链。
3. 访问直链,PDF 被打开时触发其中的 JS。

### 3.3 实战怎么用 / 易错点

- 相关度中等:现代浏览器内置的 PDF 阅读器对 PDF 内 JS 的执行限制越来越严,很多场景下已经打不动,实战成功率不如 SVG。了解其"内嵌 JS + 上传直链触发"的思路即可,遇到允许上传 PDF 的点可以一试,但不必作为主攻方向。

## 4. SWF(Flash)-XSS(⚪ 了解)

> [!warning] ⏳ 时效性提示
> **Adobe Flash 已于 2020 年 12 月 31 日正式停止支持,主流浏览器全部移除了 Flash 支持。** 这一节的技术在今天的实战中几乎遇不到,仅在审计极老旧的遗留系统时可能碰到。这里按"了解"级别保留,不建议投入时间深学,但理解它的原理对理解"跨技术边界调用 JS"的思路有帮助。

### 4.1 为什么 Flash 会有 XSS

XSS 的定义是"执行恶意 JS",而 Flash 之所以也能 XSS,是因为 **Flash 提供了一批可以调用/与 JS 通信的函数**。这些函数如果使用不当(参数可控),就能被用来执行任意 JS。常见的危险函数:`getURL`、`navigateToURL`、`ExternalInterface.call`、`htmlText`、`loadMovie` 等。

### 4.2 两种玩法(了解)

**制作恶意 SWF**(用 Adobe Flash Professional CS6):新建 swf → 代码区写 `var m=_root.m; flash.external.ExternalInterface.call(m);`(取 URL 参数 m,直接丢给 JS 执行)→ 发布 → 访问时 `?m=alert(/xss/)` 触发。

**审计已有 SWF**(用 JPEXS Free Flash Decompiler):① 反编译 swf → ② 查找上面那些危险函数 → ③ 找可控参数访问触发。对应两个利用场景:上传 swf 做 XSS、或反编译目标站已有的 swf 找 XSS。

## 5. HTML-XSS / 其他格式(🟡 辅助)

最直接的一种:如果网站允许上传 `.html` 文件并能直接访问,那你上传的 HTML 里写什么 `<script>` 都会被执行——因为 HTML 本来就是网页,浏览器天经地义地执行它。其他可扩展到 XML 等任何"浏览器会当文档解析"的格式。这类的防御核心同样是:不允许直接访问用户上传的 HTML/XML,或强制当附件下载。

## 6. 功能逻辑触发 XSS 总纲

从这里开始,触发载体从"文件"换成了"前端的功能逻辑"——恶意 JS 不再藏在上传的文件里,而是利用页面自身 JavaScript 处理数据的缺陷来触发。**这一大类本质上都属于 DOM 型 XSS 的变体**(都在前端 JS 环节出问题),同样是 Source→Sink 模型,只是 Source 变成了"跨窗口消息""浏览器本地存储"这些不太显眼的地方。

## 7. PostMessage-XSS(🔴 核心)

### 7.1 它是什么

`postMessage` 是一个浏览器 API,**用于在不同窗口之间安全地发送消息**(比如同域的不同页面、或跨域的两个页面,常见于嵌入 iframe、第三方登录弹窗、复杂单页应用),让它们无需经过服务器就能通信。

它本身是为"安全通信"设计的,但**如果发送方的消息内容可控,而接收方处理消息时不做校验、直接把消息内容当代码/URL 使用,就会导致 XSS**。

### 7.2 为什么会存在(root cause + 案例源码拆解)

课程给的模拟场景源码:
```javascript
// 接收方页面 xssreceive.html
window.addEventListener("message", (event) => {
    location.href = `${event.data.url}`;
});
```

逐句翻译这段有漏洞的代码:
- `window.addEventListener("message", ...)`:这个页面注册了一个"消息监听器",任何其他窗口通过 `postMessage` 发来的消息,都会进到这个回调里。
- `location.href = \`${event.data.url}\``:**问题就在这里**——它直接把收到的消息里的 `url` 字段,赋值给了 `location.href`(页面跳转地址)。

**root cause 有两层**:
1. **没校验消息来源**:`event` 对象里有一个 `event.origin` 字段,能告诉你"这条消息是从哪个域名发来的"。安全的写法应该先判断 `event.origin` 是不是自己信任的来源,再处理。这段代码完全没判断,意味着**任何一个网站都能给这个页面发消息并让它跳转**。
2. **没校验消息内容**:直接把 `event.data.url` 当跳转地址用。攻击者可以把 `url` 设成 `javascript:alert(1)` 这类伪协议——`location.href = "javascript:alert(1)"` 会直接执行其中的 JS,从而触发 XSS(这也是开放重定向和 XSS 的结合点)。

对应到 Source→Sink:**Source = `postMessage` 发来的 `event.data`(攻击者可控),Sink = `location.href`**,中间没有任何校验。

### 7.3 怎么做(黑盒 / 白盒挖掘)

**黑盒挖掘**:这类漏洞"藏得很深"——因为消息监听是在后台静默注册的,页面上看不出任何痕迹。推荐一个国外白帽写的 Chrome 插件 **postMessage-tracker**(https://github.com/fransr/postMessage-tracker):装上之后,只要当前页面注册了 `message` 事件监听,插件就会自动定位到对应的代码,帮你快速发现"这个页面在偷偷监听跨窗口消息"。

**白盒挖掘**:在源码里搜索关键字——`addEventListener("message"`、`onmessage`、`event.data` 等,找到监听逻辑后,重点看它有没有校验 `event.origin`、以及它把 `event.data` 用在了哪里(是不是流进了 `location.href`/`innerHTML`/`eval` 这类 Sink)。

### 7.4 实战怎么用 / 易错点

- **什么时候该想到它**:页面里有 iframe 嵌套、第三方登录弹窗、跨域组件通信等场景时,优先用 postMessage-tracker 插件扫一遍。
- **易错点**:这类漏洞不会出现在常规的参数里,只能靠工具/读代码发现,纯靠手动点页面、改 URL 参数是测不出来的——这也是它"值钱"的原因(会的人少)。

## 8. localStorage-XSS(🔴 核心,存储型的"前端升级版")

### 8.1 它是什么

`localStorage` 是浏览器提供的本地存储,允许网页在**用户浏览器本地**存储键值对数据,这些数据浏览器关闭后仍然保留,且在同一域名下的不同页面之间共享。

当应用从 localStorage 读取数据并显示到页面上时,**如果没对数据做充分过滤,攻击者就能通过修改 localStorage 里的数据来注入恶意脚本**,实现 XSS。

### 8.2 为什么叫"存储型的前端升级版"(root cause)

和传统存储型 XSS 对比理解:
- 传统存储型:恶意数据存在**服务器数据库**里,服务器输出时没过滤。
- localStorage 型:恶意数据存在**用户浏览器本地**,前端 JS 读取并输出时没过滤。

两者的"存储-读取-未过滤输出"模型完全一样,只是存储位置从服务端换到了客户端。它本质仍是 DOM 型(问题在前端 JS),但因为数据有"持久化"的特性(关浏览器还在),所以兼具存储型的某些特征。

对应 Source→Sink:**Source = localStorage 里被读出来的值,Sink = 把这个值输出到页面的地方**(如 `innerHTML`)。

**场景 A:配合另一个漏洞当"二段火箭"**  
假设这个网站还有一个**反射型 XSS**(比如 URL 参数能执行 JS)。攻击者给你发一个恶意链接,你一点,那个反射型 XSS 执行了一段 JS——这段 JS 做的事就是:`localStorage.setItem('key', '<img onerror=坏代码>')`,悄悄往**你自己的 localStorage** 里塞了 payload。

然后呢?反射型 XSS 是"用完即走"的,刷新就没了。但它刚才往 localStorage 里写的东西**留下来了**。之后你每次正常打开这个网站,页面的 JS 都会去读 localStorage 并渲染——于是那个 payload **每次都触发**。

**看出精妙之处了吗**:攻击者用一个"一次性"的反射型 XSS,借助 localStorage 把它**升级成了"持久化"的攻击**——这正是笔记里叫它"存储型的前端升级版"的原因。你中招一次,之后天天中招,直到你清掉浏览器数据。

**场景 B:多个页面/子域共享 localStorage**  
localStorage 是"同源共享"的——`a.example.com/page1` 写进去的,`a.example.com/page2` 能读到。如果攻击者能在**某一个页面**控制写入(比如那个页面有个弱一点的注入点),写进去的 payload 就会在**同源的另一个页面**被读取触发。你以为"写入页"和"触发页"是两个功能,其实它们共享同一个 localStorage。

**场景 C:物理接触 / 共享设备**  
网吧、公司公用电脑等场景,攻击者先在这台机器上往某网站的 localStorage 埋好 payload,下一个用这台电脑登录该网站的人就中招。

**所以一句话纠正你的直觉**:不是"localStorage 能被别人读到"(它不能),而是"**攻击者有办法控制你自己浏览器里的 localStorage 内容**",然后利用"页面会自动读取并渲染 localStorage"这个逻辑,让 payload 在**你自己的浏览器**里反复触发。受害者确实是你自己,但"下毒的人"是攻击者。
### 8.3 怎么做(黑盒 / 白盒挖掘)

**挖掘的核心是两步**(原笔记问的"怎么找"):
1. **先找"能被控制的键名/键值"**:怎么找——观察页面有哪些输入点(表单、搜索框、评论区等)的内容会被写进 localStorage(可以在 F12 → Application → Local Storage 面板实时看哪些 key 在变化),确认哪个 key 的值是你能影响的。
2. **再找"对这些键名/键值做输出操作的地方"**:怎么找——白盒下在代码里搜 `localStorage.getItem`,看读出来的值流向了哪个 Sink;黑盒下手动在 F12 的 Application 面板里直接修改某个 localStorage 的值为 payload,再刷新/操作页面,看会不会触发。

**黑盒挖掘**:找输入点构造测试用例,配合在 Application 面板手动改 localStorage 值测试。
**白盒挖掘**:查找与 localStorage 相关的代码段(`setItem`/`getItem`),分析数据存储和读取链路。

### 8.4 实战怎么用 / 易错点

- **什么时候该想到它**:现代前端框架(Vue/React)的 SPA 大量使用 localStorage 存用户状态、草稿、配置,是这类 XSS 的高发地。
- **易错点**:别忘了可以**直接在 F12 的 Application 面板里手动篡改 localStorage 的值**来测试——很多人只盯着输入框,忽略了攻击者在已经能执行一点 JS、或物理接触浏览器的场景下,可以直接改本地存储。

## 10. 把它串起来:触发载体 → 本质类型 → 挖掘方式

```
看到一个"可能触发 XSS"的点,先判断它属于哪类载体:

【文件类载体】有文件上传功能?
    ├─ 能传 SVG/HTML 且能拿到直链 → 上传内嵌 <script> 的文件 → 抓包确认 Content-Type → 访问触发
    ├─ 能传 PDF → 内嵌 JS 试(成功率较低)
    └─ 遇到 SWF → 基本是遗留系统,了解即可

【功能逻辑类载体】(本质都是 DOM 型,需读代码/用工具)
    ├─ 页面有 iframe/跨域通信 → 用 postMessage-tracker 插件扫 message 监听 → 查 origin/data 校验
    └─ SPA/用了本地存储 → F12 Application 面板看 localStorage → 找可控 key + 输出 Sink

共同底层:全部回到 Source→Sink —— 用户可控的内容(文件/消息/本地存储),
          最终流进了会把它当代码执行的位置,中间没有过滤。
```

## 11. 自测(先自己想,再看答案)

1. 为什么上传一个内嵌 `<script>` 的 SVG 能 XSS,但上传一个同样内嵌脚本的 jpg 却不行?决定 SVG 能否真正触发的关键因素是什么?
2. 看这段代码,指出漏洞在哪、root cause 是什么:`window.addEventListener("message", e => { document.getElementById("box").innerHTML = e.data; })`
3. 为什么说 PostMessage-XSS 和 localStorage-XSS"本质上都是 DOM 型"?它们和传统反射/存储型最大的区别是什么?

<details>
<summary>参考答案</summary>

1. 因为 SVG 是基于 XML 的"文档"格式,浏览器渲染它时会执行里面的 `<script>`;而 jpg 是纯图像数据,浏览器只会解码画图,不会执行任何代码。决定 SVG 能否真正触发的关键,是**访问该文件时服务器返回的 `Content-Type`**(返回 `image/svg+xml` 当文档渲染才会执行脚本;若返回 png 类型或强制下载则不执行),以及是"直接访问 URL"还是"作为 `<img>` 嵌入"(后者通常受限不执行)。必须抓包确认。
2. 漏洞在 `innerHTML = e.data`——它把 postMessage 收到的消息内容直接写进了 innerHTML(会解析 HTML 的 Sink)。root cause 两层:① 没校验 `e.origin`,任何网站都能发消息;② 没过滤 `e.data` 内容,攻击者发一个 `<img src=x onerror=alert(1)>` 就能 XSS。Source(e.data)→ Sink(innerHTML)中间无校验。
3. 因为它们的问题都出在**前端 JavaScript 处理数据的环节**(读 postMessage 消息/读 localStorage,然后未过滤就输出),服务器可能全程不知情,这正是 DOM 型的定义。和传统反射/存储型最大的区别:反射/存储型的恶意数据要经过服务器(服务器输出时出问题),而这两类纯粹在浏览器端完成,服务端的 WAF/日志往往对它们无感,因此更隐蔽、也更难被常规扫描发现。

</details>
