## 困惑一:数据存在自己客户端,怎么影响到别人?

### 先肯定你的直觉:对,localStorage 只能影响自己

**localStorage 是"同源隔离 + 本地存储"的,别人的浏览器读不到你的 localStorage。** 这个理解完全正确。

### 关键转折:攻击目标从一开始就是"你自己",不是"别人"

"攻击自己有什么意义?"——意义在于:**能往你 localStorage 里写数据的,不一定是"你本人"**。攻击者有办法控制"你自己浏览器"里的 localStorage 内容,然后利用"页面会自动读取并渲染 localStorage"这个逻辑,让 payload 在你自己的浏览器里反复触发。下毒的是攻击者,中招的是你。

有三种现实场景:

### 场景 A:配合另一个漏洞当"二段火箭"(最经典)

假设网站还有一个**反射型 XSS**(URL 参数能执行 JS)。攻击链:
1. 攻击者发给你一个恶意链接,你点击 → 触发反射型 XSS。
2. 这段反射的 JS 做的事是:`localStorage.setItem('key', '<img src=x onerror=坏代码>')` —— 悄悄往**你自己的** localStorage 里塞了 payload。
3. 反射型 XSS 本身"用完即走",刷新就没了——**但它写进 localStorage 的东西留下来了**。
4. 之后你每次正常打开这个网站,页面 JS 都去读 localStorage 并渲染 → payload **每次都触发**,直到你清掉浏览器数据。

> **精妙之处**:攻击者用一个"一次性"的反射型 XSS,借 localStorage 把它**升级成了"持久化"攻击**——这就是它被叫作"存储型的前端升级版"的原因。

### 场景 B:同源多页面共享 localStorage(展开)

> 这是三个场景里最容易被忽略、但真实挖洞中**最高频、最值钱**的一种。核心是打破"一个页面的输入只会影响这个页面"这个新手直觉——**localStorage 同源共享,所以"在哪写"和"在哪触发"可以是两个不同的页面**。

**先搞清楚"同源"指什么(场景 B 的地基)**

localStorage 的共享范围由**同源策略**决定。**同源 = 协议 + 域名 + 端口,三者完全一样**才算同源,才共享同一份 localStorage:

| 页面 A | 页面 B | 同源?共享 localStorage? |
|---|---|---|
| `https://a.com/page1` | `https://a.com/page2` | ✅ 同源(只是路径不同) |
| `https://a.com/user/profile` | `https://a.com/admin/panel` | ✅ 同源 |
| `https://a.com` | `https://sub.a.com` | ❌ 不同源(子域名不同) |
| `https://a.com` | `http://a.com` | ❌ 不同源(协议不同) |
| `https://a.com:443` | `https://a.com:8080` | ❌ 不同源(端口不同) |

**划重点**:同一域名下、不同"路径"的页面(`/page1`、`/profile`、`/admin`)几乎都同源、共用一份 localStorage。一个网站几十上百个页面,大多共享同一个"储物柜"——这是场景 B 成立的基础。

**攻击模型:读写分离**

```
【写入点】页面 X                【触发点】页面 Y
攻击者在 X 找到一个能          Y 的 JS 有:
控制 localStorage 写入的点      xxx.innerHTML = localStorage.getItem('key')
       │                              │
       └──────► 同一份 localStorage ◄──────┘
                 (X 和 Y 同源)
```

关键洞察:X 和 Y 可能是**完全不相关的两个功能**,写代码的人根本没想到"我在这个页面存的数据,会在另一个页面被当 HTML 渲染"。这种**跨页面的数据流**,最容易出漏洞、也最难被发现。

**为什么这比"同一页面读写"危险得多——它能绕过单页面的防护**

举个具体推演:
- "个人设置"页(`/settings`)允许设置"个性签名",存进 localStorage 的 `signature` 键。这个页面**做了防护**——显示时用 `textContent`,所以在设置页本身打不出 XSS。
- 但"用户主页"页(`/profile`)也要显示这个签名,写它的是**另一个开发者**,图省事用了 `element.innerHTML = localStorage.getItem('signature')`,**没做任何过滤**。

攻击成立:你在 `/settings` 把签名设成 `<img src=x onerror=坏代码>`(设置页用 textContent,这里不触发,你也看不到异常)→ 存进 localStorage → 访问 `/profile` 时那个没防护的 `innerHTML` 把 payload 渲染出来 → **XSS 在 `/profile` 触发**。

**本质**:防护强度取决于"**最弱的那个读取点**"。哪怕 99 个页面都正确用了 `textContent`,只要有 1 个页面用 `innerHTML` 读同一份 localStorage,整条防线就破。而这种"跨页面的不一致"在多人协作的大项目里**极其常见**——没人能保证所有读取 localStorage 的地方都用了安全写法。

**实战挖掘启发:不要把"写入"和"触发"绑死在同一页面看**

1. **全站盘点读写点**:白盒下全局搜 `localStorage.setItem`(写入点)和 `localStorage.getItem`(读取点),列成两张清单。
2. **重点找"写入有防护、读取没防护"的同名 key**:同一个 key,某页面写入时过滤了,另一页面读取时直接 `innerHTML`——就是场景 B 的漏洞。
3. **关注"一处设置、多处显示"的功能对**:签名(设置页写/主页读)、草稿(编辑页写/预览页读)、搜索历史、购物车、用户偏好配置……都是高发区。
4. **黑盒验证**:在"写入页"把某值设成 payload,然后挨个访问其他会用到这份数据的页面,看哪个触发——触发的那个就是有漏洞的读取点。

### 场景 C:物理接触 / 共享设备

网吧、公司公用电脑等场景,攻击者先在这台机器上往某网站的 localStorage 埋好 payload,下一个用这台电脑登录该网站的人就中招。

### 这一困惑的正确结论

不是"localStorage 能被别人读到"(它不能),而是"**攻击者有办法控制你自己浏览器里的 localStorage 内容**",再利用页面自动读取渲染的逻辑让 payload 反复触发。受害者是你自己,下毒者是攻击者。

## 困惑二:它本质是 DOM 型,那我前端校验不就行了?

### 你的推理完全正确

localStorage-XSS 的漏洞点(读 localStorage → 塞进 `innerHTML`)**全程在前端 JS 里**,所以:
- **防御方修复就在前端**:把 `innerHTML` 换成 `textContent`(只当文字显示,不解析标签),或读出来后先用过滤库(如 DOMPurify)净化。**不需要动后端。**
- 这确实和反射型/存储型不同——那两类的防御责任在后端(服务器输出时做编码),而 DOM 型(包括 localStorage 型)的防御责任在前端。

**这个推理没有错,抓住了"DOM 型防御在前端"这个关键区别。**

## 困惑三:既然前端代码能看到,还分什么黑盒白盒?

### 这是唯一需要纠正的误解

误区在于把"黑盒"等同于"看不到代码 / 只能碰后端"。**其实不是。**

### 正确定义:黑盒 / 白盒,区分的不是"前端还是后端",而是"用什么角度找漏洞"

| | 白盒挖掘 | 黑盒挖掘 |
|---|---|---|
| 本质 | **读代码**,从代码逻辑里"看"出漏洞 | **发请求 / 试操作**,从外部行为"试"出漏洞 |
| 对应 localStorage 的做法 | 打开 Sources 面板,在 JS 里搜 `localStorage.getItem`,顺着数据流分析"读出来的值流向了哪个 Sink、中间有没有过滤" | 不读代码,直接在 F12 的 Application 面板**手动改** localStorage 的值为 payload(如 `<img src=x onerror=alert(1)>`),刷新页面看会不会弹窗 |
| 关键点 | 在分析**代码逻辑** | 在用**输入→观察输出**的方式试探 |

**两种方法都在"前端"操作,但一个是"读代码推理"(白盒),一个是"改值试探"(黑盒)。** 所以哪怕是纯前端的漏洞,一样分白盒黑盒。

### 为什么前端漏洞也要分这两种(互补关系)

- **黑盒更快**:不用读懂一大堆混淆过的 JS,直接改个值试试,成了就说明有洞,适合快速筛查。
- **白盒更准更全**:改值试探可能漏掉隐蔽的触发路径(比如某 payload 要特定格式才触发),读代码能完整看清"什么样的输入会流到 Sink",不会漏。
- **现实补充**:前端 JS 常被压缩混淆(见《前端加密与代码混淆笔记》),白盒读起来费劲,这时黑盒试探反而更高效——所以两种方法是**互补**,不是二选一。

## 三个困惑串起来总结

1. **localStorage 确实只影响自己** —— 但攻击者能通过别的漏洞(反射型 XSS 当二段火箭)、同源页面共享、或物理接触,控制"你自己浏览器"里的 localStorage,让 payload 在你自己浏览器反复触发,把一次性攻击变成持久化。受害者是你,下毒者是攻击者。
2. **它本质是 DOM 型,防御确实在前端** —— 这个推理对了,把 `innerHTML` 换成 `textContent` 或加过滤即可,不用动后端。
3. **黑盒白盒分的不是"前端后端",而是"读代码 vs 试操作"** —— 读 JS 追 Source→Sink 数据流是白盒,直接在 F12 的 Application 面板改 localStorage 值试探是黑盒,两者互补。
