## 0. 先看这张地图

本篇的所有变体,底层依然是 **Source→Sink + 用户内容被当代码执行**(前几篇反复讲过),但它们多了一个共同的新特征——**"安全责任"从应用开发者,部分转移到了框架/库/浏览器身上**。

| 知识点                            | 相关度   | 本质                            | 触发条件                                                    |
| ------------------------------ | ----- | ----------------------------- | ------------------------------------------------------- |
| 框架逃生舱口认知(Vue/React 的危险 API) | 🟡 重要 | 开发者主动用了框架的"危险 API"绕过了框架自带的防护  | 用了 `v-html` / `dangerouslySetInnerHTML` / `innerHTML` 等 |
| Electron XSS → RCE 的危害质变 | 🟢 了解 | 同样的 innerHTML,在 Electron 里升级成 RCE | `nodeIntegration: true` + 任一 XSS 点 |
| 框架搭建步骤 / demo 代码 | ⚪ 扫过 | 纯操作步骤,用到再查 | —— |
| 第三方库:jQuery XSS                | 🟢 了解 | 库的某个版本自身有漏洞                   | 用了存在漏洞的 jQuery 版本(< 3.5.0)                              |
| mXSS(Mutation XSS,突变型)         | ⚪ 扫过  | 浏览器解析 HTML 时的"突变"导致看似安全的内容变危险 | 特定的嵌套标签 + 浏览器解析怪异行为                                     |
| uXSS(Universal XSS,通用型)        | ⚪ 扫过  | 浏览器/浏览器扩展本身的漏洞                | 存在漏洞的浏览器版本或插件                                           |

**三类的分界线(原笔记的分类,很重要)**:
1. **框架或三方库的 XSS**(Vue/React/Electron/jQuery)——问题在**应用层**(代码或库)。
2. **浏览器或插件的 XSS**(uXSS)——问题在**浏览器本身**。
3. **客户端预览内核的 XSS**(mXSS 可归入)——问题在**HTML 解析引擎**。

**一句话抓住本质**:用框架/第三方库开发的应用,**默认安全写法会自带过滤**,所以要打这类应用,要么它用了**漏洞版本的库**,要么开发者用了**不安全的写法(逃生舱口)**;uXSS 要有**漏洞浏览器/插件**;mXSS 要有**特定环境下的解析突变**——这三类都比普通 XSS 更依赖"特定前置条件",需要更多测试才能命中。

**前置知识**:必须先掌握《XSS跨站-原理与三大类型》的三大基础类型和 Source→Sink 模型。框架部分还需回顾《Vue开发环境搭建与安全笔记》里讲过的"框架默认安全、但逃生舱口破功"这个核心认知——本篇是把它从 Vue 扩展到所有框架。

## 1. 框架型 XSS 的共同逻辑(先建立总纲)

### 1.1 它是什么

现代前端框架(Vue/React)在设计上就是**默认防 XSS 的**——你用正常方式(文本插值)把用户数据显示到页面上,框架会自动做 HTML 转义,用户输入的 `<script>` 会被当纯文字显示,不会执行。

但每个框架都留了一个"**逃生舱口**"(escape hatch):当开发者**确实需要**把一段内容当作原始 HTML 渲染时(比如渲染富文本编辑器产出的带格式内容),框架提供了一个专门的 API 来"关掉自动转义"。**一旦用了这个 API 去渲染用户可控的内容,XSS 就回来了。**

| 框架 | 安全的默认写法 | 危险的"逃生舱口" |
|---|---|---|
| Vue | `{{ 变量 }}`(文本插值,自动转义) | `v-html="变量"` |
| React | `{变量}`(自动转义) | `dangerouslySetInnerHTML={{__html: 变量}}` |
| 原生 JS/Electron | `textContent = 变量`(只当文字) | `innerHTML = 变量` |

### 1.2 为什么会存在(root cause)

root cause 一句话:**框架帮你挡住了默认情况,但它挡不住"你自己主动要求它别挡"的情况。**

注意看 React 那个逃生舱口的名字——`dangerouslySetInnerHTML`(危险地设置 innerHTML)。**框架作者特意把"dangerously(危险地)"这个词放进 API 名字里**,就是在用最直白的方式警告开发者:"你用这个的时候,安全责任从框架转移到了你自己身上,你必须自己保证内容是干净的。" 但现实中很多开发者:要么没意识到风险、要么图省事直接把用户输入塞了进去,于是 XSS 成立。

> [!note] 🔎 补充(非原笔记内容)
> 这里有一个对你做审计特别有用的认知:**框架型 XSS 的挖掘,本质上变成了"关键词搜索"**。因为危险只可能来自那几个固定的逃生舱口 API,所以白盒审计一个 Vue/React 项目时,第一件事就是全局搜索 `v-html`、`dangerouslySetInnerHTML`、`innerHTML` 这几个关键词,然后逐个检查"喂给它的内容是不是用户可控、有没有过滤"。这比在一个传统 PHP 项目里到处找拼接点高效得多——框架反而帮你把"可能出事的地方"收窄到了几个固定关键词上。

## 2. Vue-XSS(🟡 重要 —— 逃生舱口认知)

> 这个在《Vue开发环境搭建与安全笔记》里已经完整讲过,这里只做简要复习,重点是和本篇其他框架横向对比。

### 2.1 漏洞代码核心

```vue
<div v-html="displayContent"></div>
```
其中 `displayContent` 的值直接来自用户输入(`userInput`),点击按钮后未经任何过滤就赋值过去。`v-html` 会放弃 Vue 的自动转义,把内容当原始 HTML 渲染。

### 2.2 测试与修复

- 测试 payload:`<img src="x" onerror="alert('XSS')" />`
- 修复:把 `v-html` 换成文本插值 `{{ displayContent }}`(自动转义),或在赋值前用 DOMPurify 净化。

## 3. React-XSS(🟡 重要 —— 逃生舱口认知)

### 3.1 它是什么

React 和 Vue 同理,默认用 `{变量}` 显示内容时会自动转义。它的逃生舱口叫 `dangerouslySetInnerHTML`。

### 3.2 漏洞代码核心拆解

```jsx
// 危险写法
<div dangerouslySetInnerHTML={{__html: displayedInput}}/>
// 安全写法(注释掉的那行)
{/*<div>{displayedInput}</div>*/}
```

| 片段 | 作用 | 安全性 |
|---|---|---|
| `dangerouslySetInnerHTML={{__html: displayedInput}}` | 把 `displayedInput` 当**原始 HTML** 渲染 | 危险——`displayedInput` 来自用户输入,未过滤就渲染 = XSS |
| `<div>{displayedInput}</div>` | 用正常的 `{}` 插值显示 | 安全——React 自动转义,`<img onerror>` 会被当纯文字显示 |

### 3.3 测试与修复 / 易错点

- 测试 payload:`<img src="x" onerror="alert('XSS')" />`
- 修复:直接用 `{displayedInput}` 显示(就是把那行被注释掉的安全写法启用,删掉危险的那行)。
- **易错点**:React 开发者常有一种"我用了 React,React 很安全,所以不用管 XSS"的错觉。但只要代码里出现了 `dangerouslySetInnerHTML` 且内容用户可控,这个"安全错觉"就是漏洞的温床——审计时这个关键词出现一次就要查一次。

## 4. Electron-XSS(🟢 了解 —— 危害质变的思路值得懂)

### 4.1 它是什么

Electron 是用**前端技术(HTML/JS)来开发桌面应用**的框架(VS Code、Discord 等桌面软件都是 Electron 做的)。它的 XSS 从"代码层面"看和普通的 `innerHTML` XSS 一模一样:

```javascript
// index.html 里的漏洞代码
displayArea.innerHTML = input;   // input 来自用户输入,未过滤
```

### 4.2 为什么 Electron XSS 的危害"质变"了(这是重点)

普通网页的 XSS,恶意 JS 被限制在浏览器的"沙箱"里,顶多偷 Cookie、操作页面。但 Electron 不同——看它的配置:

```javascript
webPreferences: {
  nodeIntegration: true,       // ← 关键
  contextIsolation: false       // ← 关键
}
```

- `nodeIntegration: true` 的意思是:**这个页面里的 JavaScript,可以直接调用 Node.js 的能力**(读写文件、执行系统命令等,回忆《NodeJS环境搭建与安全笔记》里 Node.js 能做的事)。
- `contextIsolation: false` 关掉了隔离保护。

**这两个配置合在一起意味着什么**:一旦 Electron 应用里有 XSS,攻击者注入的 JS **不再被困在浏览器沙箱里,而是直接获得了 Node.js 的权限**——可以读写用户电脑上的任意文件、执行任意系统命令。**XSS 在这里直接升级成了 RCE(远程代码执行)**,危害从"偷个 Cookie"变成了"控制你整台电脑"。

> 这就是 Electron XSS 虽然定级 🟢(你暂时不会碰 Electron 开发)、但**思路特别值得懂**的原因:同样一行 `innerHTML = input`,在网页里是普通 XSS,在开启了 `nodeIntegration` 的 Electron 里就是 RCE。真到了要审计 Electron 应用那天,记住"`nodeIntegration: true` + 任何一个 XSS 点 = 高危"这一句就够了。

### 4.3 测试与修复

- 测试 payload:`<img src="x" onerror="alert('XSS')" />`(能弹窗只是起点,真实利用会执行 Node.js 命令)
- 修复:① 代码层用 `textContent` 代替 `innerHTML`;② 架构层关掉 `nodeIntegration`、开启 `contextIsolation`(现代 Electron 默认就是安全配置,这个漏洞 demo 是故意开了危险配置)。

## 5. jQuery-XSS(🟢 了解 —— 顺手查版本号即可)

### 5.1 它是什么——和前面框架型的关键区别

前面 Vue/React/Electron 的 XSS,根源是**开发者用错了 API(逃生舱口)**;而 jQuery XSS 不一样,它的根源是 **jQuery 这个库的某些版本自身存在漏洞**——哪怕开发者用法完全正常、甚至对输入做了过滤,只要用的是漏洞版本,依然会 XSS。

### 5.2 为什么会存在(真实 CVE 拆解)

> [!note] 🔎 补充(非原笔记内容,CVE 细节经联网核实,来源见文末)
> 最著名的是 **CVE-2020-11023**(以及姊妹漏洞 CVE-2020-11022):
> - **影响版本**:jQuery 1.0.3 到 3.5.0 之前(3.5.0 修复)。
> - **漏洞本质**:当把包含特定 HTML(如 `<option>` 等元素)的内容——**哪怕已经做过"净化处理"**——传给 jQuery 的 DOM 操作方法(`.html()`、`.append()` 等)时,jQuery 内部有一个叫 `htmlPrefilter` 的处理逻辑会用正则表达式改写这段 HTML(本意是把 `<div/>` 这种自闭合标签补全成 `<div></div>`)。**问题就出在这个"改写"上**——某些精心构造的输入,经过 jQuery 这步内部改写后,原本安全的 HTML 会"突变"成能执行 JS 的形态(这其实和下一节 mXSS 的"突变"思想相通)。
> - **为什么这个漏洞特别坑**:它打破了开发者的一个基本假设——"我已经净化过输入了,应该安全了"。但 jQuery 在净化之后、渲染之前,又自己偷偷改了一次 HTML,把安全的东西改成了不安全的。这意味着**即使应用层做对了防护,漏洞版本的 jQuery 依然会让防护失效**。
> - **现实严重性**:2025 年初,美国 CISA 把 CVE-2020-11023 列入了"已知被在野利用"漏洞目录(KEV),说明这个老洞至今仍在被真实攻击利用——因为大量老网站还在用过时的 jQuery 版本没更新。

### 5.3 实战怎么用

- **什么时候该想到它**:看到目标网站引用了 jQuery,**第一件事是查它的版本号**(通常在 JS 文件 URL 里,或控制台输入 `jQuery.fn.jquery` 可查看)。如果版本 < 3.5.0,就去查对应版本的已知 XSS,尝试利用。
- **漏扫工具**(课程提供):`jQuery-with-XSS`、`cve-2020-11023-scanner`(GitHub)可自动检测目标 jQuery 版本是否存在该漏洞。
- 这正好印证了《SRC漏洞挖掘经验》里讲的"历史漏洞库思维"——识别出组件和版本,直接查它的已知 CVE。

### 5.4 易错点

- **误区:以为"做了输入过滤就不会有 XSS"。** CVE-2020-11023 恰恰证明了:在漏洞版本的 jQuery 里,过滤过的内容也可能被库自己二次改写成恶意代码。根本解法是升级 jQuery 版本,而不只是加强应用层过滤。

## 6. mXSS(Mutation XSS,突变型 XSS)(⚪ 扫过)

### 6.1 它是什么

mXSS 的核心是"**突变(mutation)**"——一段 HTML 字符串,在被过滤器检查的时候**看起来是安全的**(过滤器认为没问题,放行了),但当它被浏览器真正解析、放进 DOM 的那一刻,浏览器的解析引擎会对它做一些"自动修正/补全",导致它**突变成了一段能执行 JS 的危险 HTML**。

> 类比:就像一个违禁品,过安检时伪装成普通形态骗过了安检仪(过滤器),但进入特定环境(浏览器解析引擎)后发生化学反应,变回了危险形态。问题不在安检仪不努力,而在"它检查时的样子"和"它最终的样子"不一样。

### 6.2 为什么会存在(root cause)

root cause:**过滤器看到的 HTML 和浏览器最终解析出的 DOM 不一致。** 过滤器是基于"字符串"做检查的,而浏览器解析 HTML 时有大量复杂的容错/补全规则(比如自动补全缺失的标签、修正嵌套错误),这些规则会改变 HTML 的实际结构。攻击者正是利用这种"检查时"和"解析后"的差异来绕过过滤。

课程给的经典 PoC(来自 PortSwigger 的 mXSS 实验):
```html
<math><mtext><table><mglyph><style><!--</style><img title="--&gt;&lt;img src=1 onerror=alert(1)&gt;">
```
这段 HTML 混用了 MathML(`<math>`)、表格(`<table>`)、SVG(`<mglyph>`)、样式(`<style>`)等不同"命名空间"的标签——正是这种跨命名空间的复杂嵌套,触发了浏览器解析引擎的突变行为,让原本藏在属性值(`title`)里的无害文本,突变成了真正的 `<img onerror>` 标签。

### 6.3 相关度说明

mXSS 是 XSS 里**较进阶、较冷门**的一类,利用门槛高(要深入理解浏览器解析引擎的怪异行为),实战中遇到的概率远低于前面几类。作为初学阶段,**理解它的核心思想("过滤时安全、解析后突变")即可**,不建议现在深挖具体 payload 构造,等有了扎实的 HTML/浏览器解析基础后再回来研究。

## 7. uXSS(Universal XSS,通用型 XSS)(⚪ 扫过)

### 7.1 它是什么

前面所有 XSS,漏洞都在"某个网站"身上——你只能打有漏洞的那个站。而 uXSS 的"Universal(通用)"体现在:**漏洞在浏览器本身或浏览器扩展里,所以它能对"任何网站"发动 XSS**,不管那个网站自己防护做得多好。

### 7.2 为什么会存在(root cause + 真实 CVE 拆解)

root cause:**漏洞不在网站代码,而在浏览器/扩展处理网页内容的代码里。** 浏览器扩展通常有"访问任何页面 DOM"的超级权限,一旦扩展或浏览器某个功能有漏洞,攻击者就能借它的权限在任意网站上执行 JS。

> [!note] 🔎 补充(非原笔记内容,CVE 细节经联网核实,来源见文末)
> 课程提到的 **CVE-2021-34506**(微软 Edge 翻译功能 uXSS):
> - **漏洞本质**:Edge 浏览器内置的"网页翻译"功能(Microsoft Translator),在翻译网页内容时,有一段代码**没有对内容做净化**——它把整个页面 DOM 转成文本去翻译,但处理 `<img>` 等标签时没有正确转义,导致藏在网页内容里的 XSS payload,**在用户点击"翻译此页"时被执行**。
> - **为什么它是"Universal"**:这个漏洞在翻译功能里,而翻译功能对所有网站都生效。所以攻击者只需要在**任何一个允许用户发内容的网站**上留下 payload——研究者实测的方式包括:在一条非英语的 YouTube 视频下发一条带 XSS payload 的评论、或发一个带 payload 的 Facebook 好友请求。当受害者用 Edge 浏览这些页面并触发翻译时,payload 就在那个网站的上下文里执行了,**连 Google、YouTube、Facebook 这些防护极强的站点都能被打中**——因为漏洞根本不在这些网站,而在浏览器的翻译功能。
> - **结局**:2021 年 6 月微软修复,给研究者发了 2 万美元赏金(修复版本 Edge 91.0.864.59)。

### 7.3 相关度说明

uXSS 同样是进阶冷门方向——它本质上是"**浏览器漏洞挖掘**",而不是"Web 应用漏洞挖掘",需要的是浏览器内部机制的深入知识,和你当前的 Web 渗透学习路线不在同一条线上。了解它"打的是浏览器、能通杀所有网站"这个概念即可,不需要现在投入。
- 复盘参考:CVE-2021-34506 的 B 站视频讲解和公开分析文章(课程提供)

## 8. 把它串起来:整个 XSS 系列的全景收束

到这里 XSS 的四篇笔记走完了,用一张图把所有类型按"漏洞在哪一层"收束:

```
XSS 的本质永远是:用户可控内容 → 被当代码执行(Source→Sink)
区别只在于"漏洞出现在哪一层":

【应用代码层】(你最该花时间的地方)
 ├─ 反射型 / 存储型 / DOM 型(基础三类,见第一篇)
 ├─ 文件类触发(SVG/PDF/HTML)+ 功能逻辑触发(PostMessage/localStorage)(第二篇)
 └─ 框架逃生舱口(Vue 的 v-html / React 的 dangerouslySetInnerHTML / Electron 的 innerHTML)(本篇)
        ↑ 这些都是"开发者写法不当",占实战 XSS 的绝大多数

【第三方库层】
 └─ jQuery 等库的版本漏洞(CVE-2020-11023)—— 查版本号、挂已知 CVE

【浏览器解析引擎层】
 └─ mXSS —— 过滤时安全、解析后突变(进阶冷门)

【浏览器/扩展本身】
 └─ uXSS —— 打浏览器,通杀所有网站(属于浏览器漏洞挖掘,另一条路线)
```

**给你的学习优先级建议(按新四档)**:
- 🔴 **真正该练熟的是前两篇的基础三类 + 文件/功能逻辑触发**——那才是 Web 渗透/SRC 里 95% 的 XSS 所在。本篇整体不属于这一档。
- 🟡 **本篇唯一要"记进脑子"的:Vue/React 的逃生舱口关键词**(`v-html`/`dangerouslySetInnerHTML`)——审计时会搜就行,不用背 demo。
- 🟢 **Electron 的 RCE 质变、jQuery 查版本号**——泛读建立概念、存着备查;Electron 等真碰到桌面应用审计再回来,jQuery 记住"查版本"这个动作即可。
- ⚪ **框架搭建步骤、mXSS、uXSS**——扫一眼知道有这回事就行,可遇不可求,现在花时间精读性价比极低。

## 9. 自测(先自己想,再看答案)

1. 用一句话说清楚:Vue/React 这类"默认安全"的框架,为什么还会有 XSS?挖这类 XSS 最高效的方法是什么?
2. 为什么同样一行 `innerHTML = input`,在普通网页里是"普通 XSS",在某些 Electron 应用里却是"RCE(远程代码执行)"?
3. jQuery 的 CVE-2020-11023 打破了开发者的哪一个"想当然"的假设?这给你的实战启发是什么?

<details>
<summary>参考答案</summary>

1. 因为框架只帮你挡住了"默认写法"(自动转义),但留了逃生舱口(Vue 的 `v-html`、React 的 `dangerouslySetInnerHTML`),一旦开发者用这些 API 去渲染用户可控内容,自动转义就被关掉了,XSS 回来。最高效的挖掘方法:全局搜索这几个固定的逃生舱口关键词,逐个检查喂进去的内容是否用户可控、有没有过滤。
2. 因为普通网页的 JS 被困在浏览器沙箱里,XSS 顶多偷 Cookie/操作页面;而开启了 `nodeIntegration: true` 的 Electron 应用,页面里的 JS 能直接调用 Node.js 能力(读写文件、执行系统命令),所以注入的 JS 不再被沙箱限制,直接获得操作系统级权限,XSS 就升级成了 RCE。
3. 它打破了"我已经对输入做过净化/过滤了,所以就安全了"这个假设——因为漏洞版本的 jQuery 在净化之后、渲染之前,内部又用正则偷偷改写了一次 HTML,把安全内容"突变"成了恶意代码。实战启发:遇到用 jQuery 的站,不能只看应用层有没有过滤,必须查 jQuery 版本号;组件自身的版本漏洞,是应用层防护管不到的,只能靠升级组件解决(呼应"历史漏洞库思维")。

</details>

## 10. 待核实 / 存疑

- CVE-2020-11023:影响版本 jQuery 1.0.3–3.4.1(3.5.0 修复)、2025年1月被 CISA 列入 KEV,均经 2025 年多家英文安全媒体(SecurityAffairs 等)核实。
- CVE-2021-34506:Edge 翻译功能 uXSS、2021年6月24日修复、2万美元赏金、修复版本 91.0.864.59,经 The Hacker News / PortSwigger / Threatpost 等核实。
- mXSS 的 PoC 利用效果高度依赖具体浏览器版本,不同浏览器/版本结果会有差异,文中 PoC 来自 PortSwigger 实验环境。
