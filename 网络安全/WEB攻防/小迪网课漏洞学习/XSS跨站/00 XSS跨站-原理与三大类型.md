**前置知识**:
- 需要先理解 **Source(污染源)→ Sink(危险接收点)** 这个模型——这在《DOM与BOM及基于DOM的漏洞笔记》里讲过,一句话回顾:**用户可控的输入(Source)未经处理,流进了某个会把它当代码执行的位置(Sink),漏洞就产生了**。这个模型在 SQL 注入和 XSS 里是完全通用的,区别只是逃逸的语法不同(SQL 逃逸的是 SQL 语法,XSS 逃逸的是 HTML/JS 语法)。

## 1. XSS 核心原理(🔴 核心)

### 1.1 它是什么

XSS,是指攻击者想办法让一段自己写的脚本代码(通常是 JavaScript),被网站当成"正常网页内容"返回给浏览器,从而在**其他用户的浏览器里**执行。

> 类比:想象你往一家餐厅的"留言墙"上贴了一张纸条,纸条上写的不是普通留言,而是一句"看到这张纸条的服务员,请把收银台的钱交给贴纸条的人"。如果餐厅的服务员**不加分辨地照着墙上任何纸条的指令去执行**,那么后面每一个读到这张纸条的服务员,都会照做。XSS 就是这样——网站(服务员)把用户写的内容(纸条)不加分辨地当成了"该执行的指令"。

**"跨站"这个名字的由来**:最经典的利用方式是,让受害者的浏览器把它当前持有的敏感信息(比如登录 Cookie),偷偷发送到**攻击者自己控制的另一个站点**上去——数据"跨"到了另一个"站"点,所以叫 Cross-Site。

### 1.2 为什么会存在(原理)

Root cause 一句话:**网站对"用户输入的数据"和"网页本身的代码"没有做严格区分,把前者直接当成后者输出了。**

一条完整的数据流:

```
用户输入数据(可能含 <script> 等 HTML/JS 代码)
      ↓
网站接收数据,未做"实体化编码"等处理
      ↓
网站把这段数据原样输出(拼)进了 HTML 页面里
      ↓
浏览器拿到页面,分不清哪些是网站本来的代码、哪些是用户塞进来的
      ↓
浏览器把用户塞进来的 <script> 当成正常脚本解析执行 → XSS 触发
```

关键在最后两步:**浏览器是"无脑"的**——它拿到一段 HTML,看到 `<script>` 标签就执行,它没有能力判断"这段脚本到底是网站开发者写的,还是某个恶意用户偷偷塞进来的"。所以防御的责任,完全落在网站后端"输出数据时有没有做处理"上。这也呼应了课程笔记里那句话——**"接受输入数据,输出显示数据后解析执行"**,漏洞恰恰出在"输出显示"到"解析执行"这个环节没有被拦住。

> [!note] 🔎 补充(非原笔记内容)
> 很多初学者会把 XSS 和 SQL 注入搞混,其实用一句话就能分清**两者的根本差异在于"代码最终在哪里执行"**:SQL 注入的恶意代码是在**服务器的数据库**里执行的(攻击的是服务端);而 XSS 的恶意代码是在**用户的浏览器**里执行的(攻击的是其他访问者,也就是客户端)。这个区别决定了它们的危害形态完全不同——SQL 注入偷的是数据库数据,XSS 偷的是"以受害用户身份能做的一切"(他的 Cookie、他能访问的页面、他能提交的操作)。

### 1.3 怎么做(过程)—— 通用测试思路

课程笔记里给的测试流程是"**看输出想输入在哪里,更改输入代码看执行**",拆解成可操作的步骤:

**步骤 1:找到"输入点"和"输出点"的对应关系**
- 做什么:观察页面上哪些内容是"你能控制的"(URL 参数、搜索框、评论框、昵称、留言等),然后看这些内容会**原样出现在页面的哪个位置**。
- 为什么这么做:XSS 成立的前提是"你的输入会被输出到页面上",如果你输入的内容压根不会显示出来,就没有 XSS 的土壤(如果你的输入**从头到尾都不会以任何形式进入浏览器所解析渲染的页面内容里**,就没有 XSS 的土壤)。这一步是在确认"输入→输出"这条链是否存在。
- 做完得到什么:找到一个"我输入 `test123`,页面某处就显示出 `test123`"的对应关系,这个位置就是候选注入点。

**步骤 2:测试输入是否被"当作代码"解析**
- 做什么:把输入从普通文字 `test123` 换成一个最简单的 HTML 标签,比如 `<h1>test</h1>` 或 `<b>test</b>`。
- 为什么这么做:这一步在验证"输出环节到底有没有做处理"——如果页面把 `test` 显示成了**大号标题或加粗字**,说明浏览器真的把你的标签当 HTML 解析了,**输出没有被编码,存在 XSS 风险**;如果页面原样显示出 `<h1>test</h1>` 这串文字(标签没生效),说明网站对输出做了实体化编码(把 `<` 转成了 `&lt;`),这个点大概率是安全的。
- 做完得到什么:确认输入会不会被当代码解析。用无害的 `<h1>`/`<b>` 而不是直接上 `<script>`,是因为前者更不容易被 WAF 拦截、也更不容易打草惊蛇,是一种"最小代价探测"。

**步骤 3:构造能证明"脚本可执行"的 payload**
- 做什么:确认标签能被解析后,换成一个能明确证明"JS 被执行了"的 payload,最经典的是 `<script>alert(1)</script>`,或者在标签过滤的情况下用事件触发,如 `<img src=x onerror=alert(1)>`。
- 为什么这么做:标签能解析不代表 JS 能执行(有的网站只过滤了 `<script>` 却漏了事件属性),这一步是用一个"弹窗"作为**无害但明确的成功信号**,证明任意 JS 都能在这个页面执行。
- 做完得到什么:页面弹出一个对话框 → XSS 确认成立。
- 如果不是预期结果:没弹窗,但步骤 2 确认标签能解析 → 说明存在过滤(可能过滤了 `script` 关键字、或过滤了某些符号),需要分析过滤规则去绕过,这正是课程说的"**标签、过滤决定**(用什么 payload)"的含义。

命令 / payload 拆解:

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `<img src=x ...>` | 插入一个图片标签,但 `src=x` 指向一个不存在的地址 | 故意让图片加载失败,从而触发下面的 `onerror` |
| `onerror=alert(1)` | 图片加载出错时自动执行的 JS 事件 | 当 `<script>` 被过滤时,用事件属性这种"迂回方式"执行 JS,是绕过过滤的常见手法 |
| `alert(1)` | 弹出一个内容为 1 的对话框 | 无害的"成功信号",证明 JS 能执行(实战中会换成真正的窃取代码) |

> 常用标签/payload 大全可参考课程给的这篇:https://www.freebuf.com/articles/web/340080.html

### 1.4 业务里长什么样(案例锚点)

> **真实案例:Samy 蠕虫(MySpace,2005 年)** —— 这是历史上最著名的 XSS 事件,也是存储型 XSS 的教科书级案例。
> - **发生了什么**:一个名叫 Samy 的人,在自己的 MySpace 个人主页的资料里,嵌入了一段利用存储型 XSS 的 JavaScript。任何访问他主页的用户,浏览器都会自动执行这段脚本——脚本做了两件事:把 Samy 加为好友、并把这段恶意代码**复制到受害者自己的主页上**。
> - **根因对应本笔记哪一环**:MySpace 允许用户在个人资料里填入内容,却没有对这些内容做彻底的输出编码过滤(对应本笔记 1.2 节的原理:用户输入未经处理就输出给了其他访问者)。
> - **业务后果**:由于每个中招的用户主页又成了新的传播源,它像病毒一样指数级扩散,**不到 24 小时感染了超过 100 万个账号**,最终迫使 MySpace 临时关闭网站处理。
> - **渗透测试者的启发**:XSS 的真正威力不在于"弹个窗",而在于**它能以受害者的身份,在受害者的浏览器里做任何该用户能做的操作**——加好友、发帖、改资料、甚至自我复制传播。这也是为什么存储型 XSS 的危害评级通常远高于反射型。

### 1.5 实战怎么用

- **什么时候该想到它**:只要看到"用户输入的内容会显示在页面上"的地方,就应该条件反射地想到测 XSS——搜索框、评论区、昵称、留言、个人简介、URL 参数回显、甚至报错信息里回显的输入。
- **怎么验证**:按 1.3 节的三步走,从无害的 `<b>`/`<h1>` 探测开始,再上 `alert(1)`。授权测试中用 `alert(document.domain)` 比 `alert(1)` 更好——它能明确显示"脚本在哪个域名下执行",避免因为页面套了 iframe 等情况产生误判。
- **怎么判断结果**:弹窗出现 = 成立;标签被原样显示成文字 = 输出做了编码,不成立;标签消失但没弹窗 = 存在过滤,需要研究绕过。
- **下一步**:确认成立后,根据 XSS 类型(反射/存储/DOM,见第 2-4 节)判断危害范围和利用方式——是只能靠诱导点击(反射),还是能自动影响所有访客(存储)。

### 1.6 防御与检测视角

对应课程笔记里的"安全修复"思路,从开发者角度看,防御 XSS 的核心手段:
- **实体化编码(HTML Encoding)**:输出到页面前,把 `<`、`>`、`"`、`&` 等特殊字符转成 HTML 实体(`&lt;`、`&gt;` 等),这样浏览器就会把它们当**文字**显示而不是当**代码**执行——这是最根本的防御,对应前面讲的"在输出环节拦住"。
- **字符过滤**:黑名单过滤危险标签/关键字(但容易被绕过,不如编码可靠)。
- **HttpOnly**:给 Cookie 加上 HttpOnly 标志后,JavaScript 就无法通过 `document.cookie` 读取它——即使 XSS 成立,也偷不到这个 Cookie(详见《身份验证机制笔记》里讲过的 HttpOnly)。这是一道重要的"减损"防线。
- **CSP(Content Security Policy)**:通过 HTTP 响应头限制页面能加载/执行哪些来源的脚本,能大幅降低 XSS 的可利用性。
- **WAF**:在流量层拦截常见的 XSS payload 特征(可被绕过,作为补充层)。

> 这些防御手段里,**实体化编码是"治本",HttpOnly/CSP 是"减损兜底"**——作为渗透测试者,理解这些防御正好反过来告诉你绕过思路从哪来:编码不彻底(只编码了部分场景)、过滤有遗漏(只过滤 script 没过滤事件)、没上 HttpOnly(Cookie 可偷)、CSP 配置不严,都是可以突破的点。

### 1.7 易错点

- **误区:以为"能弹窗"就等于"有高危漏洞"。** 弹窗只是证明脚本能执行,真正的危害大小取决于 XSS 类型(反射 vs 存储)、能不能偷到有效 Cookie(有没有 HttpOnly)、影响多少用户。报告漏洞时要说清楚实际能造成的影响,而不是只截一张弹窗图。
- **误区:只测 `<script>alert(1)</script>` 一种 payload,测一次没弹窗就判定"没有 XSS"。** 实际上大量 XSS 是在"标签能解析但 `<script>` 被过滤"的情况下,靠事件属性(`onerror`/`onload`)、或其他标签绕过触发的。排错线索:先确认"标签到底能不能解析"(用 `<b>` 测),再研究"是哪个关键字/符号被过滤了"。

## 2. 反射型 XSS(Reflected / 非持续型)(🔴 核心)

### 2.1 它是什么

反射型 XSS,是指恶意脚本作为**请求参数**(通常在 URL 里)发给服务器,服务器又把这个参数"原样反射"回到响应页面里,从而在打开这个链接的用户浏览器里执行。它是"非持续"的——恶意代码不会被保存在服务器上,**只对"点击了这个特定恶意链接"的那一次访问生效**。

> 类比:就像有人递给你一张字条,让你拿去前台念出来,前台听到就照做。字条(恶意代码)本身没有留在前台,只有你这一次"拿字条去念"的行为触发了效果。别人不去念这张字条,就不受影响。

### 2.2 为什么会存在(原理)

拆解这条链:

```
① 攻击者构造一个带恶意脚本参数的链接,如 http://正常网站/search?kw=<script>...</script>
② 诱导用户点击这个链接,用户的浏览器访问了【正常服务器】
③ 正常服务器把 kw 参数的值(含恶意脚本)原样拼进了搜索结果页面返回
④ 用户浏览器解析页面,执行了其中的恶意脚本,向【攻击者的恶意服务器】发起请求
⑤ 攻击者从自己的恶意服务器上,收到了脚本偷偷发来的用户信息(如 Cookie)
```

Root cause 和 1.2 节一致——服务器把 URL 参数未经编码就输出进了页面。它和存储型的唯一区别是:**这段恶意代码的"来源"是 URL 参数,用完即走,没有被存起来**。

### 2.3 怎么做(过程)

**步骤 1:找到一个"参数会回显到页面"的位置**
- 做什么:最典型的是搜索功能——搜索 `test`,页面显示"您搜索的'test'没有结果",这个 `test` 就是从 URL 参数回显出来的。
- 为什么这么做:反射型的本质就是"参数被反射回页面",找到这种回显点是第一步。
- 做完得到什么:一个候选的反射点。

**步骤 2:在参数里注入 payload 测试**
- 做什么:把搜索词换成 `<script>alert(document.domain)</script>`,直接在 URL 里构造好。
- 为什么这么做:验证这个回显点有没有做输出编码。
- 做完得到什么:弹窗 = 成立。

**步骤 3(利用阶段):构造恶意链接并诱导点击**
- 做什么:把真正的窃取脚本放进参数,生成一个完整的恶意 URL,通过钓鱼邮件、私信等方式诱导目标用户点击。
- 为什么这么做:反射型 XSS **必须靠用户主动点击那个特制链接才能触发**,这是它和存储型最大的实战差异——它的利用高度依赖社会工程(诱导点击)。

### 2.4 业务里长什么样(案例锚点)

> **示例场景**(此处用典型业务场景说明):某网站的站内搜索 `https://shop.example.com/search?q=手机`,搜索关键词 `q` 会原样显示在"搜索结果为:手机"这句话里,且未做输出编码。攻击者构造 `https://shop.example.com/search?q=<script>把当前用户Cookie发到攻击者服务器</script>`,通过伪装成"大促活动"的短信把这个链接群发出去(对应本笔记 2.2 的链路)。后果是:任何点击了这条链接、且当时处于登录状态的用户,其登录凭证会被窃取,攻击者可借此接管账号。

### 2.5 实战怎么用

- **什么时候该想到它**:看到任何"URL 参数的内容会显示在页面上"的功能,尤其是搜索框、错误提示、"返回上一页"之类回显 referer/参数的地方。
- **怎么验证**:直接在 URL 参数里放 payload,看是否弹窗,成本极低。
- **怎么判断结果**:弹窗成立。注意反射型通常是"改一个参数、打开一次链接"就能验证,不需要像存储型那样等别人访问。
- **下一步**:成立后评估影响——因为它需要诱导点击,单独的反射型 XSS 危害评级通常低于存储型,但如果能配合其他手法(如 CSRF)组合利用,危害会放大。

### 2.6 防御与检测视角

和 1.6 节通用——核心是对输出到页面的 URL 参数做实体化编码。反射型因为"即时反射",相对容易在测试中发现,也相对容易修复。

### 2.7 易错点

- **误区:以为反射型 XSS 危害很小不用管。** 虽然它需要诱导点击,但结合精心设计的钓鱼场景,在真实世界里成功率并不低,尤其针对特定高价值目标(鱼叉式钓鱼)时危害很大。

## 3. 存储型 XSS(Stored / 持续型)(🔴 核心)

### 3.1 它是什么

存储型 XSS,是指恶意脚本被**保存到了服务器端(通常是数据库)**,之后**每一个访问到这段内容的用户**,浏览器都会执行这段脚本。它是"持续型"的——代码一次存入,长期生效,危害范围是"所有访问者",而不是"点了特定链接的人"。

> 类比:回到最开始"留言墙"的比喻——存储型就是攻击者真的把那张恶意纸条**钉在了留言墙上**,之后每一个来看留言墙的人都会读到它、被它影响。这比反射型(递字条给特定一个人去念)的杀伤面大得多。

### 3.2 为什么会存在(原理)

对应你上传的"存储型 XSS 攻击流程"图:

```
① 攻击者在目标网站上(如评论区、个人资料),提交一段恶意脚本,这段脚本被【存进了数据库】
② 其他用户在登录状态下,正常访问了包含这段内容的页面(如看了那条评论)
③ 正常服务器把含恶意脚本的页面返回给这些用户
④ 用户浏览器解析页面,执行恶意脚本,向【攻击者的恶意服务器】发起请求
⑤ 攻击者从恶意服务器收到用户信息
```

和反射型的唯一区别就在第①步:**恶意代码不是通过 URL 临时携带,而是被持久化存进了数据库**,所以不再需要"诱导每个受害者点特制链接",受害者只要正常浏览网站就会中招。

### 3.3 怎么做(过程)

**步骤 1:找到"用户提交的内容会被保存、并展示给其他人看"的功能**
- 做什么:定位评论、留言、昵称、个人简介、发帖、商品问答等——凡是"我提交的内容,别人也能看到"的地方。
- 为什么这么做:存储型的前提是"内容被存储且被多人访问",这类功能才是存储型的温床。课程笔记里"数据输出的地方(用户资料、评论、留言、关键词标签)"说的就是这些点。
- 做完得到什么:一个候选的存储点。

**步骤 2:提交 payload 并确认被保存**
- 做什么:在该功能里提交 `<script>alert(document.domain)</script>`,提交后刷新页面、或换一个浏览器/账号再访问该页面。
- 为什么这么做:存储型的验证关键是"换一次访问还在不在"——如果刷新后、甚至退出登录用别的身份访问,脚本依然执行,就证明它被存进了服务器,是真正的存储型。
- 做完得到什么:每次访问该页面都弹窗 = 存储型成立。

### 3.4 业务里长什么样(案例锚点)

直接复用本笔记 1.4 节的 **Samy 蠕虫**案例——它正是存储型 XSS 的典型:恶意脚本存进个人主页资料(存储),所有访问者自动执行并二次传播,24 小时感染百万账号。它完美说明了存储型"一次存入、持续生效、影响所有访问者"的特征,以及为什么存储型的危害评级是三种类型里最高的。

### 3.5 实战怎么用

- **什么时候该想到它**:看到任何"内容会被保存并展示给其他用户"的功能,优先测存储型——它不需要诱导点击,危害最大,也是 Bug Bounty 里最值钱的 XSS 类型之一。
- **怎么验证**:提交 payload 后,**用另一个账号或退出登录后再访问**,确认脚本对"别人"也生效——这是区分存储型和"只对自己可见"的关键。
- **怎么判断结果**:对其他用户/其他会话也弹窗 = 存储型成立。
- **下一步**:成立后,利用方式通常是植入窃取 Cookie、劫持会话的脚本,因为它能自动命中所有访问者(尤其如果能存进管理员会看的页面,比如"用户反馈"后台,就能打到管理员——这叫"XSS 盲打")。

### 3.6 防御与检测视角

和 1.6 节通用,但存储型的防御要特别注意:**不仅要在"输出时"做编码,"输入存储时"也应做校验**,双重防护。富文本编辑器(允许用户发带格式的内容)是存储型 XSS 的重灾区,因为它天然需要保留部分 HTML 标签,过滤规则很难做得既安全又不影响功能。

### 3.7 易错点

- **误区:提交 payload 后只在自己的页面看到弹窗,就以为是存储型。** 有可能只是"自己提交、自己可见"的伪存储,或者其实是 DOM 型。一定要换个身份/会话验证"对别人是否也生效"。

## 4. DOM 型 XSS(DOM-Based)(🔴 核心)

### 4.1 它是什么

DOM 型 XSS,是指**整个攻击过程完全发生在浏览器前端**(三种XSS的执行也都发生在前端 真正的区别在于**恶意代码有没有经过服务器这一趟"**)——恶意代码是被页面里的 JavaScript 读取、处理后,直接写入了当前页面的 DOM 结构里触发的,**服务器返回的页面内容本身可能根本没有变化,服务器甚至完全不知道发生了攻击**。这个漏洞从"数据被注入"到"代码被执行"的整个过程,全程没有服务器的参与;服务器返回的页面是干净的,是前端 JS 自己把 payload 捡起来并引爆的。

> 类比:前面反射型和存储型,都是"服务器这个厨师把带毒的菜端给了你";而 DOM 型更像是"服务器端给你的是一份正常的食材和菜谱,但菜谱里有一步写着'把顾客自己带来的调料直接加进去',而顾客带来的'调料'(URL 里的参数)被下了毒"——出问题的是前端 JS 这份"菜谱"处理数据的方式,而不是服务器端。

### 4.2 为什么会存在(原理)

拆解这条链:

```
① 攻击者发给受害者一个链接,链接的参数里携带了恶意 JS 代码
② 受害者点击,浏览器访问目标网站(如微博),请求里带着这段恶意参数
③ 服务器返回的是【正常的、不含恶意代码的】静态 HTML/JS —— 注意这一步,服务器是干净的
④ 浏览器里的前端 JS,读取了 URL 里的那个参数,并用它去修改了页面的 DOM 结构
⑤ 由于这段参数被当成了 HTML/JS 处理,恶意代码在修改 DOM 的过程中被执行,访问了攻击者的服务器
```

Root cause:**漏洞不在服务器的输出环节,而在前端 JavaScript 处理数据的环节**。前端 JS 从一个 Source(如 `location.hash`、`location.search` 这类 URL 里用户可控的部分)取了数据,未经处理就交给了一个 Sink(如 `innerHTML`、`document.write` 这类会把字符串当 HTML 解析的属性/函数)——这正是《DOM与BOM及基于DOM的漏洞笔记》里讲过的 Source→Sink 模型在 XSS 上的体现。

### 4.3 怎么做(过程)
### 常见的 Source(攻击者可控的输入来源)

这几个是读 JS 时要盯着的——看到 JS 在读这些东西,就说明"用户输入从这里进来了"：

|Source(JS 写法)|它读的是什么|为什么攻击者可控|
|---|---|---|
|`location.hash`|URL 里 `#` 后面的部分|你能随便改 URL|
|`location.search`|URL 里 `?` 后面的参数部分|同上|
|`location.href`|整个完整 URL|同上|
|`document.referrer`|用户从哪个页面跳过来的|攻击者能伪造来源页面|
|`window.name`|跨页面传递的一个值|可被攻击者设置|
### 常见的 Sink(会把字符串当代码执行的危险点)

看到 JS 把数据交给下面这些东西,就要高度警觉——数据到这里会被"解析执行"：

|Sink(JS 写法)|它干了什么危险的事|
|---|---|
|`innerHTML = xxx`|把字符串当 **HTML** 塞进页面并解析(标签会生效)|
|`document.write(xxx)`|直接把字符串当 HTML 写进页面|
|`eval(xxx)`|把字符串当 **JS 代码**直接执行|
|`location = xxx` / `location.href = xxx`|把字符串当跳转地址(可被 `javascript:` 伪协议利用)|
|`$(xxx).html(xxx)`|jQuery 的写法,等同于 innerHTML|
**步骤 1:判断页面是否存在"前端 JS 处理用户输入"的逻辑**
- 做什么:查看页面的 JS 代码(F12 → Sources),搜索危险的 Sink 关键词:`innerHTML`、`document.write`、`eval`、`location`、`$(...).html()` 等,再反向追踪它们处理的数据是不是来自 URL(`location.hash`/`location.search`/`document.referrer` 等 Source)。
- 为什么这么做:DOM 型的根源在前端代码,所以必须读前端 JS 才能定位,这和反射/存储型"主要看服务器输出"的排查方式不同。
- 做完得到什么:找到一条"Source → Sink 中间没有过滤"的数据流。
- 假设你 F12 → Sources 面板,在页面的 JS 里看到这么一段代码：

javascript

```javascript
function showWelcome() {
    var name = location.hash.substring(1);      // ← 第 1 行
    var box = document.getElementById("welcome");
    box.innerHTML = "欢迎你," + name;            // ← 第 3 行
}
showWelcome();
```

**你的大脑应该这样逐步分析:**

**① 先搜 Sink 关键词**:你在代码里搜 `innerHTML`,定位到第 3 行 `box.innerHTML = "欢迎你," + name;` —— 找到一个 Sink 了(innerHTML 会解析 HTML)。

**② 反向追踪:喂给这个 Sink 的数据是哪来的?** 第 3 行用到了变量 `name`,那 `name` 是从哪来的?往上看第 1 行:`var name = location.hash.substring(1);` —— **`name` 来自 `location.hash`,这是一个 Source!**(`substring(1)` 只是把开头的 `#` 去掉,不影响它是用户可控数据)

**③ 检查中间有没有过滤**:从第 1 行(Source)到第 3 行(Sink),中间有没有对 `name` 做任何编码/过滤/校验?——**没有**,它被原样拼进了 `innerHTML`。

**④ 结论:找到一条完整的漏洞数据流!**

```
location.hash (Source,你可控)
      ↓  中间没有任何过滤
box.innerHTML (Sink,会解析 HTML)
```

**⑤ 这条数据流怎么引爆**(就是讲的步骤 2):既然 `location.hash` 的内容会被原样塞进 `innerHTML`,那你访问 `http://目标/page#<img src=x onerror=alert(1)>`,这个 `<img>` 就会被写进页面解析、触发 `onerror` 弹窗。

**步骤 2:构造 payload 验证**
- 做什么:根据这条数据流,构造能触发的 URL,常用 `#` 后面的 hash 部分(因为 hash 不会发给服务器,更能体现"纯前端触发"的特点),如 `http://目标/page#<img src=x onerror=alert(1)>`。
- 为什么这么做:验证前端 JS 确实把 URL 里的内容当代码写进了 DOM。
- 做完得到什么:弹窗 = DOM 型成立。
- **一个关键的判断技巧**:DOM 型的 payload 如果放在 URL 的 `#` hash 部分,这部分内容**根本不会被发送到服务器**(浏览器不会把 `#` 后面的内容放进 HTTP 请求),所以如果你用这种方式能打成功,基本可以确认是纯 DOM 型——服务器全程没见过你的 payload。

### 4.4 业务里长什么样(案例锚点)

> **示例场景**(此处用典型业务场景说明):某单页应用(SPA)的页面用 JS 读取 URL 里 `#` 后面的内容来决定显示哪个"标签页",代码类似 `document.getElementById('content').innerHTML = location.hash.substring(1)`。开发者本意是用 hash 做页面内导航,但因为直接把 hash 内容塞进了 `innerHTML`(对应本笔记 4.2 的 Source→Sink 链路),攻击者构造 `http://app.example.com/#<img src=x onerror=窃取脚本>` 诱导点击。后果是:脚本在受害者浏览器执行,而服务器日志里完全看不到任何异常请求(因为 hash 没发给服务器),导致这类漏洞极难被服务端的安全监控发现。

### 4.5 实战怎么用

- **什么时候该想到它**:当你发现"参数明明回显了/影响了页面,但服务器返回的原始 HTML 源码里却找不到你的 payload"时,就要怀疑是 DOM 型——因为是前端 JS 动态写进去的,不在服务器返回的原始源码里。现代前端框架(Vue/React/jQuery)用得多的站点,DOM 型尤其常见。
- **怎么验证**:优先用 `#` hash 部分构造 payload,既能验证又能确认"纯前端触发"。
- **怎么判断结果**:弹窗成立;特别地,如果 payload 放 hash 里能触发,确认是 DOM 型。
- **下一步**:DOM 型的利用方式和反射型类似(需诱导点击),但它的隐蔽性是最大优势——服务端 WAF 和日志往往对它无感。

### 4.6 防御与检测视角

DOM 型的防御责任在**前端开发者**:不要用 `innerHTML`/`document.write` 这类会解析 HTML 的方式处理用户可控数据,改用 `innerText`/`textContent`(只当文本显示,不解析标签);必须插入 HTML 时,用成熟的前端过滤库(如 DOMPurify)先净化。这也解释了为什么服务端做了再多防护,如果前端代码有这个缺陷,XSS 依然成立——防御点和漏洞点必须对应在同一侧。

### 4.7 易错点

- **误区:只看服务器返回的 HTML 源码(右键"查看网页源代码")里有没有自己的 payload,没看到就判定"没有 XSS"。** DOM 型是 JS 运行后才动态生成的,"查看网页源代码"看到的是 JS 运行前的原始 HTML,看不到 DOM 型的痕迹。正确做法是用 F12 的"元素(Elements)"面板看运行后的实时 DOM,或直接读 JS 代码分析数据流。

## 5. 把它串起来:三种类型的判断流程

```
发现一个"输入会影响页面"的点
    ↓
① 用 <b>/<h1> 测试:输入会被当 HTML 解析吗?
    被当文字原样显示 → 输出做了编码,基本安全,换下一个点
    被当代码解析 → 继续
    ↓
② 这段 payload 被存起来了吗?(刷新/换账号访问还在不在)
    换个身份访问仍然触发 → 【存储型】(危害最大,不需诱导点击)
    只有本次/本参数生效 → 继续
    ↓
③ 服务器返回的原始 HTML 源码里,能找到我的 payload 吗?
    能找到(是服务器反射回来的) → 【反射型】(需诱导点击)
    找不到,是前端 JS 动态写进去的(尤其 payload 放 # 后能触发) → 【DOM 型】(最隐蔽,服务端无感)
```

**三种类型的核心差异一句话对比**:

| 类型 | 恶意代码存在哪 | 谁会中招 | 服务器知情吗 | 危害评级 |
|---|---|---|---|---|
| 反射型 | URL 参数,用完即走 | 点了特制链接的人 | 知情(参数经过服务器) | 中 |
| 存储型 | 服务器数据库,长期保存 | 所有访问该页面的人 | 知情 | 高 |
| DOM 型 | 不经服务器,纯前端处理 | 点了特制链接的人 | **不知情** | 中(但最隐蔽) |
