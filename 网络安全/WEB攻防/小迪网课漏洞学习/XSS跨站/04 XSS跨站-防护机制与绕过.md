## 0. 先看这张地图

一个网站防 XSS,通常有三道独立的防线,分别管不同的环节。理解它们的分工,才知道遇到某道防线时该怎么绕:

| 防护机制                | 相关度   | 它挡住的是什么                        | 对应的绕过方向                       |
| ------------------- | ----- | ------------------------------ | ----------------------------- |
| **WAF / 代码 Filter** | 🔴 核心 | 在输入/输出环节过滤危险字符和关键字             | **过滤绕过**(本篇重点,大小写/双写/编码/换标签)  |
| **HttpOnly**        | 🟢 了解 | 禁止 JS 读取 Cookie(减损,不是防 XSS 本身) | 绕过手法都很鸡肋;实战转向"不偷 Cookie"的利用方式 |
| **CSP**             | 🟢 了解 | 限制页面能加载/执行哪些来源的脚本              | 配置不当才能绕(文件上传、302 跳转等)         |

**关键认知:这三道防线的定位完全不同**

- **Filter/WAF** 是"**不让 XSS 发生**"——在源头过滤掉 payload。
- **HttpOnly** 和 **CSP** 是"**就算 XSS 发生了,也尽量减少损失**"——HttpOnly 让你偷不到 Cookie,CSP 让你的恶意脚本加载不进来/数据发不出去。

所以作为攻击者:**Filter 是你每次都要正面硬刚的**(所以过滤绕过是 🔴 核心必练);而 HttpOnly/CSP 是"看运气"的——配置严就难受,配置松就有空子,它们的绕过更多是"了解有哪些思路"。

**前置知识**:必须先掌握《XSS跨站-原理与三大类型》的触发原理、《XSS跨站-攻击利用手法》里 Cookie 窃取和"数据提交绕过 HttpOnly"的思路、以及《身份验证机制笔记》里 HttpOnly 的作用。本篇大量复用。

## 1. WAF / 代码 Filter 与黑盒绕过思维(🔴 核心,本篇重中之重)

### 1.1 它是什么

Filter(代码里的过滤函数)和 WAF(Web 应用防火墙)都是在**检测并拦截 XSS payload**。它们的手段无非是:删关键字(`script`)、转义特殊字符(`<` → `&lt;`)、用引号把输入括起来等。**XSS 过滤绕过,就是和这套过滤规则斗智——找到它没考虑周全的角度,让 payload 换个"长相"骗过过滤、却依然能执行。**

### 1.2 黑盒 XSS 手工分析四步法(核心方法论,背下来)

这是面对任何一个输入点时的通用流程,原笔记给的四步,拆开讲清楚每步在干嘛:

**步骤 1:在页面中找可控的数据(包括隐藏的)**

- 做什么:观察页面上哪些内容是你输入进去、又显示出来的(搜索框、评论、URL 参数回显);**特别留意"隐藏的"可控点**——比如你的输入可能被塞进了某个标签的属性值里(`value="你的输入"`)、或某个隐藏表单字段里,页面上不直接显示,但在 HTML 源码里能看到。
- 为什么:找到"输入→输出"的对应关系是一切的前提(呼应《XSS跨站-原理与三大类型》的测试思路)。隐藏的可控点往往是过滤的盲区,反而容易绕。

**步骤 2:用可控的地方发送 JS 代码,看执行加载情况**

- 做什么:在找到的可控点,输入一个测试 payload(先从最简单的 `<script>alert()</script>` 开始)。
- 为什么:直接试探"这里到底能不能执行脚本"。

**步骤 3:成功执行即 XSS;不能成功,就看语句输出的地方怎么显示**

- 做什么:如果没弹窗,**不要直接放弃**,而是去页面 HTML 源码里找到你的输入被显示在了什么位置、变成了什么样子。
- 为什么:**这一步是整个绕过的核心**——你必须先看清"过滤把你的 payload 改成了什么样",才能知道该怎么改写。这也是为什么《XSS跨站-原理与三大类型》强调"先确认标签能不能解析"。

**步骤 4:根据显示分析"为什么不能执行"**

- 做什么:对照看你的 payload 变成了什么,判断过滤的具体手段:
  - 变成了 `&lt;script&gt;`(**实体化编码**)→ 尖括号被转义了,标签不生效。
  - 你的输入被包在 `value="..."` 里面(**被引号括起来**)→ 需要先闭合引号才能逃出来。
  - `script` 这个词被删掉了,变成了 `alert()`(**关键字过滤**)→ 需要换写法绕过关键字检测。
- 为什么:**对症下药**。不同的过滤手段对应完全不同的绕过方法(见第 1.3 节的一整套手法)——先诊断,再开方,而不是盲目乱试 payload。

> [!note] 🔎 补充(非原笔记内容)  
> 这套四步法的精髓&#x662F;**"失败不是终点,而是信息"**。新手一看没弹窗就换下一个点,老手会盯着"没弹窗时我的 payload 变成了什么样"——因为过滤后的那个形态,恰恰暴露了过滤规则的全部信息。你把"它删了什么、转义了什么、把我括在哪里"看清楚了,绕过方法基本就自己浮现出来了。这就是《SRC漏洞挖掘经验》里"耐心处理看起来失败的响应"在 XSS 上的具体体现。

### 1.3 过滤绕过手法速查(🔴 核心,对照 xss-labs 关卡)

下面是 xss-labs 靶场经典关卡对应的绕过手法,每个都标注"它绕的是哪种过滤"。**这张表是本篇最该练熟的部分**——建议配合 xss-labs 靶场逐关打一遍。

| #     | 过滤场景                                                        | 绕过 payload                                        | 原理(人话)                                                                                                                                                   |
| ----- | ----------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | **无任何过滤**                                                   | `<script>alert()</script>`                        | 直接打,基准关                                                                                                                                                  |
| 2     | 输入被包在 `value="..."` 里,没过滤                                   | `"><script>alert()</script><"`                    | 先用 `">` 闭合掉前面的 `value="`,逃出属性,再写自己的标签                                                                                                                    |
| 3     | 尖括号被实体化(`<`→`&lt;`),但在属性里                                   | `' onfocus=javascript:alert() '`                  | 标签打不出来了,但可以给**当前所在的标签**加一个**事件属性**(`onfocus`),用单引号闭合属性值                                                                                                  |
| 4     | 同上,双引号闭合                                                    | `" onfocus=javascript:alert() "`                  | 同 3,只是这里属性用的是双引号,所以用 `"` 闭合                                                                                                                              |
| 5     | 事件关键字(`onfocus` 等)被过滤                                       | `"> <a href=javascript:alert()>xxx</a> <`         | 事件打不了,改用 `<a>` 标签的 `href=javascript:` 伪协议来执行(换一种 JS 执行入口)                                                                                                |
| 6     | 关键字正则匹配**没考虑大小写**                                           | `"> <sCript>alert()</sCript> <"`                  | 把 `script` 写成 `sCript`——HTML 不区分大小写照样执行,但过滤的正则只匹配了全小写,漏了                                                                                                 |
| 7     | 关键字被**删除一次**(没递归删)                                          | `"> <a hrehreff=javascript:alert()>x</a> <"`      | 双写绕过:把 `href` 写成 `hrehreff`,过滤删掉中间的 `href` 后,剩下的字符**又拼回了** `href`——因为过滤只删一次,没循环删                                                                         |
| 8     | 关键字替换 + `htmlspecialchars`(标签打不出、事件/双写都废了),但输入落在 `href` 属性里 | `&#x006a;&#x0061;...`(javascript 的 **HTML 实体编码**) | 把 `javascript:alert()` 用 **HTML 实体编码**(`&#xNN;`)写,过滤器看到的是一堆编码字符(不认识关键字)而放行,但浏览器解析 `href` 属性值时会**自动解码回** `javascript:alert()` 伪协议并执行(详见 §1.6 深度解析)        |
| 9     | 同 8,但带额外内容检测                                                | 同上编码 + `('http://')`                              | 在编码 payload 后拼接看似正常的内容,进一步混淆过检测                                                                                                                          |
| 9     | 同 8,但**额外要求输入必须包含 `http://`**                               | 同 8 的编码 payload + 拼一个 `('http://')`               | 防御只做"字符串里有没有 http://"的表层检查。在 payload 里拼个 `http://` 当诱饵(如作 `alert('http://')` 的参数)凑数,既满足检测、又保留伪协议执行(详见 §1.7)                                              |
| 10    | 真正的可控点是**隐藏参数**(过滤盲区)                                       | `...&t_sort=" type="text" onclick="alert('xss')`  | 显眼的输入框被严格过滤打不动;真正突破口是藏在 HTML 源码里、开发者忘了过滤的 hidden 参数(`t_sort`)。先意识到它可控(URL 手动加 `&t_sort=`),再闭合把 `type=hidden` 覆盖成 `type=text` 让它显形可点,加 `onclick`(详见 §1.8) |
| 11-20 | 更复杂的 Referer/编码组合等                                          | 见 CSDN 参考文章                                       | 思路类似,都是"诊断过滤 → 对症换写法"的延伸                                                                                                                                 |

**把这些手法归成几大类记忆**(比记具体 payload 更重要):

1. **闭合逃逸**:输入被括在属性/标签里 → 用 `">` 或 `'` 闭合逃出来(关卡 2/3/4/10)。
2. **换执行入口**:`<script>` 被封 → 用标签事件(`onerror`/`onfocus`/`onclick`)或伪协议(`href=javascript:`)(关卡 3/4/5)。
3. **变形绕关键字**:大小写混写、双写、编码(Unicode/HTML 实体)——让过滤"认不出"关键字,但浏览器解析时还原(关卡 6/7/8/9)。

## 1.6 深度解析:编码绕过的底层原理(🔴 核心,最该吃透的一节)

> 第 8 关的"HTML 实体编码绕过"看着简单,但它背后藏着整个 XSS 攻防最核心的一条原理:**浏览器"先认结构、后解码"的解析顺序**。吃透这一节,你不光懂第 8 关,还能彻底理解"为什么防御方把 `<` 实体化能防住 XSS,而攻击方用实体编码却能绕过"——同一个技术,方向完全相反。

### 1.6.1 浏览器解析 HTML 的工作顺序:先认结构,后解码实体

浏览器处理一段 HTML,不是一口气看完,而是**分成有先后顺序的两个阶段**:

**阶段一:分词/建树(认结构)** —— 解析器从左往右扫,靠**没解码的原始** `<` `>` `"` `=` 这些符号判断"哪里是标签、哪里是属性、属性值范围到哪"。

**阶段二:解码实体(还原字符)** —— 结构定死之后,才把属性值/文本里的 HTML 实体(`&lt;`、`&#x6a;`)解码成真实字符。

以这段为例:

```html
<input value="&lt;script&gt;alert(1)&lt;/script&gt;">
```

- **阶段一**:解析器扫到 `&lt;` 时,看到的是四个普通字符 `& l t ;`(**还没解码!**),所以它认定"value 属性里就是一串文字",input 标签干净结束。**结构在此刻定死:只有一个 input,没有别的标签。**
- **阶段二**:现在才把 `&lt;` 解码成 `<`,页面上显示出 `<script>...` 这行文字。**但认标签的阶段早过了**,这个迟到的 `<` 只能当文字,解析器不会回头把它当新标签。

> 💡 比喻:像机场安检。**阶段一(认结构)= 安检清点行李**,按行李"当下的样子"(`&lt;` 是四个字符)登记成"普通文字";**阶段二(解码)= 过安检后还行李**,`&lt;` 变回 `<`,但清点早做完了,安检员不会回头重新清点。

### 1.6.2 "用实体化结构符号伪造标签"为什么必然失败

这解释了**防御方把 `<` 实体化为什么能防住 XSS**。假设攻击者异想天开,想用 `&lt;script&gt;` 解码出 `<script>` 来伪造一个新标签:

```
阶段一(认结构):解析器看到 &lt; 是普通字符 → 认定是文字 → 结构定死,没有新标签。
阶段二(解码):  才把 &lt; 解码成 < → 页面显示出 <script> 文字。
               → 但"认标签"的窗口已永久关闭 → 它只是纯文字,不是标签 → 不执行。
```

**核心:你想伪造的是"标签结构",而标签结构在阶段一(解码之前)就定死了;你的 `<` 要等阶段二才现身,来晚了。** 这就是防御方实体化 `<` `>` 能挡住"打新标签"的根本原理。

### 1.6.3 第 8 关为什么能成功:不伪造标签,而在"已有属性"里藏"解码后仍生效的内容"

第 8 关攻击者聪明在**他根本不去伪造标签**(知道那是死路),而是:

1. **利用一个已经合法存在的标签**(`<a href="...">` 本来就在,结构完整真实,不用伪造)。
2. **把 payload 藏在 `href` 属性值里**。而 `href` 的值**在解码之后才被解释用途**(当成 URL/协议处理)。
3. 所以 `href` 里的 `&#x6a;...` 在阶段二解码成 `javascript:alert()` 后,**正好赶上"把 href 值当协议处理"这个发生在解码之后的环节** → 伪协议执行。

**伪造标签(死路)vs 第8关(活路)对比:**

|       | 伪造标签(失败)                  | 第8关(成功)                   |
| ----- | ------------------------- | ------------------------- |
| 想干什么  | 用 `&lt;` 变出 `<` 来**造新标签** | 在**已有标签**的属性值里藏功能         |
| 依赖的时机 | 需要"解码后还能被当标签识别"           | 需要"解码后还能被当协议处理"           |
| 成/败原因 | ❌ 标签识别在解码**之前**,来不及       | ✅ href 协议解释在解码**之后**,正好赶上 |

### 1.6.4 关键澄清:同一个"HTML 实体编码",防御和攻击方向相反

`&#x6a;` 这种东西的**正式名字是 HTML 实体编码(数字字符引用)**,不是"Unicode 编码"——只是它内部的数字恰好是字符的 Unicode 码点,所以常被俗称 Unicode,这个叫法不精确。

**同一个实体编码技术,用在不同人手里、针对不同内容,效果完全相反:**

|      | 防御方的实体化(`htmlspecialchars`) | 攻击方(第8关)的实体编码                         |
| ---- | --------------------------- | ------------------------------------- |
| 谁做   | 网站后端/开发者                    | 攻击者手动构造 payload                       |
| 对什么做 | 对**危险结构符号** `<` `>` `"` 做   | 对**自己 payload 的关键字字母** `javascript` 做 |
| 目的   | 破坏标签结构,让 payload **失效**     | 藏住关键字骗过过滤,让 payload **生效**            |
| 结果   | XSS 打不了                     | XSS 能打                                |

**判断它是"防御"还是"攻击",不看用没用实体化,而看:它编码的是"破坏结构的符号"还是"躲避检测的关键字"。** 前者让 payload 死(结构被毁、解码太晚),后者让 payload 活(结构没动、只藏关键字、解码后生效)。

### 1.6.5 为什么必须用 HTML 实体(`&#x6a;`)而不是 JS 转义(`\u006a`)

有好几种东西都和"编码"沾边,但**谁来解码、在哪解码**完全不同,选错就失败:

| 写法                  | 正式名字                  | 谁解码          | 在 HTML 属性里会还原吗            |
| ------------------- | --------------------- | ------------ | ------------------------- |
| `&#x6a;` / `&#106;` | **HTML 实体编码**         | **HTML 解析器** | ✅ 会(第8关用的就是这个)            |
| `\u006a`            | JavaScript Unicode 转义 | JS 引擎        | ❌ 不会(这是 JS 语法,HTML 解析器不认) |
| `%6a`               | URL 编码                | URL 解析器/服务器  | ❌ 不会(这是 URL 的规矩)          |

**第 8 关的 payload 落在 HTML 的 `href` 属性里,解析它的是 HTML 解析器,所以只认 HTML 实体。** 判断任何编码绕过能不能成功,核心永远是问:**我的 payload 落在哪个解析环境(HTML / JS / URL)?那个环境会不会自动解码我用的这种编码?** 选对和当前环境匹配的编码才能成功。

### 1.6.6 【重要】"解码后仍会执行值"的 Sink 清单(可迁移的规律)

第 8 关能成功,本质是因为 `href` 是一个 **"值在解码之后,还会被当成功能性指令去执行"的 Sink**。这样的位置不止 `href` 一个,记住这一类,以后遇到任何一个都能用同样思路打:

| Sink 写法                                                             | 用法 / 作用                                                                     | 为什么能被利用                              |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------ |
| `<a href="javascript:alert(1)">`                                    | 超链接的 href 用 `javascript:` 伪协议——**用户点击链接时执行后面的 JS**                          | href 的值在解码后被当协议解释,可藏 `javascript:`   |
| `<iframe src="javascript:alert(1)">`                                | 内嵌框架的 src 同样支持 `javascript:` 伪协议,**加载 iframe 时执行**(比 a 标签更"自动",不一定需要点击)     | src 值解码后被当协议处理                       |
| `<img src=x onerror="alert(1)">`                                    | 图片 src 指向无效地址 `x` 使其加载失败,**自动触发 onerror 事件执行 JS**(无需用户操作,最常用)               | 事件属性的值也是解码后被当 JS 执行                  |
| `<svg onload="alert(1)">`                                           | SVG 标签加载完成时**自动触发 onload** 执行 JS(常用于 `<script>` 被过滤时)                       | 同上,事件属性解码后执行                         |
| `<body onload="alert(1)">` / `<input onfocus="alert(1)" autofocus>` | 页面/元素加载或获得焦点时自动执行(autofocus 让 input 自动获焦触发 onfocus)                         | 同上                                   |
| `<... style="...">`(老浏览器)                                           | 老版本 IE 里 CSS 的 `expression()` 能执行 JS,如 `style="width:expression(alert(1))"` | 老浏览器会执行 CSS 表达式(现代浏览器已废弃,**⚪ 扫过**即可) |

> **共性(这是你要记住的规律)**:这些位置的值,都&#x5728;**"解码之后"才被解释用途**(当协议、当事件 JS、当 CSS 表达式)。所以藏在里面的实体编码 payload 解码后能赶上"被执行"的时机。而普通的"标签之间的文本"(`<div>这里</div>`)没有这个特性——文本解码后只会**显示**,不会被**执行**,所以在那种位置伪造标签才是死路。
>
> **实战判断:payload 落点如果是上面这类"解码后会执行值的 Sink",就可以用实体编码藏关键字绕过;如果落点是"纯文本显示区",就得想办法打新标签(而打新标签又会被 htmlspecialchars 挡住)。落点决定打法。**

## 1.7 第 9 关:表层字符串检测的绕过(🟢 了解)

第 9 关在第 8 关基础上,**额外加了一道检测:输入里必须包含 `http://` 字符串,否则拒绝**(开发者想当然地以为"正常友情链接的 href 肯定含 http://,以此挡掉伪协议 payload")。

防御代码新增逻辑:

```php
if(false === strpos($str, 'http://')){      // 查输入里有没有 http://
    echo '<a href="链接不合法">...';          // 没有就打回,payload 进不了 href
}else{
    echo '<a href="'.$str.'">...';           // 有才正常输出
}
```

**绕过**:这个检测只做了"字符串里有没有 `http://` 这几个字"的**表层检查**,根本不验证 http:// 是否真的作为协议在起作用。所以在第 8 关的编码 payload 后面拼一个 `http://` 当诱饵即可,例如让它作 `alert()` 的参数:

```
javascript:alert('http://')   // javascript 部分仍用实体编码绕关键字
```

- **过滤器**:一搜 → "有 http://" → 放行。
- **浏览器**:解码执行 `alert('http://')`,那个 `http://` 只是 alert 的字符串参数,**对 XSS 触发毫无作用,纯粹是骗检测器的诱饵**。

**核心教训**:黑名单/关键字检测类防御的通病——**检查的是"表面特征"(含不含某字符串),攻击者只要"满足表面特征、实际干别的事"就能绕过。** "含有 http://" 和 "这是个安全网址" 之间隔着十万八千里。

## 1.8 第 10 关:隐藏参数——过滤的盲区(🔴 核心,训练"找隐藏可控点")

第 10 关的突破口**不在你一眼看到的输入框**(那个 `keyword` 被过滤得死死的),而在一个**页面上看不见、但其实可控**的隐藏参数。

源码里除了显示的 input,还藏着几个 `type="hidden"` 的 input,其中 `t_sort` 的值也取自用户输入、却几乎没过滤:

```php
echo '<input name="t_sort" value="'.$_GET['t_sort'].'" type="hidden">';  // 突破口
```

**为什么它是盲区**:开发者的注意力全集中在"用户看得见、会去输入"的那个显眼输入框上,把过滤火力都招呼在它身上,却**忘了这些藏起来的 hidden 参数也是用户可控的**(用户照样能在 URL 里手动加 `&t_sort=`)。

**绕过两步**:

1. **先意识到并控制它**:在 URL 后面手动加 `&t_sort=你的payload`(页面上看不到这个点,得扒 HTML 源码才发现)。
2. **闭合 + 改 type + 加事件**:payload `" type="text" onclick="alert('xss')` 代入后:
   ```html
   <input name="t_sort" value="" type="text" onclick="alert('xss')" type="hidden">
   ```
   - `"` 闭合掉 `value="`;
   - 新加的 `type="text"` **覆盖**掉后面原有的 `type="hidden"`(HTML 同名属性以先出现的为准)→ 隐藏框**显形成可见文本框**;
   - `onclick` 事件:点它就弹窗。点击这个现形的框 → 触发 → XSS 成功。

**核心教训(呼应 §1.2 步骤 1 和《SRC漏洞挖掘经验》)**:**越是"不起眼、不显示、容易被开发者忽略"的输入点,越可能是防护薄弱的突破口。** 测 XSS(及所有注入)时不能只盯显眼的输入框,要扒 HTML 源码,把所有 hidden 字段、所有 URL 参数都列出来挨个试。**"能不能找到那个看不见的可控点",是这一关真正训练的能力。**

## 2. HttpOnly(🟢 了解,防御方视角)

### 2.1 它是什么(复习)

HttpOnly 是设置 Cookie 时的一个标记。**Cookie 被标记为 HttpOnly 后,JavaScript 无法通过 `document.cookie` 读取它**,这个 Cookie 只能在 HTTP(S) 请求中由浏览器自动携带传输。详见《身份验证机制笔记》。

### 2.2 它防的是什么(精确定位)

**它只防"XSS 通过 JS 偷 Cookie"这一种利用方式,不防 XSS 本身。** 这个区分极其重要(在《XSS跨站-攻击利用手法》里强调过):

- HttpOnly 挡住:`document.cookie` 读 Cookie → 所以凭据窃取打不了。
- HttpOnly 挡不住:XSS 照样能执行、能发请求(数据提交手法)、能钓鱼、能挂 BeEF。

### 2.3 绕过手法(都很鸡肋,了解即可)

原笔记直接说了"有但鸡肋",几种历史手法:

> [!note] 🔎 补充(CVE 细节经联网核实)  
> **(1) CVE-2012-0053**:Apache HTTP Server **2.2.21 及更早版本**的一个信息泄露漏洞。原理:当请求触发一个畸形的 **400 错误页**时,Apache 默认的错误页会把请求头信息(**包括 HttpOnly 的 Cookie**)回显出来。攻击者可以用 XSS 让受害者浏览器发一个畸形请求,从 400 错误页里读到本该读不到的 HttpOnly Cookie。
>
> - **为什么鸡肋**:① 影响的 Apache 版本极老(2012 年的洞,2.2.21 以前),现代服务器基本都修了;② **它本身没法单独利用,必须配合另一个 XSS 漏洞才能触发**——而你既然已经有 XSS 了,往往有更直接的利用方式(数据提交等),没必要绕这个弯去偷 Cookie。

**(2) PHPINFO 页面**:如果目标站存在一个可访问的 `phpinfo.php`,这个页面会把当前请求的所有信息(包括 Cookie)打印出来。XSS 让受害者浏览器请求这个页面,就能从返回内容里提取 Cookie。鸡肋点:依赖目标恰好有暴露的 phpinfo 页面,少见。

**(3) Flash / Java**:利用早期 Flash/Java 插件的某些接口读取 Cookie。鸡肋点:**Flash 已于 2020 年底全面停用**(见《XSS跨站-框架与浏览器层变体》),Java 浏览器插件也早已淘汰,这条路基本死了。

### 2.4 实战结论

**遇到 HttpOnly,不要死磕"绕过它去偷 Cookie"**——这些绕过手法要么太老、要么条件苛刻。正确思路是**换利用方式**:用《XSS跨站-攻击利用手法》里讲的**数据提交(模拟请求,绕过 HttpOnly)、钓鱼、BeEF 浏览器控制**等,这些都不需要读 Cookie。这也是原笔记那句"一般可不采用获取 Cookie 利用,采用方式(钓鱼、浏览器攻击框架等)"的含义。

## 3. CSP(内容安全策略)(🟢 了解,防御方视角)

### 3.1 它是什么

CSP(Content Security Policy,内容安全策略)是一种**白名单机制**,由网站通过 HTTP 响应头(或 meta 标签)明确告诉浏览器:**这个页面只允许加载/执行来自哪些来源的脚本、样式、图片等资源。** 它的执行完全由浏览器完成,开发者只需提供配置。

> 类比:CSP 就像给页面请了一个严格的门卫,网站给门卫一份"准入名单"(白名单),门卫(浏览器)只放行名单上的资源来源,名单外的一律拒绝。

### 3.2 它能挡住什么(为什么它能减损 XSS)

CSP 能做到几件对 XSS 很致命的事:

- **禁止加载外域代码**:即使你注入了 `<script src="http://攻击者服务器/evil.js">`,CSP 不允许加载外域脚本 → BeEF 的 hook.js 这种外链脚本直接被挡(呼应《XSS跨站-攻击利用手法》BeEF 的防御视角)。
- **禁止外域提交**:即使 XSS 成立,偷到的数据也发不到攻击者的外域服务器(Cookie 外带被挡)。
- **禁止内联脚本执行**(规则较严格,原笔记提到 GitHub 在用):连 `<script>alert()</script>` 这种直接写在页面里的内联脚本都不执行——这几乎封死了大部分 XSS。
- **合理配置上报**:CSP 可以配置"违规上报",帮开发者及时发现 XSS 尝试。

### 3.3 绕过(依赖"配置不当",了解思路)

CSP 本身很强,**绕过的前提是它配置得不够严**。原笔记给的实验场景:

| CSP 配置             | 绕过条件                                                                              |
| ------------------ | --------------------------------------------------------------------------------- |
| 允许任何域加载 JS(配置形同虚设) | 直接外链脚本即可                                                                          |
| 只允许本地域加载 JS        | **文件上传 JS 绕过**:如果网站允许上传文件且能传到本域,把恶意 JS 当文件传上去,再用本域路径引用它——因为它现在是"本域资源",通过了 CSP 白名单 |
| 只允许本地域 + 限制目录      | **绕过 1**:目录里有 302 跳转——利用跳转从白名单目录"跳"到实际的恶意脚本<br />**绕过 2**:文件上传到 CSP 指定的那个允许目录     |

> **核心思路**:CSP 绕过本质是"**在白名单允许的范围内,塞进我的恶意脚本**"——最常见的就是配合文件上传(把恶意 JS 变成"本域合法资源")。这也再次说明漏洞常常是**组合利用**的(文件上传 + XSS + CSP 配置不当)。

### 3.4 相关度说明

CSP 的详细绕过是一个较进阶的专题(⚪ 扫过级别)。现阶段**理解"CSP 是脚本来源白名单、它能挡外链脚本和内联脚本"这个概念**,以及"绕过它通常要靠配置不当+文件上传"这个思路即可,不需要深挖每种 CSP 指令的绕过 payload。

- 深入参考:安全客 news/11816(课程提供)

## 4. 三道防线的协同:为什么现代 XSS 越来越难打

把三道防线合起来看,就明白为什么"纯弹窗容易、真正利用难":

```
你的 payload
    ↓
① WAF/Filter 这关 → 要过滤绕过(大小写/双写/编码/换标签)才能让脚本执行
    ↓ (假设绕过了,XSS 能执行了)
② CSP 这关 → 外链脚本加载不了、内联脚本执行不了、数据发不到外域
    ↓ (假设 CSP 配置不严,绕过了)
③ HttpOnly 这关 → 偷不到 Cookie,只能改用数据提交/钓鱼/BeEF 等方式利用
```

**攻击者视角的应对优先级**:

- **Filter 必须正面突破**(过滤绕过,🔴 核心,每次都要用)。
- **CSP 看配置吃饭**:配置松就靠文件上传等绕;配置死(禁内联+禁外域)就很难,可能要放弃 XSS 转找别的洞。
- **HttpOnly 别死磕**:直接换"不偷 Cookie"的利用方式。

## 5. 自测(先自己想,再看答案)

1. 黑盒测 XSS 时,你打了个 payload 没弹窗。按四步法,你接下来最该做的一件事是什么?为什么"没弹窗"反而是有用的信息?
2. xss-labs 里,你的输入被显示成了 `&lt;script&gt;alert()&lt;/script&gt;`(尖括号被实体化),而且你的输入是被包在 `<input value="你的输入">` 里的。这种情况下 `<script>` 标签打不出来,你会怎么绕?
3. 一个网站同时上了 HttpOnly 和严格的 CSP(禁内联脚本、禁外域)。假设你还是打出了 XSS,HttpOnly 让你偷不到 Cookie——这时候你还能怎么利用这个 XSS?

<details>

<summary>参考答案</summary>

1. 最该做的是:去页面 HTML 源码里找到"我的 payload 被显示在了什么位置、变成了什么样子"。因为"没弹窗"背后,过滤把 payload 改成的那个形态,恰恰暴露了过滤规则的全部信息(删了什么、转义了什么、把我括在哪)——看清楚了才能对症换写法。失败不是终点,而是诊断过滤规则的信息来源。
2. 尖括号被实体化意味着打不出新标签,但我的输入在 `value="..."` 属性里——所以改用"闭合属性 + 加事件"的思路:输入 `" onfocus=javascript:alert() autofocus="`(或类似),先用 `"` 闭合掉 `value="`,然后给这个 input 标签加一个 `onfocus` 事件执行 JS(配合 autofocus 自动触发)。核心是"标签打不了就给现有标签加事件属性"。
3. HttpOnly 只挡"偷 Cookie",挡不住 XSS 本身能执行 JS。所以可以改用《XSS跨站-攻击利用手法》里的"数据提交"手法——用 JS 借受害者已登录的身份直接发请求(浏览器会自动带上 HttpOnly 的 Cookie),冒充受害者做操作(改密码、发帖、如果是管理员甚至写 Shell)。不过注意:如果 CSP 严格到禁止内联脚本,那连 XSS 执行这一步都可能被挡——所以题目假设"还是打出了 XSS"的前提下,数据提交是最现实的利用方式。

</details>
