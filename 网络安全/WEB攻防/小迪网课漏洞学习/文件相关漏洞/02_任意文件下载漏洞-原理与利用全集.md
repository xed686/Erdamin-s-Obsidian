## 1. 任意文件下载是什么 🔴 核心 —— 必须吃透

### 1.1 它是什么：两种 URL 形态（从"固定文件"到"参数可控"）

**定义**：任意文件下载 = 服务器**按你指定的路径**读一个文件、把内容返回给你。下载功能天生就是"读取"接口，所以"文件下载漏洞"和"任意文件读取"是同一件事，只是叫法随场景走。

它有两种 URL 形态：

```text
① 常规下载（安全写法）：路径写死，参数只决定"哪一个"
   http://target/upload/123.pdf

② 危险写法：文件名本身来自参数
   http://target/download?file=123.pdf
   http://target/xx.xx?file=123.pdf&name=报表
```

**关键就在第 ②  种**：`file=` 这个值一旦不做限制，你填 `../../etc/passwd`、`../config.php`、`/root/.ssh/id_rsa`，服务器就照着读。

> 类比：**下载接口像一个"代取快递"的服务**——你报单号，它去仓库把包裹拿出来给你。正常只该取**你自己那格**的包裹；但如果它按你报的"路径"去拿，你就能报"管理员办公室的抽屉号"。
> 类比哪里不准确：真实系统里通常还有一层"前缀拼接"（`/var/www/upload/` + 你输入），所以要靠 `../` 把前缀抵消掉才能出去——这正是路径穿越要解决的问题。

### 1.2 为什么会存在（root cause）：路径由数据决定

**正常流程**：开发者写死文件路径，或者只允许用户传"编号"，由服务端映射到真实文件。

**错误写法**：

```php
// ❌ 有问题：用户输入直接拼进读取路径
$file = $_GET['file'];                       // source：用户可控
$path = '/var/www/upload/' . $file;          // sink 前半段：前缀拼接
header('Content-Type: application/octet-stream');
header('Content-Disposition: attachment; filename="' . basename($file) . '"');
readfile($path);                             // sink：读文件并输出
```

```php
// ✅ 修复思路：白名单映射 + 规范化后校验前缀
$allow = ['report' => 'report_2026.pdf', 'invoice' => 'invoice.pdf'];
if (!isset($allow[$_GET['key']])) { http_response_code(403); exit; }
$path = realpath(__DIR__ . '/upload/' . $allow[$_GET['key']]);
if ($path === false || strpos($path, realpath(__DIR__ . '/upload/')) !== 0) { http_response_code(403); exit; }
readfile($path);
```

**root cause 一句话**：**"读哪个文件"这个决定权，从代码转移到了用户输入**——和 SQL 注入、文件包含同一个根：**数据越界成了指令**。
- SQL 注入：数据进了语句
- 文件包含：数据进了"被执行的路径"
- **文件下载：数据进了"被读取的路径"**

**为什么前缀拼接挡不住**：`/var/www/upload/` + `../../etc/passwd` = `/var/www/upload/../../etc/passwd` → 规范化后就是 `/var/etc/passwd` 的上一层，`../` 能把前缀整段抵消。**只要拼接发生在"校验之后"或干脆没校验，前缀就等于不存在。**

### 1.3 下载点 ≠ 包含点：一个必须分清的边界 🟡 重要

同一个 `?file=` 参数，可能是三种完全不同的漏洞，**打法完全不同**：

|        | 文件下载 / 读取                                      | 文件包含（LFI）                 | 文件写入                           |
| ------ | ---------------------------------------------- | ------------------------- | ------------------------------ |
| 服务端做什么 | 读**字节**并输出                                     | 把文件**当代码执行**              | 把数据**写进文件**                    |
| 你看到什么  | 文件**原文**（php 源码就是源码）                           | 代码的**执行结果**（源码看不到）        | 看写入结果                          |
| 典型函数   | `readfile` / `file_get_contents` / `fpassthru` | `include` / `require`     | `file_put_contents` / `fwrite` |
| 打法重点   | 读配置、读源码、读私钥                                    | `php://filter` 读源码、伪协议求执行 | `php://filter/write` 落 shell   |

> [!note] 🔎 补充（非原笔记内容）+ 实测：本机 PHP 7.3.4 上的四条结论
> 我用一个"前缀拼接 + readfile"的迷你下载点做了实测，结果对判断很关键：
>
> | 测试 | 结果 | 说明 |
> |---|---|---|
> | `readfile('upload/../secret/config.php')` | 输出**文件原文** | 下载点是"读字节"通道，php 文件给你的是**源码**，不是执行结果 |
> | `file_get_contents('php://filter/read=convert.base64-encode/resource=secret/config.php')` | 得到 base64（`PD9waHAg...`） | 读点同样支持伪协议 |
> | `readfile('php://filter/...')` | 成功，返回 48 字节 | **`readfile` 也吃 `php://filter`**——下载点被 WAF 拦 `<?php` 关键字时，编码后再输出很实用 |
> | `readfile("config.php\0.jpg")` | `false`（失败） | **`%00` 截断在 PHP 7 已失效**，别在现网系统上指望它 |
> | 参数里直接写 `%2e%2e` / `..%2f` | **失败** | 编码必须由 HTTP 层**解码之后**才变成 `../`；把 `%2e` 直接塞进 PHP 字符串里就是字面量，不是穿越 |
> | `file_get_contents('phar://nope.phar/x')` | `false`，无致命错误 | phar 用错不炸，但**能否触发反序列化要看是否存在可上传的 phar 文件**（本条未实测） |

> 💡 **记住一句**：**下载点是"读"，包含点是"执行"。** 拿到一个 `?file=`，先用 `?file=index.php` 试一次——**看到源码原文就是下载点，看到页面结构/空白就是包含点**。这个判断决定了后面所有打法。

## 2. 黑盒：从功能点和 URL 特征里找人 🟡 重要

### 2.1 先找功能点（这几类地方最出问题）

| 功能点                        | 为什么高发                        |
| -------------------------- | ---------------------------- |
| **文件下载 / 附件下载 / 导出**       | 天生就是"按名字取文件"，最典型             |
| **文件上传**                   | 上传后常带"预览/下载"回显接口             |
| **文件删除**                   | 后台文件管理；见 §5.3                |
| **文件管理器 / 网盘 / 在线预览**      | 一个接口管全目录，出洞概率最高              |
| **报表导出、发票/合同下载、日志查看、备份下载** | 业务性强，常由外包或老代码实现              |
| **头像/图片预览、静态资源代理**         | `?src=` `?url=` 类，可能同时是 SSRF |

### 2.2 URL 与参数特征（照着挑，别逐个点）

| 类别          | 常见取值                                                                                                                         |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **路径里的动作名** | `download`、`down`、`downfile`、`readfile`、`read`、`getfile`、`export`、`preview`、`del`、`delete`、`dir`、`list`、`path`、`src`、`lang`  |
| **参数名**     | `file`、`filename`、`fileName`、`path`、`filepath`、`filePath`、`realpath`、`readfile`、`data`、`url`、`src`、`name`、`doc`、`attachment` |
| **可疑形态**    | `?file=xxx.pdf`、`?path=/upload/`、`?name=../../`、`?url=http://...`（顺带测 SSRF）                                                  |

> 🔎 补充（非原笔记内容）：`?url=` / `?src=` 这类参数要**同时按两个方向测**——当它只接受站内相对路径时是文件读取，当它接受任意域名时就是 SSRF（详见 [[01_SSRF实战挖掘-功能点识别与工具辅助]]）。同一个参数两种洞，别漏。

### 2.3 判断三步（每一步都在排除一种可能）

> 类比：**像试钥匙**。先用一把"肯定配得上"的（已知存在的文件）确认锁没换；再试"能不能开别人家的门"（`../`），确认它认不认路径；最后试"有没有加装锁芯"（过滤），确认哪把钥匙还插得进去。
> 类比不准的地方：锁不会告诉你"钥匙错了"的原因，而服务器会——报错、403、超时都是线索，别把"没打开"直接当成"没有门"。

**步骤 1：确认响应是不是"文件流"**
- 做什么：请求 `?file=` 换成一个**确定存在的**文件名（如 `index.php`、`robots.txt`）
- 为什么：先确认这个参数确实在控制文件，而不是被忽略或只做展示
- 得到什么：看响应头 `Content-Disposition: attachment`、`Content-Length`、`Content-Type: application/octet-stream`——有这些基本就是真下载；正文里出现文件内容也算
- 如果不是预期：参数可能只接受 ID（那要换思路：ID 遍历就是越权/IDOR）、或者需要登录态/签名

**步骤 2：确认路径基准在哪**
- 做什么：依次试 `?file=../index.php`、`?file=../../index.php`、`?file=/etc/passwd`（Windows：`C:\Windows\win.ini`）
- 为什么：前缀拼接的层数决定了要几个 `../`；绝对路径能直接越过前缀（如果代码用 `file_get_contents($f)` 且没做 realpath 校验）
- 得到什么：找到一个稳定的"能读到已知文件"的深度
- 如果不是预期：见下表

**步骤 3：试过滤边界**
- 做什么：`..%2f`、`%2e%2e%2f`、`....//`、`..\`（Windows）、`/./`、双写、加后缀白名单绕过（`?file=x.pdf/../../config.php`）
- 为什么：过滤多半是"删一次 `../`"或"只校验后缀"，这两种都能绕
- 得到什么：穿过过滤的那一种写法，就是你后面所有请求的模板

**失败原因排查表（比换 payload 有用）**：

| 现象               | 最可能的原因                                                         |
| ---------------- | -------------------------------------------------------------- |
| 永远返回同一个文件 / 参数无效 | 参数不是路径，是 ID 或枚举（换思路：IDOR / 枚举）                                 |
| 报 403 / 拒绝       | 有白名单或 realpath 前缀校验（大概率绕不过，别硬刚）                                |
| 提示"文件不存在"但路径明明对  | 相对基准不是你以为的目录；试 `./`、`../` 多加一层，或用报错里的绝对路径反推                    |
| 能读小文件、读大文件超时/截断  | 服务端有 `readfile` 分块或超时；优先读配置（几 KB），别去读几十 MB 的日志                 |
| 只能读特定后缀          | 后缀白名单 → 试 `x.pdf/../../config.php`、`x.pdf%00`（PHP7 已失效，见 §1.3） |
|                  |                                                                |

## 3. 白盒：搜什么函数，问三个问题 🟡 重要

### 3.1 函数清单（按"读 / 下 / 目录 / 删"四类记）

| 语言 | 读取 / 下载 | 目录操作 | 删除 |
|---|---|---|---|
| **PHP**（最常考） | `readfile`、`file_get_contents`、`fopen`+`fread`/`fpassthru`、`SplFileObject`、`highlight_file`/`show_source`、`readgzfile` | `scandir`、`opendir`/`readdir`、`glob`、`dir()` | `unlink`、`rmdir`、`rename` |
| **Java** | `Files.copy`、`FileInputStream`、`ResponseEntity<Resource>`、`ResourceHttpRequestHandler` | `File.listFiles`、`Files.walk`、`Files.list` | `File.delete`、`Files.delete`、`Files.deleteIfExists` |
| **ASP.NET** | `Response.WriteFile`、`FileStream`、`File.ReadAllBytes`、`PhysicalFile` | `Directory.GetFiles` | `File.Delete`、`Directory.Delete` |
| **Node.js** | `fs.createReadStream`、`res.sendFile`、`res.download` | `fs.readdir`、`fs.readdirSync` | `fs.unlink`、`fs.rm` |

**审计要点**：`res.sendFile` / `ResponseEntity<Resource>` / `PhysicalFile` 这类**框架级下载 API** 最容易被忘——开发者以为"用了框架就安全"，实际上路径还是他拼的。

### 3.2 审计三问（跟文件包含是同一套）

1. **路径可控吗**：来自 `$_GET`/`$_POST`/`$_COOKIE`/header/数据库？还是写死的？
2. **过滤做了什么**：删 `../`（可绕）、白名单后缀（可绕 `x.pdf/../..`）、`realpath` + 前缀校验（难绕）、还是干脆没有？
3. **读出来的东西去哪了**：直接输出给浏览器（下载）？还是拼进别的函数（可能就是包含/命令执行）？

> 第三问最容易被忽略：**同一个参数先被下载、又被 `include`** 的代码并不少见——那它同时是读取和 RCE 两个洞。

## 4. 读到什么才值钱 + 怎么证明影响 🔴 核心 —— 这一节决定你报低危还是高危

### 4.1 按"值不值钱"排的读取清单

> 类比：**进了大楼别只在前台拍照。** `/etc/passwd` 相当于"我能证明我进得来"；真正值钱的是机房钥匙（配置里的口令）、保险柜密码（云 AK/SK）、员工名册（会话与凭据）。报告里贴哪张照片，决定这个洞值多少钱。

| 目标文件 | 你能拿到什么 | 价值 |
|---|---|---|
| `/etc/passwd`、`/etc/hosts`、`C:\Windows\win.ini` | 只证明"能读" | **低**（大多数系统它本来就可读） |
| 应用配置：`config.php`、`.env`、`web.config`、`appsettings.json`、`application.yml` | **数据库口令、云 AK/SK、JWT/加密密钥、第三方 API key** | **高** |
| 源码 / 源码备份：`.php` 原文、`www.zip`、`wwwroot.tar.gz`、`.git/config`、`.svn/entries` | 上传点、后台路径、SQL 写法、其他洞 | **高** |
| SSH 私钥 / 凭据：`~/.ssh/id_rsa`、`/root/.bash_history`、`/etc/shadow`（有权限才行） | 直接登录主机 | **极高** |
| 会话与日志：`/tmp/sess_xxx`、`/var/log/nginx/access.log` | 会话劫持；配合包含 → RCE | **高（间接）** |
| 数据库文件：MySQL 数据目录、SQLite `.db` | 全量数据 | **高** |
| 容器与云元数据（不是文件但同类） | `169.254.169.254` 凭据（走 SSRF） | **高** |

> **实战顺序**：先读**应用自己的** `config` / `.env`（命中率最高、体量小、价值最大），再读源码备份，最后才是系统文件。**别一上来就读 `/etc/passwd`——那是最没信息量的一个。**

### 4.2 从"能读"到"能控制"的四条常见延伸

1. **读配置 → 连数据库**：拿到 MySQL 口令后从外网/内网连库 → 读全量数据、写文件拿 shell（详见 [[04_MySQL高权限注入利用笔记]]）。
2. **读源码 → 找下一个洞**：源码里往往有上传点、后台口令、内部接口地址、测试环境域名。
3. **读日志 / 会话 → 结合文件包含拿 RCE**：见 [[01_文件包含漏洞-原理与利用全集]] §4.2。
4. **读云凭据 / 私钥 → 横向到主机或云账号**：这一步的定级通常是"严重"。

### 4.3 影响证明的三级写法（报告里直接用）

| 层级    | 证据                                                 | 常见定级        |
| ----- | -------------------------------------------------- | ----------- |
| **弱** | 能读 `/etc/passwd` 之类公共可读文件                          | 低 / 中（信息泄露） |
| **中** | 读到应用配置里的**数据库口令、云 AK/SK、JWT 密钥**（在报告里打码，只露键名与前后几位） | 高           |
| **高** | 用读到的凭据**实际连上数据库/进入后台**，或由此拿到 RCE                   | 严重          |

> ⚠️ 三条纪律：① 只读到"能证明危害"为止，**不要拖库、不要改数据**；② 报告里的密钥/口令**打码**，用"存在且有效"作为证明；③ 读取行为、时间、文件路径要如实记录，方便复测与清理。

### 4.4 案例锚点：一个"读文件"读成 9.8 分的真实事件

> **CVE-2018-13379（Fortinet FortiOS SSL VPN 路径穿越）**——已联网核实（NVD、Rapid7、Fortinet PSIRT，2026-11）
> **发生了什么**：FortiOS SSL VPN Web 门户存在路径穿越，**未认证**攻击者可构造特殊 HTTP 请求**下载系统文件**；被读取的会话文件里含**明文凭据**，2020 年 11 月公开报道约 **5 万台** VPN 设备的凭据被打包泄露，2021 年 4 月 CISA/FBI 联合预警，该 CVE 已进 CISA 已知被利用目录，CVSS 9.8。
> **根因对应本篇哪一环**：路径穿越（§1.2 的"读哪个文件由请求决定"）——它连"登录后才有下载功能"这层都没有，**未认证**就能读。
> **业务后果**：会话文件 → 明文 VPN 凭据 → 攻击者直接以员工身份进入内网；打补丁后没改口令的设备**依然中招**（凭据已经泄露）。
> **对你的启发**：① 一个"只能读文件"的洞，价值取决于**读到了什么**——读会话文件等同于读到了身份；② 补丁修的是漏洞，**不修已经泄露的凭据**，所以复测要看"是否改口令"；③ 别把任意文件读取当"低危凑数"，先找会话/配置/密钥。

## 5. 同一类功能的另外三个面

### 5.1 目录索引（Directory Listing）🟢 了解 —— 顺手捞备份

服务器没关目录浏览，访问以 `/` 结尾的目录会**列出全部文件名**：

```
GET /backup/        →  Index of /backup  →  www.zip  db.sql  config.bak
GET /upload/        →  一堆用户上传的文件，能找到别人的报表/证件/源码
```

- **判断**：URL 以 `/` 结尾返回文件列表（不是 403、不是首页）；常见 `/backup/`、`/upload/`、`/uploads/`、`/logs/`、`/temp/`、`/.git/`。
- **利用**：拿到备份包/源码压缩包就下载 → 里面通常有配置和口令；`.git/` 可配合 git 泄露工具还原源码（详见 [[04_Webpack技术与源码泄露笔记]] 同族思路）。
- **可迁移思路**：**"能列目录"是"能下载"的放大器**——它直接告诉你该下载哪个文件，省掉猜名字。

### 5.2 路径穿越（Path Traversal）🟢 了解 —— 原理已在别处讲透

本篇所有 `../` 的写法，底层都是路径穿越：**用户可控的路径里用 `../` 抵消掉服务端拼的前缀，从而访问目录之外的文件**。

- 完整原理、各种编码与过滤绕过、Windows 特性（`..\`、`::$DATA`） → 详见 [[00_路径穿越漏洞详解]]，本篇不重复。
- 这里只补一句**衔接**：路径穿越是**手段**，任意文件读取/下载是**结果**；你在下载点上打的所有 `../`，都该回到那篇去查有没有更细的绕法。

### 5.3 文件删除 🟡 重要 —— 后台里的组合拳

> 类比：**把门上的"本店已开业"封条撕掉，再按一遍"开张流程"，你就能自己当老板。** 很多建站程序的安装向导正是这套逻辑：看到 `install.lock` 就认为"已装好"、拒绝重装；删掉封条，重装流程就重新开放，管理员账号和数据库连接都能被重设。
> 类比不准的地方：真实程序往往还有第二道判断（数据库非空、已安装标记写在配置里），所以"删了封条"不一定"能开张"——这就是下面三个前置条件要逐个确认的原因。

文件删除本身危害看似小（删个文件而已），但它能造成的后果常常被低估：

| 利用方式                                  | 机制                                                                                | 后果                  |
| ------------------------------------- | --------------------------------------------------------------------------------- | ------------------- |
| **删安装锁 → 重装 → 接管**（原笔记："配合程序重装或高危操作"） | 很多 CMS 用 `install.lock` / `install/` 目录标记"已安装"；删掉锁文件后重新访问安装向导，就能**重新设置管理员账号和数据库** | 网站完全被接管             |
| **删 `.htaccess` / 安全配置**              | 上传目录原本靠 `.htaccess` 禁止执行 php；删掉后上传的马就能跑                                           | 上传漏洞被"解锁"           |
| **删日志 / 删审计记录**                       | 清掉自己的访问痕迹                                                                         | 反取证                 |
| **删配置文件 / 关键目录**                      | 直接造成业务中断                                                                          | DoS（部分 SRC 只认可用性影响） |

**前置条件（缺一不可，也是复测要点）**：
1. 有可用的删除功能，且**删除路径可控**（很多只允许删上传目录内的文件，那就只能配合上传点做组合）；
2. **安装程序或向导文件还在**（`install/`、`setup.php` 没被删）；
3. 站点**允许重新安装**（有些程序检测到已安装会拒绝，或要求数据库为空）。

> 🔎 补充（非原笔记内容）：这条链在真实环境里成功率不高（三个条件都得满足），但在**打包下载的 CMS / 建站程序**上很常见，尤其"安装目录忘了删 + 删除功能没做路径限制"两个错误同时出现的站点。复测时先查这三条，别一上来就在客户生产站上试删除——**删除是不可逆操作，必须书面授权**。

## 6. 防御与检测 🟡 重要

| 攻击手法    | 正确防御                                                                     | 为什么"简单过滤"不够                                       |
| ------- | ------------------------------------------------------------------------ | ------------------------------------------------- |
| 参数直接拼路径 | **白名单映射**（用户传键，真实文件名写死在代码里）                                              | 只删 `../` → 可用绝对路径、`....//`、编码绕过                   |
| 相对路径穿越  | `realpath()` 规范化后**校验是否在允许目录前缀内**                                        | 只判断"包不包含 `..`" → `..%2f`、`..\`、二次解码都能过            |
| 后缀白名单被绕 | 先规范化再校验后缀，不接受"路径里带后缀"                                                    | `x.pdf/../../config.php` 这类写法靠"路径中含 .pdf"就能骗过朴素校验 |
| 读配置/密钥  | **下载目录与配置分离**；Web 用户对配置、私钥、日志**无读权限**                                    | 权限不收紧，代码修好了换个入口还能读                                |
| 目录被遍历   | Nginx `autoindex off` / Apache `Options -Indexes`；`.git`、`backup` 目录禁止访问 | 只是"没有链接"，不代表不能直接访问                                |
| 删除被滥用   | 删除操作加**权限校验 + CSRF + 二次确认 + 软删除（回收站）**；安装锁文件不放 Web 目录                    | 只在前端藏按钮 → 直接调接口照样删                                |
| 会话/日志被读 | 会话目录、日志目录权限收紧；日志不放在 Web 根下                                               | 日志总要写，路径可猜、权限放开就还能读                               |

**一句话防御**：**不让用户输入进路径（白名单映射 + realpath 前缀校验）**，再叠加"敏感文件对 Web 用户不可读 + 目录索引关闭 + 删除走回收站、安装锁不放 Web 根"。

## 7. 把它串起来

**先用 5 条复述出骨架**：

1. **机制**：下载 = 服务器读文件给你，路径可控 → 任意文件读取（§1）。
2. **边界**：看到源码原文是"读"，看到执行结果是"包含"，打法不同（§1.3）。
3. **找点**：URL 动作名 + 参数名（`download/del/dir`、`file/path/src`），功能点优先看下载/上传/文件管理器（§2）。
4. **值钱**：先读配置与源码（口令、密钥、上传点），别把 `/etc/passwd` 当成果（§4.1）。
5. **定级**：能读普通文件≠高危；读到凭据或由此接管才有分量（§4.3）。

```
① 找一个"按名字取文件"的参数（§2.2）
        ↓
② 换已知文件，看响应头/正文（§2.3-1）——拿到文件流就确认了
        ↓
③ 试 ../ 层数 / 绝对路径（§2.3-2），失败按排查表换原因而不是换 payload
        ↓
④ 先读 config/.env/源码备份（§4.1），拿到的是"键"还是"值"决定下一步
        ↓
⑤ 分叉：
   ├─ 读到数据库口令 → 连库 → 数据/写文件（§4.2）
   ├─ 读到源码     → 找上传点/后台/其他洞（§4.2）
   ├─ 读到会话/日志 → 配合文件包含 → RCE（§1.3 + 包含篇 §4.2）
   └─ 只有 /etc/passwd → 继续找配置，或降级如实写"信息泄露-低"
        ↓
⑥ 报告：打码证据 + 三级定级（§4.3）→ 复测看 realpath/白名单/权限是否都改了
```

## 8. 自测（先自己想，再看答案）

1. 同一个 `?file=` 参数，你怎么用一次请求判断它是"下载点"还是"包含点"？判断错了会浪费什么时间？
2. 服务端已经拼了 `/var/www/upload/` 前缀，为什么 `../` 还能读到 `/etc/passwd`？前缀拼接在什么情况下反而能挡住你？
3. 你手上有一个能读任意文件的洞，只能读 3 个文件。你读哪三个？为什么不是 `/etc/passwd`？
4. 后台有个删除文件的功能，"删安装锁 → 重装 → 接管"要满足哪三个条件？哪一个是复测时最容易被忽略的？
5. 实测里 `?file=..%2f..%2fetc/passwd` 在 URL 里有效、但把 `%2e%2e` 直接写进 PHP 字符串就无效——为什么？
3
<details>
<summary>参考答案</summary>

1. 请求 `?file=index.php`（一个确定存在的 php 文件）：**返回源码原文**说明它只是"读字节"（下载点）；**返回页面结构/空白/报错**说明它把文件当代码执行了（包含点）。判断错方向的代价：在下载点上一直试 `php://input`/`data://`（永远不会成功），或在包含点上一直想读源码（永远读不到，因为源码被执行了）。
2. 因为 `../` 是文件系统的"上一级"指令，`/var/www/upload/../../etc/passwd` 规范化后就是 `/etc/passwd`，前缀被抵消。前缀能挡住你的是两种情形：① 代码用 `realpath()` 规范化后再校验"结果是否还在允许目录内"；② 用户根本不能控制整段路径（只能传 ID，由服务端映射真实文件名）。
3. 例如：① 应用配置（`config.php` / `.env` / `application.yml`）——数据库口令、云密钥；② 源码或源码备份——上传点、后台路径、其它洞；③ 会话文件或日志——可结合文件包含拿 RCE。不选 `/etc/passwd` 是因为它只证明"能读"（价值低），而这些文件能证明"能控制"，直接决定报告的定级。
4. ① 删除功能可用且删除路径可控；② 安装程序/向导文件还在（`install/`、`setup.php` 没删）；③ 站点允许重新安装（不检测"已安装"或数据库为空时可装）。最容易被忽略的是第 ③——很多人删完锁文件发现装不上，是因为程序自己还有一层"已安装"判断；另一个易漏点是"删除路径被限制在上传目录内"，那就得先配合上传点。
5. 因为 `%2e%2e` 是 **URL 编码**：只有在 HTTP 请求进入应用、被**解码一次**之后，它才变成 `../` 这个真实字符序列。你在 PHP 里直接把 `"%2e%2e"` 当字符串传给文件函数，传进去的就是字面的 `%2e%2e`，文件系统不认识它，自然读不到。

</details>

- **原笔记引用的 4 篇复盘文章**（微信公众号）我**未核实内容**，仅作为你自己阅读的线索保留，不作为本笔记的论据。

- **`readfile` 支持哪些 wrapper**：`php://filter` 已实测通过；`zip://`、`compress.zlib://` 等未测，用到时以目标环境的 PHP 版本为准。
