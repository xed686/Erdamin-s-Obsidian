## 1. CSRF 原理(🔴 核心)

### 1.1 它是什么

CSRF(Cross-Site Request Forgery,跨站请求伪造)——攻击者**诱导一个已经登录目标网站的受害者**,去访问一个攻击者精心构造的页面/链接,这个页面会**悄悄地以受害者的身份,向目标网站发出一个攻击者想要的请求**(比如转账、改密码),而受害者**全程不知情**。

> 类比:你(受害者)在银行(网站A)办完事没退出登录,银行认得你这个人(Cookie)。这时一个骗子(网站B)给你一张"看起来人畜无害的传单"(恶意页面),你一看,传单背面却偷偷印着"请银行把我账户的钱转给骗子"的指令,而且这张传单会**自动替你把这个指令递给银行**。银行一看指令是从"你的手"递过来的(带着你的 Cookie),以为是你本人要转账,就照做了。你从头到尾只是看了张传单,钱却没了。

### 1.2 为什么会存在(root cause)

root cause 一句话:**网站无法区分"这个请求是用户本人主动发起的,还是被攻击者诱导发起的"——因为两者带的 Cookie 一模一样。**

拆解整条攻击链(对应你上传的图1):
```
① 用户登录受信任的网站 A(如银行)→ A 返回 Cookie,浏览器保存
② 用户没退出登录(Cookie 还有效)
③ 攻击者诱导用户访问恶意网站 B(发个链接、诱人的页面)
④ 网站 B 的页面里,藏了一个"自动向网站 A 发请求"的代码
   (比如一个自动提交的表单,或一个 <img src=A的转账接口>)
⑤ 用户浏览器向 A 发这个请求时,【自动带上了 A 的 Cookie】
   → A 一看 Cookie 有效,以为是用户本人操作 → 执行了(转账/改密码)
```

**最关键的是第⑤步**:浏览器有一个"天性"——**只要向某个网站发请求,就自动带上该网站的 Cookie,不管这个请求是从哪个页面发起的。** 攻击者正是利用这个"天性":他让受害者的浏览器向 A 发请求,浏览器就乖乖带上了 A 的 Cookie,A 无法分辨"这请求到底是用户自己点的,还是被 B 诱导的"。

> [!note] 🔎 补充(非原笔记内容):CSRF 和 XSS 的区别
> 这两个经常被搞混,一句话分清:
> - **XSS**:攻击者让**恶意 JS 在受害者浏览器里执行**(偷 Cookie、改页面)。XSS 是"在你的页面里运行了我的代码"。
> - **CSRF**:攻击者**不执行任何 JS**(不需要),只是**诱导你的浏览器发一个请求**。CSRF 是"借你的身份发了个请求",它甚至不需要往目标网站注入任何代码。
> - **联系**:CSRF 需要"诱导受害者访问恶意页面"这个前提;如果目标站本身有存储型 XSS,攻击者可以用 XSS 来**自动触发 CSRF**(不用诱导,受害者正常浏览就中招)——这就是后面绕过里"配合存储 XSS"的思路,两者可以组合。

### 1.3 怎么做(攻击流程)

**步骤 1:找到一个"有价值、且无 CSRF 防护"的功能点**
- 做什么:找目标网站里"执行某个操作"的请求(改密码、转账、改邮箱),分析它的请求格式(URL、参数、方法)。
- 为什么:CSRF 要伪造的就是这个请求,得先搞清楚它长什么样。

**步骤 2:构造一个"自动发起这个请求"的恶意页面(PoC)**
- 做什么:做一个 HTML 页面,里面放一个会**自动提交**的表单(或图片),目标指向那个功能点的接口,参数填好攻击者想要的值。
- 为什么:让受害者一打开这个页面,浏览器就自动替他发出攻击请求。

**步骤 3:诱导已登录的受害者访问这个页面**
- 做什么:把这个恶意页面放到自己的服务器,通过钓鱼(邮件、私信)诱导受害者点击;或配合目标站的存储型 XSS 自动触发。
- 为什么:CSRF 成立的前提是"受害者当前登录着目标网站"且"访问了恶意页面"。

**步骤 4:受害者访问 → 浏览器自动带 Cookie 发请求 → 攻击完成**

### 1.4 哪些功能点被 CSRF 打中危害最大(🔴 核心,实战必记)

这是你挖 CSRF 时要优先盯的高价值功能点:

| 功能点 | 被 CSRF 打中的后果 |
|---|---|
| **删除账户** | 直接把受害者账户删了 |
| **更改电子邮件** | 改成攻击者的邮箱 → 后续可用"忘记密码"接管账户 |
| **更改密码(尤其不需要输旧密码的)** | 直接把密码改成攻击者知道的 → 接管账户 |
| **添加新管理员(如果支持角色)** | 给攻击者加一个管理员账号 → 控制整站 |
| **更改个人信息**(姓名等) | 篡改受害者资料 |
| **更改/删除头像** | 篡改 |
| **通知类复选框设置** | 篡改设置 |

> 💡 优先级判断(呼应《SRC漏洞挖掘经验》):**"改邮箱"和"改密码(不验旧密码)"是 CSRF 里最值钱的两个点**——因为它们能直接导向"账户接管"。看到这类功能且没 CSRF 防护,危害评级很高。

### 1.5 实战怎么用

- **什么时候该想到它**:看到任何"执行状态改变操作"的请求(增删改类,不是单纯查询),就该检查它有没有 CSRF 防护。
- **怎么验证(黑盒)**:把这个请求用 Burp 重放,**去掉 Referer、去掉可能的 token**,看它还能不能成功执行。能 → 大概率有 CSRF。
- **怎么验证(白盒)**:看代码里这个接口有没有校验 token、有没有校验来源(Referer/Origin)。
- **下一步**:确认无防护后,用 Burp 生成 PoC(见第 4 节),诱导/配合 XSS 触发。

### 1.6 易错点

- **误区:以为"查询类"功能也能 CSRF。** CSRF 的危害在于"**让受害者执行了改变状态的操作**"(转账、改密码)。纯查询(看数据)就算被 CSRF,攻击者也拿不到返回结果(返回给的是受害者浏览器,不是攻击者),所以 CSRF 几乎只针对**增删改**类操作。

## 2. 防护方案一:Referer 校验(🟡 重要)

### 2.1 原理

对应你上传的图2。服务器检查请求的 **`Referer` 头**(这个请求是从哪个页面发起的),**如果 Referer 不是本站域名,就判定为非法请求,拒绝。**

```
正常转账:用户在 www.bankchina.com 上操作 → Referer: www.bankchina.com → 放行
CSRF 攻击:请求从 www.bankhacker.com 的恶意页面发起 → Referer: www.bankhacker.com → 拒绝 ✅
```

**思路**:正常的转账请求,肯定是从银行自己的页面发起的;如果一个转账请求的来源页是别的网站,那十有八九是 CSRF,拒绝掉。

### 2.2 为什么这个防护不够牢靠

Referer 校验属于"**比较弱的防护**",因为:
1. **Referer 可能为空**:用户直接访问、或页面设置了 `<meta name="referrer" content="no-referrer">`,请求就不带 Referer 了。如果服务器"Referer 为空时也放行"(很多图省事的代码会这样),就被绕过了。
2. **校验逻辑容易写不严谨**:见第 5 节的绕过(如只检查"有没有包含本站域名"这种表层匹配)。

---

## 3. 防护方案二:CSRF Token(🔴 核心,根本防御)

### 3.1 原理

对应你上传的图3。这是 **防 CSRF 最根本、最可靠的方案**。核心思路:**给表单里塞一个攻击者"拿不到、也猜不到"的随机值(Token),提交时校验它。**

完整流程:
```
① 用户第一次请求表单页面时,服务器生成一个随机值 Token,
   一方面存进服务器的 session,另一方面藏在表单的一个 hidden 字段里返回
   <input type="hidden" name="csrf_token" value="随机值abc123">
② 用户提交表单时,这个 Token 跟着一起提交
③ 服务器比对:提交的 Token == session 里存的 Token?
   相同 → 合法请求,放行
   不同/没有 → 判定为 CSRF 攻击,拒绝
```

### 3.2 为什么 Token 能防住 CSRF(关键)

**因为攻击者构造恶意页面时,拿不到这个 Token。**

回想 CSRF 的攻击方式——攻击者在**自己的恶意网站 B** 上构造一个"向 A 发请求"的表单。但这个 Token 是 A 动态生成、藏在 A 的页面里的,而且由于**同源策略**(攻击者的 B 站 JS 读不到 A 站页面的内容),**攻击者根本没办法从 A 的页面里把这个 Token 偷出来**。

所以攻击者构造的恶意请求里**要么没有 Token、要么是瞎填的错 Token** → 服务器一校验就发现对不上 → 拒绝。

> 💡 这就是为什么 Token 比 Referer 校验可靠:Referer 是"检查来源"(可能被绕过/为空),而 Token 是"检查一个攻击者根本拿不到的秘密"——攻击者拿不到,就伪造不出合法请求。

## 4. CSRF 利用:无防护情况(🔴 核心)

### 4.1 检测
- **黑盒**:手工测试——把增删改请求去掉 Referer/token 重放,看能否成功。
- **白盒**:看代码——这个接口有没有校验 token、有没有校验来源。

### 4.2 生成 PoC(实战常用)

Burp Suite 自带 CSRF PoC 生成器,非常方便:
```
Burp → 选中目标请求 → 右键 → Engagement tools → Generate CSRF PoC
```
它会自动生成一个 HTML 页面,里面是一个"自动提交、指向目标接口、带好参数"的表单。

### 4.3 利用
- 把生成的 PoC 页面**放到自己的服务器**上。
- **诱导受害者访问**(钓鱼),或者**配合目标站的存储型 XSS 自动触发**(受害者正常浏览就中招,不用诱导)。

## 5. CSRF 绕过手法(🔴 核心,针对防护不严谨)

防护代码写得不严谨时,有一整套绕过思路。**核心思想:防护的"校验逻辑"往往有漏洞,找到它没考虑周全的情况。**

### 5.1 针对 Token 校验的绕过(多为代码逻辑不严谨)

| 绕过手法 | 原理 |
|---|---|
| **删除 token 参数** | 有些代码只在"token 存在时才校验",你干脆**整个删掉 token 参数**,它就不校验了 → 绕过 |
| **token 参数值置空** | 把 token 的值留空(`csrf_token=`),有些代码对空值不做严格校验 → 绕过 |
| **token 复用** | 同一个 token 被反复使用也不失效(没做一次性),那攻击者用一个已知的旧 token 就行 |
| **用另一个用户的 token** | 如果服务器只校验"token 合法"但不校验"token 是不是属于这个用户",攻击者用自己账号的合法 token 去打别人 |
| **替换 token 为随机值 / 改一个字符** | 测试服务器是不是真的在逐字符严格比对,还是只看长度/格式 |

### 5.2 针对 Referer 校验的绕过

| 绕过手法 | 原理 |
|---|---|
| **删除 Referer** | 用 `<meta name="referrer" content="no-referrer">` 让请求不带 Referer。如果服务器"Referer 为空时放行",就绕过了 |
| **规则匹配不严谨** | 服务器可能只检查"Referer 里**包含**本站域名"。那攻击者构造 `http://www.bankhacker.com/http://www.bankchina.com` 或 `http://www.bankchina.com.hacker.com` 这种——里面"包含了"本站域名字符串,骗过表层匹配 |

### 5.3 其他通用绕过

| 绕过手法 | 原理 |
|---|---|
| **POST 改 GET** | 如果接口同时接受 GET 和 POST,把 POST 请求改成 GET(GET 更容易用 `<img>`/链接构造 CSRF) |
| **更改 body 编码** | 改请求体的 Content-Type(如改成 `text/plain`),绕过某些基于特定编码的校验 |
| **Content-Length 绕过** | 篡改内容长度配合其他手法 |

### 5.4 配合其他漏洞的"硬绕过"(同源策略防护下)

当目标有较严格的同源/来源防护时,单纯改请求绕不过,就**配合别的漏洞**:
- **配合文件上传**:把 CSRF 的 PoC 当文件上传到**目标站自己的域名下**,这样请求就"同源"了,绕过来源校验。
- **配合存储型 XSS**:在目标站存一个 XSS,让它在目标站自己的页面(同源)里发起 CSRF 请求——既绕过了来源校验(同源),又不用诱导受害者(存储型自动触发)。

> 💡 这两种是"**严谨防护下的正规绕过思路**"——核心都是"**想办法让攻击请求从目标站自己的域名发起**",从而满足同源/来源要求。这再次体现了漏洞的**组合利用**(CSRF + 文件上传 / CSRF + 存储XSS)。

## 6. 把它串起来:CSRF 测试思维

```
① 找增删改类的高价值功能(改密码/改邮箱/删账户/加管理员)
        ↓
② 这个请求有没有 CSRF 防护?(Burp 重放,去掉 token/Referer 看能不能成功)
   ├─ 无防护 → 直接 Burp 生成 PoC,诱导/配合 XSS 触发
   └─ 有防护 ↓
        ↓
③ 是什么防护?分别尝试对应绕过:
   ├─ Token 校验 → 删token / 置空token / 复用token / 换用户token
   ├─ Referer 校验 → 删Referer(no-referrer) / 规则匹配不严谨
   └─ 严格同源防护 → 配合文件上传 / 配合存储XSS(让请求同源发起)
```

## 7. 自测(先自己想,再看答案)

1. 用自己的话说清楚:CSRF 攻击里,为什么攻击者"不需要偷受害者的 Cookie,也不需要知道密码",就能以受害者身份发请求?
2. 为什么 CSRF Token 比 Referer 校验更可靠?攻击者为什么拿不到 Token?
3. 一个改密码的接口用了 Token 防护,但你发现:把请求里的 `csrf_token` 参数**整个删掉**后,请求居然还能成功。这说明防护代码有什么问题?

<details>
<summary>参考答案</summary>

1. 因为 CSRF 利用的是浏览器的一个天性——**向某个网站发请求时,会自动带上该网站的 Cookie**,不管请求从哪个页面发起。攻击者只要诱导受害者(当前登录着目标站)的浏览器向目标站发一个请求,浏览器就自动带上了有效 Cookie,目标站以为是用户本人操作。攻击者全程没碰 Cookie、没要密码,只是"借用"了受害者已登录的会话。
2. 因为 Token 是目标站动态生成、藏在自己页面里的随机值,而**同源策略**让攻击者的恶意站点无法读取目标站页面的内容,所以攻击者拿不到这个 Token。构造恶意请求时没有正确的 Token,服务器一校验就拒绝。而 Referer 校验检查的是"来源",可能为空、也可能被规则漏洞绕过,不如"校验一个攻击者拿不到的秘密"可靠。
3. 说明防护代码只做了"**如果 token 参数存在,才校验它**"的逻辑,却没处理"**token 参数不存在**"的情况——漏掉了"没有 token 就应该直接拒绝"这一步。攻击者干脆把 token 参数整个删掉,代码就跳过了校验 → 绕过。正确的防御应该是"没有 token 或 token 不匹配,一律拒绝"。

</details>
