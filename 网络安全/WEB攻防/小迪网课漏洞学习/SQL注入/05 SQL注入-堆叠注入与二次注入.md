## 1. 堆叠注入(Stacked Queries)(🔴 核心)

### 1.1 它是什么

堆叠注入,是指利用 SQL 语句的结束符 `;`,在一次提交的请求里塞进**多条相互独立、完全不相关**的 SQL 语句,让数据库依次把它们都执行一遍。

> 类比:普通的联合查询注入像是你在填一张"问卷"时,在某道问答题里多写了几句话,这几句话会被算作"同一道题的回答"(即被合并进同一个结果集);而堆叠注入更像是你在提交问卷的同时,**偷偷在信封里又塞了一张完全独立的新申请表**——工作人员如果"来者不拒、见表就办",会把这第二张表也单独处理一遍,这和"篡改第一张问卷的某道题"是完全不同的两件事。

### 1.2 为什么会存在(原理)

普通的 SQL 注入之所以存在,根因是"用户输入被当成了 SQL 代码的一部分拼接执行"。但堆叠注入能不能成立,**根因不在注入点本身,而在应用程序后端调用数据库时所用的接口/函数是否支持一次执行多条语句**。

以 PHP 为例:
- `mysqli_query()`:这个函数**在设计上只接受并执行一条 SQL 语句**。即使你往里面塞一个用分号分隔的、包含两条语句的字符串,它也只会执行第一条,多出来的部分要么被忽略要么直接报错——开发者选用这个函数,相当于在"数据库连接层面"就默认关掉了"一次执行多条语句"这扇门。
- `mysqli_multi_query()`:这个函数则**专门被设计成支持一次性执行用分号分隔的多条语句**。

> [!note] 🔎 补充(非原笔记内容)
> 这个"能不能堆叠"的差异不是 MySQL 数据库本身的限制,而是**客户端驱动/接口层面的限制**。数据库引擎本身完全有能力顺序执行多条语句,真正把这扇门关上或打开的是开发者选用的那个函数。这也解释了为什么原笔记说"堆叠注入触发条件很苛刻"——这不是一个你能通过构造更巧妙的 payload 去突破的限制,而是一个**在你拿到注入点之前,后端技术选型就已经决定好了"能不能走这条路"**的客观事实,黑盒测试阶段很难提前判断,往往要实际尝试分号才知道。

### 1.3 怎么做(过程)

**步骤 1:确认目标存在基础的 SQL 注入漏洞**
- 做什么:用前面笔记讲过的单引号探测、`and 1=1`/`and 1=2` 对比等常规方法先确认注入点存在。
- 为什么这么做:堆叠注入是建立在"注入点已经成立"基础上的进阶利用手法,不是独立的发现手段——这一步是整条利用链的地基。
- 做完得到什么:确认参数可控且会被拼进 SQL;如果连基础注入都不成立,堆叠注入无从谈起。

**步骤 2:测试分号是否被过滤/转义**
- 做什么:尝试提交一个带分号的简单 payload,比如 `1;select 1`,观察响应。
- 为什么这么做:如果应用对分号做了过滤或转义,你写的"第二条语句"根本不会被数据库识别成一条独立语句,堆叠注入这条路直接被堵死,不需要再往下试。
- 做完得到什么:分号没被处理 → 进入下一步;分号被转义成了 `\;` 或直接被删除/报错 → 这条路走不通,回头考虑其他手法(报错注入、盲注)。

**步骤 3:测试一条无害的第二语句,确认是否真的被执行**
- 做什么:比如提交 `1;select sleep(3)`,观察响应是否真的延迟了约 3 秒。
- 为什么这么做:用一个"有明确可观察效果、但不会破坏数据"的语句做探测,比直接上 `DROP TABLE` 这种危险操作安全得多——这是用最小代价验证"数据库真的把第二条语句当独立语句执行了",而不是误把其他原因(比如网络波动)当成堆叠注入成功的信号。
- 做完得到什么:响应确实延迟 → 堆叠注入成立,可以继续构造真正要执行的第二条语句;响应没有变化 → 说明中间层确实用的是单语句函数,堆叠这条路同样走不通。

**步骤 4:构造真正的利用语句**
- 做什么:把第二条语句换成你真正想执行的操作,比如针对 INSERT 场景:`INSERT INTO users (username) VALUES ('a'); SELECT password FROM admin WHERE id=1;-- `
- 为什么这么做:前面三步已经验证了"堆叠能生效",现在可以放心让第二条语句承载真正的攻击目的——因为它是一条完全独立的语句,甚至理论上可以是 `UPDATE`/`DELETE` 这类有数据改写风险的操作,不再受"必须和原语句合并成一个结果集"这个限制。
- 做完得到什么:如果页面有办法把第二条语句的执行结果体现出来(比如后续再查一次),就能确认利用成功;如果没有直接回显,通常还要配合盲注的思路去验证第二条语句是否真的生效。

命令 / payload 拆解:

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `'a'` | 闭合原 INSERT 语句里某个值的字符串边界 | 让后面的 `;` 之后的内容脱离原语句的语法束缚 |
| `;` | 语句结束符,告诉数据库"这一条语句到此为止" | 这是堆叠注入能成立的**唯一语法基础**,没有它数据库无法区分"这是两条语句还是一条很长的语句" |
| `SELECT password FROM admin WHERE id=1` | 真正想执行的第二条语句 | 这里以读取数据举例,实战中也可以换成 `UPDATE`/`INSERT`/`DELETE` 等任意语句 |
| `-- ` | 注释掉原语句里剩余的、可能导致语法错误的部分 | 和前面几篇笔记讲过的闭合+注释思路完全一致 |

正常输出怎么读:如果第二条语句是只读查询且应用没有把它的结果单独显示出来,通常**看不到直接回显**,需要换一种方式验证(比如让第二条语句改成一个会造成明显副作用的操作,如 `UPDATE` 某条可观察的数据,再去前台确认数据是否真的被改了)。

### 1.4 业务里长什么样(案例锚点)

> **示例场景**:某企业内部的"工单提交"系统,用户提交工单时后端用 `mysqli_multi_query()` 批量处理"插入工单记录 + 更新工单编号计数器"这类需要在一次事务里连续执行多条语句的逻辑(这类需求在业务中并不少见,是 `mysqli_multi_query()` 被选用的真实原因之一,不是开发者"失误")。如果提交工单的标题字段存在未处理的注入点,攻击者可以在标题里塞入 `';DROP TABLE work_orders;-- ` 这样的 payload,触发后不仅能读取其他工单数据,理论上还能直接删除整张工单表——对应本笔记 1.3 的第 4 步。后果是:企业核心业务数据被直接破坏,而不只是"信息泄露",修复成本和业务中断损失都远高于普通的只读注入。

### 1.5 实战怎么用

- **什么时候该想到它**:确认存在基础注入漏洞、且目标的注入点是在 INSERT/UPDATE/DELETE 这类不产生结果集的操作上(回顾《HTTP请求头注入面与增删改查注入思路笔记》)、同时 UNION 和盲注效率都不理想或想追求更高破坏力时,应该想到测一下堆叠注入。
- **怎么验证**:按 1.3 节的四个步骤走,**优先用 `sleep()` 这类无害的探测语句**,不要一上来就用 `DROP`/`DELETE` 这类有破坏性的语句做试探,即使是在授权测试环境,也应该遵循"最小影响原则"。
- **怎么判断结果**:能观察到第二条语句的明确执行效果(延迟、数据变化)就算成立;分号被过滤、或延迟/数据变化都没发生,基本可以判定目标不支持堆叠执行。
- **下一步**:成立 → 可以把攻击目标从"单纯读取数据"升级为"任意语句执行"(含数据篡改/删除,也是 SQLMap 里 `--sql-shell` 功能背后的原理之一,详见《SQLMap使用指南》);不成立 → 回退到报错注入或布尔/时间盲注。

### 1.6 防御与检测视角

开发者防御这类问题最直接的办法是:**非必要不使用支持多语句执行的数据库接口**。如果业务确实需要在一次请求里执行多个相关的 SQL 操作,更推荐使用**数据库事务**(多条语句分开调用,但用事务包裹保证原子性),而不是用"拼接一个带分号的大字符串"这种方式。此外,预编译语句(PreparedStatement)在大多数驱动实现下本身也会天然拒绝在一次预编译里执行多条语句,这也是为什么"坚持用预编译"几乎能同时防住普通注入和堆叠注入两类问题。

### 1.7 易错点

- **误区:以为所有数据库 / 所有场景都能用堆叠注入。** 实际上这完全取决于中间层接口选型,黑盒测试中无法提前判断,必须实际测试分号和无害探测语句才能确认。
- **排错线索**:如果分号测试没有任何异常(既不报错也没有预期的延迟),八成是中间层用的单语句接口,不要在这个方向上反复浪费时间,应尽快切换到报错注入/盲注思路。

## 2. 二次注入(Second-Order Injection)(🔴 核心)

### 2.1 它是什么

二次注入,是指攻击者**第一次提交的恶意数据,在当时被安全处理、没有立刻触发注入**,但这份数据被完整存进了数据库;等到之后某个完全不同的功能,把这份数据重新取出来、并且未经处理地拼进了一条新的 SQL 语句时,注入才真正被触发。

> 类比:普通注入像是你递给门卫一张写了暗语的纸条,门卫当场就被骗开了门;二次注入更像是你把一张写了暗语的纸条,**先存进了公司的档案柜**(存档时档案员做了基本的格式核对,纸条本身被完好地收了起来,没有引发任何异常)。几个月后,另一个完全不知情的同事,从档案柜里把这张纸条取出来,**原样读给了另一位门卫听**——这时暗语才真正起了作用。危险的不是"存档"这个动作本身,而是"后来有人毫无防备地拿这份档案去做了别的事"。

### 2.2 为什么会存在(原理)

```
用户提交数据(含恶意字符) → 写入时做了基础转义,安全存入数据库(此时不触发)
     ↓(时间、功能完全分离)
数据被另一处功能取出 → 未做二次处理,直接拼进新的 SQL 语句 → 触发注入
```

Root cause 可以拆成开发者在两个不同环节分别做出的假设,这两个假设各自看起来都合理,叠加在一起才酿成问题:

1. **写入环节的假设**:"我已经对这次用户输入做了转义处理(比如用 `addslashes()`),这次写入是安全的。"——这个假设本身是对的,写入这一步确实不会被注入。
2. **读取复用环节的假设**:"这份数据来自我自己的数据库,不是用户这次请求里新提交的内容,应该可以信任,不需要再处理一遍。"——**这才是真正的漏洞所在**:开发者把"数据来源是不是用户当前这次请求"当成了"这份数据安不安全"的判断依据,但实际上,**一份数据是否需要转义/预编译处理,只取决于它接下来要被怎么使用,和它是刚从用户表单里来的,还是从数据库里读出来的,没有任何关系**。只要它即将被拼进一条新的 SQL 语句,就必须被当作不可信输入对待。

### 2.3 怎么做(过程)

以"注册用户名 → 登录 → 修改资料"这条典型路径为例:

**步骤 1:构造一个包含注入特征的用户名并注册**
- 做什么:注册一个用户名为 `admin'-- ` 这类包含单引号和注释符的账号。
- 为什么这么做:探测写入环节是否存在基础的转义处理——如果注册直接报错或失败,说明写入这一步本身就不安全,就不需要走"二次"这条更复杂的思路,直接当普通注入处理即可;如果注册顺利成功,说明写入环节大概率做了转义保护,值得继续往下验证"二次"路径。
- 做完得到什么:注册成功,账号正常创建,此时没有任何注入迹象——**这是预期中的"安全表象"**,不代表没有漏洞。

**步骤 2:正常登录,让这份数据进入会话凭证**
- 做什么:用刚注册的账号正常登录。
- 为什么这么做:很多系统登录后会把用户名(或其他字段)存进 Session,后续功能可能会直接从 Session 里取这份"看起来可信"的数据。
- 做完得到什么:登录成功,服务端的会话里持有了这个带有恶意字符的用户名。

**步骤 3:触发一个会"重新使用"这份数据的功能**
- 做什么:比如访问"修改个人资料"功能,提交一次资料修改请求。
- 为什么这么做:这一步在验证"后端修改资料的逻辑,是否直接把 Session 里的用户名(而不是这次请求里新提交的参数)拼进了 SQL 语句的 `WHERE` 条件"——这正是漏洞实际触发的那个环节。
- 做完得到什么:如果后端确实存在这个逻辑缺陷,此时注入被触发,可能表现为:修改操作影响了不该影响的数据行、返回了异常的错误信息、或其他业务逻辑异常(具体表现取决于注入点在语句里的位置和权限,详见《HTTP请求头注入面与增删改查注入思路笔记》里 UPDATE 类业务的盲注思路)。
- 如果不是预期结果:资料修改一切正常、没有任何异常 → 可能是该字段确实在"重新使用"时也做了转义处理(说明这条路径本身是安全的,需要换其他字段/功能继续排查),也可能是该功能压根没有复用这份数据拼接 SQL,需要回到白盒/黑盒思路重新定位"哪个功能点真正用到了这份被污染的数据"。

命令 / payload 拆解:

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `admin` | 构造一个看起来正常、不会让注册环节产生警觉的前缀 | 降低写入阶段被基础校验规则(如用户名格式白名单)拦截的概率 |
| `'` | 单引号,用于在"第二次使用"的那条 SQL 语句里闭合字符串边界 | 这是整个利用链条真正起作用的符号,但它要等到第二次被使用时才"生效" |
| `-- ` | 注释掉第二条语句里原本跟在后面的部分(如 `AND password=...`) | 和普通字符型注入的闭合思路完全一致,只是触发的时间点被推迟了 |

### 2.4 业务里长什么样(案例锚点)

本篇暂无能精确对应"二次注入"这一具体子类型、且可公开核实的独立事件(二次注入通常是更大规模注入事件里的一个技术细节,公开披露的事件报告很少会专门区分"是一次注入还是二次注入"),因此用一个带业务名词的示例场景说明:

> **示例场景**:某论坛系统的"昵称"字段,注册时后端对昵称里的单引号做了转义后存库(写入安全)。但论坛的"后台管理 - 用户管理"页面里有一个"按昵称搜索用户"的功能,这个功能的实现方式是:后台管理员输入搜索词后,系统**从数据库里先取出所有用户昵称列表,再把这些昵称逐个与管理员的搜索词拼接进一条动态生成的匹配 SQL 里**(这是真实项目里常见的一种偷懒实现)。如果攻击者的恶意昵称中带有闭合符号,就可能在管理员使用这个搜索功能时,触发注入,从后台管理视角看是无缘无故出现异常——对应本笔记 2.3 的第 3 步。后果是:攻击者不需要攻破后台权限,只需要用普通用户权限"埋雷",等着有管理权限的人使用相关功能时"代为触发",危害可能比直接攻击普通查询接口更隐蔽、权限影响面更大。

### 2.5 实战怎么用

- **什么时候该想到它**:黑盒测试中,看到任何一个"先填写/提交信息,之后在另一个完全不同的功能里,这份信息又被用来做查询/筛选/展示"的业务流程,都值得专门测一遍——常见的"雷区"字段包括:用户名、昵称、收货地址、备注信息、文件名。
- **怎么验证**:最小代价的做法是——先用一个带有明确、无害的"指纹特征"的恶意字符串完成写入(比如 `test'and'1'='1`),再去尝试触发所有可能会"重新使用"这份数据的功能点,观察哪个功能点出现了异常。避免直接用破坏性 payload 做首次验证,防止不确定触发位置时造成不必要的数据影响。
- **怎么判断结果**:某个"二次使用"功能点出现了报错、数据异常、或可观察的盲注信号(参照《SQL盲注原理笔记》的判断方法),即可确认该路径存在二次注入。
- **下一步**:定位到具体触发点后,后续的注入利用手法(联合查询、报错、盲注)和普通注入完全一致,区别只在"注入点在哪里被触发",一旦定位到触发语句,就回到了标准的注入利用流程。

### 2.6 防御与检测视角

**开发者常见的修复误区**:很多团队发现二次注入问题后,只是在"写入"那个环节加强转义,但**真正的修复点应该在"每一次使用数据拼接 SQL 语句的地方",而不是"数据第一次进入系统的地方"**。正确的做法是:任何时候只要在构造 SQL 语句,就统一使用预编译语句/参数化查询(详见《MySQL入门笔记》第 13 章),而不区分这份数据"是不是用户这次新提交的"——这才是从根本上同时防住普通注入和二次注入的办法。

### 2.7 易错点

- **误区:以为只要在用户提交数据的入口做好过滤,就万事大吉。** 二次注入恰恰证明了"入口过滤"和"输出到 SQL 时的处理"是两件必须分别做、不能相互替代的事。
- **误区:只在黑盒测试里对着表单反复提交 payload,却忽略了"数据会被用在别处"这条隐藏路径。** 排错线索是:遇到"看起来功能点本身没有注入"的情况时,不要轻易下结论说"这里没有漏洞",应该多问一句"这个字段的数据,之后还会出现在系统的哪些地方"。

## 3. 把它串起来:方法论总览

```
拿到一个疑似注入点或可疑业务流程
    ↓
① 这是"当下提交、当下触发"的常规注入,还是"先存后用"的二次注入场景?
    常规场景 → 走 SELECT/INSERT/UPDATE/DELETE 对应的标准注入流程(详见前置笔记)
    "先存后用"场景 → 重点关注步骤 2.3,先完成无害写入,再逐一测试所有"重新使用"该数据的功能点
    ↓
② 如果注入点恰好落在 INSERT/UPDATE/DELETE 且 UNION、盲注都效率不佳或希望扩大破坏力:
    → 测试是否支持堆叠注入(1.3 节四步法,从无害探测开始)
    ↓
③ 确认触发点后,回到标准利用流程:
    有回显 → 联合查询
    报错可见 → 报错注入
    有真假差异但无报错 → 布尔盲注
    什么差异都没有 → 时间盲注
    支持多语句执行 → 堆叠注入(可直接执行任意语句,含数据篡改)
```

## 4. 自测(先自己想,再看答案)

1. 用自己的话复述:为什么同样是调用 MySQL,有的网站能被堆叠注入,有的不能?
2. 场景题:一个电商网站的"商品评价"功能,用户提交的评价内容会被展示在商品详情页,同时后台有一个"按关键词统计评价情绪"的功能会把所有评价内容拉出来做二次处理。如果怀疑这里存在二次注入,你会怎么验证?
3. 排错题:你在测试一个疑似支持堆叠注入的参数时,提交了 `1;select sleep(3)`,但响应没有任何延迟,可能是哪几个原因?

<details>
<summary>参考答案</summary>

1. 根因不在 MySQL 数据库本身,而在应用后端连接数据库时选用的驱动函数——`mysqli_query()` 这类函数只认一条语句,`mysqli_multi_query()` 才支持多语句堆叠,这是开发阶段的技术选型决定的,不是注入点本身的问题。
2. 先用一个带无害指纹特征的恶意字符串(如 `test'and'1'='1`)提交一条评价,正常情况下评价展示页面不会立刻触发异常(因为展示页面通常只是回显文本,不是把内容当 SQL 拼接);接着尝试触发后台的"关键词情绪统计"功能,观察该功能是否因为把评价内容重新拼进了统计用的 SQL 语句而出现异常响应或报错——这正是二次注入"写入安全、复用时触发"的验证逻辑。
3. 可能原因包括:① 中间层用的是不支持堆叠的单语句函数(最常见);② 分号本身被过滤或转义,根本没有被识别成语句分隔符;③ 前置的基础注入点其实并不存在,连第一条语句本身都没有被正确拼接执行;④ 目标数据库类型本身在当前驱动/配置下关闭了多语句支持。

</details>
