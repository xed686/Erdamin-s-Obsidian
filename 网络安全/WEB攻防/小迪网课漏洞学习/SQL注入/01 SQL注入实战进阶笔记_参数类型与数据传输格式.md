## 一、三种参数类型的本质区别

| 类型 | 后端代码长什么样 | 参数在原 SQL 里的位置 |
|---|---|---|
| **数字型** | `select * from news where id=$id;` | 不带引号，直接拼在等号后面 |
| **字符型** | `select * from news where name='$name';` | 被一对单引号包住 |
| **搜索型（模糊匹配）** | `select * from news where name like '%name%';` | 被单引号包住，**前后还各多了一个 `%` 通配符** |

**为什么要专门区分"搜索型"，而不是直接归进"字符型"**：数字型和普通字符型只需要考虑"要不要闭合一个引号"；但搜索型的参数外面除了引号，**还包了一层 `%`**，这意味着你构造的 payload 除了要闭合引号，往往还要先处理掉这个 `%`，才能让后面拼接的内容不被当成"模糊匹配的一部分"而是真正成为新的 SQL 语法。这也是为什么案例里 payload 的开头会出现 `1%` ——下面马上讲原因。

**符号干扰**指的就是这几类字符在参数里"有没有、怎么摆"：有没有单引号、有没有双引号、有没有 `%` 通配符。测试一个新参数时，第一件事永远是先搞清楚它属于这三种里的哪一种，这决定了你接下来怎么下手。

## 二、完整实战案例：从判断符号到拿到密码

假设当前数据库是 MySQL，目标是一个**搜索型**参数（`like '%name%'` 这种），数据库名是 `news_db`。下面逐步还原整个"获取数据库名 → 表名 → 列名 → 数据"的过程，每一步都讲清楚"为什么这样写"。

### 第一步：判断字段数

```
order by 3 #应该是' ORDER BY 3 -- 
```

**为什么要先做这一步**：联合查询注入（`union select`）要求你补的那一行数据，列数必须和原查询完全一致，否则直接报错。`order by` 本来的作用是"按第几列排序"，如果数据库里压根没有第 3 列，它就会报错——拿它来"投石问路"，不断加大数字直到报错为止，报错前的那个数字就是真实列数。这个思路和《SQL注入全数据库类型实战笔记》第 5 章讲的通用流程完全一致，这里是它在真实参数上的第一步应用。

### 第二步：确定回显位置

```
union select 1,2,3 #这里也和上面一样 ' union select 1,2,3 -- 
```

**为什么**：知道了是 3 列，先填三个随便的数字占位，提交后看页面上显示出来的是哪个数字——那个数字所在的位置，就是"你接下来想查的真实数据应该放的位置"。

### 第三步：获取数据库名

```
database() #同上 ' database() -- 
```

返回：`news_db`

这一步直接用内置函数拿到当前库名，不需要查系统表，是最省力的一步。

### 第四步：获取该库下的表名

```
1%' union select 1,2,table_name from information_schema.tables where table_schema='news_db'#
```

这一行 payload 看起来复杂，拆开来看其实是在"拼凑"出一个合法新语句，同时把原来模板里多余的部分处理掉。回忆一下原始查询模板：

```sql
select * from news where name like '%$name%';
```

把上面的 payload 当作 `$name` 代进去，整句话会变成：

```sql
select * from news where name like '%1%' union select 1,2,table_name from information_schema.tables where table_schema='news_db'#%';
```

逐段拆解：
- **开头的 `1%`**：这是凑在原本 `%...%` 模糊匹配里的"陪衬字符"，内容本身不重要，它存在的意义只是让紧跟着的单引号出现在一个"该出现的位置"，不会让前面的语法显得突兀。
- **紧接着的单引号 `'`**：真正起作用的地方——它和模板里前面那个没写出来的 `'` 配对，提前把 `like` 后面的字符串"闭合"掉了，原本应该继续匹配的 `%` 通配符逻辑到这里就终止了。
- **`union select 1,2,table_name from information_schema.tables where table_schema='news_db'`**：闭合引号之后，后面写什么就是全新的、完全由你掌控的 SQL 语句了——这里让它去查 `information_schema.tables`（详见前置笔记，这是 MySQL 自带的"记录所有库下所有表名"的系统表），条件限定为 `news_db` 这个库。
- **末尾的 `#`**：MySQL 的单行注释符，作用是把原模板里**我们闭合引号之后、原本还跟在后面的 `%';`** 这部分"吃掉"，不让它们继续生效导致语法错误（如果不注释掉，最后会多出一段 `%';`，破坏整条语句的合法性）。

返回：`admin`（说明 `news_db` 库下有一张叫 `admin` 的表，直觉上这就是重点目标）。

### 第五步：获取 `admin` 表下的列名

```
1%' union select 1,2,column_name from information_schema.columns where table_schema='news_db' and table_name='admin'#
```

写法和上一步几乎一模一样，唯一的区别是：这次查的系统表换成了 `information_schema.columns`（记录所有表对应的列名信息），并且多加了一个 `table_name='admin'` 的条件，把范围从"整个库"收窄到"只看 `admin` 这一张表"。

返回：`username`、`password`

### 第六步：取出真正的数据

```
1%' union select 1,2,password from admin#
```

前面五步都是在"摸清结构"（库名→表名→列名），**到这一步结构已经完全清楚了，所以不再需要查 `information_schema` 这类系统表，直接对着目标表 `admin` 取 `password` 列的值**。

**这整个六步，和前置笔记第 5 章讲的"判断字段数 → 确定回显位置 → 获取数据库信息 → 获取库名表名列名 → 获取数据"五步法完全对应**，唯一的新知识点是：当参数属于"搜索型"时，闭合引号的 payload 开头要多考虑一下 `%` 通配符的处理（也就是这里 `1%` 的作用），这是和纯字符型参数相比唯一需要多想一步的地方。

## 三、数据传输格式的复杂化：XML、JSON、编码、混合

前面的案例里，参数是以最朴素的方式直接出现在请求里的（比如 URL 参数或表单字段）。但现代应用，尤其是前后端分离的 API 接口，数据往往不是这样简单直接传递的，而是打包成了结构化格式，这会给测试带来额外的一层麻烦。

### 3.1 XML 格式

```xml
<?xml version="1.0" encoding="UTF-8"?>
<news>
    <article>
        <id>1</id>
        <title>xiaodi</title>
        <content>i am xiaodi</content>
        <created_at>2025-03-07</created_at>
    </article>
</news>
```

**对测试带来的影响**：如果某个接口的请求体或响应体是这种 XML 结构，而注入点恰好在某个节点的内容里（比如 `<title>` 对应的值），直接把 SQL payload 塞进去之前，要先确保**整个 XML 本身的语法依然合法**——比如 payload 里如果出现了 `<`、`>`、`&` 这类 XML 本身的特殊字符，需要先做 XML 转义（如 `&lt;`），否则请求可能在到达后端 SQL 拼接逻辑之前，就先被 XML 解析器判定为格式错误直接拒绝，根本轮不到触发注入。

> 顺带一提：XML 格式本身还有另一类独立的高危漏洞 XXE（XML External Entity），这是另一个话题，不在本篇展开。

### 3.2 JSON 格式

```json
{
    "news": [
        {
            "id": 1,
            "title": "xiaodi",
            "content": "i am xiaodi",
            "created_at": "2025-03-07"
        }
    ]
}
```

**对测试带来的影响**：和 XML 同理，payload 如果包含双引号 `"`、反斜杠 `\` 这类 JSON 语法本身用到的字符，需要先做 JSON 转义（比如 `\"`），不然这个 JSON 本身就先解析失败了。很多初学者直接把从 URL 参数场景下试出来的 payload原样粘贴进 JSON 字段里去测试，结果请求直接报 400（JSON 格式错误），会误以为"这里没有注入"，其实只是payload 的外层格式没适配好。

### 3.3 Base64 编码

```json
{
    "news": [
        {
            "id": "MQ==",
            "title": "eGlhb2Rp",
            "content": "aSBhbSB4aWFvZGk=",
            "created_at": "MjAyNS0wMy0wNw=="
        }
    ]
}
```

**对测试带来的影响**：这是比 XML/JSON 语法转义更进一步的障碍——这里的每个字段值本身就是经过 Base64 编码后的结果（比如 `eGlhb2Rp` 解码后就是 `xiaodi`）。如果你直接把 SQL payload 当作明文塞进这个字段，后端在用这段内容之前，大概率会先对它做一次 Base64 **解码**，解码出来的内容如果不是合法 Base64（因为你塞的是明文 SQL 语句），要么解码直接报错，要么解码出一堆乱码，payload 根本不会以你期望的样子参与到后续的 SQL 拼接里。

**正确的测试思路**：必须先把你的 SQL payload 本身也用 Base64 编码一遍，再把编码后的结果填进这个字段——这样后端解码出来之后，才会"还原"成你真正想要注入的那段 SQL 语句。

### 3.4 混合场景：JSON + 编码

实战中最复杂的情况，是以上两种叠加：**外层是 JSON 结构，内层某些字段的值又是 Base64（或其他编码/加密方式）**。测试这种场景需要分两层处理：
1. 先确定 JSON 的整体结构不能破坏（外层转义问题）。
2. 再确定你要注入的那个具体字段，是不是经过了二次编码（内层编码问题），如果是，payload 要先编码好，再放进 JSON 对应的位置。

这也呼应了此前《前端加密与代码混淆笔记》里讲过的思路——**不管外层包了多少层"壳"（XML/JSON/Base64/加密），核心判断逻辑永远是同一个：找到最终真正会被拼进 SQL 语句执行的那个"裸值"是什么，再倒推出"要让后端最终拿到这个裸值，我现在应该提交什么样的外层数据"**。

## 四、这对安全测试意味着什么

把今天这部分内容和前置笔记第 2 章"影响 SQL 注入的六个因素"对应起来看：

| 前置笔记里的因素 | 今天具体讲的内容 |
|---|---|
| 参数数据类型（符号干扰） | 数字型 / 字符型 / 搜索型的差异，以及搜索型多出来的 `%` 处理 |
| 参数数据格式（加密编码等） | XML / JSON / Base64 编码对 payload 外层格式的要求 |
| 提交数据方式（数据包部分） | 数据从"裸参数"演变为结构化格式（XML/JSON）后，注入点要在结构内部重新定位 |

**一句话总结**：数据传输格式越复杂，测试的**难度和步骤**就越多，但 SQL 注入本身的**判断逻辑从未改变**——永远是"找到用户输入最终落在 SQL 语句的什么位置，再构造闭合/拼接"。多出来的 XML/JSON/编码这些，只是在这条核心逻辑外面多包了几层"壳"，测试时要做的，就是先把壳处理好（保证格式合法），再让里面的 payload 按原来的思路生效。
