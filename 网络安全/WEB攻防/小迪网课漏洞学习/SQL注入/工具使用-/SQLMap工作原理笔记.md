# SQLMap 工作原理笔记：它到底替你做了什么

> **这篇不讲参数**（参数速查见《SQLMap使用指南》），只讲**SQLMap 内部的工作逻辑**——它拿到一个目标之后，按什么顺序尝试了哪些方法，每种方法底层等价于你前面哪篇笔记学过的哪个手工动作。搞清楚这个，你才能在 SQLMap 报告"没有发现注入"或者"跑不动"的时候，立刻反应出"它已经把哪几条路都走过了、哪几条路它根本没走、现在该我自己上手走哪条路"。

---

## 一、SQLMap 的核心工作流程：四个阶段

SQLMap 处理一个目标，本质上是按顺序走完下面四个阶段，**每一步都在自动化你早就学过的某个手工判断动作**：

```
① 参数识别            —— 这个请求里，哪些位置可能是注入点？
       ↓
② 技术探测（Detection）—— 对每个候选位置，依次尝试几种"注入技术"，
                          确认哪种技术能让数据库按我的条件做出反应
       ↓
③ 指纹识别（Fingerprint）—— 确认了存在注入之后，顺便问清楚：
                             这是什么数据库、什么版本？
       ↓
④ 利用（Exploitation）  —— 用第②步确认有效的技术，
                           正式开始提取数据/操作文件/执行命令
```

### 1.1 第一步：参数识别

SQLMap 会把你提供的请求（URL、POST 数据、Cookie、请求头等）**拆成一个个独立的参数**，默认情况下逐个测试每一个参数是否存在注入——这一步对应的手工动作，就是《HTTP请求头注入面与增删改查注入思路笔记》里讲的"把请求拆开看，哪里可能是用户可控的输入"，只是 SQLMap 会**机械地、不遗漏地把能找到的每个参数都测一遍**，而人工测试时往往会凭经验优先挑几个"看起来像"的参数先试。

### 1.2 第二步：技术探测——这是最核心的部分

对每一个候选参数，SQLMap 会依次尝试**六种内置的"注入技术"**（技术代号用单个字母表示），每一种都对应你前面笔记学过的一类手工方法：

| 代号 | 技术名称 | 底层在做什么，等价于手工的哪一步 |
|---|---|---|
| **B** | Boolean-based blind（布尔盲注） | SQLMap 会在参数后面自动拼接类似 `AND [随机数]=[随机数]`（条件恒真）和 `AND [随机数]=[随机数+1]`（条件恒假）这样的 payload，分别发两次请求，**逐字节比对两次响应内容是否不同**。这和《SQL盲注原理笔记》里 `and length(database())=7` 的判断逻辑完全一样——都是"构造真/假两种条件，看页面有没有差异"，只是 SQLMap 在这一步**只是用随机数字做"是否存在布尔盲注"的确认测试，还没有真的开始猜数据**，真正用 `length()`/`substr()` 等函数去猜字符，是第④步利用阶段才会做的事 |
| **E** | Error-based（报错注入） | SQLMap 内置了一整套针对不同数据库的报错函数 payload（MySQL 对应 `updatexml`/`extractvalue`，Oracle/MSSQL/PostgreSQL 各自有对应的报错函数），依次尝试拼接，观察响应里是否出现了数据库的报错信息。等价于《SQL盲注原理笔记》第四节讲的报错注入原理，只是 SQLMap 把"该用哪个数据库的哪个报错函数"这个判断也自动化了——你需要先手动想清楚用 `updatexml` 还是 `extractvalue`，它会按数据库类型自动挑 |
| **U** | UNION query-based（联合查询注入） | SQLMap 先用类似 `ORDER BY` 递增的方式探测字段数，再依次在每个字段位置插入一个独特的标记字符串，看响应里哪个位置显示出了这个标记——这正是《SQL注入全数据库类型实战笔记》第五章讲的"判断字段数"和"确定回显位置"这两步手工流程的自动化版本 |
| **S** | Stacked queries（堆叠查询） | SQLMap 尝试在原参数后追加一个分号 `;`，再跟上一条无害的测试语句（比如调用一个数据库版本函数），看这条独立语句是否真的被执行了。这和《堆叠注入与二次注入笔记》1.3 节讲的"先用无害探测语句验证堆叠是否生效"的四步手工流程，思路完全一致，只是自动化了 |
| **T** | Time-based blind（时间盲注） | SQLMap 会**先测一次"正常"请求的基准响应时间**，再发送一个带 `SLEEP()`/`WAITFOR DELAY` 之类延时函数、且被包在条件判断里的 payload，对比这次响应时间是否明显变长。这个"先测基准、再测条件触发"的对照思路，就是《SQL盲注原理笔记》里 `and if(1=1,sleep(5),0)` / `and if(1>2,sleep(1),0)` 那组"真假对照实验"的自动化版本——SQLMap 这么做也是为了排除网络本身波动造成的误判，原理和你手工测试时的考量完全一样 |
| **Q** | Inline queries（内联查询） | 把子查询直接内联嵌入原语句中获取数据，使用频率较低、依赖场景较特殊，前面笔记里没有专门展开，了解这个代号存在即可 |

> **一句话理解**：SQLMap 并没有发明任何新的注入手法，**它内置的 payload 库，本质上就是把你前面几篇笔记里学的那些手工 payload，连同各数据库的语法差异，全部提前写好、排好优先级，然后按顺序自动化地挨个尝试一遍。**

### 1.3 第三步：指纹识别

一旦某种技术被确认有效，SQLMap 会顺便通过报错信息、特定函数的支持情况等线索，判断目标具体是哪种数据库、哪个版本——对应《SQL注入全数据库类型实战笔记》第一节讲的"先判断数据库类型"这一步，只是这一步在手工流程里通常要你自己先观察再决定用哪套语法，SQLMap 则是在探测过程中顺带自动完成判断。

### 1.4 第四步：利用（真正的数据提取/文件操作等）

确认了"哪种技术有效、是什么数据库"之后，后续你用 `--dump`、`--file-read`、`--os-shell` 等参数发起的所有操作，都会**优先选用第②步里确认成功的那种技术**去执行，不会每次都重新测试一遍所有技术——这也是为什么《SQLMap使用指南》里建议先做基础探测、再做具体数据提取的原因。

## 二、SQLMap 怎么决定"优先用哪种技术"

默认情况下，SQLMap 会按内置的优先级顺序依次尝试所有技术（除非你用 `--technique=` 显式指定只测某几种），**一旦某种技术被验证有效，后续数据提取阶段会优先使用这种技术**，原因很直接：**不同技术的"取数据效率"天差地别**：

```
效率从高到低：
联合查询注入(U) > 报错注入(E) > 堆叠查询(S) > 布尔盲注(B) > 时间盲注(T)
```

联合查询和报错注入往往能"一次请求拿一大段数据"；布尔盲注和时间盲注则必须"一个字符一个字符猜"，哪怕猜测过程本身做了二分查找优化，请求次数依然是数量级的差距。这也是为什么《SQL盲注原理笔记》第二节讲"先试报错注入、不行再布尔、最后才时间盲注"——SQLMap 内部的优先级逻辑，和你手工测试时应该遵循的判断顺序是同一套道理。

## 三、知道了这些底层逻辑，对你有什么实际帮助

这是本文的核心目的——**当 SQLMap 跑不出结果，或者只跑出部分结果时，你应该立刻知道"它已经试过了什么，没试过什么"，从而决定你接下来该亲自动手走哪条路**：

| SQLMap 的反馈 | 说明它已经做过了什么 | 你接下来该怎么想 |
|---|---|---|
| **报告"目标参数不存在注入"（所有技术均失败）** | 六种技术的标准 payload 全部按内置形态发送过了，都没拿到预期反应 | 不是简单地"再跑一次"，而是要换个角度想：① 是不是 WAF/过滤拦截了 SQLMap 的标准 payload 特征，而不是真的没有注入（配合 `--proxy` 接 Burp 观察实际发出的请求，再决定用哪个 tamper）；② 是不是属于《堆叠注入与二次注入笔记》讲的二次注入场景——这种"先存后用"的触发方式，SQLMap 默认流程完全覆盖不到，必须手工按那篇笔记的步骤去定位真正的触发点；③ 是不是参数本身被 XML/JSON/Base64 包了一层（《SQL注入实战进阶笔记》第三节），SQLMap 发出的标准 payload 在到达真正拼接点之前，可能已经因为外层格式不合法而被拦在半路；④ 是不是注入点其实在请求头里，而默认 `--level=1` 根本没测那些位置（详见下一行） |
| **只确认了布尔盲注（B），没有确认联合查询（U）** | 说明页面对"真/假"有可观察的差异，但没有一个"会被显示出来的查询结果位置" | 这种情况下，即使你再怎么手工找 `UNION` 的回显列，大概率也找不到——没必要浪费时间重复尝试，直接按布尔盲注（或退一步看看有没有报错注入可能）的思路继续走就好 |
| **确认了报错注入（E）** | 说明页面会把数据库报错信息显示出来 | 这是目前已确认技术里效率最高的一种，后续无论是用 `--dump` 还是手工验证，都优先走这条路，没必要特意再等时间盲注跑完（它会慢得多） |
| **只确认了时间盲注（T）** | 说明页面对真假没有任何可见差异、也不报错 | 心理上要有预期：接下来的数据提取会比较慢（一个字符一个字符靠延时猜），这是没有其他更快方式可选时的正常现象，不代表哪里出了问题 |
