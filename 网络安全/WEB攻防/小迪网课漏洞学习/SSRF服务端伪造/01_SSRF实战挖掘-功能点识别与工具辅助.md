## 1. 功能逻辑挖掘:SSRF 高发功能点(🔴 核心)

### 1.1 它是什么 & 核心判断

SSRF 的本质是"**让服务器去访问一个 URL**"。所以反过来——**任何一个"你给它一个地址/URL,服务器就去访问/获取那个地址内容"的功能,都是 SSRF 的天然温床。**

> 🔎 判断口诀:**"这个功能,是不是让服务器替我去'够'一个我指定的东西?"** 是 → 重点测 SSRF。

### 1.2 高发功能点清单(看到就精神一振)

这些功能的共同点都是"**服务器拿你给的 URL 去访问**",对应你《SRC漏洞挖掘经验》里"涉及外部交互的功能是高发区"的具体化:

| 功能点 | 为什么是 SSRF 温床 |
|---|---|
| **社交分享 / 收藏** | 你给个链接,服务器去抓取那个网页的标题/摘要/图片来显示 → 服务器访问了你给的 URL |
| **转码服务**（网页转手机版） | 服务器去访问原网址,把内容调优 → 访问了你给的 URL |
| **在线翻译**（翻译整个网页） | 你给网址,服务器去抓取该网页内容来翻译 |
| **图片/文件 加载/下载** | 富文本编辑器"从URL下载图片到本地"、通过URL加载图片 → 服务器去取你给的图片地址 |
| **视频解析 / 格式转换** | 你给视频/文件的URL,服务器去下载解析 |
| **代码执行 / 在线工具** | 一些在线工具会去访问你指定的资源 |
| **数据采集 / 网站抓取** | 你输入URL,服务器去采集那个网站的信息 |
| **云服务厂商功能** | 远程执行命令判断网站是否存活(如"检测我的网站能不能访问") |
| **数据库内置功能** | 如 MongoDB 的 `copyDatabase` 等会发起网络请求的函数 |
| **邮件系统** | 配置"接收邮件服务器地址"等 |
| **文件/编码处理器** | ffmpeg、ImageMagick、docx/pdf/xml 处理器等,处理时可能发起外连 |
| **未公开 API / 扩展调用 URL 的功能** | 可用 Google 语法 + 关键字去搜这类隐藏功能 |

> 💡 **实战思路**:拿到一个站,先过一遍有没有上面这些功能。尤其"分享""收藏""导入URL""在线预览""网页截图/转PDF"这类——它们几乎一定在后台发起了服务器端请求,是 SSRF 的首要目标。

### 1.3 危险参数名识别(🔴 核心,看名知意)

和你挖 XSS/SQLi 一样,**很多 SSRF 从参数名就能预判**。看到这些参数名,高度怀疑 SSRF:

```
url      link      src       source     target
share    wap       u         display    domain
sourceURL          imageURL
```

> **原理**:一个参数叫 `url`、`imageURL`、`source`,它背后的代码大概率就是"拿这个值去 `curl`/`file_get_contents`/`request` 一下"——这正是 SSRF 的发生点。看到参数值是一个完整 URL(`http://...`),更是直接信号。

### 1.4 白盒视角

代码审计时,找"**文件读取、加载、数据操作类的函数**"——凡是接收一个 URL/地址参数、然后发起网络请求或读取资源的函数(`curl_exec`、`file_get_contents`、`fsockopen`、`request`、各种 HTTP 客户端),都要检查它的 URL 参数是否用户可控、有没有做内网/协议限制。

### 1.5 实战怎么用

- **什么时候想到它**:看到"输入URL→服务器去访问"类功能,或参数名命中上面清单时。
- **怎么验证**:把 URL 参数改成一个**你能监听的地址**(你自己的服务器/DNSLog/Burp Collaborator),看服务器会不会真的来访问你——来了就证明服务器发起了请求(SSRF 成立)。再进一步测内网地址(`127.0.0.1`、`169.254.169.254` 云元数据)、换伪协议(`file://` 等,详见原理篇)。
- **下一步**:确认后按原理篇的"伪协议利用 + 绕过 + 打内网服务(Redis/MySQL/Tomcat)"展开。

## 2. 参数盲测辅助:HaE 插件(🟡 重要)

### 2.1 它是什么 & 解决什么问题

**痛点**:真实渗透时,一个站抓下来几百上千个数据包,**靠肉眼一个个找"哪个参数像 SSRF"太慢**。

**HaE**(github.com/gh0stkey/HaE,Highlighter and Extractor)是一个 **Burp 插件**,作用是——**根据你配置的规则,自动在海量数据包里高亮标记、提取出符合特征的内容**。配合 SSRF 规则,它能帮你把"含 url/src/link 等参数的、可疑的数据包"自动标出来,省掉肉眼大海捞针。

> 它不只用于 SSRF——HaE 是通用的"数据包特征高亮/提取"工具,你可以配规则让它标记各种敏感信息(API key、手机号、可疑参数等),是信息收集/分诊阶段的效率利器。

### 2.2 怎么用(配置三步)

```
1. Burp 安装插件 HaE
2. 修改 HaE 的规则配置文件(加入/启用 SSRF 相关参数的匹配规则)
3. 在插件选项里开启、配置,然后正常浏览/抓包,它会自动高亮标记命中规则的数据包
```

> 💡 定位:HaE 是"**帮你快速从流量里圈出可疑点**"的分诊工具,对应《SRC漏洞挖掘经验》里"危险词雷达"的自动化版本——你定义好"危险词/危险参数"规则,它替你在流量里扫。

## 3. 自动检测:Auto-SSRF 插件(🟡 重要)

### 3.1 它是什么

**Auto-SSRF**(github.com/banchengkemeng/Auto-SSRF)是一个 **专门检测 SSRF 的 Burp 插件**。它比 HaE 更进一步——不只是标记可疑参数,而是**自动给参数注入"探针地址"(指向 Collaborator 的 URL),再监听有没有带外请求打回来**,从而自动判断 SSRF。

### 3.2 原理(带外检测)

SSRF 的验证核心是"**让服务器去访问一个我能监听的地址,看它来不来**"。Auto-SSRF 自动化了这个过程:
1. 把参数值替换成一个 **Burp Collaborator 生成的唯一地址**(带外探针)
2. 发出去
3. **监听 Collaborator**——如果收到了来自目标服务器的请求(DNS/HTTP),说明服务器真的去访问了这个探针地址 → **SSRF 确认**

> 这就是"带外(OOB)检测"——和你《MySQL高权限注入利用笔记》里学的 DNSLog 外带、以及 XSS 盲打的思路是同一套:**没有回显也没关系,让目标主动发起一次外连请求到我能看到的地方,以此证明漏洞存在。** SSRF 天然适合带外检测,因为它的本质就是"让服务器发请求"。

### 3.3 怎么用(配置三步)

```
1. Burp 安装插件 Auto-SSRF
2. 配置并开启 Burp Collaborator(带外监听服务器)
3. 在插件选项里开启监听,正常测试时它会自动注入探针、监听回连
```

> ⚠️ **Collaborator 是关键**:它是 Burp 提供的"带外接收服务器"。专业版自带公共 Collaborator;如果用社区版或想更隐蔽,需要自建 Collaborator 服务器(或用 DNSLog 类平台替代)。

## 4. 把它串起来:SSRF 实战挖掘流程

```
① 信息收集:过一遍目标有没有"服务器帮你访问URL"类功能(§1.2 清单)
        ↓
② 分诊:全站抓包 → 用 HaE 自动高亮出含 url/src/link 等可疑参数的数据包(§2)
        ↓
③ 快速检测:对可疑参数,用 Auto-SSRF 自动注入 Collaborator 探针 + 监听回连(§3)
   或手工:把 URL 参数改成你的监听地址(DNSLog/Collaborator),看服务器来不来
        ↓
④ 确认 SSRF 后,按《SSRF服务端请求伪造完整笔记》展开利用:
   探内网 → 打 127.0.0.1/内网IP → 云元数据 169.254.169.254 → 伪协议(file://等)
   → 打内网服务(Redis/MySQL/Tomcat)→ gopher 协议
        ↓
⑤ 绕过(如有防护):进制转换、@绕过、短网址、302重定向、域名解析(详见原理篇)
```

> **工具 vs 手工**:HaE/Auto-SSRF 是提效工具(帮你从海量流量里快速定位+初步验证),但**"判断哪个功能点值得测、确认后怎么深入利用"还是靠你对 SSRF 原理和业务的理解**。工具负责"广度快速筛",你负责"深度判断和利用"。

## 5. 自测(先自己想,再看答案)

1. 用一句话说清楚:为什么"社交分享""网页翻译""URL导入图片"这类功能是 SSRF 高发区?
2. Auto-SSRF 插件判断 SSRF 用的是"带外检测",它的原理是什么?为什么 SSRF 特别适合用带外检测?
3. HaE 和 Auto-SSRF 两个插件的分工有什么不同?

<details>
<summary>参考答案</summary>

1. 因为这些功能的本质都是"**你给服务器一个 URL,服务器替你去访问那个 URL 并获取内容**"(抓标题、翻译网页、下载图片)。这个"服务器去访问你指定的 URL"的动作,正是 SSRF 的发生点——如果服务器不限制你给的 URL 范围,你就能让它去访问内网/本地/云元数据。
2. 带外检测原理:把参数值替换成一个你能监听的唯一地址(Collaborator/DNSLog),发出去后监听那个地址——如果收到来自目标服务器的请求,说明服务器真的去访问了你给的地址,SSRF 成立。SSRF 特别适合带外检测,是因为 SSRF 的本质就是"让服务器主动发起请求",而带外检测正是"看服务器会不会主动来访问我的监听地址",两者天然契合;而且很多 SSRF 没有回显,带外是最可靠的验证方式。
3. HaE 是"**高亮/提取**"工具——根据规则在海量数据包里标记出含可疑参数(url/src等)的包,帮你快速分诊定位(广度筛选);Auto-SSRF 是"**自动检测**"工具——对参数自动注入 Collaborator 探针并监听回连,自动判断是否真的存在 SSRF(验证)。一个帮你"找可疑点",一个帮你"验证可疑点"。

</details>
