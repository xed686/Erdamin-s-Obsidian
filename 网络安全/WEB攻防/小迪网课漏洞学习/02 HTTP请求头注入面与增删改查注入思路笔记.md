# HTTP 请求头注入面 与 增删改查业务对应的注入思路笔记

> **与前置笔记的关系**：这是《SQL注入全数据库类型实战笔记》《SQL注入实战进阶笔记》的延续。前两篇讲的是"注入点已经确认在某个参数里，具体怎么打"；今天这篇往前退一步，讲**注入点可能藏在哪些你容易忽略的位置（请求头）**，以及往后退一步，讲**拿到注入点之后，要根据这个功能背后到底是 SELECT/INSERT/UPDATE/DELETE 中的哪一种，换用完全不同的打法**——这是很多初学者容易卡住的地方：以为所有 SQL 注入都靠 `union select` 解决，遇到 INSERT/UPDATE/DELETE 类功能直接懵住。

---

## 一、常见请求头详解与注入机会分析

先明确一个核心认知：**请求头（Header）本质上也是用户可以完全自定义的输入**，和 URL 参数、表单字段没有本质区别——唯一的差别是它们出现的"位置"不同（在 HTTP 请求的头部，而不是请求体/URL）。只要后端代码把某个请求头的值**拿去做了判断、记录或拼接**，它就有可能成为注入点。下面逐个拆解。

### 1.1 User-Agent（UA）

**含义**：浏览器/客户端在每次请求时自动携带的一段字符串，描述"我是什么设备、什么浏览器、什么操作系统"。

**网站什么时候会用到它**：
- **场景 1：按设备类型返回不同展示方案**——比如判断 UA 里含不含"Mobile"字样，决定返回手机版页面还是电脑版页面。
- **场景 2：把 UA 记录下来做统计**——比如后台统计"今天有多少用户用的是 iPhone 访问"，这类统计功能通常会把每次请求的 UA 原样存进数据库的访问日志表。

**这是不是你能利用的点**：**场景 2 是经典注入点**。因为"记录 UA 到数据库"这个动作，本质上就是一条 `INSERT INTO access_log (ua, ...) VALUES ('$UA', ...)` 之类的语句——如果开发者直接把你发来的 UA 字符串原样拼进这条 SQL，而不做任何处理，你完全可以把 UA 改写成一段注入 payload。这也是为什么渗透测试中，**UA 头是黑盒测试时的标准必测点之一**，即使页面上完全看不到和"设备信息"相关的任何功能，也应该默认尝试对 UA 做注入测试，因为你永远不知道后台是否在悄悄记录它。

> 场景 1（按 UA 做展示切换）本身一般不直接涉及 SQL（更多是前端判断或简单的字符串匹配），不是注入重点，但了解这个场景能帮你猜测"这个网站可能对不同设备做了限制"，必要时可以通过伪造 UA 绕过设备访问限制，这是另一类"访问控制绕过"的思路，和 SQL 注入是两回事，不要混淆。

### 1.2 X-Forwarded-For（XFF）

**含义**：标准设计用途是在经过代理/负载均衡等中间节点转发请求时，记录"最原始发起请求的客户端真实 IP"——因为一旦经过代理，服务器直接看到的连接 IP 会变成代理服务器的 IP，XFF 就是用来把原始 IP"带过去"的。

**网站什么时候会用到它**：
- **场景 1：基于 IP 做访问限制**——比如某些后台管理系统只允许内网 IP 访问，判断逻辑可能是"检查 XFF 里的 IP 是否在允许范围内"。
- **场景 2：记录访问日志**——和 UA 类似，把每次请求的来源 IP 存进数据库做统计分析。

**这是不是你能利用的点**：**两个场景都值得关注，但原理不同**：
- 场景 2（记录日志）和 UA 的道理完全一样——如果 IP 被直接拼进 SQL 存库，就是注入点，同样应作为黑盒测试的标准必测项。
- 场景 1（基于 IP 做访问限制）本身**不是 SQL 注入**，而是另一类**访问控制绕过**——**这正好直接回答你问的"网站说我权限不够时，是通过哪个请求头判断的"这个问题**：如果一个后台提示"仅允许内网访问"或"检测到异常访问被拒绝"，很多老旧/配置不当的系统，判断逻辑仅仅是"检查 `X-Forwarded-For` 请求头里的值是不是内网 IP 段"，而 XFF **是客户端自己随便填的**，服务器如果没有在网络层面（而是单纯信任这个用户可控的请求头）做校验，你只需要在请求里手动加一个 `X-Forwarded-For: 127.0.0.1` 或 `X-Forwarded-For: 192.168.1.1` 这类内网地址，就可能直接绕过这层"权限不够"的限制——这不是 SQL 注入，但是是你能利用的点，而且是极其常见的真实漏洞类型。

### 1.3 Cookie

**含义**：服务器下发、浏览器保存，并在后续每次请求中自动携带回去的一小段数据，通常用来维持登录状态（详见此前《身份验证机制笔记》）。

**网站什么时候会用到它**：开发者为了实现"查询我自己的信息"这类功能，一种偷懒（也是危险）的实现方式是：**不通过服务端的 Session 机制去校验"你是谁"，而是直接把用户 ID 明文存在 Cookie 里，后端直接读取这个 Cookie 值去拼 SQL 查询**，比如 `SELECT * FROM users WHERE id = $cookie_user_id`。

**这是不是你能利用的点**：**是，而且危害通常比 UA/XFF 更大**，原因有两层：
1. **注入层面**：Cookie 里的这个 `user_id` 和 URL 参数、表单字段一样，是用户完全可控的输入，只要被拼进了 SQL，就是标准的注入点，测试方法和前面几篇笔记讲的完全一样（先判断字符型/数字型，再往下走）。
2. **即使没有注入，这个设计本身也是一个独立的高危漏洞**——如果后端只信任 Cookie 里的 `user_id` 而不做权限校验，你直接**修改 Cookie 里的 `user_id` 为别人的 ID**，就能看到别人的数据，这是典型的**水平越权（IDOR）**问题（详见《鉴权与身份验证技术全景笔记》里提到的访问控制篇）。这也再次印证了"权限不够"这种提示背后的判断依据，很多时候就落在 Cookie 这一类客户端可控凭证上，一旦校验逻辑有缺陷，改一下值就能绕过。

### 1.4 Referer

**含义**：告诉服务器"这次请求是从哪个页面跳转过来的"，浏览器根据你点击链接/提交表单前所在的页面自动填写。

**网站什么时候会用到它**：防止跨站请求伪造（CSRF）或盗链的一种简单手段——比如登录接口，服务器期望"登录请求必须是从本站的登录页面发出的"，如果 Referer 显示请求来自其他网站，就直接拒绝，提示"非法请求"或"权限不够"。

**这是不是你能利用的点**：
- **绕过角度**：这同样**回答了你问的"权限不够"场景**——如果一个功能仅凭 Referer 做来源校验，而 Referer 本身是**客户端在请求时自行声明、服务器无法验证真伪**的字段（可以用 Burp 等工具任意修改这个请求头），只要把 Referer 伪造成"看起来像是本站域名"的内容，就可能绕过这层校验——这也不是 SQL 注入，但同样是典型的可利用点。
- **注入角度**：如果网站有"访问来源统计"这类功能，把 Referer 记录进数据库，同样遵循前面讲过的规律——凡是"被记录进数据库"的用户可控字段，都要默认当成潜在注入点去测试。

### 1.5 四个请求头小结：判断"权限不够"背后用的是哪个

| 场景 | 很可能是哪个请求头在起作用 | 本质 |
|---|---|---|
| "检测到非法设备/浏览器" | UA | 访问控制（非标准安全机制，较弱） |
| "仅允许内网/白名单 IP 访问" | XFF（或直连 IP，但很多系统会错误地优先信任 XFF） | 访问控制 |
| "请先登录"/"无权查看他人数据" | Cookie（Session/Token） | 身份鉴权 |
| "请从本站页面发起请求" | Referer | 简单的来源校验（非标准 CSRF 防护） |

**统一结论**：UA、XFF、Referer 这三者都属于**客户端自己声明、服务器单纯信任而未做强校验**的情况下才会被绕过的"弱校验"，遇到基于它们的限制，第一反应应该是"伪造/修改这个请求头试试"；而 Cookie 通常承载的是更核心的身份信息，一旦相关查询逻辑把 Cookie 值直接拼进 SQL，往往是"注入 + 越权"两个问题叠加在一起的高价值目标。

## 二、增删改查业务功能映射

先把业务功能和它背后对应的 SQL 操作类型对应起来，这是黑盒测试时快速判断"这里该用哪种注入手法"的第一步：

| SQL 操作        | 常见业务功能                                         |
| ------------- | ---------------------------------------------- |
| **SELECT（查）** | 用户查询、新闻查询、搜索框、列表展示、详情页                         |
| **INSERT（增）** | 用户注册、新闻/评论发布、文件上传记录、前文提到的"UA/XFF/Referer 日志记录" |
| **UPDATE（改）** | 用户资料修改、密码修改、新闻编辑                               |
| **DELETE（删）** | 用户注销/删除账号、新闻删除、评论删除                            |

黑盒测试中看到任何一个功能点，第一步先判断它属于这四类里的哪一种（往往从功能的字面意思就能猜到），这直接决定了你该用本文第三节里的哪一套思路，而不是无脑套用 `union select`。

## 三、为什么不同的增删改查业务不能用同一套注入语句

这是今天的核心问题：**为什么 `UNION` 这个万能钥匙，只能用在 SELECT 类型的业务上，一到 INSERT/UPDATE/DELETE 就不管用了？**

### 3.1 根本原因：UNION 的本质是"合并两个查询结果集"

`UNION` 这个关键字的设计用途，是把**两条 SELECT 语句各自查出来的结果集，纵向拼接成一个结果集**。它的语法要求非常明确：**`UNION` 前后必须都是 `SELECT` 语句**。

而 `INSERT`、`UPDATE`、`DELETE` 这三类语句，从语法设计上就**根本不会产生一个"结果集"**——它们执行完之后，数据库返回的只是"受影响的行数"（比如"成功插入 1 行"、"成功删除 3 行"），而不是一张可以展示的数据表。**既然没有"结果集"这个东西存在，`UNION` 就没有东西可以去"合并"**，所以你不可能写出 `INSERT INTO users (...) VALUES (...) UNION SELECT ...` 这样的语句——这在语法层面就是不合法的，数据库解析到这里直接报语法错误，根本不会执行。

**用一个类比理解**：`UNION` 就像是把两份 Excel 表格的数据粘贴在一起，前提是必须先有"两份表格"（两个 SELECT 的结果）才能粘贴；而 INSERT/UPDATE/DELETE 做的事情是"往表格里写一行字"或"擦掉一行字"，这个动作本身根本不产生"表格"，自然没法拿去跟别的表格"粘贴合并"。

### 3.2 SELECT 类业务：联合查询注入（UNION-based）是首选

因为 SELECT 本身就在"查数据并把结果展示出来"，页面上通常能直接看到查询结果，这正好符合 `UNION SELECT` 的使用条件——拼接一条你自己构造的 `SELECT`，让它的结果混进原本要展示的数据里，一起显示到页面上。这也是《SQL注入全数据库类型实战笔记》第 5 章、《SQL注入实战进阶笔记》第二章详细演示的场景。

### 3.3 INSERT 类业务：该用什么

既然不能用 UNION，INSERT 类业务（如用户注册）能用的手法主要有两类，取决于注入点出现的位置：

**情况一：注入点在 VALUES 的某个值里**，比如：
```sql
INSERT INTO users (username, email) VALUES ('$username', '$email');
```
如果 `$username` 可控，你没法在这里"合并"出一个新的查询结果集，但你可以：
- **报错注入**：把 `$username` 构造成一个会触发报错、同时报错信息里会带出你想要的数据的表达式，比如用之前学过的 `updatexml()`/`extractvalue()` 包一层子查询塞进去（详见《SQL注入全数据库类型实战笔记》第 11 章原理，手法通用，只是这次出现的位置从 `SELECT ... WHERE` 变成了 `INSERT ... VALUES`）。
- **布尔盲注/时间盲注**：把 `$username` 构造成一个带条件判断的子查询（比如 `(SELECT IF(1=1,'正常用户名','x'))`），通过"注册是否成功"或"响应是否延迟"来判断条件真假，逐字符猜出数据——原理和之前讲的盲注完全一致，只是"看真假"的依据从"页面内容是否变化"换成了"这次注册请求是否成功/是否卡顿"。 简单来说,**盲注(Boolean/Time-based Blind SQLi)是在页面既不回显数据、也不报错、甚至数据库都不报错的情况下,攻击者通过“问问题”的方式,靠猜测把数据硬生生“盲”出来的技术。**

**情况二：如果数据库/驱动支持堆叠查询（Stacked Queries）**，你可以直接在原语句后面用 `;` 拼接一条全新的、完全独立的语句：
```sql
INSERT INTO users (username) VALUES ('a'); SELECT password FROM admin WHERE id=1;-- ');
```
这种情况下，你拼接的已经不是"合并进同一个结果集"，而是**另起一条全新的语句去执行**，理论上甚至可以拼接一条 `UPDATE`/`DELETE` 语句去做数据篡改，而不仅仅是读取数据。但要注意：**并不是所有应用环境都支持堆叠查询**（取决于具体用的数据库驱动/框架是否允许一次提交执行多条语句），这是实战中需要先验证的前提条件。

### 3.4 UPDATE 类业务：该用什么

和 INSERT 同理，`UPDATE` 同样不产生结果集，无法使用 UNION。常见位置：

```sql
UPDATE users SET email='$email' WHERE id=$id;
```

如果 `$email` 可控，手法和 INSERT 一致：**报错注入**（构造能报错并带出数据的表达式）或**布尔/时间盲注**（构造带条件判断的子查询放进 `SET` 的值里）。如果 `$id` 可控（这是数字型参数，更接近前面几篇笔记讲过的标准场景），则可以考虑堆叠查询（若环境支持）去拼接独立语句。

### 3.5 DELETE 类业务：该用什么

```sql
DELETE FROM news WHERE id=$id;
```

`DELETE` 语句的特殊之处在于：它本身的核心逻辑就是"`WHERE` 条件为真的行会被删掉"，这天然适合拿来做**布尔盲注**——不需要你额外构造复杂的子查询技巧，只需要利用它本身的行为：

- 构造一个会让 `WHERE` 条件判断为**真**的 payload：这一行数据真的会被删掉。
- 构造一个让条件判断为**假**的 payload：这一行数据**不会**被删除，保持原样。

你可以通过"**这条数据删除前后是否还存在**"（比如配合一个能查询到该数据是否还在的功能）来间接判断条件真假，这本质上也是布尔盲注的一种变体，只是"真假的证据"从"页面内容"换成了"数据是否被删掉了"。同样，时间盲注（在条件里拼接 `SLEEP()`）也完全适用，而且更直接，不需要额外验证数据是否被删，直接看响应时间即可。

### 3.6 四类操作的注入手法对照表

| SQL 操作     | 能否用 UNION | 核心原因                 | 常用替代手法                                  |
| ---------- | --------- | -------------------- | --------------------------------------- |
| **SELECT** | ✅ 可以      | 本身就产生结果集，且结果通常直接展示   | 联合查询注入（优先）、报错注入、布尔/时间盲注                 |
| **INSERT** | ❌ 不可以     | 不产生结果集，UNION 无结果集可合并 | 报错注入、布尔/时间盲注、堆叠查询（如环境支持）                |
| **UPDATE** | ❌ 不可以     | 同上                   | 报错注入、布尔/时间盲注、堆叠查询（如环境支持）                |
| **DELETE** | ❌ 不可以     | 同上                   | 布尔盲注（借助"数据是否被删"作为真假依据）、时间盲注、堆叠查询（如环境支持） |

**最终统一结论**：能不能用 `UNION`，本质上只取决于一件事——**当前这条 SQL 语句执行后，有没有一个"结果集"存在**。有结果集（SELECT）就优先考虑 UNION 和报错/盲注；没有结果集（INSERT/UPDATE/DELETE）就只能考虑报错注入、盲注、或堆叠查询这几种"不依赖合并结果集"的手法。遇到任何一个新的业务功能点时，先判断它背后是哪种 SQL 操作，就能立刻排除掉不适用的手法，避免在 INSERT/UPDATE/DELETE 类型的功能上浪费时间去尝试根本不可能成功的 `union select`。
