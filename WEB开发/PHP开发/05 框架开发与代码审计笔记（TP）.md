# ThinkPHP5 框架开发与代码审计安全笔记

> PHP 生态常用组件/框架一览表已在《PHP生态组件与模板引擎安全笔记》中整理过，此处不再重复列出，仅聚焦 ThinkPHP5（TP5）这一具体框架的开发要点与审计思路。

官方手册参考：https://www.kancloud.cn/manual/thinkphp5/118003

## 一、TP5 开发基础技术（五大模块）

### 1. 配置架构 — 导入使用
- 入口文件（`public/index.php`）是应用的统一入口。
- `config/` 目录下管理数据库配置、应用配置等。
- **调试开关**（`APP_DEBUG`）：审计时需重点关注生产环境是否仍开启调试模式 —— 若开启，报错信息可能直接暴露数据库配置、路径结构等敏感信息，是信息泄露的常见入口。

### 2. 路由访问 — URL 访问
- URL 访问模式（普通模式 / PATHINFO 模式 / 兼容模式等），决定请求如何被解析映射到对应的控制器/方法。
- 目录结构与控制器、方法之间存在默认对应关系（`模块/控制器/方法`）；审计时应先梳理路由规则，才能准确定位某个功能入口对应的具体代码文件。

### 3. 请求变量 — 数据接收
- 框架提供 `Request` 对象及 `input()` 等助手函数统一处理 GET/POST/路由参数等输入。
- **审计要点**：留意业务代码是在通过框架的 `Request` 对象/助手函数接收参数（框架层面通常自带基础过滤），还是绕过框架直接使用原生 `$_GET`/`$_POST`/`$_REQUEST`（这类写法往往缺少框架自带的安全处理，是更值得重点审计的位置）。

### 4. 数据库操作 — 应用对象
- 引用 `Db` 类进行基础查询，或使用 Model 基类进行 ORM 式操作；同时提供 `db()` 等助手函数。
- **审计要点**：框架内置的查询构造器（如 `where()` 方法传入数组条件）本身具备一定防注入能力，但若写法不规范（例如直接拼接字符串条件、或向查询方法传入未经处理的用户可控数组），仍可能绕过框架自带防护产生 SQL 注入（见下文"写法内置安全绕过"案例）。

### 5. 前端页面渲染 — MVC 模型
- 模板引擎配置（内置模板引擎/第三方模板引擎）、`assign()` 渲染变量、模板文件输出。
- 与前述 Smarty SSTI 的审计思路一致：核查是否存在用户输入被当作模板字符串本身（而非变量）渲染的路径。

## 二、TP 框架写法安全

### 1. 自写代码逻辑的三种情况（风险从高到低排序）

| 写法类型 | 说明 | 审计关注度 |
|---|---|---|
| 完全自写、不合规的代码写法 | 完全绕开框架机制，自行处理请求/数据库操作等 | **最高**——最容易出现未经框架基础防护的原始漏洞（如拼接 SQL、直接回显用户输入） |
| 一半框架、一半自写代码 | 部分功能用框架标准方法，部分自行实现 | **中等**——需要重点核查自写部分与框架机制衔接处是否存在逻辑缺口 |
| 框架标准内置写法 | 完全遵循框架推荐的开发范式 | **较低**——框架标准方法通常经过较充分的测试和社区审计，但仍需结合框架版本本身是否存在已知漏洞判断 |

> 代码审计实战经验：**越偏离框架标准范式的自定义逻辑，越应优先审计**；而使用标准写法的代码，审计重心应转向"所用的框架版本是否存在已知 CVE"。

### 2. 框架版本安全

参考漏洞库：https://github.com/Mochazz/ThinkPHP-Vuln

| 案例类型 | 说明 |
|---|---|
| 写法内置安全绕过 — TP5 SQL 注入 | 即使使用了框架自带的查询构造器/ORM，若写法不当（如将用户可控内容直接作为数组键名或特殊条件传入 `where()` 等方法），仍可能绕过框架内置的参数化防护，构造出 SQL 注入 |
| 内置版本安全漏洞 — TP5 代码执行 | 框架自身版本存在的已知 RCE 缺陷，无需业务代码本身存在编写错误即可触发，是 ThinkPHP 生态中最广为人知的高危漏洞类别之一，审计时应第一步确认目标 TP 版本号并比对已知漏洞列表 |

> 两类案例对应两种完全不同的审计路径：前者需要**读懂业务代码的具体写法**，后者只需要**识别框架版本号**即可快速判断风险，二者缺一不可。

## 三、代码审计案例

### WeMall（基于 TP5 框架开发的商城系统）

**典型审计思路**：
1. 先确认目标系统所使用的 ThinkPHP 版本号（可通过报错信息、特征文件、指纹识别等方式获取）。
2. 对照已知 CVE/公开漏洞库（如上方 ThinkPHP-Vuln 仓库）判断是否命中已知版本漏洞。
3. 若版本本身无已知漏洞，再回到业务代码层面，核查其自写逻辑（尤其是"一半框架一半自写"或"完全自写"的部分）是否存在二次开发引入的缺陷。

---

## 四、总结

1. 审计 TP5（及同类框架）项目时，应先理清五大基础模块（配置、路由、请求、数据库、渲染）各自的标准用法，才能准确判断具体业务代码是否偏离了框架的"安全默认值"。
2. 写法规范程度与漏洞风险基本成反比——越自定义、越绕过框架机制的代码，越需要重点审计；同时框架本身的版本号也必须单独核查，两条线（**写法审计** + **版本漏洞核对**）需要同时进行，缺一不可。
