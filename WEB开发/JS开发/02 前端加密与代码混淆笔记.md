## 一、前端数据传输的两种大致流程

### 1. 非加密数据流程
```
客户端发送 → 明文数据传输 → 服务端接收数据 → 处理数据
```

### 2. 加密数据流程
```
明文加密 → 客户端发送 → 密文数据传输 → 服务端接收数据 → 解密数据 → 处理数据
```

两者的本质区别只在于：**加密/解密这两步被插入到了"客户端发送"之前和"服务端处理"之前**，中间网络传输层面看到的内容不同（明文 vs 密文），但业务逻辑本身没有变化。

## 二、关键问题解析：安全测试中"修改数据"到底发生在流程的哪一步

这是一个非常核心的实战问题，答案取决于你用什么工具去拦截，拦截点不同，能拿到的数据形态也不同：

### 1. 网络层拦截（Burp Suite 等代理工具）— 拦的是"客户端发送"之后
Burp 这类代理工具工作在**网络传输层**，意味着它拦到的请求，是浏览器 JS **已经执行完加密逻辑之后**才发出的。对应到上面流程图，Burp 拦截的位置在：

```
明文加密 → 客户端发送 →【Burp 在这里拦截】→ 密文数据传输 → ...
```

**这就带来一个实际问题**：如果业务做了前端加密，你在 Burp 里直接改请求包里的参数值，改的其实是**密文**。服务端解密后得到的会是一堆乱码或者解密失败，请求大概率直接报错，修改"看似生效了"但实际没有意义。

要想真正篡改业务数据，这条路线需要你：
1. 先逆向出前端的加密算法和密钥/IV 等参数（通过分析 JS 代码，见下文 Crypto-js/jsencrypt 两节）。
2. 在 Burp 外部（比如用脚本还原同样的加密逻辑）把明文改好 → 重新加密 → 再把算出来的新密文替换进请求包。

这个路线对加密逆向能力要求较高，但好处是可以脱离浏览器环境、批量自动化构造请求（如写爆破/扫描脚本）。

### 2. 代码执行层拦截（浏览器开发者工具 断点调试）— 拦的是"明文加密"之前
更常用、更直接的做法是**不碰网络层，而是直接在浏览器里"拦截 JS 执行过程"**：在浏览器 DevTools 的 Sources 面板，找到执行加密逻辑的那一行代码（比如 `CryptoJS.AES.encrypt(...)`），打一个断点。

对应到流程图，这个拦截点在：

```
【在这里打断点，修改即将被加密的变量】→ 明文加密 → 客户端发送 → ...
```

这样做的好处是：**你不需要自己逆向实现一套加密算法**——只需要在断点处把即将被加密的那个明文变量改成你想要的值，然后放行，让浏览器用它自己原本的 JS 代码正常完成加密和发送，服务端收到的就是一个"看起来完全正常、实际携带了你篡改后数据"的合法加密请求。

### 小结对比

| 拦截方式 | 拦截位置 | 拿到的数据 | 适用场景 |
|---|---|---|---|
| Burp 等代理工具 | 客户端发送之后（网络层） | 密文 | 已掌握加密算法，适合自动化批量构造请求 |
| 浏览器断点调试 | 加密之前（代码执行层） | 明文 | 不需要逆向算法，适合手工测试单次请求、理解加密逻辑 |

> 实战中两者经常配合使用：先用断点调试法理解清楚"到底加密了哪些字段、用了什么算法"，再决定是否值得花时间逆向还原算法来做自动化批量测试。

## 三、前端加密库：Crypto-js

用于在前端实现 MD5、SHA1、HMAC、AES、DES 等**对称加密/哈希算法**。

- 项目地址：https://github.com/brix/crypto-js
- 参考教程：https://juejin.cn/post/7382893339181613068

**引入方式**：
```html
<script src="crypto-js.js"></script>
<script src="https://cdnjs.cloudflare.com/ajax/libs/crypto-js/4.0.0/crypto-js.min.js"></script>
```

> 审计价值：前端代码中若出现 `CryptoJS.AES.encrypt()`、`CryptoJS.MD5()` 等调用，说明该接口的请求参数经过了前端加密处理，需要结合断点调试找出**密钥（key）和偏移量（IV）**，这两者通常也硬编码在前端 JS 代码中（属于前文"发现敏感信息"审计点的典型场景）。

## 四、前端加密库：jsencrypt

用于在前端实现 **RSA 等非对称加密算法**。

- 项目地址：https://github.com/travist/jsencrypt
- 参考教程：https://www.cnblogs.com/Lrn14616/p/10154529.html

**引入方式**：
```html
<script src="jsencrypt.js"></script>
<script src="https://cdn.bootcdn.net/ajax/libs/jsencrypt/3.3.2/jsencrypt.js"></script>
```

> 审计价值：RSA 为非对称加密，前端通常只持有**公钥**（用于加密），私钥理论上只在服务端。若在前端代码中意外发现私钥，属于严重的密钥泄露问题。

## 五、代码混淆

### 1. 目的
混淆代码的主要目的是**保护源代码**，防止未经授权的复制、篡改或逆向工程。通过修改变量名、字符串、控制流等，混淆后的代码看起来毫无逻辑，但**本质功能不变**。该技术常用于商业应用中保护核心逻辑，也常被恶意软件用来逃避分析检测。

### 2. 常见混淆/压缩手段

| 手段 | 作用 |
|---|---|
| 压缩 | 去除代码中不必要的空格、换行等，将源码压成几行，降低可读性，同时提升加载速度 |
| 变量替换 | 把有语义的变量名替换为无意义的随机字符，破坏代码可读性 |
| 僵尸函数（死代码注入） | 插入大量从不被实际调用的无用函数/代码，干扰分析者判断真实逻辑 |
| 字符串阵列化 | 把代码中的字符串统一抽取到一个数组中，通过索引访问，拆散字符串与其使用上下文的直接关联 |
| 控制流平坦化 | 把原本线性/分支清晰的执行逻辑，改写成基于状态机（如 `switch` + 循环）的形式，让代码执行路径变得难以静态追踪 |
| 调试保护 | 在代码中加入反调试逻辑（如检测是否打开了开发者工具、检测断点），干扰分析者使用 DevTools 调试还原逻辑 |

> 以上手段组合使用，是目前相对理想、实用的 JavaScript 前端保护方案——不影响代码原有功能，但大幅提高逆向分析的成本。

### 3. 在线混淆工具
https://obfuscator.io/

> 审计意义：遇到被混淆的前端代码时，不要试图"一眼看懂"，应优先尝试用在线反混淆工具或 AST 还原工具处理后再分析；若存在调试保护，还需先想办法绕过反调试逻辑，才能正常使用断点调试法（见本文第二节）定位加密/校验逻辑。
