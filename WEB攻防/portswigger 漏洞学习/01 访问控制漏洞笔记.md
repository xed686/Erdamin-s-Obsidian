## 1. 什么是访问控制

**访问控制**用来决定:**谁**(或什么)可以对**哪些资源**执行**哪些操作**。

在 Web 应用中,访问控制建立在两项基础能力之上,并与之配合工作:

| 环节                           | 回答的问题          | 说明                   |
| ---------------------------- | -------------- | -------------------- |
| **认证**(Authentication)       | 你是谁?           | 确认用户身份确实是他所声称的那个人    |
| **会话管理**(Session Management) | 这些请求是不是同一个人发的? | 识别后续的 HTTP 请求属于同一个用户 |
| **访问控制**(Access Control)     | 你有权做这件事吗?      | 判断该用户是否被允许执行他尝试的操作   |

**三者的顺序:** 先认证身份 → 再用会话保持身份 → 最后用访问控制判断权限。

### 为什么访问控制漏洞这么常见?

访问控制失效(Broken Access Control)非常普遍,而且往往是**严重的安全漏洞**。原因在于:

- 访问控制的设计与管理是一个复杂且不断变化的问题,涉及**业务规则、组织架构和法律限制**,再把这些规则落实到技术实现里。
- 权限规则**只能由人来设计和决定**,没有通用的自动化方案,因此很容易出错、遗漏。

### 直观例子(对应原文插图)

同一个网站里有两个页面:

| 页面       | URL                                                             | 用途      |
| -------- | --------------------------------------------------------------- | ------- |
| 管理员页面    | `https://insecure-website.com/admin`                            | 删除用户    |
| 普通用户账户页面 | `https://insecure-website.com/accounts/ab12345/accountmenu.jsp` | 查看余额、转账 |

如果服务器没有检查"访问者到底是不是管理员 / 这个账户是不是他自己的",攻击者只要**直接输入 URL** 就能访问这些页面。

## 2. 垂直权限升级

### 定义

> 用户能够访问**本不允许他访问的功能**,就是垂直权限升级(Vertical Privilege Escalation)。

**例子:** 普通用户能访问管理员页面并删除其他用户的账号。

**理解方式:** 把权限想成楼层,普通用户在 1 楼,管理员在 5 楼。垂直升级就是**往上爬了几层**,用到了更高级别的权限。

### 2.1 未保护的功能

**最基础的垂直权限升级:** 应用对敏感功能**完全没有任何保护**。

管理功能的链接可能只出现在管理员的欢迎页面里,普通用户的页面上看不到。但是,如果服务器没有校验权限,普通用户只要**手动在浏览器里输入管理员的 URL**,照样可以访问。

例如,敏感功能放在:

```
https://insecure-website.com/admin
```

这个地址对**所有用户**都可能是开放的,不只是管理员。

**URL 可能在别的地方泄露,例如 `robots.txt`:**

```
https://insecure-website.com/robots.txt
```

`robots.txt` 是告诉搜索引擎"哪些路径不要抓取"的文件,开发者常常把后台路径写进去,结果等于**公开告知了后台地址**。

**即使 URL 没有公开,攻击者也能"猜"出来:** 使用**字典(词表)进行暴力枚举**,批量尝试常见的路径名(如 `/admin`、`/manage`、`/dashboard`),从而发现隐藏的敏感功能。

### 2.2 "隐藏 URL"不等于安全(Security by Obscurity)

有些应用会给敏感功能起一个**很难预测的 URL** 来"隐藏"它,比如:

```
https://insecure-website.com/administrator-panel-yb556
```

这种做法叫**隐蔽性安全**(Security by Obscurity,靠"藏起来"保证安全)。它**并不能提供真正的访问控制**,因为用户有很多办法发现被混淆的 URL。

**典型泄露方式:前端 JavaScript 暴露 URL**

应用可能用 JS 根据用户角色动态生成页面链接:

```html
<script>
  var isAdmin = false;
  if (isAdmin) {
      ...
      var adminPanelTag = document.createElement('a');
      adminPanelTag.setAttribute('href', 'https://insecure-website.com/administrator-panel-yb556');
      adminPanelTag.innerText = 'Admin panel';
      ...
  }
</script>
```

逻辑上看:只有 `isAdmin` 为真时,才会给页面添加"管理员面板"的链接。

**问题在于:** 这段 JS 是**发给所有用户的**。无论你是不是管理员,浏览器都会收到这份脚本,里面就**明文写着**管理员面板的 URL。攻击者只需要查看页面源码或 JS 文件(F12 开发者工具)就能拿到。

> **核心教训:** 前端隐藏 ≠ 后端保护。真正的权限检查必须在**服务端**完成,每一次请求都要验证。

### 2.3 基于参数的访问控制

有些应用在**用户登录时**确定其权限或角色,然后把这个信息存放在**用户可以控制的位置**,例如:

- 一个**隐藏表单字段**
- 一块 **Cookie**
- 一个**预设的查询字符串参数**

之后应用根据请求里提交的这个值来做访问控制决策。例如:

```
https://insecure-website.com/login/home.jsp?admin=true
https://insecure-website.com/login/home.jsp?role=1
```

**为什么不安全?** 这些值是由**客户端传上来的**,用户可以任意修改。只要把 `admin=false` 改成 `admin=true`,或者把 `role=0` 改成 `role=1`,就能获得管理功能的访问权限。

**常见可篡改位置:**

| 位置       | 例子                                               | 修改工具                  |
| -------- | ------------------------------------------------ | --------------------- |
| URL 查询参数 | `?admin=true`                                    | 直接改地址栏 / Burp Suite   |
| Cookie   | `Admin=false`                                    | 浏览器开发者工具 / Burp Suite |
| 隐藏表单字段   | `<input type="hidden" name="role" value="user">` | 开发者工具 / Burp Suite    |

## 3. 水平权限升级

### 定义

> 用户能够访问**属于其他用户的资源**,而不仅仅是自己的同类资源,就是水平权限升级(Horizontal Privilege Escalation,也叫横向权限升级)。

**例子:** 员工既能看自己的记录,也能看**其他员工**的记录。

**理解方式:** 大家都在同一层楼(权限级别相同),水平升级是**走进了别人的房间**。

### 攻击方式

水平升级可以使用和垂直升级类似的利用手法,最典型的是**参数篡改**。

假设用户访问自己的账户页面是:

```
https://insecure-website.com/myaccount?id=123
```

攻击者把 `id` 的值改成别人的:

```
https://insecure-website.com/myaccount?id=456
```

如果服务器没有检查"这个 id 是不是当前登录用户自己的",攻击者就能看到**另一个用户的账户页面,以及相关的数据和功能**。

### IDOR(不安全的直接对象引用)

> **注释:** 上面这个例子就是 **IDOR(Insecure Direct Object Reference,不安全的直接对象引用)** 漏洞。
> 当**用户可控制的参数值**被**直接用来访问资源或功能**,而没有校验访问者是否有权访问时,就会出现这种漏洞。

**IDOR 的本质:** 应用相信"你提交什么 ID,我就给你什么数据",却没有问一句"这个数据是不是你的?"

**常见的"对象引用"参数:** `id`、`uid`、`user_id`、`order_id`、`account`、`file`、`doc` 等。

### 参数不可预测怎么办?(GUID 的情况)

有些应用不使用递增的数字 ID,而是使用 **GUID(全局唯一标识符)** 来标识用户,例如:

```
?id=3f2504e0-4f89-11d3-9a0c-0305e82c3301
```

这样攻击者就**很难猜出**其他用户的标识符。

**但是依然可能被绕过:** 其他用户的 GUID 可能会在应用的**其他地方泄露**,例如:

- 用户之间的**消息**
- 帖子下的**评论**
- 公开的**个人资料页、文章作者信息**
- API 响应里附带的用户信息

攻击者从这些位置**收集到别人的 GUID**,再拿去访问对方的账户页面,照样能越权。

> **核心教训:** 用难猜的 ID 只是增加了猜测难度,**不是**权限校验。ID 再难猜,只要有地方泄露,就会失效。

## 4. 水平到垂直权限升级

水平权限升级往往可以**转化为**垂直权限升级。关键在于:**攻击的目标换成了更高权限的用户。**

### 攻击思路

1. 先利用水平越权(如改 `id` 参数),访问到别人的账户页面。
2. 如果目标恰好是**管理员账户**,攻击者就获得了**管理员账户页面**的访问权限。
3. 这个页面可能:
   - **泄露管理员的密码**
   - 提供**修改密码**的功能
   - 直接提供**特权功能**的入口

于是攻击者**接管了管理员账号**,完成了垂直权限提升。

### 例子

攻击者使用前面的参数篡改技术,访问另一个用户的账户页面:

```
https://insecure-website.com/myaccount?id=456
```

如果 `456` 恰好是管理员的用户 ID,攻击者就得到了管理员账户页面的访问权限。

### 另一种情形:接管其他用户的凭证

水平越权还可能允许攻击者**重置或获取其他用户的密码**。如果被攻破的是管理员用户,攻击者就拿到了管理员的访问权限,从而实现垂直提权。

> **核心教训:** 看似"只能看别人的信息"的水平越权,一旦目标是高权限用户,危害会**升级成完全控制系统**。所以不要因为是"水平"就轻视它。

## 5. 速记对比表

| 对比项 | 垂直权限升级 | 水平权限升级 |
|---|---|---|
| **含义** | 访问**更高权限级别**才有的功能 | 访问**同级别其他用户**的资源 |
| **形象比喻** | 往上爬楼层 | 走进邻居的房间 |
| **典型例子** | 普通用户进入 `/admin` 删除用户 | 修改 `id=123` 为 `id=456` 查看他人账户 |
| **常见成因** | 敏感功能无保护、靠隐藏 URL、依赖客户端传来的角色参数 | 缺少"资源归属"校验(IDOR) |
| **典型手法** | 直接访问管理 URL、改 `admin=true` / `role=1` | 改 ID 参数、利用泄露的 GUID |
| **相互转化** | 可由水平升级转化而来(盯上管理员账号) | 可作为垂直升级的跳板 |

## 6. 渗透测试检查清单 -- 工作流

以下方法仅用于**授权的测试环境或靶场**。

### 测试垂直权限升级

- [ ] 用**普通用户**直接访问管理员 URL(`/admin`、`/administrator`、`/manage` 等)
- [ ] 查看 `robots.txt`、`sitemap.xml`,寻找泄露的后台路径
- [ ] 用目录扫描工具配合字典枚举隐藏路径(如 dirsearch、gobuster、ffuf)
- [ ] 审查前端 **JS 文件和页面源码**,寻找硬编码的后台 URL、角色判断逻辑
- [ ] 检查 **Cookie、隐藏字段、URL 参数**中是否有角色类字段(`admin`、`role`、`isAdmin`、`level` 等),尝试修改
- [ ] 抓包(Burp Suite)观察请求,尝试**未登录或低权限状态**下重放高权限请求

### 测试水平权限升级(IDOR)

- [ ] 找出所有带**对象标识**的参数(`id`、`uid`、`order_id`、`file` 等)
- [ ] 用**两个不同账号**(A、B)对照测试:用 A 的会话去请求 B 的资源
- [ ] 数字 ID:尝试递增/递减、遍历
- [ ] GUID:去**消息、评论、公开页面、API 响应**里搜集其他用户的 GUID
- [ ] 不仅测试读取(GET),也测试**修改、删除**(POST/PUT/DELETE)

### 测试水平转垂直

- [ ] 尝试通过 IDOR 访问**管理员账户**的页面/数据
- [ ] 检查账户页是否泄露密码、令牌、密码重置功能

## 7. 防御思路

| 问题          | 正确做法                                            |
| ----------- | ----------------------------------------------- |
| 敏感功能无保护     | **每个**敏感功能都必须在**服务端**校验权限,默认拒绝(Deny by Default) |
| 靠隐藏 URL 保安全 | 隐藏只能当辅助,不能当防线;权限校验才是根本                          |
| 角色信息存在客户端   | 角色/权限**只存在服务端会话中**,绝不信任客户端传来的 `admin=true` 之类的值 |
| IDOR        | 每次访问资源时,校验"**当前登录用户是否拥有/有权访问该资源**"              |
| 使用 GUID 当防护 | GUID 可以作为补充,但**不能替代**权限校验                       |
|             |                                                 |

---

## 8. 一句话总结

> **访问控制 = 认证 + 会话 + 权限判断。** 权限判断一旦只靠"隐藏"或"相信客户端传来的值",就会出现漏洞:
> **垂直越权**是"拿到了不该有的更高权限",**水平越权**是"看到了不属于自己的别人数据",而水平越权盯上管理员账号时,就能**升级为垂直越权**。
